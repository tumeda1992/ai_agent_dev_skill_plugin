# 命名

名前は本質。コード・ファイル・ディレクトリなど、名前を付けるあらゆる場面で守る標準。

## §1 基本

命名全般に効く原則。

### 初見でも自明にわかる名前にする

その名前が生まれた経緯・議論を知らない初見の人が、**名前だけ見て中身を正しく受け取れる**こと。参加者だけに通じる略語・対比・内部符号は避ける。

- ✗ `spec_over_implementation` — 何の spec か、なぜ implementation との対比なのか、議論を知らないと読めない
- ○ `business_specification` — 「ビジネス仕様の標準」だと初見で受け取れる

### 手続き的な how でなく、宣言的な what / why を表す

「どう実現するか（手順）」でなく「何であるか・何のためか」で名付ける。手順は変わるが、what / why は変わりにくい。

- ✗ `recalculate_and_save_balance` — やり方の羅列
- ○ `settle` — 何をするか（結果・意図）

### 中身が大まかにわかる具体性を備える

名前から内容が大づかみできること。汎用化・意味抜きをしすぎて「**間違ってはいないが、何も意味していない**汎用的な名前」になる失敗を避ける。

- ✗ `data` / `manager` / `info` / `util` — 何でも入る＝何も言っていない
- ○ 実態を名指す具体語にする

### 命名後、名前と実態の対応をレビューする

付けた名前と実態の対応を上の観点で見直し、外していたら**改名して再レビュー**する。命名は工程の最後でも本質として詰める（軽視して流さない）。

## §2 ファイル名

### 同階層の存在と足並みを揃える

同じディレクトリのファイルと、表面（接頭辞など）も抽象度も揃える。1 つだけ足並みを乱す抽象度・表記にしない。

- 表面: 周りが接頭辞を使っているなら合わせる。表記（snake / kebab 等）も所属ツリーの慣習に従う（例: skills は kebab `domain-research-with-code-reading`、docs は snake `business_specification.md`。どちらが正しいではなく、周囲に合わせる）
- 抽象度: 周りが広い標準の粒度なら広く、具体トピックの粒度なら具体で揃える

### 全体を説明する一員として名付ける

「間違っていない名前」を単体で付けることを恐れるより、同階層のファイル群と合わせて**ディレクトリ全体を説明する役割**を担っている、と意識する。

### 直上ディレクトリのコンテキストを継承する

そのディレクトリ配下のファイルは、直上ディレクトリの文脈をそのまま引き継ぐ。親が語ることを、ファイル名に重複して持たせない。

- ○ `documentation_standards/business_specification.md` — 親が「ドキュメンテーション標準」を語るので、ファイルは `business_specification` で足りる（`documentation_standard_for_business_spec.md` としない）

## §3 メソッド名

### `レシーバー.メソッド名` で意味が通る名前にする

メソッド名単体でなく、呼び出しの形 `receiver.method` で読んだときに意味が通ること。

- ✗ `member.check` / `bill.process` — レシーバと合わせても何をするか曖昧
- ○ `member.active?` / `bill.settle` / `member.initial_verification_status` — 呼び出しの形で意味が通る
