# 作業の範囲

開発の進め方のうち、作業中に出た判断や気付いた不備を、今の作業で扱うかを扱う。

**前提: 作業の範囲は、その作業の目的が決める。** 今の作業の設計の論点になるのは、目的の決定・実装範囲を変える判断だけである。**一方、目的の外にある不備は、目的の外であることを理由に別の作業へ回さない。** 小さければ今の作業で拾う。

この前提が共有されていないと、二つの方向に崩れる。一つは、目的の外の不備に気付くたびに「scope 外だから別 issue」と判断し、その場でしか気付けない不備が誰にも拾われずに溜まる方向である。もう一つは、選択肢に code の変更が含まれることを理由に目的の外の判断を論点に起こし、設計が目的と関係のない議論で膨らむ方向である。

## 判定は二段で行う

作業中に新しい判断が出たとき、または作業の目的の外にある不備に気付いたときに使う。

```text
一段目  結論が変わると、今の作業の目的の決定・実装範囲が変わるか
          変わる      → 目的の内。今の作業の設計判断として扱う
          変わらない  → 目的の外。設計の論点にしない。不備なら二段目へ
二段目  今の作業に含めたら、今の作業の review・revert・本番適用の単位が崩れるか
          崩れない    → 今の作業で拾う（既定）
          崩れる      → 別の作業へ切り出す
```

判定をどの手順の中で行い、結果を誰と合意するかは、気付いた段階の workflow が持つ。設計中は `task-design`、実装・動作確認中は `skills/runtime-feedback-review.md` である。

## 一段目: 目的の内か外か

判断の問いは **「その判断の結論が変わると、今の作業の目的の決定・実装範囲が変わるか」** である。選択肢に何が含まれるかではなく、結論によって何が変わるかを見る。

- やってしまいがちな行動: 選択肢に成果物の変更（code の変更など）が含まれることを、目的の内の根拠にする
- それをやると何が起きるか: 目的の外と決めていた事柄が、変更を含むという理由だけで設計の論点になる。例えば、目的の外と決めていた別の作業の費用を下げる案を、code の変更を含むという理由で design の論点に起こした。設計は目的と関係のない議論で膨らみ、design の合意が遅れる
- 正しい判断のための問い: 「この判断の結論がどちらになっても、今の作業の完成後の姿は同じか」

## 二段目: 目的の外の不備を拾うか切り出すか

既定は今の作業で拾う。その場でしか気付けない不備は、別の作業へ回すと誰も拾わずに溜まる（ボーイスカウトルール）。

次のどれかに当たるものだけを、別の作業（issue・steering）に切り出す。

- 大きすぎる
- 単体で分けた方が revert しやすい
- 今の作業に含めると、本番への適用が遅れる

**「今の作業の目的の外である」ことは、切り出す理由にならない。** 二段目へ来た不備は、すべて目的の外にある。

判断の問いは **「これを今の作業に含めたら、今の作業の review・revert・本番適用の単位が崩れるか」** である。崩れなければ拾う。

```text
拾った例       運用の README で、暫定の判断の暫定性と見直す条件が落ちていた記述の修正
               CI の state lock の待ち時間の不足（workflow の 3 行）
               どちらも作業の目的の外だったが、小さく、今の作業の単位を崩さなかった
切り出した例   大きな機能の削除（単体で revert できるようにしたい）
               同期処理の非同期化（含めると本番への適用が遅れる）
```

- やってしまいがちな行動: 「今の作業の scope 外だから」と別の issue を推奨する
- それをやると何が起きるか: 切り出した issue は、気付いた時の文脈を失って後回しになる。その場でしか気付けない不備ほど、文脈が無いと直す動機が残らず、溜まる
- 正しい判断のための問い: 「切り出す理由は、三つの条件のどれか。目的の外であることを理由にしていないか」

拾うか切り出すかを決めた後は、次のとおり扱う。

- 拾う: 今の作業の design と plan に戻して範囲に加える。拾った不備の修正で完成後の姿が変わるためである。
- 切り出す: 切り出し先の issue・steering を先に作る。そのうえで今の作業の記録に、今はやらない理由と切り出し先を書く。書き方は [`provisionality_explicitness.md`](../../documentation_standards/provisionality_explicitness.md) に従う。切り出し先を作る前に、記録へ「切り出し済み」と書かない。
