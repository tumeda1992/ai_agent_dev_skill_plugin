# branch・PR・issue の対応

開発の進め方のうち、branch・PR・issue の対応と、merge が何を終わらせるかを扱う。

**前提: branch は issue に属する。** branch 名から issue 番号を一意に引ける。一つの issue に複数の branch があってよい。**issue の終わりは、`Closes` を持つ PR の merge が宣言する。**

この前提が共有されていないと、`Closes` を付けるかどうかが「この PR で issue を閉じたいか」という個別判断になり、branch 名の再利用が「履歴が綺麗になるか」という別の軸で判断される。どちらも、merge が何を終わらせるかを決めないまま操作を選んでいる。

## 二つの merge 経路を区別する

既定 branch への merge には二つの経路がある。選択は **「この merge で issue の作業が終わるか」** で判定する。終わらないなら経路 2 である。

```text
経路 1: issue 完了の merge        経路 2: 検証のための merge
  その issue の作業が終わった       既定 branch 上でしか動かない仕組みを確認する必要がある
  PR は `Closes` を持つ             PR は `Closes` を持たない。issue へは参照として書く
  merge 後、branch 名は再利用しない merge 後、既定 branch を本線へ取り込み、作業を続ける
```

経路 2 が必要になるのは、CI、deploy、scheduled job のように、既定 branch 上でしか動かない仕組みを確認する場合である。作業 branch 上では動かないため、確認するには一度 merge するしかない。

- やってしまいがちな行動: 検証のための merge に、いつもの PR テンプレートをそのまま使い `Closes` を付ける
- それをやると何が起きるか: 残作業があるのに issue が閉じる。issue を再度開く操作が必要になり、閉じた時点の記録が実態と食い違う
- 正しい判断のための問い: 「この merge の後、この issue でまだやることが残っているか」

## 検証のための merge は、同じ issue に属する branch で立てる

```text
branch 名   `issue-<番号>-<検証内容>`。本線と同じ issue に属する
差分        既定 branch 上でしか動かない仕組みを動かすのに必要な範囲を含めてよい。
            本線の変更を取り込むことを妨げない
PR          `Closes` を持たない。issue へは参照として書く。
            本文に「この PR は issue の完了を意味しない」を明記する
merge 後    既定 branch を本線へ取り込み、作業を続ける
後始末      検証のためだけに入れた差分は本線で削除し、issue 完了の merge で反映する
```

**差分を最小限に絞らない。** 検証したい仕組みが CI や deploy である場合、それを意図どおり動かすには本線の修正が既定 branch に入っている必要がある。最小差分に制限すると、検証したい仕組みそのものが動かない。

**merge 後に既定 branch を本線へ取り込む。** 検証のための merge は既定 branch を進める。本線がそのままだと、以降の作業が古い既定 branch の上に乗る。

## `Closes` は issue の終わりを宣言する

`Closes` は「この PR が merge されたら issue を閉じる」という宣言であり、PR の性格を決める唯一の印である。

- やってしまいがちな行動: `Closes` を「関連する issue を示す書き方」として使う
- それをやると何が起きるか: 参照のつもりで書いた `Closes` が issue を閉じる。関連を示したいだけなら `参照: #NN` のように書く
- 正しい判断のための問い: 「この PR が merge された時点で、この issue は完了していてよいか」

## merge 済みの branch 名を再利用しない

merge して役目を終えた branch 名を、別の作業に使わない。

- やってしまいがちな行動: squash merge の後、同じ名前の branch を作り直して作業を続ける
- それをやると何が起きるか: 同じ名前が二つの異なる作業を指す。履歴を辿るとき、その名前がどちらの作業を指すかを外から判定できない
- 正しい判断のための問い: 「この branch 名は、過去に merge された作業の名前ではないか」

同じ issue の作業を続けるなら、派生形式（`issue-<番号>-<説明>`）で新しい名前を作る。issue との対応は保たれる。

## 既定 branch への merge が本番適用を起こす場合

既定 branch への merge が deploy や infrastructure の適用を起こす repository では、**経路 2 も適用を起こす。** 「検証のための merge だから安全」は成り立たない。

- やってしまいがちな行動: 検証が目的なので、作業中の変更をまとめて merge する
- それをやると何が起きるか: 検証したい一点以外の変更も本番へ適用される。適用されて困る変更が混ざっていても、merge するまで気づかない
- 正しい判断のための問い: 「この merge で既定 branch へ入る変更のうち、いま本番へ適用されて困るものはないか」

検証用の差分そのものも、適用される前提で選ぶ。application の動作を変えない値を足す、確認用の変数を一つ入れる、といった形にする。

## branch 名の原則と推奨形式

**原則。** 形式を問わず次を満たす。

- branch 名から issue 番号を一意に引けること
- その issue の本線がどれかを名前から判定できること
- merge 済みの branch 名を再利用しないこと

二つ目が必要なのは、一つの issue に複数の branch があってよいためである。`Closes` を持つ PR を出すのは本線であり、本線が識別できないと、どの PR に `Closes` を付けるかが個別判断になる。

**推奨形式。**

```text
本線   issue-<番号>            例: issue-42
派生   issue-<番号>-<説明>      例: issue-42-verify-ci

`issue-` の直後の数値列を issue 番号として読む。それ以降は自由にする。
本線は番号で終わることで、派生と機械的に区別できる。
```

`issue-` を prefix に使うのは、branch の性質（機能追加、修正）ではなく所属を示すためである。検証用 branch は機能追加ではないが、同じ issue に属する。

**利用先が宣言する。** この形式を採るか、別の形式を採るかは、利用先 repository の context file（`.agents/skills/tumeda-dev-plugin-context.md` の `### Branch / issue 契約`）が宣言する。issue を持たない repository は、その旨と代わりの識別子を書く。
