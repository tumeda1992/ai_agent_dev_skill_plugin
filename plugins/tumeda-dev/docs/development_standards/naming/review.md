# 命名のレビュー

付けた名前と実態の対応を見直す場面で使う。観点の当て方、書き方、レビュー後の扱いを持つ。

## 観点は各fileが正本

レビューで当てる観点の中身は、このfileが持たない。

- 判断基準 → [core.md](./core.md)
- ファイル名に固有の規則 → [file.md](./file.md)
- メソッド名に固有の規則 → [method.md](./method.md)
- 初見の人にどう読まれるかの検算 → [reverse_translation.md](./reverse_translation.md)

`core.md` は常に当てる。他は対象と場面に応じて必要なものを見る。

観点の中身をこのfileへ写さない。写すと二重管理になり、正本を直してもこのfileが古いまま残る。

やってしまいがちな失敗: レビューを書く手元で参照しやすいように、判断基準の要約をこのfileへ書き写す。書いた時点では正本と一致しているため問題が見えない。正本が更新されたとき、このfileの要約は更新されず、どちらが正しいかを読み手が判定できなくなる。

判断の問い: **「いま書こうとしている内容は、他のfileが本体を持っているか。持っているなら参照だけを書いたか」**

## 一言コメントで済ませない

良い点と足りない点を分け、それぞれ段落で書く。

一言コメントは減点法になり、重箱の隅を突く指摘が並ぶ。どこが良かったのかも見えない。

同じ案への二つのレビューを比べる。

一言コメント。

> `UserManager` は汎用的すぎる

段落で書いたもの。

> `UserManager` を見た人は、ユーザーに関する何らかの処理をまとめたクラスだと想像する。ユーザーという対象は正しく伝わる。一方、何をまとめているかは想像しない。作成・更新・削除なのか、権限判定なのか、セッション管理なのかが読めない。実際に開いたときに何が入っていても驚かないため、名前が予想の役に立っていない。

一言コメントは判定だけを返し、どう直せばよいかを含まない。段落で書くと「名前が予想の役に立っていない」という判定が出て、次に何を名前へ入れるべきかが見える。

## 点数のグラデーションを出す

段落で書けば、その案が何点かを判定できる。

グラデーションが見えないと、残った候補の中の相対優位を出して終わる。「相対的に b が良い」となっても、詳細なレビューがあれば「b も 15 点であり、さすがに選べるわけがない」と考え直せる。

判断の問い: **「この案は何点か。選べる水準に達しているか」**

やってしまいがちな失敗: 候補を並べて「この中では b が最も良い」と結論する。全候補が低い水準にあることに気づかず、出し直しへ戻らない。

## 誤解の方向で判定する

完璧に伝わることを求めない。判定の第一基準は **「意味する方向が同じか」** である。

読み手が誤解しても、方向が同じなら中を見て軌道修正が効く。**方向が違う誤解**（読み手が別のドメインの話だと受け取る）だけを落とす。

- 方向が同じ誤解: `undo` を「取り消し操作」と読むが、対象が編集なのか送信なのかまでは分からない。中を見れば分かる
- 方向が違う誤解: `preproduction` を「本番環境の前段階（ステージング環境）」と読む。制作段階の話だと気づけない

判断の問い: **「この誤解は、中を見れば直るか。それとも別のドメインの話だと思ったまま進むか」**

やってしまいがちな失敗: 想像と実態のギャップをすべて欠点として数える。粒度が上がるほど完璧な含意の難易度は上がるため、方向が同じ誤解まで数えるとどの案も落ちる。

## 評価基準を到達可能な水準へ合わせる

粒度が上がるほど、完璧に内容を含意する命名の難易度は上がる。閾値が 60 点のときに 65 点の案へ 100 点基準のレビューを当てると、重箱の隅を突く指摘になる。

モジュール名などが 1〜2 語でバッチリ決まるのは、現実の運用で使われるユビキタス言語が既に存在し、その業界のオペレーションが似通っているために、言語の進化上、短い語が存在するからである。新しい概念には既存の短い語がない。長くなるのは当然であり、長さを理由に落とさない。

到達可能な水準は、**同じ性質の対象が世の中でどう名付けられているか**で測る。

- 同種の対象に確立した名前があるなら、その語数と具体性が到達可能な水準である。`undo`、`commit`、`rollback` のように 1 語で決まっている領域では、1 語で決まらない案は水準に達していない
- 同種の対象に確立した名前がないなら、完璧な含意は期待できない。その領域で最も近い既存の名前を探し、それと同程度の伝わり方で足りる

判断の問い: **「この対象と同じ性質のものは、世の中で何語で、どこまでの具体性で名付けられているか」**

やってしまいがちな失敗: 自分が理想とする伝わり方を基準に置く。対象が新しい概念であるほど理想と現実の差は開き、どの案も落ちる。

## レビュー結果を方向性の抽出へ回す

案を出す、レビューする、残った中から相対優位を選ぶ、で止めない。

落ちた理由をまとめ、**通る方向性を帰納的に抽出**し、その方向で案を出し直す。

落ちた理由が特定のパターンへ集中しているとき、方向性はそのパターンの裏側にある。たとえば落ちた理由が「既存用語と衝突する」に集中しているなら、方向性は「既存用語を避ける」ではなく「意味が一致する既存用語を探す」かもしれない（[core.md](./core.md) の「表現が同じでも、名前空間が違えば別の意味を持つ」）。落ちた理由を並べるだけでは、この転換に気づけない。

やってしまいがちな失敗: レビューを書いて終わり、次のターンでまた同じ方向の案を出す。落ちた理由が蓄積しているのに、そこから方向性を導いていない。

判断の問い: **「落ちた理由を並べて、通る方向が見えたか。その方向で案を出し直したか」**
