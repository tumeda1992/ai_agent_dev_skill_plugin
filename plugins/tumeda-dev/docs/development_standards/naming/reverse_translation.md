# 逆翻訳

名前が [core.md](./core.md) の「初見でも自明にわかる名前にする」を満たしているかを検算する手段。名前を評価する場面で使う。

## 手法

**初見の人がその名前を見たとき、中に何が入っていて何をする場所だと想像するか**を書き出し、実態と照合する。

書き出すのは次の三つである。三つが揃って初めて逆翻訳したことになる。

1. **その名前を見た人が予想する中身。** 何が入っていると思うか
2. **予想する用途。** 何をする場所・何をするものだと思うか
3. **実態との差。** 予想に入っていて実態に無いもの、実態にあって予想に入らないもの

三つ目が出ないなら、照合が起きていない。想像と実態のギャップが、その名前の問題である。

外れているときの見え方: 名前の意味を丁寧に説明して終わっている。実態を並べていないため、ギャップが一つも挙がらない。

## 語義の言い換えと区別する

逆翻訳は、名前から辞書的に導ける意味を書くことではない。

- ✗ 語義の言い換え: 「`UserManager` はユーザーを管理するクラス」
- ○ 逆翻訳: 「`UserManager` を見た人は、ユーザーに関する何らかの処理をまとめたクラスだと想像する。何をまとめているかまでは想像しない。作成・更新・削除なのか、権限判定なのか、セッション管理なのかが名前から読めない」

差は、**実態を知らない人が何を予想するか**を書く点にある。語義は名前だけから導けるが、逆翻訳は「予想」と「実態」の二つを並べて初めて成立する。

判断の問い: **「いま書いたのは、名前の意味か。それとも、実態を知らない人が予想する中身か」**

やってしまいがちな失敗: 名前の意味を丁寧に説明して逆翻訳したつもりになる。実態との照合が起きないため、ギャップが見つからない。

## 名前空間の中で読む

逆翻訳は、名前を単独で読むのではなく、置かれた場所の形で読む（[core.md](./core.md) の「名前を単独で評価しない」）。

- 親がある場合は `親/自分` の形で読み、初見の人が何を想像するかを書く
- 同列に並ぶ要素がある場合は、それらと並べたときに何が読めるかを書く

やってしまいがちな失敗: 二つの名前をペアで設計し、並べたときに対比が読めることを根拠に採用する。これは**その対比を設計した人の読み方**である。

たとえば `questions/` と `answers/` を並べれば「問いと答え」の対比が読めるが、読み手が `answers/` を単独で見る場面がある。パスの一部として現れたとき、import 文に出たとき、エラーメッセージに含まれたときである。単独で見た人は「回答集」と読み、アイデアごとにディレクトリが分かれている構造を予想しない。

逆翻訳は、ペアで読める対比ではなく、**単独で見たときに何が読めるか**を書き出す。

## 書き出した結果の扱い

書き出した想像と実態のギャップを、どう判定し、どう書くかは [review.md](./review.md) が持つ。ギャップをすべて欠点として数えるとどの案も落ちるため、判定基準を見てから結論を出す。
