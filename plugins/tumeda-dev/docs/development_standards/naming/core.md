# 命名の基本

名前を付ける対象が何であっても成立する原則。対象種別に固有の規則は同階層の各fileが持つ（[README.md](./README.md)）。

## 初見でも自明にわかる名前にする

その名前が生まれた経緯・議論を知らない初見の人が、**名前だけ見て中身を正しく受け取れる**こと。参加者だけに通じる略語・対比・内部符号は避ける。

- ✗ `spec_over_implementation` — 何の spec か、なぜ implementation との対比なのか、議論を知らないと読めない
- ○ `business_specification` — 「ビジネス仕様の標準」だと初見で受け取れる
- ✗ 章や節へ `S1`〜`S9` のような連番 ID を振り、本文の相互参照をその ID で行う — ID が中身を示さないため ID→意味の変換表を常に要求し、章の追加・統合・分割で番号が壊れる
- ○ 参照先自体が内容を示す名前を持ち、その名前で参照する

## 手続き的な how でなく、宣言的な what / why を表す

「どう実現するか（手順）」でなく「何であるか・何のためか」で名付ける。手順は変わるが、what / why は変わりにくい。

- ✗ `recalculate_and_save_balance` — やり方の羅列
- ○ `settle` — 何をするか（結果・意図）

## 中身が大まかにわかる具体性を備える

名前から内容が大づかみできること。汎用化・意味抜きをしすぎて「**間違ってはいないが、何も意味していない**汎用的な名前」になる失敗を避ける。

- ✗ `data` / `manager` / `info` / `util` — 何でも入る＝何も言っていない
- ○ 実態を名指す具体語にする

## 修飾の向きで指すものが変わる

同じ 2 語でも「A の B」と「B の A」は別物である。修飾の向きが変われば、名前が指す対象が変わる。

- 判断の問い: **「その名前が指すのは、出来事（行為）か、状態を持つ物か」**
- 出来事 → 行為を表す名詞形にする
- 物 → 状態を形容詞で修飾した形にする

- ✗ `retry_notification`（通知のリトライ＝出来事）を、リトライ済みの通知を指す名前として使う
- ○ 出来事なら `retry_notification`、物なら `retried_notification`

MUST: 形容詞を単独で名詞の位置に置かない（`retried` だけでは何が retried なのか示せない）。形容詞形を採るときは修飾先の名詞を伴わせる。

## 表現が同じでも、名前空間が違えば別の意味を持つ

同じ表現が既に別の場所で使われていても、それだけを理由に候補から外さない。

- 判断の問い: **「その2つは、同じ読み手が同じ場面で出会うか」**
- 出会う → 同じ名前空間にある。表現が同じで意味が違うなら、別の名前にする
- 出会わない → 名前空間が違う。表現が同じでも共存してよい

名前空間はディレクトリやmoduleの境界だけで決まらない。読み手と場面で決まる。同じfile内でも扱う対象が違えば別の名前空間になり得る。逆に別fileでも、同じ読み手が同じ判断のために両方を読むなら同じ名前空間である。境界で定義すると、境界をまたぐ参照がある場合に判定を誤る。

- ✗ 語の出現箇所をgrepで数え、ヒットしたことだけを理由に候補から外す
- ○ その2つが同じ読み手に同じ場面で出会うかを問い、出会わないなら共存させる

やってしまいがちな失敗: 出現数の多い一般語（`state`、`owner`、`context`等）を、他所で使われているという理由だけで使用不能にする。これらは文脈ごとに違う意味で使われており、それで機能している。正しい判断のための問い: 「その2つは、同じ読み手が同じ場面で出会うか」。

## 命名後、名前と実態の対応をレビューする

付けた名前と実態の対応を上の観点で見直し、外していたら**改名して再レビュー**する。命名は工程の最後でも本質として詰める（軽視して流さない）。
