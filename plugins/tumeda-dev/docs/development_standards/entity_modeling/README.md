# エンティティ設計

エンティティをどう切るか、切った結果をどう名付けるかの標準。命名の一般則は [naming/](../naming/README.md) が持ち、ここではエンティティを前提にしないと成立しない判断だけを扱う。

## この群の置き方

- `core.md`: エンティティがどう生まれ、どう消えるかを問わず成立する判断
- 状況ごとのfile（`evacuation.md`）: 特定のライフサイクルを前提にする判断

判断の問い: **「この判断は、そのエンティティがどう生まれ、どう消えるかを問わず成立するか」**

- 成立する → `core.md`
- 特定のライフサイクルを前提にしないと成立しない → その状況のfile

## 読む順と、既定の優先関係

MUST: `core.md` を読んだうえで、扱っているエンティティが状況fileに該当するかを確認する。該当する場合、**状況fileの既定が `core.md` の既定に優先する。**

これは [naming/](../naming/README.md) と構造が違う。`naming/` の `file.md` や `method.md` は `core.md` へ規則を足すだけで、`core.md` の内容を打ち消さない。一方この群の状況fileは、既定そのものを逆転させることがある。

やってしまいがちな失敗: `core.md` の判断基準を適用して設計を終え、状況fileを読まない
→ 該当する状況では既定が逆であるため、結論が逆になる。実際に、退避エンティティへ `core.md` のフィールド追加基準（opt-in）を適用し、退避のたびに情報が失われる設計を作った事例がある

## 各fileの守備範囲

| file | 扱うもの | 扱わないもの |
| --- | --- | --- |
| [core.md](./core.md) | ライフサイクルを問わず成立するエンティティ設計の判断 | 特定の状況でだけ成立する判断 |
| [evacuation.md](./evacuation.md) | 元データを削除して別エンティティへ移す状況に固有の判断 | ライフサイクルを問わない判断（`core.md` を参照） |

状況fileを増やすときは、まずその判断が `core.md` へ入らないことを確認する。`core.md` へ入る判断を状況fileへ書くと、他の状況から見えなくなる。
