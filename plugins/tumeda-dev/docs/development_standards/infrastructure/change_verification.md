# 変更の後の確かめ

基盤（cloud の resource とその構成）を作る・変えた後に、何を確かめれば完了とするかの判断基準。

## 変えた component の影響下にある動きを、すべて実物で確かめる

- MUST: 基盤の構造を変えたら、変えた component の影響を受ける動きを列挙し、それぞれが意図どおりに動いていることを実物で確かめる。確かめていない動きが残る間は、変更を完了としない。
- MUST: 画面が開く、apply が成功する、といった上澄みの結果だけで完了としない。

上澄みの結果は、その下で動く component の一部しか通らない。ログの出力や権限のように、利用者の操作が成功しても、動いていないことが表に出ないものがある。そうした欠落に気付くのは、それが必要になった時（障害を調べる時など）であり、その時には失われたものを取り戻せない。

列挙の観点:

- 利用者の操作: 画面、API。変えた component を通る経路ごとに確かめる。
- 利用者の操作を伴わない処理: 定期実行、非同期の job、webhook。
- 出力: ログ、metric、通知。書かれているか、届いているかを、出力先で見る。
- 権限: role、policy、認証。それを使う操作が実際に通るかを見る。
- 同じ component を共有する別の環境: 本番と確認用の環境が同じ app や account を共有するなら、両方を見る。
- 作る・更新する経路: build、deploy、infrastructure as code の apply・plan。

費用がかかる、時刻を待つ必要があるなど、すぐに確かめにくい動きは、確かめる時と方法を決めて残す。確かめるまで完了としない。

判断の問い: **「変えた component が関わる動きのうち、まだ実物で確かめていないものは何か」**

## 失敗事例

- SSR の app を infrastructure as code で作って公開した時、受け入れを「公開 URL で機能が使える」「認証が効く」「再適用で差分が出ない」で済ませた。
    - app にログを書く role が無く、本番の SSR のログは一度も出ていなかった。
    - 気付いたのは約 2 か月後、定期実行が時間上限で切られた原因を調べようとした時であり、server 側で何が起きたかを確かめられなかった。
    - 「出力」の観点でログを出力先で見ていれば、公開の時に気付けた。
- 同じ app にログを書く role を付けた後、apply は成功し、画面も開いた。
    - それだけでは、ログが書かれているかは分からない。log group を見に行くと作られておらず、deploy し直した後に初めてログが出た。role を付ける前に build された deploy が動いていたためである。
