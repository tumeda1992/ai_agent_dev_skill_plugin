# 叩き台を作る

**主軸: 叩き台は横展開で検証するまで成立していない**

同じ作業を多数の対象へ繰り返すとき、狭い範囲を先に作って型を得てから広げる。
このとき最初に作るものを叩き台と呼ぶ。

叩き台性とは、**それが固まったら他も同じように展開できること**である。
小さいことや作りやすいことは叩き台性ではない。

そして叩き台が成立したかどうかは、作った時点では分からない。
横展開で他の対象へ適用したときに耐えるかどうかが検証対象であり、耐えて初めて機能したと言える。
1 つ作って「型ができた」と宣言して次へ進むと、叩き台だったかどうかを確かめないまま全件へ広がる。

## 惰性で選んだ 1 件目は、型を出しきらない

実際に起きたことを書く。

> API 群 10 本を新しい配置へ移す作業があった。一度に全部動かすと壊れたときの切り分けができないので、
> 1 本を先に移して手順を確立し、残りへ広げる計画にした。
>
> 最初の 1 本は、一覧の先頭にあったものを選んだ。選定に理由は無く、性質も評価していない。
> 移し終えて参照が全部解決することを確認し、型ができたと判断して残り 8 本へ進んだ。
>
> そこで 2 つのことが起きた。
>
> **1 つ目。** 共有部品を旧パスからも見えるようにする仕組みを残していたが、
> どの部品を残すべきかの判断で、その部品を直接参照しているものだけを数えた。
> 「もう誰も直接使っていない」と判断して 3 つ消したところ、参照が切れた。
> 実際には、残した別の部品がその 3 つを内部で参照しており、経由して使われていた。
> **1 本目にはこの経由が発生していなかった**ため、「参照を辿って閉じるまで数える」という手順が型に入らなかった。
>
> **2 つ目。** 部品をグループ別に分けた結果、グループを跨ぐ参照が生まれた。
> 跨ぐ参照は旧パス経由では解決できず、旧パス側にも同じ階層関係を用意する必要があった。
> **1 本目には跨ぐ参照が無かった**ため、これも型に入っていなかった。
>
> どちらも 1 本目に無かった構造である。選定時に「どの 1 本なら他の 9 本が持つ構造を含むか」を
> 問うていれば、避けられた。

ここから取れる基準は 1 つ。**叩き台は、他が持つ構造を含んでいなければ型を出しきらない。**
「まず 1 個やってみる」で選んだものは、たいてい何かを含んでいない。

含んでいないことは、作っている最中には分からない。
出来上がった型は、その 1 件に対しては完璧に見える。
分かるのは 2 件目以降で、そのときには型を作り直すことになる。

## 必要な性質を数え上げ、それを満たす最小を選ぶ

では最も複雑なものを選べばよいかというと、そうではない。

やりやすさを指摘された直後は、反対側へ振れやすい。
「必要な性質を最も多く満たすもの」「一番複雑なもの」を選ぼうとする。
これは依頼が最初から置いていた制約を落としていることが多い。
叩き台は型を確かめるためのものなので、確かめられる最小で足りる。
大きいほど作るのに時間がかかり、型が誤っていたときの手戻りも大きい。

満たすべきは 3 つある。

**実在すること。** 後述する。

**型を確かめられる性質を備えること。** 備えていない性質は 2 個目以降で新しい判断として現れる。

**必要十分の最小であること。** 上の 2 つ目と引き合う。
必要な性質を多く求めるほど、それを全部満たす対象は大きくなる。

だから性質は本当に無いと破綻するものだけに絞る。判定の問いは 1 つでよい。

> その性質が無いと、2 個目でどんな判断が新しく出るか。具体的に言えるか。

言えるなら必須。言えないなら「あったほうがよい」に過ぎず、挙げれば挙げるほど最小が膨らむ。

上の例で言えば、「経由して使われる部品を持つ」と「グループを跨ぐ参照を持つ」は、
無ければ 2 個目で判断が新しく出ることが実際に証明された。だから必須である。
一方「ファイル数が多い」は、多くても判断は増えない。必須ではない。

## 実在しない対象を叩き台にしない

網羅を作ろうとすると、条件を組み合わせた架空の対象を作りたくなる。
「この性質とあの性質を両方持つ例が欲しい。実在しないが、そういうものを想定して進める」という形で現れる。

これをやると、実在しない対象に合わせた型ができる。
横展開先はすべて実在するものなので、型が合わない。検証しているつもりで検証にならない。

症状は名前に出る。実在する対象には業務の言葉で名前が付く。
合成した対象は、条件の羅列でしか名前が付けられない。
「請求が期限を過ぎて支払方法が切り替わった状態」とは書けるが、
「状態が A かつ種別が B かつ方式が C の組み合わせ」としか書けないなら、それは実在を確かめていない。

> 名前を付けてみて、条件の羅列にしかならないなら、その対象は実在を疑う。

## 単位を決めることと、選び方を決めることは別

「1 件を何とするか」を決めただけで型ができたと思いやすい。

単位が決まっても、その中のどれを選ぶかは決まっていない。
基準が無ければ、着手しやすいものから始まる。惰性の選定へ戻る。

さらに、単位そのものを間違えることがある。
最小単位の定義（1 件を何とするか）と、複数を束ねる単位の定義（何を 1 ブロックとするか）は別である。
前者が決まっていると、後者もそれで決まったように錯覚する。

> 「1 件 = X」と決めた後、「では 1 ブロック = X の集まり」と自動的に考えていないか。

実際に起きた例を書く。

> ケースの最小単位を「1 つの API の 1 つのレスポンスパターン」と定義した作業で、
> 複数ケースを束ねる単位も API だと 3 回続けて提案した。
> 指摘を受けて直すたびに、選び方や順序は直すのに、単位そのものは API のまま残していた。
>
> 破綻したのは、データ状態が API に閉じないからだった。
> ある状態を 1 回作れば、一覧の API にも詳細の API にも同時に現れる。
> API を単位にすると、同じ状態を作る手順が複数の定義へ重複する。
> 束ねる単位は状態であって、API ではなかった。
>
> 3 回繰り返した原因は、最小単位の定義を束ねる単位の定義として読んでいたことにある。
> 定義を読み違えている間は、選び方をいくら直しても直らない。

## 何を型として残すか

「型」は多義的である。構造としての型（データ構造・クラス）、表現形式としての型（フォーマット・雛形）、
考え方の型（どう捉え、どう分解し、何を確認するかの道筋）、
オペレーションの型（その骨組みに沿えば進むと言える手順）。この列挙も網羅ではない。

どれが主になるかは対象による。限定して考えない。
重要なのは、自分と相手がどの意味で型と言っているかを明示することである。

これを外すと、合意したつもりで別のものを指したまま進む。

> 「叩き台で型を作る」と合意した後、一方は記述フォーマットを想定し、
> もう一方は考え方の道筋を想定していた。
> 提出されたのは記述形式・命名規則・表記の取り決めで、形式としては揃っていた。
> しかし「どの資料からケースを見つけるか」「見つけたものをどう束ねるか」
> 「何をもって漏れが無いと言うか」は何も決まっていなかった。
> 2 件目でそこからやり直すことになる。

形式の型は考え方の型の中に含まれるが、それだけでは足りない。
先に決まっていなければならないのは、**見つける手順・束ねる単位・漏れの根拠の作り方**のほうで、
書き方はその後に来る。

あわせて、成果物そのものは型ではない。
成果物は結果であり、次の対象へ持ち越せるのは、それを作った手順と基準である。
叩き台の完了条件には、成果物に加えて手順・基準が文章として残っていることを含める。

## 2 個目は、最も性質が違うものを選ぶ

型ができたと思った時点では、まだ検証されていない。
2 個目で新しい判断が出るかを見る。出たらそれは型の不足であり、型へ書き戻してから残りを進める。

このとき **2 個目は叩き台と最も性質が違うものを選ぶ。**
似たものを 2 個目にすると型が通って当然で、検証にならない。
違うもので通れば、型の適用範囲が広いことが確かめられる。3 個目以降は順序を問わない。

冒頭の例で言えば、1 本目と似た構造の 2 本目を選んでいれば、
経由参照も跨ぐ参照も現れず、「型は通用している」という誤った確信だけが得られた。
そのまま 8 本目まで進んで、最後にまとめて破綻する。
検証を早い段階に置くのは、作り直しの量を小さく保つためである。
