# データ整合性の不変条件（認可・冪等性・独立性）

[`cases.md`](./cases.md) が「操作で状態がどう動くか」の状態遷移ケースなのに対し、こちらは **どのケースでも常に成り立つべきデータの整合性**。状態遷移でなく「結果のデータが正しいか」を扱う。1 つでも崩れると、正しく状態遷移していても、利用者に見える予約・旅程が誤る。

（利用者への返金額が正しいか等の**ビジネス上の正しさ**は、各ケースの「システムの対応」が個別に担う。ここはそれと別に、どのケースでも共通で守るべき**データ・システム側の整合性**——誰のデータか・二重に効かないか・別データと混ざらないか。）

崩れてはいけないのは 3 つ:

- **認可（予約者スコープ）** — 他人の予約が見えない・触れない
- **冪等性** — 同じ操作が複数回来ても二重に適用しない
- **複数予約の独立性** — 同じ人が複数の旅程を持っても、対象だけが処理される

いずれも動作確認で検証する。

---

## 1. 認可（予約者スコープ）

**不変条件**: 予約の参照・操作は、リクエストした本人の予約だけに効く。

- 他人の航空券・ホテル・旅程が、一覧や詳細に混ざらない。
- 未認証、または他人の予約 ID を指定したアクセスは拒否される。

**なぜ重要**: 崩れると他人の旅程・個人情報が見えたり、他人の予約を操作できてしまう（IDOR）。DB 上は全利用者の予約が同じテーブルに並ぶため、予約者での絞り込みが常に効いている必要がある。

**どこで点検**: 各 API の予約者スコープ。他人の予約 ID を指定したアクセスが拒否されるかを動作確認する。

## 2. 冪等性

**不変条件**: 同じ操作・イベントが複数回届いても、二重に適用されない。同じ操作とは:

- キャンセル・人数変更リクエストの**再送／二重クリック**。
- 通信リトライによる**同一リクエストの重複到達**。

**なぜ重要**: ネットワーク越しの操作は再送・重複が起こりうる。冪等でないと、1 回のキャンセルで二重返金、1 回の増員で二重課金など、データが実態とずれる。

**どこで点検**: 同一操作を識別子で重複排除できているか。「実行 → 取消 → 再実行」やリトライ・二重送信で二重適用が起きないかを動作確認する。

## 3. 複数予約の独立性

[`cases.md`](./cases.md) の各ケースは「1 つの旅程」を暗黙の前提にするが、実際は同じ人が複数の旅程・予約を並行して持つ。複数でも次が成り立つ。

**不変条件**:

- **対象の予約だけが処理される** — あるキャンセル・人数変更が、同じ人の**別の旅程に及ばない**（取り違え MX-1 の防止と対）。
- **一覧・合計が正しく分離・集計される** — 複数旅程の料金・件数が、取りこぼし・二重計上なく足し合わされる。

**なぜ重要**: 複数予約は日常的に起きる。対象外まで処理したり別の旅程と混線すると、利用者に見えるデータが狂う。

**どこで点検**: 操作は予約 ID で対象を一意特定しているか（氏名など曖昧なキーで結びつけない）。複数旅程を持つ利用者で、対象だけが動き他が不変かを動作確認する。
