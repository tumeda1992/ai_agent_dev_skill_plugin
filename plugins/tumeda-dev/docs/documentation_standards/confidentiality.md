# 機密情報を document へ書かない

`documentation_standards/` の傘の下の 1 トピック。**その記述が公開されたとき、それを読んだ人が何をできるようになるか**を扱う。

他の標準は、読者がその doc で作業できるかを見る。この標準だけが、書いてはいけないものが入っていないかを見る。判定の向きが逆であるため、濃さも記法も満たした document が、この標準だけを満たさないことがある。

## 一般則（判定の起点）

**この記述が公開されたとき、それを読んだ人は何ができるようになるか。** これが判定の起点である。できるようになることが実質無いなら、そのまま書いてよい。

型で判定しない。credential、構成情報、個人情報、事業上の機密といった型は、この問いから出てくる具体例であって、判定の軸ではない。型を軸にすると、判定のたびに全種類を照合する形になり、照合漏れに気づけない。新しい型が現れたときに軸そのものを作り直すことにもなる。

判定の対象を攻撃に限定しない。攻撃は「できるようになること」の一種である。個人情報が漏れて困るのは本人へ害が及ぶからであり、事業上の機密が問題になるのは競合優位を失うからである。攻撃だけを軸にすると、これらを判定できない。

## 判定の二段

### 第 1 段: 何ができるようになるか

一般則の問いを当てる。できるようになることが実質無いなら、第 2 段へ進まずそのまま書く。大半の記述はここで落ちる。第 2 段まで進むものを絞ることが、この段の役割である。

**「実質無い」を、その記述単独で判定しない。** 公開範囲の中にすでにある情報と合わせて判定する。単独では無害に見える記述でも、既知の情報と組み合わさって到達経路が完成するなら、できるようになることがある。

- 「この service は既定 port で待ち受ける」と書いたとする。port の実値は書いていない。しかし service の種類が分かれば既定 port は公開情報であり、実値を書いたのと変わらない。**実値を避けたことは、判定を通った根拠にならない。**
- 「認証は token だけで行う」と書いたとする。到達先は書いていない。しかし同じ document の別の節が到達先を説明しているなら、二つを合わせて経路が完成する。節ごとに判定して、document 全体で判定していない。

**外れているとどう見えるか。** 記述を一つずつ取り出して判定し、どれも単独では無害だと確認して通す。個々の判定はすべて正しく、集まった document が機密になる。この形は、判定を几帳面に当てるほど起きやすい。一つずつ丁寧に見ることが、組み合わせを見ないことと両立してしまう。

判定の単位は個々の記述ではなく、**公開範囲へ置かれる document 全体**である。

### 第 2 段: 識別子と構成の性質を分ける

第 1 段を通ったものを、二つに分ける。

**識別子** — domain 名、host 名、固定 IP、resource 名、account ID など、対象を一意に指す値。**その document が作る対象であっても、実値を書かない。** 変数または placeholder で参照する。識別子は到達先そのものであり、参照へ置き換えても設計の理解は損なわれない。

**構成の性質** — 何を許可するか、どの層で遮断するか、どの経路を通るかなど、対象の振る舞いを表すもの。**その document が作る対象なら書く。既存環境のものは書かない。** 構成の性質はその設計がどう動くかの説明であり、設計の正本として必要になる。

この順序を守る。第 2 段だけを先に当てると、内部 port や環境変数名のような、第 1 段で落ちるはずの識別子まで変数化することになり、document が読めなくなる。

## 型ごとの例

### credential

password、token、key、接続文字列。

第 1 段で必ず引っかかり、第 2 段へは進まない。「書かない」で完結する。

置き場所を書くことは禁じない。「この値は `.env` の `DB_PASSWORD` が持つ」と書いてよい。禁じるのは値そのものである。値を書いてしまった場合、document から消しても version 履歴に残るため、credential 自体の無効化と再発行が要る。

### 構成情報

到達先、port、経路、防御の構成。

第 2 段の判定が効く型である。同じ内容でも、その document が作る対象なら書き、既存環境のものなら書かない。

判断が分かれやすいのは、設計文書が既存環境を前提として説明する場合である。「既存の queue サーバへ接続する」と書くことと、「既存の queue サーバは接続元を絞っておらず、防御は認証だけである」と書くことは違う。前者は接続先の存在であり、後者は防御の薄さである。

### 個人情報・事業上の機密

氏名、メールアドレス、契約条件、原価、未公開の計画。

攻撃ではなく、本人への害や競合優位の喪失で判定される。第 1 段の問いをそのまま当てると、「その人物へ連絡できるようになる」「価格交渉で不利になる」という形で出てくる。

## 公開範囲の確認

識別子を実値で書いてよいかは、その repository の公開範囲に依存する。private repository で許されることが public repository では許されない。

**この標準は公開範囲を持たない。** 公開範囲は repository 固有の fact であり、その repository の固有 context file が持つ。固有 context file の所在と、そこから何を読んでよいかは `maintenance-plugin-context` skill が解決する。この標準が持つのは、識別子を実値で書く前に公開範囲を確認する、という手順だけである。

確認の対象を「これから書くもの」に限定しない。公開範囲が判明した時点で、すでに書き終えた成果物へ遡る。同じ作業の中で書いたものは、書いた時点が違っても同じ公開範囲に置かれる。

## だめな例と直した形

### 既存環境の構成を、設計の前提として書く

- だめな例: 「batch worker は既存の queue サーバへ接続する。queue は port `{n}` で待ち受けており、security group は接続元を絞っていないため、防御は接続時の認証だけである」
  - 何ができるようになるか: 到達先、port、防御の薄さが揃っている。読んだ人は攻撃経路をそのまま得る。
  - どの判定で落ちるか: 第 1 段を通る。第 2 段で、security group の設定は既存環境の構成の性質にあたり書かない。port は識別子にあたり実値を書かない。
- 直した形: 「batch worker は既存の queue サーバへ接続する。接続先は `.env` の `QUEUE_HOST` と `QUEUE_PORT` が持つ」

### その design が作る対象を、対策と対で書く

- 残してよい例: 「この design が作る task の port を `0.0.0.0/0` で開ける。IP 直アクセスは application 側の Host header 検証が弾く」
  - なぜ残してよいか: この `0.0.0.0/0` はその design が新しく作る security group のものであり、既存環境の設定ではない。設計の正本として必要であり、かつ別の層で遮断する仕組みと対で書かれている。

**同じ文字列でも判断が逆になる。** 上の二つはどちらも接続元を絞らない設定を述べているが、一方は既存環境の性質であり、もう一方はその design が作る対象である。文字列ではなく、どちらを述べているかで決まる。

## 検知手段

**書き終えた document から、調査で得た事実をそのまま写した箇所を探す。**

この標準へ違反する記述は、多くが調査の副産物である。調査で分かったことを成果物へ書き写すとき、調査の網羅性と、書いてよいかの判断が同じものとして扱われる。調査は網羅的に行ってよい。書く時点で別の判断を通す。

探す対象は二つである。

1. 既存環境について述べた記述。その document が作る対象でないものは、第 2 段で落ちる。
2. 実値で書かれた識別子。変数または placeholder で参照できないかを見る。

機械的な検知は一部にしか効かない。credential は形が決まっているため文字列 pattern で拾えるが、構成の性質は文脈で判断が逆になるため拾えない。上記「だめな例と直した形」の二つは、どちらも接続元を絞らない設定という同じ内容を述べていながら、判断が逆になる。hook や lint を置く場合は、効く範囲が credential に限られることを前提にする。

## 該当しない例

- **内部 port、変数名、環境変数名**: 第 1 段で落ちる。`QUEUE_PORT` という変数名を書いても、読んだ人ができるようになることは無い。
- **公開 API の endpoint 名**: すでに公開されている。document へ書くことで新しくできるようになることは無い。
- **その design が作る構成の性質**: 第 2 段で残る。設計の正本として必要である。

この標準は、構成について書くこと自体を禁じるものではない。禁じるのは、既存環境の構成の性質と、実値で書かれた識別子である。設計文書が自分の作る対象を説明できなくなっているなら、判定の当て方を間違えている。
