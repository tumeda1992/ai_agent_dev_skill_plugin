# 読者 — 執筆者が深さを測る物差し

ドキュメントを「どこまで詳しく書くか」は、書き手の気分ではなく**読者**で決まる。この標準は、docs を書く・構造化するときに執筆者が深さを測るための **物差し** として読者を定義する。これは **執筆・保守のための内部の道具** であって、読者に見せる定義ではない（露出のルールは末尾 §3）。物差しの目盛りは、職種ではなく「**関与の仕方**」で刻む。

## 1. なぜ「関与の仕方」で切るか

読者が必要とする情報の深さを決めるのは、職種ではなく〈**何を変えようとしているか（変更意図）× どこまで深く要るか（深さ）× 過去の経緯が要るか**〉である。だから読者は職種ではなく「関与の仕方」で捉える。

職種で切ると、二通りに外す。

- **同じ情報ニーズの別職種を、無駄に分けてしまう。** 「使うが変えない」という点では、他分野を触るエンジニアも QA も、全ケースを網羅したいという要る深さは同じ。職種が違っても分ける意味がない。
- **違う情報ニーズの同職種を、一括りにしてしまう。** 同じエンジニアでも、現行コードを直すだけの案件と、仕様そのものを設計し直す案件とでは要る情報が違う（後者は過去の経緯まで要る）。職種で括ると取り違える。

## 2. 読者の段階

関与の仕方は、浅い方から深い方へ並ぶ。「使うが変えない」読者だけは、求める深さでライト利用読者とヘビー利用読者に分かれるので、段階は全部で 5 つになる。

| 読者 | 関与の仕方 | 必要な情報 |
|------|-----------|-----------|
| **概観読者** | 触らない・使わない | ドメインが要は何をする仕組みで、なぜ在るか。これだけで完結する |
| **ライト利用読者** | 使うが変えない（狙った機能だけ） | 知りたい機能まわりの概略。全ケースの網羅までは要らない |
| **ヘビー利用読者** | 使うが変えない（網羅して使う） | 起こりうる全ケース。これで「全ユースケースを押さえた」と判断できる |
| **改修読者** | 現行のコード・仕様を変える | 現行の仕様と実装の **スナップショット**。過去の経緯は要らない |
| **設計読者** | あるべき論から変える | 改修読者の情報 **＋** 過去の経緯・棄却案・未確定 |

各読者を、想定する人物像と「現実には誰がこれにあたるか」で描く。**現実の担い手は例であって、分類の軸ではない**（軸は関与の仕方）。実際、同じ職種が案件によって複数の読者にまたがる——それが以下の例に表れる。

### 概観読者

存在と目的だけを知りたい、最も浅い読者。この物差しの原点であり、**最も制約が強い基準読者**でもある——多くの成果物は「この人が単独で読めるか」を合格ラインにする。

#### ペルソナ

この読者は最も制約が強いので、人物像を最も具体に描いておく。

- **プログラミングに詳しくない。** コード・テーブル・SQL・クラス名やメソッド名を出されても意味が取れない。
- **このドメインに詳しくない。** 業務用語を知らず、初めて聞く語として読む。
- **腰を据えて精読はしない。1〜5 分で「要は何の仕組みか」を掴みたい。** まず全体像がほしく、細部を追う気はまだない。
- **長い散文の壁で読み疲れる。** 知らない概念が続くと、なおさら脱落する。
- **図があると概念を掴みやすい。ただし図の巧拙に敏感。** 下手な図（絵になっていない／箇条書きで済むものを無理に図にした）はかえって混乱する（記法の使い分けは [`./expression_notation.md`](./expression_notation.md)）。

#### 現実の担い手

- **基本、誰でも。** その分野に初めて触れる人が最初に通る入口。

### ライト利用読者

ドメインを使うが変えない読者のうち、**狙った機能を知りたいだけ**の人。概観読者より一歩踏み込むが、全ケースのヌケモレを確認するところまではしない。

#### ペルソナ

- **前提はバラつく。** 非技術の CS・ビジネス層から、技術はあってもドメインを知らない新規エンジニアまで。共通するのは「今ある一つの疑問に答えが欲しい」こと。
- **目的駆動で、通読しない。** 全体を読み通す気はなく、用のある機能へ直行し、済めば離れる。
- **目的の機能へたどり着けて、その一節だけで用が足りる**ことを求める。関係ない全体像を通されたり、あちこち参照させられると脱落する。

#### 現実の担い手

- CS メンバー
- 新規参入エンジニア（新卒に限らず、経験はあってもドメイン知識のない中途も）
- ビジネス層（特定の機能を把握したいとき）

### ヘビー利用読者

同じく使うが変えないが、**起こりうる全ケースを網羅的に押さえる必要がある**人。当該ドメインのコードは触らない（自分の担当外）ぶん改修読者ではないが、要る網羅の深さは高い。

#### ペルソナ

- **網羅に責任を負う。** 抜けがそのまま仕事の穴になる（QA の見逃し・仕様検討の考慮漏れ）。「全部で何通りか、例外・境界はどこか」を潰したい。
- **ドメインは深く理解する（したい）。** 技術前提はまちまち（非技術のビジネス層〜他分野のエンジニア）だが、実装の中身（SQL・クラス名）までは要らない。
- 一つのケースを見て満足せず、**起こりうる状況とその条件が、抽象に畳まれず具体で出そろっている**ことを求める。

#### 現実の担い手

- 機能の仕様を検討するビジネス層
- 他分野を触っていて、当該ドメインは変えないエンジニア
- QA エンジニア

### 改修読者

現行のコード・仕様を変える読者。あるべき論は上位で決まっている前提で、**現行のスナップショット**があれば動ける。「なぜ今こうなっているか」の経緯は要らない。

#### ペルソナ

- **コードを読み書きする技術者。** 「今どう動くか」「どこを変えると何に影響するか」を正確に知りたい。あるべき論や過去の議論は、今は雑音になる。
- **ドメイン習熟度に幅がある。** その領域のメンテナーは深いが、"ついで" で触る人はほぼ初見で、**現行仕様を最短で正確に**掴む必要がある。
- 仕様と現行実装（どのデータ・どの処理か）が対応づけて分かることを求める。

#### 現実の担い手

- その領域のメンテナー
- その領域が主ではないが、影響が及ぶので "ついで" に触らざるを得ないエンジニア

### 設計読者

あるべき論から変える読者。仕様を設計し、意思決定する。現行に加えて **過去の経緯**——なぜその設計にしたか・何を捨てたか・何が未確定か——が要る。

#### ペルソナ

- **その領域を最もよく知る（知ろうとする）技術者。** 現行は読める前提で、あるべき論を動かすため「なぜ今こうなっているか」を踏まえる——踏まえないと設計を誤る。
- **過去の判断理由・棄却された案（同じ轍を踏まないため）・未確定事項**まで辿りたい。改修読者の情報に歴史を重ねた、最も深い読者。
- 現行の仕様と、その背後の経緯が切れずに辿れることを求める。

#### 現実の担い手

- その領域を主戦場にし、機能追加や仕様変更をがっつり行うエンジニア

### 読者定義の運用思想

**同じ職種が複数の読者にまたがることに注意。** ビジネス層は、機能を知りたいだけならライト利用読者、仕様を検討するならヘビー利用読者になる。エンジニアも、分野や案件によって改修読者にも設計読者にもなる。だから読者は職種で切れない（§1 の裏返し）。

**重ね着（読者は下位互換）。** 深い読者は、浅い読者向けの情報も読む。設計読者は改修読者向けの現行スナップショットも、ヘビー利用読者向けの全ケースも、概観読者向けの概略も読む。深さは浅い側から積み上がるので、概観読者向けの説明が常に土台になる。

## 3. 読者モデルを露出しない

この読者像は **書く側の道具** であって、読者に見せるものではない。したがって:

- ドキュメントの **本文・見出し・ディレクトリ名に、読者名やその定義を書き出さない。** 読者は自分のラベルを探しに来るのではないし、内部符号を出せば読み手に辞書引きを強いる。
- 読者に見せてよいのは、ドメイン直下の README に置く「**読む順の目安**」程度の軽い導線だけ。「〜したい人はまず overview」のような、役割タグ付きの導線までは許容する。読者を名付けたり、定義を書いたりはしない。
