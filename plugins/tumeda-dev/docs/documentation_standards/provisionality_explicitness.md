# 暫定性の明示

`documentation_standards/` の傘の下の 1 トピック。**今回の範囲に限った判断を書いたとき、読み手がそれを恒久の方針と取り違えないか**を扱う。

## 一般則

判断には二種類ある。変える理由が現れない限り続く恒久の判断と、今回の範囲・今の条件に限った暫定の判断である。暫定の判断を書くときは、暫定であることを文中に残す。

暫定の判断は、書いた時点では書き手にも読み手にも暫定だと分かっている。時間が経つと、暫定にした理由と見直す条件が伝わらなくなる。理由と条件の落ちた文は恒久の方針と同じ形をしており、読み手はそれを前提として固定する。見直すべき判断が、見直されないまま次の設計の土台になる。

docs と skill 本体だけでなく、steering の作業記録にも当てる。後続の作業は先行の作業記録を前提として読むためである。下の型2・型3 は、作業記録で起きた。

## 対象になる判断

- **今回の範囲に限った判断** — 「今回は含めない」「初回の公開では無効にする」
- **条件付きの保留** — 「実測が許容時間に近い場合のみ別途合意する」
- **別の作業への切り出し** — 「別の issue で扱う」

## 書く 3 点

**MUST**: 暫定の判断を書くときは、次の 3 点を書く。

1. **暫定であること** — 今回の範囲・今の条件での判断であり、恒久の方針ではないこと。
2. **暫定にした理由** — なぜ今は決めない・やらないのか。
3. **見直す条件、または切り出した先** — どうなったら見直すか。別の作業へ切り出したなら、読み手が辿れる識別子（issue 番号など）を書く。切り出し先は実在するものだけを書く。

## 写すときの規則

暫定の判断を別の document へ写すときも、3 点を落とさない。design から README へ写すとき、先行の作業記録から後続の design へ写すときが典型である。結論だけを写さない。

3 点は写すときに最も落ちやすい。写す先の文脈では、暫定にした事情が見えないためである。しかも写した先の文は元の文より長く残り、元の文を読まない読み手に多く読まれる。

## 判定の問い

**見直す条件を知らない読み手がこの文だけを読んだら、恒久の方針と受け取らないか。**

受け取らないなら、そのままでよい。受け取るなら、3 点のどれが欠けているかを特定して埋める。

## 検知手段

**「しない」「含めない」「無効」「保留」「別途」「切り出し」を含む文を拾い、その文だけを取り出して判定の問いを当てる。** 暫定の判断は、この形の語で書かれることが多い。

写した記述では、元の文と写した文を並べ、写した文で 3 点のどれが落ちたかを見る。写した文だけを読み返しても、恒久の方針として自然に読めるため気づけない。

## 型ごとの、だめな例と直した形

### 型1: 写すときに暫定性と見直す条件が落ちる

- 元の文: 先行の作業の design に「初回の公開の範囲を絞るため、この機能が使う runtime の経路を今回は無効にする。この機能を公開機能へ加える判断をした時点で改めて設計する」とあった。
- だめな例: README へ写した記述は「経路を無効に保つため、この変数は runtime へ渡さない」になった。
  - 何が起きたか: 後の session の assistant はこの README だけを読み、利用者に「最初から動かさない設計」と答えた。README の文は恒久の設計と同じ形をしており、暫定の判断だと分かる材料が無かった。
- 直した形: 「初回の公開の範囲を絞るため、この機能が使う runtime の経路を暫定で無効にしている。そのため、この変数は今は runtime へ渡さない。この機能を公開機能へ加える時点で、経路と変数の扱いを改めて設計する」

### 型2: 条件付きの保留を、決定済みとして写す

- 元の文: 先行の作業の記録に「実測が許容時間に近い場合のみ別途合意する」という保留があった。
- だめな例: 後続の作業の design の非目標が、これを「行わないと決定済み」と書いた。
  - 何が起きたか: 条件が消え、「条件が成り立てば合意する」判断が「行わない」判断に変わった。後続の design を前提にする読み手は、条件が成り立っても見直さない。
- 直した形: 「先行の作業で、実測が許容時間に近い場合のみ別途合意すると保留している。今回の実測は許容時間を十分下回るため、今回は行わない。実測が許容時間に近づいたら改めて合意する」

### 型3: 実在しない切り出し先を書く

- だめな例: design の非目標に「別作業に切り出し済み」と書いたが、切り出した issue は実在しなかった。
  - 何が起きたか: 読み手は切り出し先で扱われると受け取る。実際には今の作業でも切り出し先でも扱われないまま残る。
- 直した形: 切り出し先を先に作り、「今の作業に含めると本番への適用が遅れるため、issue #NN へ切り出した。#NN で非同期化を設計する」のように、読み手が辿れる識別子と、そこで扱う内容を書く。

## 該当しない例

- 「議論の記録役の skill は、作業の範囲の判断基準を持たない」: 責務の境界に基づく判断であり、変える理由が現れない限り続く。恒久の方針と読まれても誤りにならないため、見直す条件は書かなくてよい。理由は、恒久の判断にも通常どおり書く。

この標準は、すべての「しない」を暫定として扱うものではない。判断が今回の範囲・今の条件に依存しているときだけ当たる。
