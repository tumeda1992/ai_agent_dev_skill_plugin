<!--

調査、比較、技術検証によって、分かっていなかった問いを確定すること自体が作業の主な成果である場合だけ使う。
別の成果物を設計する途中で得た事実は、その成果物を扱う完成後の姿のsectionへ根拠として書き戻す。

なぜ必要か:
- 外部API、認証、環境によって変わる挙動を推測で埋めることを防ぐため。
- 「調べた」「動いた」という活動の報告ではなく、根拠から何が言え、何はまだ言えないかを成果にするため。
- 環境やversionが変わった後も、分かったことが当てはまるかと、確かめ直す時期を判断できるようにするため。

NG:
- APIはこのresponseを返すはず
- spikeを実装した
- testしたら動いた
- commandの出力や読んだ記録をそのまま貼る
- 一つの具体ケースから標準や運用の決まりを直接作る。それは`documentation.md`に書く
- 技術検証のcodeを、そのまま本番の実装として使い続ける

具体的な記述例:
- 分かっていなかった問い: 404 responseで、bodyがJSONか空か
- 推測で決められない理由: 公式のschemaがerror時のbodyを決めていない
- 確かめ方: sandboxのendpointへ、存在しないdocumentIdを送る
- 根拠: API version v2でHTTP 404、bodyは{"error":"not_found"}
- 分かったこと: version v2のsandboxでは、404のbodyにerror fieldがある
- できるようになった判断: parserはerror fieldを読める
- まだ言えないこと: 本番環境も同じbodyを返すこと
- 確かめ直すきっかけ: API versionまたは公式のerror schemaの変更

記述のMUST:
- 分かっていなかった問い、推測で決められなかった理由、調べた情報源または再現方法、根拠、分かったことを分ける。
- 比較の条件、command、環境、version等、別の人が同じことを試せる条件を示す。
- 根拠から直接言えることと、それによってできるようになった判断を混同しない。
- 分かったことが当てはまる範囲、確かさ、覆る条件、まだ言えないこと、確かめ直すきっかけを示す。
- 生のlogと試行錯誤は`investigation.md`または`spike/`へ置き、このsectionには結論に必要な根拠だけを残す。
- spikeは不確実性を解消する手段であり、本番の変更としてtasklist・roadmapへ載せない。

判断基準:
- 同じ条件で、別の人が根拠を確かめ直せるか。
- 根拠を超えた一般化を、分かったこととして書いていないか。
- 分かったことが変わった時、どの判断を考え直すべきか追えるか。
- 調査の活動ではなく、分かっていなかった問いへの、再び使える答えになっているか。
