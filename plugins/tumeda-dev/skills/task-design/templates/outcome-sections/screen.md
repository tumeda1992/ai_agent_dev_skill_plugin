### 画面イメージと配置意図

<!--
UI変更を伴う場合だけ使う。操作フローやcomponentの責務が決まっていても、
情報の順序、強調、まとまりが合意されていなければ、実装者が画面構成を独自に判断する。

NG:
「保存buttonを押すと更新APIを呼ぶ」とだけ書き、
どの情報と操作をどこへ配置するかを実装時に決める。

具体的な記述例:
ItemCard:
┌──────────────────────────────┐
│ タイトル                       │
│ 主操作A  主操作B               │
│ 補助属性1  補助属性2            │
│ メタ情報                       │
└──────────────────────────────┘

配置意図:
- titleを最上部に置き、一覧で判断を始める起点にする
- 同じ頻度・重要度の主操作を同じ列にする
- 補助属性とメタ情報は、主操作より見た目の優先度を下げる

記述のMUST:
- ASCIIのwireframe等で、各要素の位置、順序、まとまりを示す。
- なぜその順序・強調なのかを示す。
- 既存画面との差分だけでなく、完成後の画面全体を評価できるようにする。
- componentが受け取る値を並べた場合、各値を渡す親、loader、repositoryと、渡される経路を対応付ける。
- 初期、loading、成功、空、error、操作不可等、今回変わる状態ごとの見え方を示す。

書く状態を選ぶ条件:
- 今回の変更で新しく現れる状態、または表示、強調、操作できるかどうか、次の操作のどれかが変わる既存の状態を示す。
- `初期 / loading / 成功 / 空 / error / 操作不可`を、固定のchecklistとして機械的に全て並べない。
- 該当しない状態や、今回変わらない隣の画面を足さず、状態名は実際のdomain・UIの状態で書く。

このsectionに書くこと・書かないこと:
- このsectionには、各状態で見える情報、配置・強調、操作できるかどうか、画面からできる次の操作を書く。
- その状態に至る呼び出しの順序、serverの処理、dataの変化は`interaction-flow.md`、error type／status／payloadは`caller-contracts.md`に書く。

判断基準:
- wireframeだけで情報のまとまりと優先度が分かるか。
- 配置が単なる好みではなく、操作する人が判断する順序と操作の頻度につながっているか。
- 表示に使う値の取得・受け渡しを、実装者がその場で決める余地がないか。
-->
