### 画面イメージと配置意図

<!--
UI変更を伴う場合だけ使う。操作フローやcomponent責務が決まっていても、
情報の順序、強調、まとまりが未合意なら実装者が画面構成を独自判断する。

NG:
「保存buttonを押すと更新APIを呼ぶ」とだけ書き、
どの情報と操作をどこへ配置するかを実装時に決める。

具体的な記述例:
ItemCard:
┌──────────────────────────────┐
│ タイトル                       │
│ 主操作A  主操作B               │
│ 補助属性1  補助属性2            │
│ メタ情報                       │
└──────────────────────────────┘

配置意図:
- titleを最上部に置き、一覧での判断起点にする
- 同じ頻度・重要度の主操作を同列にする
- 補助属性とmetadataは主操作より視覚優先度を下げる

記述のMUST:
- ASCII wireframe等で各要素の位置、順序、まとまりを示す。
- なぜその順序・強調なのかを示す。
- 既存画面との差分だけでなく、完成後の画面全体を評価できるようにする。
- component inputを列挙した場合、各inputを供給する親、loader、repositoryと受渡し経路を対応付ける。
- 初期、loading、成功、空、error、操作不可等、今回変わる状態別の見え方を示す。

状態選択のgate:
- 今回の変更で新しく到達する状態、または表示、強調、操作可否、次の操作のいずれかが変わる既存状態を示す。
- `初期 / loading / 成功 / 空 / error / 操作不可`を固定checklistとして機械的に全列挙しない。
- 該当しない状態や今回変わらない隣接画面を追加せず、状態名は実際のdomain／UI状態で書く。

owner境界:
- screen sectionは各状態で見える情報、配置・強調、操作可否、画面から可能な次の操作を所有する。
- 状態へ至るcall順序、server処理、data変化はinteraction flow、error type／status／payloadはcaller contractが所有する。

判断基準:
- wireframeだけで情報のgroupと優先度が分かるか。
- 配置が単なる好みではなく、actorの判断順序と操作頻度へ接続しているか。
- inputの取得・受渡しを実装者がその場で決める余地がないか。
