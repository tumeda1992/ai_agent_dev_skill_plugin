# skill: doc-enricher（次の作業者が同じ手間を払わずに済むようにする）

## 作業限定の暫定指示を取得する

起動・別sessionからの再開・resume・把握した指示変更時に、元作業のexactな場所、consumer `doc-enricher`、
対象処理、実際に使うこのSKILL.mdの取得元を`maintenance-plugin-context`へ渡し、暫定指示を取得する。
選択・競合・実行版の判断は管理担当へ委ねる。
activeの実効指示に従い、paused/unavailableでは影響する暫定動作を止めて理由を返す。
none/endedでは既存処理へ進む。
元作業不明を別作業の探索で補わない。
通常の返信・内部file再読・think-throughの毎turn適用を定期取得へ変えない。
同一sessionの登録・改訂結果は返却された更新を使い、通知されていない編集を常時検知できるとは扱わない。

元作業directoryが未確定なら、取得不能をnoneにせず管理担当へ不足を返す。
既存ownerによる命名・directory確定に必要な処理は続け、影響する暫定動作だけを待ちにする。
元作業が確定した直後に取得し、先に対象の暫定動作を実行しない。

## repository固有文脈

「進行」の1で払った手間が一件でも挙がったら、`maintenance-plugin-context`へconsumer=`doc-enricher`、必要理由、必要fact、確認元候補を渡す。必要factは、プロジェクト指示、上位アーキテクチャ文書、[置き場所の一覧](place-map.md)である。返された範囲だけを読み、固定path・固定文書名を推測しない。

置き場所の一覧が返らなければ、[place-map.md](place-map.md) の作り方で作り、保存を`maintenance-plugin-context`へ依頼してから進む。

## 役割

作業の中で払った手間のうち、次の作業者がrepositoryだけを頼りに同じ種類の作業をすると再び払うものを見つけ、払わずに済むようにする文書の変更を提案する。

次の作業者は、この作業の会話を読めない。読めるのはrepositoryに置かれた文書とcodeだけである。この作業で分かったことは、repositoryに置かなければ、次の作業者がもう一度同じ手間を払って手に入れることになる。

この役割から、進め方が四つ決まる。「進行」の各段は、この四つを実行する形になっている。

| 決まること | 理由 | 外した時に起きること |
| --- | --- | --- |
| 候補は、払った手間から作る。「まだ書かれていないこと」からは作らない | 手間を払ったという事実だけが、その知識をrepositoryから読み取れなかった証拠になる | 「概要の節が無いから書く」のように、誰も困っていない記述を提案する |
| 読む人と読む場面は、手間を払った時の自分から取る。想像で作らない | 手間を払う直前の自分は、次の作業者と同じ立場にいた。その時に読んでいた文書と探した場所が、次の作業者も通る道になる | 次の作業者が通らない場所へ置き、読まれない |
| 当てはまる範囲は、確かめて測る。広く見せない | 狭い範囲にだけ当てはまる知識は、狭い場所に置けば役に立つ。広い場所に置けるかは、別の実例で確かめるまで分からない | 今回の一件にしか当てはまらない文が、全体に効く文書へ載る |
| 変更の種類は追加だけではない | 手間の原因は「書かれていない」とは限らない。書かれているのに辿り着けなかった、読んだのに守れなかった、書かれた内容が誤っていた、でも手間は生じる | 既に書かれていることを重ねて書く。誤った記述を残したまま隣に正しい記述を足す |

## 運用

- 既定は提案だけである。利用者が承認するまでfileを変更しない。
- 「提案なし」は正常な結果である。このskillは作業の節目ごとに呼ばれるため、提案が無い回のほうが多い。呼ばれたことを理由に提案を作らない。
- 利用者とは日本語で会話する。

## 進行

各段で、[提案の形](templates/proposal.md) の欄を埋める。欄は、起きた事実か、実在するpath・名前で埋める。評価の言葉（重要、有用、再利用できる）では埋めない。埋められない欄が出た時の扱いは、各段に書いてある。

### 1. 払った手間を挙げる

呼出し側から渡された範囲の作業で起きたことから、次の三種類を挙げる。

| 種類 | 起きたこと | 例 |
| --- | --- | --- |
| 探した | 知りたいことが最初に見た場所に無く、複数のfileを読んで分かった | 業務の決まりを業務知識の文書で探して見つからず、codeを五つ読んで分かった |
| 誤った | 前提を誤り、利用者・review・test・実行結果に訂正された | 集約をまたぐ処理をcommandに書き、利用者に「application serviceに置く」と直された |
| 決めた | 議論して決めた。決めた理由が、できあがった成果物を読んでも分からない | 文書の取得元ごとにmutationを三つに分けると決めた。codeには三つあることしか現れない |

素材は、この作業の会話、作業の記録（steeringのdiscussionがあれば最優先）、review指摘である。

一件も挙がらなければ、「提案なし」を返して終える。

- やってしまいがちな失敗: 触れたdirectoryのREADMEを開き、足りない節を探して候補にする
- それをやると何が起きるか: 誰も手間を払っていない記述が増える。読む量だけが増え、次の作業者の助けにならない
- 判断の問い: 「この候補は、この作業のどの時点の、どの手間から出たか。会話や記録のその箇所を指せるか」

### 2. 次の作業者も同じ手間を払うかを確かめる

挙げた手間の一件ごとに、次を問う。

**今回の成果物が入った後のrepositoryで、同じ種類の作業をする人は、同じ手間を払うか。**

| 答え | 扱い |
| --- | --- |
| 払わない。今回の修正で原因が無くなった（bugを直した、名前を直した、codeから読めるようにした） | 捨てる |
| 払わない。今回の作業の中だけの事情である（今回の依頼の経緯、今回の進め方、調べた時点の数値やlog） | 捨てる |
| 払う。ただしcodeやtestを直せば払わなくなり、文書より確実である | 文書の提案にせず、「文書以外で直せるもの」として返す |
| 払う。原因がrepositoryに残る | 3へ進む |

例を四つ挙げる。

- 払う: 「statusに値を足したら、外部systemとの対応表も直す必要があった。対応表があることはcodeから辿れない」。次に値を足す人も同じ場所で漏らす。
- 払う: 「文書の取得元ごとにmutationを三つに分けると決めた。分けた理由はcodeに現れない」。次に取得元を足す人は、分けるか一つにまとめるかをもう一度議論する。
- 払わない: 「migrationが失敗した原因は、columnを足す順序だった」。直したので、次の作業者は失敗しない。
- 文書以外で直せる: 「引数の順序を取り違えた」。引数を名前付きにすれば、取り違えは起きなくなる。

code以外の作業でも同じである。「本番のqueueの名前を知るために管理画面を三つ見た」は、次の作業者も払う。「deployが落ちたのは一時的な権限切れだった」は払わない。

捨てた手間の経緯を残したい時は、作業の記録が持つ。このskillは文書へ置かない。

- やってしまいがちな失敗: 起きた出来事から固有名を消し、決まりの形に書き換えて、「次も起きる」と扱う
- それをやると何が起きるか: 今回しか役に立たない記述が、決まりの顔をして文書に残る。出来事の書き方を変えても、原因がrepositoryに残っているかは変わらない
- 判断の問い: 「手間の原因は、今回の成果物が入った後もrepositoryに残っているか。残っているなら、それは何か」

### 3. 何が書いてあれば払わずに済んだかを書く

手間を払う直前の自分に戻り、その時に何が読めていれば手間を払わなかったかを、一〜三文で書く。理由も添える。

書くのは、これからも成り立つこと（決まり、性質、関係、理由）である。起きたこと（〜だった、〜を直した）は書かない。

| 起きたこと（書かない） | これからも成り立つこと（書く） |
| --- | --- |
| 集約をまたぐ処理をcommandに書いて、直された | 集約をまたぐ処理はapplication serviceに置く。commandに置くと、一方の集約がもう一方の内部を知る形になる |
| statusに値を足した時、対応表の修正を漏らした | statusの値は外部systemの値と一対一で対応する。値を足す時は対応表も直す |
| 手順書の確認を一つ飛ばして、やり直した | 権限の付与は、付与した本人以外の画面で確かめる。本人の画面は、付与前から見えていることがある |

あわせて、手間を払う直前の自分について二つを記録する。6で置き場所と導線を決めるのに使う。

- その時に読んでいた文書（作業の開始時に読まされた文書を含む）
- 知りたいことを探して、最初に見た場所

どんな形の知識になるかの手掛かりは、末尾の「知識の形の例」にある。

### 4. 当てはまる範囲を測る

3の文が、どこまでの範囲で成り立つかを測る。範囲は次の段で数える。

一箇所（関数、設定の一行） → 一つのmodule・directory → 一つの領域（domain、層） → repository全体 → repositoryの外（どのrepositoryでも成り立つ）

測り方は次のとおりである。今回の対象がある段から始める。

1. 一つ上の段の中から、今回の対象とは別の、repositoryに実在するものを一つ名指しする。
2. 名指ししたものを実際に読み、3の文がそのまま成り立つかを確かめる。
3. 成り立てば範囲を一段広げ、1へ戻る。成り立たない、名指しできない、読んで確かめられない、のどれかなら、広げる前の段で止める。

止まった段が、この知識の範囲である。狭い段で止まってよい。狭いことを理由に捨てない。狭い範囲の知識は、6で狭い置き場所に置く。

広げた範囲の中に、成り立たない実例が一つでもあれば、その範囲では成り立たない。「〜の場合は」と条件を足して成り立たせた結果、今回の一件にしか当たらなくなったら、それは決まりではなく今回の判断である。置き場所は文書ではなく、この作業の記録になる。

範囲がrepositoryの外まで広がった知識は、このskillでは置かない。範囲と確かめた実例を添えて、呼出し側へ返す。

例を三つ挙げる。

- 「集約をまたぐ処理はapplication serviceに置く」: 別のmoduleにも集約をまたぐ処理があり、読むとapplication serviceに置かれていた。さらに別の領域でも同じだった。範囲はrepository全体のcodeである。
- 「statusの値は外部systemの値と対応する」: 隣のmoduleのstatusを読むと、外部systemと対応していなかった。範囲はこのmoduleである。
- 「権限の付与は本人以外の画面で確かめる」: 別の手順書にも権限を付与する手順があり、同じ確かめ方が成り立った。範囲は運用の手順全体である。

- やってしまいがちな失敗: 「他でも当てはまりそう」という見込みで広げる。固有名を消して一般的な言い回しに直し、広い範囲の文に見せる。狭い段で止まった候補を、価値が低いとして捨てる
- それをやると何が起きるか: 裏付けが今回の一件だけの文が、全体に効く文書へ載る。別の対象で作業する人が従うと誤る。逆に、そのmoduleで次に必ず要る知識が残らない
- 判断の問い: 「この範囲で成り立つと確かめた、今回とは別の実例のpathを書けるか」

### 5. repositoryが今どうなっているかを読んで確かめる

次の文書を実際に開いて読み、3の知識がどう書かれているかを確かめる。

- 置き場所の一覧のうち、約束する範囲が4の範囲に合う文書
- 3で記録した、読んでいた文書と、最初に見た場所

読む範囲を、触れたdirectoryに閉じない。API仕様、schema定義、error codeの定義のように、隣や上位の文書に既に書かれていることがある。

読んだ結果を、四つの状態のどれかに分ける。状態で変更の種類が決まる。

| repositoryの状態 | 見分け方 | 変更の種類 |
| --- | --- | --- |
| 書かれていない | 範囲に合う文書のどこにも無い | 追加 |
| 書かれているが、辿り着けなかった | 書かれた文書がある。読んでいた文書にも最初に見た場所にも、そこへの案内が無い | 導線を足す。本体は足さない |
| 読んでいたのに、守れなかった | 手間を払う前に読んでいた文書に書かれている | その記述へ、今回の形を「やってしまいがちな失敗」の具体例として足す。決まりは足さない |
| 書かれた内容が誤っている・古い | 書かれた内容と、今回確かめた事実が食い違う | 訂正 |

読んだfileのpathを欄に書く。読んでいないfileを「書かれていない」の根拠にしない。

「読んでいたのに、守れなかった」で、足す先がこのrepositoryの文書でない時（pluginのskill等）は、このskillでは足さない。読んでいた記述と今回の形を添えて、呼出し側へ返す。

- やってしまいがちな失敗: 候補を作り終えてから既存の文書を読む。触れたdirectoryのREADMEだけを読んで「書かれていない」とする
- それをやると何が起きるか: 既に書かれた決まりを重ねて提案する。書かれた決まりを自分が守れていなかったことにも気づかない
- 判断の問い: 「『書かれていない』の根拠として、範囲に合う文書を実際に開いたか。開いたfileのpathを書けるか」

### 6. 置き場所を決める

本体の置き場所と導線を、別々に決める。

**本体の置き場所。** 置き場所の一覧から、約束する範囲が4の範囲と一致する文書を選ぶ。

- 範囲より広い文書へ置くと、関係の無い作業をする人まで読まされる。
- 範囲より狭い文書へ置くと、範囲の中の別の場所で作業する人に届かない。
- 選んだ既存のドキュメントへ足す前に、足す知識がそのドキュメントの範囲に入るかを確かめる。確かめ方と、入らない時の選び方は [`naming/core.md` の「中身を足す前に、名前が約束する範囲に入るかを確かめる」](../../docs/development_standards/naming/core.md#中身を足す前に名前が約束する範囲に入るかを確かめる) が持つ。

範囲が一致する文書が複数ある時は、次の作業者がいつ知っている必要があるかで選ぶ。

| 知識の性質 | 選ぶ文書 |
| --- | --- |
| 作る前に知っている必要がある決まり（〜する時は〜する） | 作業の前に必ず読まれる文書（作業の決まり、設計・実装の規範） |
| その対象に来た時に分かればよい説明（これは何か、なぜこの形か、どこから読むか） | その対象のそばの文書（そのdirectoryのREADME、codeのcomment） |
| 業務の決まり | 業務知識の文書 |

**導線。** 3で記録した「読んでいた文書」と「最初に見た場所」が本体の置き場所と違うなら、そこから本体への案内を一行足す。次の作業者も同じ場所を先に見るためである。案内を足す先についても、上の範囲の照合を行う。

**範囲が一致する文書が無い時。** 次のどちらかにする。合わない文書へは足さない。

- 既存の文書群の中へ新しいfileを作る提案にする。入口となる索引へ足す一行も、同じ提案に含める。
- 新しい文書群が要る、またはどの文書群に入るか判断できない時は、「置き場所が無かったもの」として知識と範囲を返し、利用者に委ねる。

例を三つ挙げる。

- 範囲がrepository全体のcodeである決まり: 本体は、設計の前に読まれるcodeの構造の規範に置く。手間を払った時に触れていたmoduleのREADMEには置かない。範囲より狭い。
- 範囲が一つのmoduleである決まり: 本体は、そのmoduleのREADMEに置く。
- 業務の決まりを業務知識の文書で探して見つからず、codeを読んで分かった: 本体は業務知識の文書に置く。最初に見た場所と、読んだcodeのそばのREADMEから、本体への案内を足す。

- やってしまいがちな失敗: 触れたdirectoryのREADMEを、近いという理由で選ぶ。よく読まれる文書を、読まれるという理由で選ぶ。知識の話題だけで探し（codeの話だからREADMEだけ、業務の話だから業務知識の文書だけ）、合う文書が見つからないまま近そうな文書へ足す
- それをやると何が起きるか: 全体に効く決まりが一つのmoduleのREADMEに埋まり、別のmoduleで作業する人に届かない。文書の名前が中身を表さなくなり、探す人が辿り着けない
- 判断の問い: 「この文書の名前と入口の説明が約束する範囲は、4で測った範囲と同じか。違うなら、広いのか狭いのか」

### 7. 書く文面を作り、初めて読む人として読み直す

実際に足す・直す文面そのものを書く。要約や方針では、利用者が採否を判断できない。

- 範囲が複数の対象に及ぶ決まりには、理由と、失敗の具体例を添える。具体例は今回の一件でよいが、この作業の会話を知らない人が読んで分かる形に書き直す。
- 範囲が一つの対象なら、その対象の名前とcodeにある用語をそのまま使い、具体的に書く。
- 日付、「現在は」、調べた時点の数値、作業の経緯は書かない。
- moduleのREADMEを新しく作る時は、[moduleのREADMEの雛形](templates/module-readme.md) を使う。

書いた後、この作業の会話を知らない人として、文面だけを読み直す。会話の中でしか通じない語がある、何をすればよいかが文面だけで決まらない、のどちらかなら書き直す。長く残る文書が満たす必要のある質は [`stock-and-flow-information.md`](../../docs/documentation_standards/stock-and-flow-information.md) の「ストック情報」が持つ。

### 8. 提示する

[提案の形](templates/proposal.md) で利用者へ示す。捨てた候補は、捨てた段と理由を一行ずつ添える。利用者が判断の誤りを見つけられるようにするためである。

### 9. 承認された変更だけを適用する

- 承認された変更だけを、承認された文面で適用する。関係の無い箇所を書き直さない。
- 適用した文書は、`document-review` を通す。
- 適用した文書の変更を起点にして、このskillをもう一度起動しない。

## 知識の形の例

払った手間から取り出した知識は、次の形になることが多い。3の文を書く時の手掛かりとして使う。「まだ書かれていない」ことは、候補にする理由にならない。

- **モジュール構想（Module Concept）**: そのmoduleが何のためにあり、何を担い、何を担わないか
- **命名意図（Naming Intent）**: publicな名前が業務の何を表すか。別の名前を退けた理由
- **進化の種（Evolution Seed）**: 将来分かれる可能性を議論した箇所。確定した設計としてではなく、見直す時の起点として書く
- **設計意図メモ（Design Intent Note）**: codeを読んでも分からない制約・前提・落とし穴
- **設計の軸**: なぜこの構造か。何の違いで種類が分かれているか（例: 三つのmutationは、文書の取得元の違いで分かれている）
- **探す時の入口**: どこから読むか。grepに掛かる安定した名前
- **破ると事故になる条件**: 守るべき約束
- **変える時に一緒に見る場所**: Xを変えるならYも見る、という関係

## 他の担当との境界

- 書かれた文が観点（濃さ、記法、言葉）を満たすかは、`document-review` が見る。このskillは、何を、どの範囲の知識として、どこへ置くかを決める。
- 作業の経緯は、作業の記録（discussion等）が持つ。このskillは文書へ移さない。
- このrepositoryの外に置くべき知識は、呼出し側へ返す。どこへ渡すかは呼出し側が決める。
