# Skill全体の構造評価

## 全体の責務と進行を照合する

対象全体について指示とコードの分担、入出力、判断・状態、停止・再開・返却、規則の正本、独立した改訂理由と検証のまとまりを確認する。今回未編集の内部処理も対象とする。
既存の不合格も通常完了までに解消し、合意範囲を越える整理は設計へ戻す。必要な合意が得られなければ未完として止める。行数やfile数では判定しない。

一fileを維持するか、同skillの内部指示へ分けるか、別skillとして独立させるかは、判断・状態・完了条件・改訂理由から決める。入力値や出力形式の違いだけで分割しない。
固有の判断・状態・完了条件と独立した改訂理由・検証を持つ工程を一fileに抱え込む構成は、混線の実績がなくても不合格とする。内部指示には読む条件・所有する判断と状態・親への返却を明示する。
分割によって入口のgate・状態・返却が欠けるなら不合格とする。別skill化には現在の単独利用・他callerの具体要求を要し、将来予測だけでは独立させない。
現在の外部利用要求があれば、実装済みcallerや利用実績を待つ必要はない。

## 変更caseで構造を評価する

具体的な改訂を当て、どの判断・状態をどこで直すか、無関係な処理への連動修正や同じ規則の重複同期が生じるかを説明する。
異なるものを同じ理由で直し続ける構造も、同じ規則を別々に手管理する構造も見落とさない。

たとえばdeployの復旧工程が固有の状態・再開条件・完了を持つなら、同じskill内の内部fileへ分ける。一方、帳票のCSV/PDFが同じ判断・状態・完了の値の切替なら、その違いで分けない。
配布recordの項目を通常処理と復旧処理が別々に手管理し、項目追加のたび両方の同期が必要なら二重正本で不合格となる。
一度だけ定義して双方が参照する共有、要約・使用例、単一正本からの生成、要求上必要な波及を重複不良にしない。

新skillでも具体caseで評価できるが、過去の障害を創作しない。反証があれば再判定する。全不合格を分割命令へ変換しない。機能・安全・既存要件の不備は対応する既存gateでも扱う。

共有先の利用処理・共通定義を通じて対象skillへ影響する問題は必須対応とする。別用途だけの独立問題で無影響と確認できたものは、所在・根拠・無影響の理由を返すが、それだけで今回の完了を止めない。
影響不明なら必要確認へ戻り、確認不能なら未確認と影響を返す。対象自身の未変更処理や依頼された共有文書更新を、この除外へ含めない。
現在の範囲外の問題を将来候補へ薄めず、対象の合格を共有先全体の合格へ拡張しない。

## 前の指摘と全体を再判定する

再reviewでは先行指摘の所在、対応、解消／未解消を対応付け、撤回にも根拠を残す。直した箇所だけへ範囲を狭めず、現物全体と必要依存を再判定する。
材料の内容、集合、解決先、必要な前提が変われば入口の再利用条件に従う。

## 結果を返す

必要な範囲を確認し、不合格がなければ合格。具体的な構造問題があれば不合格。不合格の根拠はないが必須範囲を確認できない場合は材料不足。不合格と未確認が併存する場合は両方を記録する。

不合格には問題箇所・根拠・解消条件・整理の方向と、保持する境界・状態・受渡しを示す。完成した実装構成の作成は設計へ返し、reviewが毎回完成案を作ることは要求しない。
未確認には不足材料・理由・影響・再開条件を示す。将来候補は現時点で非必須と明示し、材料不足の言い換えにしない。

対象、段階、実際の読取材料と範囲、実物の取得元・解決先・hash、比較元、判定と根拠、返却先を自然なMarkdownで返す。固定JSON、global ID、専用報告fileは要求しない。
該当しない空見出しは作らない。

呼出し側が権限を持つ既存の設計議論、task検証記録、実装reviewへ保存し、保存先と対象箇所を返す。既存writerを維持する。適切な保存先がない単独利用なら同じ作業内へ記録を用意する。
chatだけの結果、架空のfeedback、同じ根拠の正本の複製は作らない。別作業・外部連絡・無断編集を始めず、元のworkflowへ戻す。
