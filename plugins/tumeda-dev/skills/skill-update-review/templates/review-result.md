# 構造review結果の部品

固定の提出構文ではない。該当する部品だけを、呼出し側の既存記録形式で使う。空見出し、架空のfeedback、例示hashを実測結果へ使わない。

- 対象と段階、新設／更新、目的・要件の根拠。
- 実際の取得元・入口・実解決先、読取fileと範囲、内容hash。比較元の所在と当時の内容を辿る根拠。構造案・必要依存の識別。
- 合格／不合格／材料不足と根拠。確認できた能力・境界と、確認できなかった範囲を分ける。
- 不合格ごとの問題箇所、具体改訂case、不要な連動・二重同期、解消条件、整理の方向、保持する状態・gate・受渡し。
- 未確認ごとの不足・理由・影響・再開に必要な材料。
- 再review時の前回指摘と対応、解消・未解消・撤回の根拠、全体再判定。
- 非必須の将来候補、無影響を確認した共有先の独立問題はその根拠。
- 返却前の内容・file集合・参照・解決先の再照合、旧判定維持または再reviewの理由。
- 返却先担当、既存の保存先と対象箇所、次に戻る既存gate。

## 架空例

対象はdeploy/SKILL.mdの編集後版。更新前の保存版と、入口・復旧指示の全文、共有定義の利用部分を読む。実測では実際のpath・読んだbytesのhashを併記する。

判定は不合格。通常処理と復旧処理が配布record項目を別々に手管理しており、項目追加で二箇所の同期が必要となる。単一の定義へ集約し、復旧の状態と返却を維持することが解消条件となる。
さらに外部commandの失敗時の戻り値が未確認であり、既知の問題を直すだけでは合格にしない。

編集担当へ返し、既存の実装reviewへ保存する。修正後は現物全体を再判定し、機能・安全・動作検証と既存の完了条件へ戻す。
