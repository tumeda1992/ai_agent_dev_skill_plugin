# 長い議論記録を分割する

同じdiscussion ownerが格納形式だけを変更する。別skill・agent・状態正本へ渡さない。簡単な議論や10実論点以下ではdirectoryを増やさない。

## 分割済み記録を更新する

resolveがsplitを返した時は、以降の単一形式からの移行を行わない。旧単一fileの不存在をエラーにせず、同じ記録を継続する。
既存論点の次iteration・現在stateは、所属する範囲file全文を再読して局所更新する。過去回や他範囲を作り直さない。
新論点は全実論点の最大番号+1を採り、番号5件の担当範囲へ追記する。例えば12件から13は11-15へ、16は新しい16-20範囲へ置く。担当範囲が未作成なら格納用h1と新論点だけを作る。
新論点の番号・題名・本文linkを同名索引へ追加する。既存論点の題名が変わる場合だけ対応する索引行を同期し、status・親子・決定要約は追加しない。
書込み前の集合・実体・hashと使用logの照合、対象file全文再読、書込み後のcheckと差分確認は通常どおり行う。
複数file更新で中断したら、実際に保存できた境界を既存内部logから確認し、盲目的に二重追記しない。

## 分割対象を判定する

通常の新規追加で実論点が10件を超えた時に分割する。既存の長大な単一記録は次の更新機会に移す。handoffの独立構成前には移さず、catch-upと内容把握を終えてから行う。
canonical h2とlegacy h3の実論点だけを数え、code fence・引用・HTML commentの例を除外する。
最大番号を件数にしない。
新規番号は欠番を再利用せず最大番号+1とする。

## 原文と候補を用意する

1. 分割前に受領済みの応答原文を対応する既存iterationへ保存する。分割中は新しい提案・決定を混ぜず、格納切替の検証を終えてから通常の議論へ戻る。
2. [読取](read-discussion.md)の全文取得と書込み前照合を通し、原文・集合・使用logのsnapshotを保存する。
   分割の起点と移動先、原文snapshot、各作業の実結果を既存の内部logへ記録する。
   新しい進捗flagや別の管理索引は作らない。
3. stemはbasenameから最後の拡張子を除いた名前とする（拡張子なしはそのまま）。
   通常は`<directory>/<stem>/`に同じbasenameの索引を作る。
   元h1と`## 論点一覧`、番号・題名・本文linkだけを置く。
   status・親子・決定要約を索引へ複製しない。
4. 本文は`<stem>-1-5.md`、`<stem>-6-10.md`のように番号5件の範囲へ置く。
   欠番があっても番号から所属を求める。
   元の論点順・見出し深度・全iteration・原文応答・判断・訂正を保持する。
5. 元の全体前提・前書きは先頭範囲に保持する。許される変更は格納用h1、索引、移動に必要なhrefだけである。説明・表現・合意内容を同時に直さない。
6. 原文fileを残したまま`check-candidate --directory <directory> --name <name> --source <old-file> --candidate <split-directory>`を使う。
   件数・番号・順序・所属・親子・索引と、href以外の原文一致を確認する。
   href差は旧新hrefとそれぞれのpath・行・columnを辿り、移動に必要な差か判断する。
   機械検査だけで意味保存としない。

## 元fileと最終directoryが同pathになる場合

拡張子なし等で同pathになる時だけ、元作業内の別の未使用candidate pathを明示し、そのexact pathと最終pathの対応を既存内部logへ記録する。
恒久的な別入口や命名規約は増やさない。
元fileを残したまま候補の索引・範囲・参照を作り、同じcheck-candidateと旧集合の直接照合を通す。候補を通常入口として選ばせない。
切替前は、最終pathの参照先と候補の実file/anchorを一対一に対応付けて検査する。最終pathがまだfileであることを、参照欠落の補完や本文改変の理由にしない。
元版不変・候補保持・全参照の対応を確認した後、旧fileの除去を最後に行い、同じ候補を最終directoryへ切り替える。
その後に通常のresolve/check/fullで実fileと全参照を再検査する。
除去と切替の間で中断した場合も記録済みのexact候補と原文snapshotを使い、候補の再生成・別pathへの逃避・盲目的削除をしない。最終入口が復旧するまで通常追記は未完として返す。

## 原文を最後に退ける

明示候補検査中は通常のresolve/compareを呼ばない。新旧共存を拒否する通常gateは維持する。
保存済み旧snapshotのformat、entry、filesと元directoryを使い、既知の原文file・使用logのexact pathを直接再取得する。
Node標準module等のread-only操作で、各pathがfileとして取得できること、実体pathとSHA-256が保存値と一致することを一件ずつ照合する。
候補directoryを旧集合へ混ぜず、別の正本を選択しない。
自分の移行log更新や下記の参照更新で使うfileを意図的に変える場合だけ、変更直前の不変照合、許された実差分、更新後hashを記録して照合を継続する。
原文fileの本文変更や外部からの変更をこの例外へ含めない。

本文内link、discussionと内部logの往復link、design等から旧入口へ入る既知の参照を列挙し、必要なhrefだけを追随する。
全体を指す参照は同名索引へ、個別論点を指す参照は実際の所属範囲とそのanchorへ結ぶ。
保存先から相対pathを実解決し、fileと対象anchorの存在・対応を確認する。
曖昧なanchorを推測せず、対象と未確認を返す。
helperのcheck-candidateは候補本文の検査であり、外側の参照更新を代行しない。各外側fileの元内容・許されたhref差・実保存をownerが確認する。別作業を探索・変更しない。

既知の旧集合の直接照合と、再実行したcheck-candidate、全ての参照の検証成功を確かめた後だけ原文fileを削除する。候補作成時点で原文を消さない。
その後、通常のresolve/check/read full/snapshotで正本が分割形式一つだけになり、全内容が取得できることを検証する。
移動先と保持範囲を利用者へ報告する。格納だけの変更へ内容の再合意を求めない。

## 中断から戻る

内部log・原文snapshot・候補実体が同じ分割処理を一意に示す場合だけ、検証済み境界から再開する。
記録不足・原文変化・候補の余分な本文・参照先の曖昧さ・新旧の不一致では該当更新を止め、未確認範囲を示す。
既存候補を盲目的に上書きせず、原文を削除せず、自動修復や推測でrollbackしない。別作業のreadyな処理まで止める理由にしない。
