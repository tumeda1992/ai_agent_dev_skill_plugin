# 共通イテレーション

選択した一つの論点で、次の提示を準備するか、保存済み提示への応答を処理する。同じ実行者が [SKILL.md](SKILL.md) の安全な書込み・scope・親子・原因owner規則を使う。別agentへ委譲せず、もう一つのstate正本を作らない。

## 入る前に引き継ぐ状態

handlerが解決したdiscussion file、目的とconsumer固有制約、選択したdecision、実際の発言とevidenceを受け取る。
既存論点では番号、現在の末尾提示と応答、履歴、決定・仮決定・再開条件、親と未決childを確認する。新規ではscopeと他論点との関係を受け取り、まだ論点番号を仮定しない。
handlerと[読取](read-discussion.md)に従い、全体の現在state、対象範囲file全文と対象論点の内部log全文を読む。
書込み直前は対象file全体を再読込し、引継ぎ時とstateが違えばhandlerへ戻す。必須fileが読めない、欄が一意でない、書けない場合は停止し、保存済み・未同期を区別する。

## 二つの入口と戻り先

- 次の提示を準備する：新規・応答処理後の継続・決定済み論点の再開を、同じ内部loopへ接続する。
- 既存提示への応答を扱う：提示の種類と対応先を特定し、原文と結果を一度保存する。合意だけなら次の回を作らない。

提示を保存したらhandlerの通常同期へ、合意を保存したらdecision確定へ、別decisionなら論点選択へ、scope外なら取下げへ戻る。外部条件・権限・明示保留はhandlerの停止へ、過去の未収録議論は回復へ返す。
修正応答・認識合わせの回答から次提示へ進む時だけ、このfile内の提示準備へ戻る。起動やhandler入口をやり直さない。
skill起動済みという前提やtarget fileの解決を毎回分岐させない。

## 次の提示を準備する

### 作成中の回と検討記録を用意する

[templates/discussion_entry.md](templates/discussion_entry.md) と [templates/internal_record.md](templates/internal_record.md) を全文読む。
両者は保存形だけを持ち、部品の選択・挿入・省略条件はこの節が所有する。
外側の名前付き見出しとcode fenceを出力へコピーせず、必要なcode blockだけを使う。

#### 入口に応じて回を特定する

- 新規
  - 実論点の最大番号+1（なければ1）、回番号I=0を使う。新論点はfile末尾へ加える。
  - childの親をhandler規則で検証し、top-levelでは親行を省く。種別は必要なものを選び、複数なら併記する。
  - childを追加した場合だけ、未決child集合の変化に合わせてparent statusを同期する。
- 継続
  - 評価された提示への応答保存を確認し、次のIを使う。
  - templateのiteration以下だけを対象論点の現在state直前へ置き、論点metadataを複製しない。
- 決定済み論点の再開
  - 同じdecisionかを確かめ、handler規則で旧決定を現在表示から外してactiveへ戻す。
  - 旧履歴を保持し、再開evidence、無効になった判断、置換条件を今回の検討記録へ残す。同じeventからfeedback用と再開用の二回を作らない。
  - 再開条件未成立なら進めずhandlerへ返す。成立した場合は結果を新記録へ接続して現在の条件を外す。

既に作成中の同じ回があれば、新しい回を作らず保存済み記録とtool結果を照合して中断復帰する。
未保存を未実行とみなさず、取得済み結果を再取得したふりにしない。

#### 二層の骨子を順に保存する

1. 作成中は調査中とし、discussionへ論点metadataと回の骨子を保存する。未成立の提案、空の認識合わせ、空応答、空決定を作らない。
2. 内部logへ論点・開始context・同じ回の骨子を準備する。開始contextには対象の問題と語の意味、決める範囲、開始時の既決条件、残る不足を、log単独でも読める内容で示す。

既存論点の途中から二層へ分ける時は、分離開始の回を明記する。
それ以前の根拠は旧discussionの論点・回・見出しで参照し、新しい回から固定anchorを使う。
既存logの過去blockへ一括採番せず、過去本文を移動・改名・再要約しない。

#### 起点と今回の必要条件を結ぶ

最初の回は最初のuser input・finding・既存状態から必要条件を残す。review起点の最上位論点では原文をdiscussion背景へ変更せず保存し、独立feedback ledgerやFB-Nを作らない。一つのfeedbackが複数decisionになるなら原文と分解判断はparentが持ち、leafをchildへ分ける。複数feedbackが一decisionなら同じ論点で保持できる。
継続は前の応答と今回のfindingから必要条件を作り、原文と評価結果を複製しない。原因診断・scopeが変わる場合は維持・置換・拡張したものを読み分ける。外部evidenceで旧判断が無効になった場合の記録も全回の固定fieldにしない。
原因追跡、discussion scopeへ属する理由、別decisionとして分けた理由等は、proposalを評価するために必要な時だけ内容固有の見出しや段落で示す。

### 判断材料を確かめ、検討記録を育てる

内容を作り始める直前に、[making_and_choosing_options.md](../../docs/think_standards/making_and_choosing_options.md) 全文を読み、今の判断材料へ適用する。起動時の読取、案への確信、調査や否定の回数で代替しない。判定基準の正本は標準に保ち、ここへ複製しない。

```text
現在の材料へ標準を適用
  ├─ 自力で取得できる不足 → 目的別の実施前入力を保存
  │                           → 調査・比較・検証等を実施
  │                           → 結果・限界・次actionを保存 ─→ 再判定
  ├─ 判断可能な案が成立 → 提案を形にする → case検証 ─→ 不足なら再判定
  ├─ user所有の前提・見方が必要 → 認識合わせを形にする
  ├─ 判断可能な別の上位decision → handlerの論点選択
  └─ 今は解消不能な外部条件 → handlerの停止
```

#### 内部検討を記録する

提示準備中の内部loopに加え、handlerのorigin-reviewから追加検討を記録する時も、この手順を使う。
これは記録の手順であり、呼出しだけで外向き回を追加したり、材料確認・提案を要求したりしない。

新しい検討blockを始める前に [templates/consideration-records/README.md](templates/consideration-records/README.md) を読み、目的を選び、該当fileを全文読む。目的が変われば再選択する。全六fileの毎回読取・使用や、常に調査から始めることは要求しない。
選んだformatの実施前入力（問い・探索先・方法、判断対象・評価軸、検証claim等）を内部logの同じ回へ保存してから実施する。
記録単位のanchorと意味ある用途titleを置き、formatの見出し深度はその配下へ合わせる。目的別の読み方を一律の三見出しへ変えない。
結果・解釈・不足・次action・案への影響を得たら、次actionより前に同じ記録単位へ保存する。書込み前は毎回handler指定の `expression_notation.md` を全文読む。
何を知ろうとし、どこをどの方法で確認し、どの証拠から何を判断したかを具体的に残す。必要条件と案の内容の対応を辿れるようにする。
同じ問いと方法で判断材料を一段更新する単位にまとめ、tool一回・file一枚を単位にしない。複数sourceをまとめても、結果から問い・方法を変える時は結果と変更理由を先に保存する。内部blockだけ増えても外向きIを増やさない。
事実と解釈、範囲内の不在と取得失敗・未実施を区別する。資料全文や生logは写さず、後のevidenceによる訂正は新blockから元を指す。完成済みblockへ遡って結果を混ぜない。
短さのために問い・方法・具体的finding・限界の接続を落とさない。生logを貼ることも、具体過程を「調査して確認した」へ潰すことも、単独で過程を理解できる記録の代わりにならない。
既存findingだけで足りれば不要な調査を作らず、比較と案への影響を記録する。
六用途へ合わない時は、[READMEの該当する形がない場合](templates/consideration-records/README.md#該当する形がない場合) に従い、理由と内容固有の形を記録する。

#### 保存結果から判断材料を再判定する

提示準備の内部loopでは、この節へ進む。origin-reviewから記録だけを行った場合はhandlerのその処理へ戻る。

自力で取れる不足は権限とconsumer境界を守って調べ、調査方針の承認を聞かない。一回調べたという回数で認識合わせへ移らない。自力確認後も残るuser所有の問題・前提・見方だけを問う。外部actionや追加権限はhandlerへ返し、形式だけの質問を作らない。
何が分かれば案を作れるかを言えなければ、確認対象の整理へ戻る。停止・別decisionへ返す場合も、それまでの記録と行き先の理由を保存する。

### 提案または認識合わせを形にする

提案では一つの採否を問える案を作る。a/b/cを作るための弱い対抗馬や、調査結果だけを案に見せるものは作らない。保存前にSKILL.mdの「decisionの境界を判定する」と論点タイトルのscope照合を通し、別decisionまたはscope超過ならhandlerへ戻す。
既決内容は今回の判断に必要な範囲だけ示し、完全性のためだけに再掲しない。完全状態そのものが判断対象なら完全版を示す。
[templates/discussion_entry.md](templates/discussion_entry.md) 全文から「提案本文」を使い、本文をdiscussionの同じ回の検討記録の直前へ加える。templateの結果欄や未成立の部品を丸ごとcopyしない。

今回の問いへ何を示せば判断できるかを先に考える。`templates/proposal-sections/README.md`から判断対象の理解を助けるpatternを確認し、必要なら複数を組み合わせる。複数案を提示する場合は選択肢patternをwrapperとして使い、各案の内部に別patternを置いてよい。該当patternがなければcatalogへ押し込まず、内容から構成を決める。

提案本文の構成は内容から決める。
独立した説明を持つ内容は、たとえば「保存構造」「読み取り範囲」「fallback」のような固有見出しへ分ける。
短く同格な要素だけを箇条書きにする。
`総論 / 各論 / ルール / 適用例`や箇条書きを固定しない。
抽象と具体の両方が必要でも、一つの疑似箇条書きへ平坦化せず、意味関係が読める段落、固有見出し、表等を選ぶ。

新規fileの作成では、配置、周辺fileとの関係、作らないfileが判断対象なら、`structure-tree.md`を使って対象範囲を絞った完成後treeを示す。新規documentは、`document-heading-outline.md`を使って各見出しの役割と扱う内容へ合意してから実fileを作成し、作成されたfile自体をreviewする。本文全文を作成前のdiscussionへ複製しない。

既存fileの変更が局所範囲に閉じ、全追加・削除行と必要contextを読みやすい一つのunified diffで示せる場合は、`existing-file-local-diff.md`を使う。変更hunk内を省略せず、変更しないfile残部は再掲しない。

#### 不可分な変更集合を示す

複数file、file間の対応、または一file内の複数hunkが一つのdecisionとして不可分に変わる場合は、`file-change-set.md`を使う。
独立して採否を変えられる変更は、一つの変更集合へまとめず別decisionへ分ける。

変更集合では、次を判断できるようにする。

- 今回含む対象の全体と、beforeからafterへの対応
- 変えてよい範囲、維持・削除・scope外
- 適用が完了した状態

対応の主単位は、file path、責務・contract、保持する意味等からcaseに合うものを選ぶ。
各対象の内部表示はtree、機械的置換、完全diff、before / after、outline、flow等を使い分け、同じ方式へ揃えない。

#### 表示patternと正式な提示種別を分ける

上のpattern参照はすべて [templates/proposal-sections/](templates/proposal-sections/) 内である。内容の理解を共有するための表示patternと、次の正式な提示種別を混同しない。

scopeまたは情報ownerの移動が元proposalから独立して変更できるdecisionなら、同じiterationへ累積せず別論点へ分ける。同じdecision内の判断材料として移動前後やowner境界を示す時は、process flow、tree、対応表、散文等から内容に合うproposal patternを選ぶ。

認識合わせは `templates/discussion_entry.md` 全文から「認識合わせ本文」を使い、同じ位置へ置く。今は提案できない理由、確認したい理解、具体的な回答・訂正対象、回答で進む判断を示す。確認済み事実・自分の読解・未確定を区別し、調査結果と読解の根拠を内部logへ残したうえで、回答に必要な根拠をdiscussionの検討記録へ再構成する。
調べられる事実の問い返し、単なる調査報告、調査許可の依頼に使わない。判断可能な定義・見方の採用は提案とし、未提示の案や別decisionの採否を質問へ混ぜない。初回もI=0で使い、形式だけの提案0や別counterを作らない。

### 保存した回を提示可能にする

内部logの結果を保存した後、discussionの「検討記録」を今回の判断に必要な因果へ再構成する。
時系列の短縮版ではなく、なぜこの問いになり、どの条件が必要で、どの事実・反証が案を規定し、何を代償として残すかを説明する。
案または質問と背景を一緒に読めば、内部logを開かずに理解・判断・応答できる十分な情報量を持たせる。
重要な反証・未確認・適用限界をlink先へ追い出さない。内部logへの回単位のlinkを添え、必要なら個別根拠も指す。
新しい背景への再構成は過去提示を書き換える許可ではない。内部logの完了済み経過も移動・再要約しない。

[templates/discussion_entry.md](templates/discussion_entry.md) 全文から、提案なら「空の提案応答欄」、認識合わせなら「空の認識合わせ回答欄」を選び、同じ回の検討記録直後へ置く。保存後の読順を「本文→検討記録→応答」にする。
応答本文へ`未回答`、`結果: 未回答`を入れず、返答を推測しない。既に提示済みの提案背景・旧見出しを改名せず、新しく準備する回だけ新役割名を使う。
内部logは目的別formatの完成時の読み順へ仕上げる。判断は推奨、検証は保証できる結論を取得後に先頭へ置けるが、実施前入力と具体的な結果を保つ。
保存後、discussionだけから判断・応答できるか、内部logだけから開始context・問い・方法・結果・訂正・限界を追えるかをそれぞれ確認する。
不足があれば提示前に該当層を補う。未確認のことを確認済みにして穴を埋めない。
本文・再構成した背景・空応答を保存し、handlerの差分確認と通常同期を通してからfile・論点・提示番号・判断対象を明示して提示し、応答待ちにする。通常の応答待ちには再開条件を作らない。

### 保存境界から中断処理へ戻る

完了flagや別の進捗ledgerを増やさず、二層の実本文・tool結果・実際のchatから未完部分を特定する。

| 保存されているもの | 同じ中断処理として復帰する場所 |
| --- | --- |
| discussionの作成中骨子だけ | 未作成を確認し内部logを準備する。新しい回を増やさない |
| 内部logの実施前入力 | 実行済みかをtool結果と照合し、未実行なら実施する |
| 取得した結果が未保存 | 確認できる結果を保存する。確認不能ならその範囲を明記し、安全に再取得できるものだけ新たな確認として行う |
| 内部logの結果まで保存済み | discussion背景の再構成・提示準備へ戻る |
| discussionの提示内容まで保存済み | 未提示と確認できれば同期後に提示する。提示済みか不明なら停止する |
| 原文と応答結果まで保存済み | 二重記録せず、未完の確定・consumer反映・次準備へ戻る |

未保存を未実行とみなさず、再取得を昔の実行結果として偽装しない。
既に別の処理や提示へ進んだ後に欠落を発見した場合は通常復帰とせず、handlerからrecord-recoveryへ返す。
同じ処理か、保存先か、実際の提示・応答かを解決できない場合は停止し、曖昧なまま上書き・再送・再実行しない。

## 既存提示への応答を扱う

### 所属と評価対象を照合する

feedbackを受けた時は、iterationを追加する前に必ずこの分類をやり直す。同じdecisionかどうかはSKILL.mdの「decisionの境界を判定する」を使い、部分修正というだけで別論点にしない。
handlerが選んだ論点と同じdecision scopeか、child・sibling・後発parent・独立論点か、決定済みの再開か、scope外かを実際の内容で確認する。別decisionなら回を足さずhandlerへ戻る。原因ownerの分類とは別であり、両方を通る。
作業再開指示だけなら提示への回答にせず、実stateから未完処理へ復帰する。保存状態が不明なら停止する。
同じdecisionなら提示種類・番号・確認対象を特定し、対応する空欄を選ぶ。既に同じ応答を保存済みなら二重保存せず次処理へ、異なる確定応答があれば上書きせず再開／別decisionをhandlerへ返す。

### 原文と結果を一度保存する

`templates/discussion_entry.md` 全文から「受領応答の本文」を使い、対応する既存の空欄へ内容だけを入れる。結果は固定候補ではなくその回の結果が分かる短い表現とする。必要な原文、原文だけでは分からない評価・入力・訂正・不足を内容に合う段落や表で示す。
提案ではどこが受け入れられ、どこが成立しなかったかを残す。原因診断への影響が重要なら`修正要求`だけに丸めず、前の診断を維持するか遡るかを短い結果でも読み分ける。
認識合わせでは得た入力・訂正・残る空白を扱い、部分回答・回答不能も記録する。固定三欄を要求しない。理解への了承はその理解だけ、経験への質問に対する`ok`は経験未取得とする。外部事実への主張は必要な照合を行う。
過去の本文・検討記録は変更せず、原文と結果を次の背景へ複製しない。認識の了承を決定や仮決定へ自動転記しない。
feedback確定後の過去iteration、却下理由、誤っていた認識は変更・削除せず、`ここまでの議論`等で再要約しない。

### 応答から次の行き先へ進む

保存済みの具体案への明示合意なら、新回も材料確認も作らずhandlerのdecision確定へ返す。
同じdecisionの修正・認識合わせの回答なら、応答結果を次の回の条件へ接続し、上の提示準備へ進む。調査中へ戻し、材料が揃えば同じturnで提案まで作る。追加の「提案してよいか」は聞かない。
再質問が必要なら、既に埋まったもの、残る必要な空白、自力では埋められない理由を記録する。答えられない問いは具体化等の方法を見直し、取得不能なら不足と再開条件をhandlerへ返す。回数だけで打ち切ったり継続したりしない。
別decision、明示保留、外部待ち、過去の未収録を含む場合は、新提示より先にhandlerへ戻す。認識合わせ一回の完了は回答保存と行き先接続であり、論点の決定ではない。
