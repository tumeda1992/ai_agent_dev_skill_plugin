# 比較・判断の記録

## 判断対象と選択条件

判断するdecision、必須条件、評価軸、使う根拠を評価前に保存する。何を優先するかがuser所有で未共有なら、勝手に重みを補わない。
調査済みfindingは参照して使い、事実を調べ直す形式的な段を足さない。

## 案を評価する

### 複数案の差を比べる

実在する強い代替案を、同じ意味・粒度の軸へ当てる。推奨案を勝たせる弱い対抗馬や、既に支持されたメタ方針を選ばせるためだけの比較を作らない。
必須条件を満たさない案と、成立するがtrade-offで選ばない案を区別する。各案の優劣が別の問いなら一つの選択へ束ねない。

### 一案の成立条件を照合する

選択肢を水増しせず、必要条件と案の対応・反例・残る不足を示す。一案への採否もdecisionであり、形式的な「確認」と呼んで背景を省略しない。

## 推奨の決め手と、引き受ける代償

評価後、推奨と決め手を冒頭へ加え、条件・各案・代償・不確実性へ読める形にする。推奨の根拠と棄却理由を自分の中だけに残さない。
判断結果が最終案のどの内容を規定するかを示す。調査不足を断定に変えたり、見出しが揃ったことを選べる証拠にしたりしない。

## 判断の記入形

複数案の開始形：

```markdown
##### 判断: 通知先を再送時に解決し直すか

###### 判断対象・必須条件・根拠

再送の宛先を初回値と現在値のどちらにするか。必須条件は同じ通知の監査可能性、比較軸は利用者の変更意図との整合と再現性。根拠は「再送payloadで保持されるもの」のfindingと、合意済みの通知要件。
```

評価後の完成時には、例えば「初回snapshotを推す。再現性を必須とする要件が決め手」と先頭へ加える。本文には各案の充足、変更後も旧宛先へ届く代償、採用条件を残す。要件が未合意ならこの結論は書けない。

一案の開始形：

```markdown
##### 判断: 宛先snapshotを送信記録へ含める案は要件を満たすか

###### 必要条件と確かめる対応

再送を再現でき、削除要求では宛先情報を消せる必要がある。案はsnapshotを送信記録の一部とし、保存期間と削除単位も同じにする。両要件との対応と、別保管が必要になる反例を調べる。
```

評価後は成立する範囲を先頭へ加え、保存期間の異なる宛先がある等の反例が出た場合は案を修正する。形だけの二案目を作らない。
