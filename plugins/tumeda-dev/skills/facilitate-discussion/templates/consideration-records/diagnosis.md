# 診断・修正の記録

## 期待との差と原因候補

期待した挙動と実際の差、原因候補、支持・反証のため調べるものを実施前に保存する。「指摘どおり直す」を原因の代わりにしない。
共有知識の誤りか、成果物固有の逸脱かを区別する。原因ownerのroutingはhandlerの判定を使い、このformatが独自に決めない。

## 原因を支持・反証する証拠

症状と原因の間を具体的な証拠で結ぶ。確定原因と仮説、調べて否定できた候補と未確認を分ける。
原因が分かったら、修正先・内容と期待する再発防止を対応させる。今回の見た目を直すことと原因を除くことを混同しない。

### 誤診を新しいevidenceで置き換える

前の診断の何を維持・置換・拡張したかを、新しいblockで示す。旧結果や原文を書き換えず、訂正元と新evidenceを参照する。
前の診断を残したまま矛盾する例外を足すのでなく、現在の原因と修正範囲が分かる形へ再構成する。

## 修正先と再検証を結ぶ記入形

```markdown
##### 診断: 再送だけ古い宛先へ届く

###### 期待との差と原因候補

利用者は宛先変更後の再送にも新設定が効くと期待したが、実際は初回宛先になった。設定cacheの失効漏れか、意図的なsnapshot契約かを、worker・schema・設計記録で切り分ける。
```

結果後は、例えば「schemaと旧設計からsnapshot契約と分かった。cache障害の仮説は棄却する」と証拠を示す。その場合は即座にcacheを直さず、要件の認識齟齬をhandlerへ返す。
修正が合意された後は、どのcontractをどこへ反映し、どのcaseで再検証するかを残す。この診断記録だけを対象修正の承認にはしない。
