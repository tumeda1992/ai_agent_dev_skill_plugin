# 導出した変更を報告して反映する

既存の原因owner判定を先に通る。その後、同じ記録ownerが変更の権限と残る判断から経路を選ぶ。全てを利用者の採否decisionへ変換しない。

## 変更の種類を判定する

| 種類 | 扱い |
| --- | --- |
| 利用者が決める未決事項 | 既存iterationの具体案・応答・明示合意を通る |
| 既決事項からAIが一意に導出した変更 | このfileで変更内容と根拠を報告し、同じ作業の次の実応答を確認してから反映する |
| 利用者が明示委託した範囲の選択 | 委託原文・範囲を確かめ、このfileで選択と根拠を報告して次の実応答を確認する |
| 意味を変えない機械的適用・誤字・format・link修正 | 既存の権限で適用し、結果を記録する。新しい採否や待ちを作らない |

一意に導出できない残余判断は未決事項へ戻す。『AIが選んだ』だけで委託としない。既存decisionに従う機械適用へ新scopeを混ぜない。

## 同じ論点と回へ保存する

[templates/discussion_entry.md](templates/discussion_entry.md)の`変更内容`と`現在の変更`を使う。
既存の論点・共通iteration番号Iを使い、独立した判断基準や独立反映単位なら別論点へ分ける。
新しい変更専用採番を作らない。
`変更内容I`には変更前後、実際の原因・原文、根拠となる既決事項または委託、変更先と変更後の完全な対象範囲、必要な理由、他変更との相互作用、
検証と限界を自己完結して書く。
明示委託では、任された範囲内の候補を比較し、選定理由と受容する弱点を保存する。
内部logへ入力・調査・検証の証拠を残す。
`現在の変更`には対象iteration、報告した実際の問いまたは完了reviewと版、変更対象、報告済みか、対応する実応答、反映状態・実結果、
未解決を現在値として置く。
過去の報告・応答を上書きしない。
空のfeedback欄や架空の承認を作らない。

## 報告を次の判断より先に返す

未報告の変更内容を保存し、file・論点・回・変更前後と理由をchatで特定する。別decisionの問いや完了reviewを出す前に報告する。報告は追加の『承認してよいか』を要求する手続ではない。
導出・委託による変更の反映は、報告後に届いた同じ作業に対する利用者の実応答を確認した後とする。時間経過・別作業の発言・別の問いへの古い応答を通過根拠にしない。
利用者が同じ応答で複数の変更へ答えた場合は原文を一度保存し、各変更から対応範囲を参照する。複数の架空承認へ複写しない。応答がどれに対応するか不明ならその変更の反映を待つ。

## 修正と反映を追跡する

修正応答は原文とAIの解釈を分ける。
利用者が修正を一意に指定し、既存権限内であれば再承認を求めず反映できる。
AIが新たに導出した修正なら次のiterationで変更内容を報告し、新しい実応答を待つ。
以前の報告への応答を新しい変更へ流用しない。
反映する担当はconsumerのままである。対象・権限・最新snapshotを確認し、実際の適用結果・検証・未反映部分を返す。部分反映や検証失敗を全件反映済みにしない。
未反映・未報告・応答待ちの変更は全体の未解決へ数え、親の未決child導出にも含める。他の独立taskは進められる。全てが反映済みになるまで、報告完了だけで元作業完了にしない。
