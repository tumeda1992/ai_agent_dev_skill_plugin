# 一往復で示す論点を組み、返事を振り分ける

[SKILL.md](SKILL.md)の担当が、次の時点で読む内部指示である。同じownerが実行し、別agentへ委譲しない。

- 論点を立てた時: 重さを付ける
- 次に利用者へ示す論点を選ぶ時: 一往復で示す論点の組を作る
- まとめて示した論点への返事を受けた時: 返事を各論点へ振り分ける

利用者との往復は一回ごとに時間がかかる。一方で、利用者が一往復で扱える論点の数は、論点の重さで違う。一つを深く考える論点に別の論点が混ざると思考が乱れ、確かめるだけの論点を一つずつ問うと、利用者は流れ作業でokを押すだけになる。このfileは、論点の重さで一往復に示す数を変え、両方を避ける。

まとめるのは一往復に示す論点の数であり、論点そのものではない。一つの提案は一つのdecisionのままにし、複数の論点を一つの提案へ混ぜない（SKILL.md「decisionの境界を判定する」）。組んだ後の各論点の提示と応答の保存は[iteration.md](iteration.md)へ、合意した論点の確定はSKILL.md「合意したdecisionを確定する」へ戻る。

## 論点に重さを付ける

### 四つの観点

各観点は、「この論点の答えを別の案に置き換えたら、何が変わるか」で見る。題材そのものの大事さでは見ない。

- 波及 — 答えを置き換えると、今の作業の中で何が変わるか
    - 小: この論点の中で閉じる
    - 中: 同じ作業の他の論点・成果物の一部が変わる
    - 大: 作業の目的・範囲、または同じ作業の多くの論点・成果物が変わる
- 戻しにくさ — 誤りに後で気づいた時、何を直し直すか
    - 小: 一箇所直せば戻る。答えを前提に作られるものが無い
    - 中: 直すと複数箇所の追随が要る
    - 大: 答えを前提に作られるもの（名前を参照するfile、規範に従って作られた設計やcode）が積み上がる、または作業を破棄しても残る変化（公開、外部への登録、本番のデータ）を伴う
- 確かめる手間 — 利用者が答えの良し悪しを判断するために、何を読み・見て・動かす必要があるか
    - 小: 提案の文面だけで判断できる
    - 中: 変更の全体（複数file、数十行）や材料を読む必要がある
    - 大: 実物を動かす、成果物全体を通して見る必要がある
- 利用者の前提への依存 — 推す案を、既決事項・既存の規範・前例から導けるか
    - 小: 推す案を導いた根拠を名指せる（既決の論点番号、規範のpathと節、前例のsteering directory）。利用者はそれを確かめるだけでよい
    - 中: 推す案はあるが、根拠を名指せない、または利用者の好みや優先順位で変わりうる
    - 大: 利用者しか持たない情報・意図・経験がないと案を作れない、または認識合わせから要る

規範の文面や置き場のように、意味を保ったまま後で一箇所直せる違いは、どの観点でも大にしない。後の作業が従う中身（規範の意味、名前、構成）が答えによって変わる時だけ、戻しにくさを大にする。

利用者の前提への依存を小にするのは、根拠を名指せる時だけにする。重さを判定するのはassistant自身であり、自分の確信は小の根拠にならない（[making_and_choosing_options.md](../../docs/think_standards/making_and_choosing_options.md)の「選べたという感覚は確信として現れるため、疑う契機が自分の側にない」）。名指した根拠なら、利用者が開いて確かめられる。

- やってしまいがちな行動: 規範を扱うrepositoryで、「後の作業が読む規範が変わる」ことを理由に、合意済みの中身の文面や置き場を問う論点まで大にする
- それをやると何が起きるか: 一言で閉じる論点まで単独で示し、往復が減らない。過去の議論記録では、論点名に「文面」「書き方」等を含む35論点のうち22論点が、一言の受け入れで閉じていた。往復を重ねたのは、文面ではなく規範の意味の切り分けを問う論点だった
- 正しい判断のための問い: 「この論点の答えを別の案に置き換えたら、後の作業が従う中身が変わるか。言葉や置き場が変わるだけか」

### 三つの段と並べる順

四つの観点の判定を、利用者がその論点で何をするかで名付けた三つの段にまとめる。

| 段 | 判定 |
| --- | --- |
| 一つずつ考える | 大が一つでもある、または中が二つ以上 |
| まとめて考える | 中が一つだけ |
| 確かめるだけ | 全部小 |

大が一つでもあれば一つずつ考える段にするのは、決め自体は小さくても、失敗した時に直しにくい論点があるためである。観点ごとの点数を合計すると、一つの観点の大きさが他の観点の小ささで薄まる。過去には、利用者の前提だけが大の論点（定期起動の頻度）が4回の往復を要した。

段の名前は、利用者がその論点で何をするかを表す。名前から重さの順と扱いを読めるようにするためである。重さの度合いで名付けた段（「小粒」と「軽い」）を使った時、利用者はどちらが重いかを読み違えた。

並べる順は、依存の上位からにする（[advancing_discussion.md](../../docs/think_standards/advancing_discussion.md)の主軸）。依存で前後が決まらない時は、一つずつ考える、まとめて考える、確かめるだけの順にし、同じ段の中は大と中の数が多い順にする。重さの順で、依存の上位を飛ばさない。

### 根拠にする前例を探す

論点を立てる時と、示す直前に判定し直す時に、次の三つを順に確かめ、推す案の根拠を探す。

1. この作業の議論記録の決定と`design.md`
2. 既存の規範（repository contextが返す文書、pluginのskillとdocs）。設計前調査で読んだ範囲を使い、論点に関わる節を読み直す
3. 同じrepositoryの`.steering/`配下の議論記録の「決定」の節。論点の語で検索し、当たった決定だけを読む。全記録は読まない

見つかった決定や規範は、仮決めや推す案の根拠として名指す。過去の決定どうし、または過去の決定と今の規範が食い違う時は、新しい方と規範を使い、食い違いを根拠に書く。

前例から答えが一つに決まっても、問わずに決めない。根拠を名指した仮決めとして示す（下の「確かめるだけの論点は仮決めで示す」）。

- やってしまいがちな行動: 論点を立てる時に、既にある決定や規範を答えの在りかとして確かめない
- それをやると何が起きるか: 規範に決め方がある問いを、論点として繰り返し問う。過去には、version の上げ方を規範（`maintenance-plugin-context`「Plugin version」）が定めているのに、別々の作業で三度問い、どれも一言のokで閉じた
- 正しい判断のための問い: 「この論点の答えは、この作業の決定、規範、過去のsteeringの決定のどこかに既にないか」

### 判定し直す時点と利用者の上書き

重さは論点を立てた時に付け、利用者へ示す直前に判定し直す。立てた時点では調査前のことが多く、調査で前例が見つかる、利用者しか知らない条件が要ると分かる等で、重さが変わるためである。

判定した重さは、論点metadataの`**重さ:**`に書く（[templates/discussion_entry.md](templates/discussion_entry.md)）。判定し直したら、今の重さへ更新する。

利用者が重さを上書きしたら（「これは1個で」等）、その重さを優先する。

## 一往復に示す論点を組む

### 段ごとに示す数

| 段 | 論点を初めて問う時 | 応答を受けて回を重ねた時 |
| --- | --- | --- |
| 一つずつ考える | 1つ。他の論点を同じ往復に入れない | 1つ。他の論点を同じ往復に入れない |
| まとめて考える | 3つまで。確かめるだけを混ぜても合わせて3つまで | 1つ。他の論点を同じ往復に入れない |
| 確かめるだけ | 5つまで | 1つ。他の論点を同じ往復に入れない |

一つずつ考える論点を単独にするのは、利用者が一つを真剣に考えている時に、隙間に別の論点が入るとノイズになるためである。中の観点を二つ持つ程度の論点でも、三つ並ぶと利用者には重い。まとめて考える論点が入る往復は、確かめるだけの論点を混ぜても3つまでにする。全部が確かめるだけなら5つまで一緒に答えられる。同じ往復の中では、まとめて考える論点を先、確かめるだけの論点を後に並べる。

- やってしまいがちな行動: 議論記録に論点を作り置いたため、一つずつ考える論点を二つ三つ一度に示す
- それをやると何が起きるか: 一つを考えたい時に別の重い論点が目に入り、利用者は鬱陶しく感じる
- 正しい判断のための問い: 「今回の組に、一つずつ考える論点と他の論点が一緒に入っていないか」

- やってしまいがちな行動: まとめて考える論点と確かめるだけの論点を、確かめるだけの上限（5つ）で数えて組む
- それをやると何が起きるか: 過去に、まとめて考える論点2つと確かめるだけの論点3つを一度に示し、利用者に「多いな」と言われた
- 正しい判断のための問い: 「この組に、まとめて考える論点が一つでも入っていないか。入っているなら合わせて3つ以内か」

### 回を重ねた論点と横展開

応答を受けて回を重ねた論点は、段によらず一往復に1つで示す。最初の案で合意に至らなかった論点であり、改めて考える回になるためである。

ただし、ある論点の応答で決まった修正が、他の論点へ同じ形で当てはまる（横展開する）時は、元の論点の次の回と、修正が波及する先の論点の回を一往復にまとめてよい。波及先の数に上限は設けない。同じ修正の当てはめであり、利用者は一つの修正として確かめられる。波及先で同じ修正を当てるだけでは決まらず、その論点に固有の判断が要る場合は、その論点の回を一往復に1つで示す。

- やってしまいがちな行動: 一つの修正が波及する先を、一論点ずつ別の往復で問う
- それをやると何が起きるか: 過去に、利用者から「影響範囲の波及ばっかで何論点使ってんだ。まとめて洗い出して一気に反映する提案出せよ」と言われた
- 正しい判断のための問い: 「この波及先は、同じ修正を当てるだけで決まるか。その論点に固有の判断が要るか」

### 依存先が未決の論点

依存先が未決の論点（状態「依存先待ち」）は、案を作らないため、依存先と同じ往復に示さない。依存先が決まったら、重さを判定し直して案を作り、次の組へ入れる。依存先の答えで不要になったら取り下げる。論点を立てる時点と記録する内容は、SKILL.md「scopeと親子関係」が持つ。

### 利用者の指示を優先する

段ごとの数は既定である。利用者が「1個ずつ」「全部まとめて」等と指示したら、その指示に従う。

## 仮決めと推す案を示す

### 確かめるだけの論点は仮決めで示す

確かめるだけの段の論点は、推す案を「仮決め」とし、名指した根拠を添えて示す。まとめて考える段と一つずつ考える段の論点は、「推す案」として示す。根拠を名指せても、利用者が考える論点だからである。どちらも、他の案に記号（`a`、`b`等）を付けて示す。

既決事項・規範・前例から一つに決まる論点も、問わずに決めず、仮決めとして示す。利用者は合意の積み重ねである`design.md`を細かく読まないため、聞かれずに決まった判断は、出来上がった後のreviewで「あれって聞かれなかったけど、どうなってるのかな」と探すことになる。自明でも後で翻ることもある。

まとめて示した論点でも、採らなかった案と理由は、論点ごとに議論記録の提案と検討記録へ残す。結論を持っている論点ほど、採らなかった案と理由の記録価値が高い（[making_and_choosing_options.md](../../docs/think_standards/making_and_choosing_options.md)「補助: 畳めたことは、議論が不要になったことを意味しない」）。

- やってしまいがちな行動: 一方が決まった後に別に答えられる問いを、一つの論点にまとめて問う
- それをやると何が起きるか: 過去に、利用者への答え方の推奨、答えの読み方、応答欄への記録の三つを一つの論点で問い、利用者に「これって1論点として答えること？」と問い返された。答え方の推奨が決まれば、残りの二つはそれぞれ確かめるだけの論点として答えられた
- 正しい判断のための問い: 「この論点の中に、一方が決まった後に別に答えられる問いが入っていないか」

### 答え方を毎回添える

まとめて示す時は、答え方を毎回一文で添える。

> 全部そのままなら「ok」、違うものがあれば「8はb、他はok」のように書いて

「ok」は「全部ok」の別名であり、どちらで答えてもよい。利用者は、暗黙の答え方より明示された答え方の方が答えやすく、複数の時の答え方を覚えていないため、毎回添える。

chatでは、各論点の番号と仮決めの根拠を示し、案は記号を付けて並べる。論点の段はchatに示さない。段は一往復の組を選ぶためのものであり、利用者が気になれば議論記録の`**重さ:**`を読む。仮決め・推す案の印は、論点の行ではなく、該当する案の行の末尾に「（仮決め）」「（推奨）」と付ける。論点の行に「推す案: a」と書くより、案を読みながらどれが推されているかが分かり、読みやすいためである。議論記録のfile名と論点番号を特定し、「これ」「上記」で合意を求めない（SKILL.md「workflow全体で守る不変条件」）。

## まとめた返事を各論点へ振り分ける

### 返事を読む

返事は、名指された論点だけを、その答えとして扱う。

| 返事 | 扱い |
| --- | --- |
| 「ok」「全部ok」 | まとめて示した全部への合意 |
| 「8はb、他はok」 | 8をbにする答えと、名指されなかった残りへの合意 |
| 「8はb」だけ | 8をbにする答え。残りは答えを待つ状態のまま残す |
| まとめて示した論点に一つも触れない返事 | 全部を答えを待つ状態のまま残す |

名指されなかった論点を合意とも却下ともしないのは、利用者が「8はb」とだけ書いた時に、残りを後で答えるつもりのことがあるためである。答えを待つ論点は個別に聞き直さず、次にまとめて示す時に同じ仮決めを入れ直す。聞き直すと、後で答えるつもりの利用者への催促になる。

答えのあった各論点は、[iteration.md](iteration.md)「既存提示への応答を扱う」で論点ごとに処理する。返事に訂正と選択が混ざる時も、論点ごとに所属と評価対象を照合する。

### 各論点の応答欄に書く

答えのあった論点それぞれの応答欄に、返事の原文全体を引用し、その論点の結果を書く。「他はok」で合意した論点の結果には、まとめて示した往復で「他はok」と答えられたことを書く。答えの無い論点の応答欄は空のまま残し、答えが来た往復の原文で書く。

各論点の応答欄が、その論点の中だけで読めるようにするためである。まとめた返事は短く、全体を各論点へ引用しても読みにくくならない。

合意された論点は、SKILL.md「合意したdecisionを確定する」で一論点ずつ確定し、consumerへ一decisionずつ返す。
