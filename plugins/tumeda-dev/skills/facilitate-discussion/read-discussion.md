# 議論記録を目的に合わせて読む

入口は[解決](resolve-discussion.md)済みとする。
同じownerがread-only helper `scripts/inspect-discussion.mjs`で取得し、意味・合意・応答・完了は原文から判断する。
helperへ正本の選択や修復を委ねない。

## 判断に使う版を固定して読む

本文を読める段階で、次の順序を守る。snapshotは判断した原文の版を照合する起点であり、保存直前に新しく取って即compareするものではない。

1. 最初の原文読取より前に、`snapshot --directory <directory> --name <name>`を取り、索引・全範囲の集合・実体path・SHA-256を起点として保持する。
   既に使うことが確定している既存logは反復可能な`--log <evidence-log>`で含める。各原文と同じ読取目的にこの起点を結び付ける。
2. `check`で実論点・件数・順序・親子・索引と範囲所属を確認する。
   構造問題があれば対象の書込みを止め、自動修復・改番しない。
3. 通常継続では`read --view current --directory <directory> --name <name> --offset 0 --limit 1`で、
   全体前提、全論点metadata、現在結果、未決の最新iteration、現在の変更を原文取得する。
   対象論点は`read --topic N`で、その論点を含む範囲file全文を読む。単一形式では単一file全体になる。
4. `next_offset`がnullになるまで同じ条件で取得し、`total_chunks`とpath・行・columnを保持する。
   一file・一行の途中も分割されるため全chunkを合わせる。tool出力の打切りを読了にしない。
   `needs_full_read`のfileは全文へ広げる。未知の形式や取得不能を空・決定済み・確認済みにしない。
5. 対象log全文、根拠に使う他論点の現在結果・該当範囲と内部log、後続訂正を必要な分だけ読む。
   新しく必要と分かったlogは、下の手順で起点へ追加してから読む。無関係な全履歴・全logは毎回通読しない。
6. 読取後、同じ条件の`compare`へ保持した起点JSONをstdinで渡す。
   取得中に集合・実体・内容が変われば、その版の原文から判断せず、入口解決と必要な再読へ戻る。
   exit 0で不変を確認してから、末尾提示・原文応答・現在state・親子と根拠を判断する。

`read --view full`は索引と全範囲fileの原文を返す。大きい時もoffset/limitで最後まで取得する。
helperのcompleteは取得範囲の完了であり、意味理解や承認を保証しない。
書込みを伴わない読取結果を後続判断へ使う場合も、同じ起点と読取後比較を使う。

## 後から根拠logを追加する

最初の起点にない既存logを使う前に、旧log指定のまま旧snapshotをcompareし、既に読んだ集合の不変を確認する。
次に旧logと追加logを全て指定して拡張snapshotを取得し、旧集合の各path・実体・hashとformat・entryが旧起点と一致することを照合する。
一致した拡張snapshotを起点として追加log全文を読み、全log指定のcompareを通してから判断に使う。
どこかで変更・取得失敗があれば、新snapshotへすり替えず必要な再読・再判定へ戻る。
未作成の新規logは既存根拠として読んだことにせず、下の意図した保存として作成後に集合へ加える。

## 起点を保持したまま保存する

更新対象file全体と使用log全文を保存直前に再読する。分割済みでも対象欄だけを抜き出して書かない。
再読後・保存直前に、判断に使った起点を同じ全log指定のcompareへ渡す。
exit 0は不変、2は変更あり、1は不正input・取得不能である。
2や1では対象更新を止め、入口解決・再読・影響評価・再判定へ戻る。
再取得したsnapshotだけを直ちにcompareして、旧判断の有効性を認定しない。

保存は許可された欄と現在stateに限定し、一fileの保存ごとに次の境界を通る。

1. そのfileと使用logを再読し、直前まで保持した起点のcompareを通してから保存する。
   新規fileは未作成と追加先を確認する。まだ存在しないfileを既存根拠の`--log`へ入れない。
2. 保存した実物と実差分を読み、想定した追加・削除・内容だけであり、過去履歴・別欄・親子・linkを保持したか確認する。
   新規logを作った場合は、作成先と実体を確認し、そのlogを含む候補の全`--log`指定で更新後snapshotを取得する。
   既存fileの更新では従来の全log指定で取得する。保存対象以外の集合・実体・hashが直前の起点と一致し、
   保存対象の実体・hashが許された差分の実物と一致することを照合する。新規logの追加も、この照合の対象に含める。
3. 一致した更新後snapshotと、それを取得した全log指定の組を、次の起点として採用する。
   次のfileや既存logの保存前比較は、この同じ指定とsnapshotを使う。指定だけを増やしたり、元の起点へ戻して自分の意図した保存を外部変更と誤認したりしない。

意図した変更と検査結果のlog保存も、上の一file保存として扱う。
log自身の最終hashを同じlogへ追記する循環は作らず、最後のsnapshot JSONはtool結果として保持する。
既存の検証artifact等へ保存する場合もsnapshot自身を対象集合へ加えない。
未知の差を自分の保存へ含めたり、複数fileの部分保存を全件完了にしたりしない。

中断後は保存済み起点、許された実差分、現在の実物とtool結果を照合し、同じ処理の未完部分へ戻る。
起点と原文の対応を確認できなければ、現物の新しい読取から判断をやり直す。過去の比較成功を作らず、曖昧なまま上書きしない。

単一から分割への明示移行中だけは、新旧共存が意図された状態になる。
通常resolverを使うcompareへ通さず、[分割](split-discussion.md)の旧集合の直接照合を使う。この例外を通常継続へ広げない。

## handoffで全文を追いつく

既存designの独立構成前には本文もsnapshotも取らない。
task-designの既存gateを通った後のcatch-upだけ、全文取得前に起点を固定し、
`read --view full`の索引・全範囲の全chunkと必要logを上の手順で読む。
読取後と最終返却前に集合・実体・hashを照合する。
差があれば再取得・再読・照合し、古いsnapshotによる完了を返さない。
bounded extractionをcanonical全文読取の許可へ読み替えない。
