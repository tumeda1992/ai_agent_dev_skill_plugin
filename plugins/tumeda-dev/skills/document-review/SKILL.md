# ドキュメントレビュー（md 作成・更新のゲート）

md を作成・更新したら、**出す前にこれを通す**。doc を書く／直すフローは、各成果物を emit する前にここをゲートとして通す。

## 役割

この skill は、md を emit する前に、**読者がその doc で作業できる状態に達しているかを判定し、達していないものを出させない**。書き手が自分では見えない薄さを検知させ、指摘の性質に応じて直すか書き直すかを判断させる。書くこと自体、何を書くべきかの取捨選択は担当しない（能力境界は後述）。

## 判断方針

### 要素の充足ではなく観点の充足で判定する

書き手は「載せた」で満足でき、読者は「使える」でしか満足しない。この非対称があるため、トピックが挙がっていることや節が揃っていることを完了条件にすると薄い doc がそのまま通る。判定は常に観点を満たしたかで行い、満たさないなら出さない。

違反の兆候は、指摘を返すときに「触れてはいる」「抜けは無い」を根拠にすることである。これが出たら、その節を読み終えた読者が何をできるようになるかを 1 文で言えるかへ戻る。言えないなら濃さの目標が定まっていない。外れているときは、「載っているか」だけを確認して pass を返し、読者が実際に作業できるかを確認していない見え方になる。

### 薄さは微細な指摘ではない

指摘は 2 種類に分かれ、対処が違う。記法の一部・命名・言い回しは微細であり、直してレビューを最初から回し直す。指摘が尽きるまで繰り返すのは、直した結果が別の観点を崩すことがあるためである。

骨子・構造・実質の破綻は微細でなく、書く工程へ戻して生成をやり直す。パッチで繕わない。**濃さ不足はこちらに属する。** 1 行足すと書き手の基準では満たされるが、読者は依然として何も持ち帰れないためである。正しい対処は、そのトピックを読者が実行できる形まで降ろすか、親へ畳むかのどちらかになる。

違反の兆候は、濃さ不足の指摘に対してパッチ的に 1 行・1 文を足して満たしたとみなすことである。外れているときは、指摘のたびに部分修正を積み重ね、doc 全体としては薄いままレビューが通る見え方になる。

### 観点の当て方は標準 file が正本

この skill は観点の名前と、いつ当てるかだけを持つ。当て方の中身は `content_density.md` / `expression_notation.md` / `file_naming.md` が正本であり、skill 本文へ写さない。写すと二重管理になり、標準を直しても skill 側が古いまま残る。

新規作成は作成と更新の両方にあたるため、作成時観点と更新時観点の両方を当てる。更新時の濃さ観点では、書き足した箇所だけでなく前の版から削った要素も見る。指摘を受けて書き直すと、指摘された点だけを直して前版に成立していた要素を無自覚に捨てることがあるためである。

違反の兆候は、skill 本文に標準 file が持つべき判定基準や具体例を書き足すことである。外れているときは、標準 file を更新してもこの skill の記述と食い違ったまま気づかれない見え方になる。判断質問は、**skill 名と workflow を残したままこの記述を削除したとき、実装者が別の思想を持つ skill へ作り替えられるか**。作り替えられるなら、標準の中身を書かず参照だけを持てている。

### 能力境界と非目標

何を書くべきかという知識の取捨選択は `doc-enricher` が担う。この skill は書かれたものが観点を満たすかだけを見る。逆に、観点を満たさない doc を「残す価値がある知識だから」という理由で通さない。

違反の兆候は、この skill が「載せるべきか」の判断まで引き受け、`doc-enricher` の判断領域と重複することである。判断質問は、判定しているのは「書く価値があるか」ではなく「書かれたものが観点を満たすか」か。

観点を増やすときは「ケース別観点」の下へ足す。現時点で中身は無く、必要になったときに追加する枠として置く。

## 当てる観点

観点は 3 系統。新規作成は「作成＝更新でもある」ので作成時・更新時の両方を当てる。
各系統は小見出しで持ち、標準が増えたらその下に足す。
**各標準の当て方はその標準ファイルが正本 —— ここに内容を写さない**（上記「観点の当て方は標準 file が正本」）。
標準の実体は `plugins/tumeda-dev/docs/documentation_standards/` 配下。

### 作成時観点

新規に md を作るとき、必ず当てる。

- 内容の濃さ → `content_density.md`
- 記法 → `expression_notation.md`
- 命名 → `file_naming.md`

### 更新時観点

既存 md を直すとき、必ず当てる。

- 内容の濃さ → `content_density.md`（**書き足した箇所だけでなく、前の版から削った要素も見る**）
- 記法 → `expression_notation.md`

### ケース別観点

成果物や状況に応じて足す観点。**今は無し**。必要になったら、ここに追加する。

## 回し方

- **微細な指摘**（記法の一部・命名・言い回し）→ 直して、このレビューを最初から再度回す。指摘が尽きるまで。
- **微細でない指摘**（骨子・構造・実質の破綻）→ 書く工程へ戻り、指摘を活かして生成をやり直す（パッチで繕わない）。
    - **薄い（濃さ不足）は微細でない。** 1 行足して繕わず、そのトピックを読者が実行できる形まで降ろすか、親へ畳む。
- 「要素が揃った」でなく「観点を満たした」で判定する。満たさないなら出さない。

## 呼び出し経路

- `tasklist-executor` と `task-design` が、docs と skill 本体の作成・更新を行った後の emit 前ゲートとして呼ぶ。
- ユーザーが明示して単独起動する（「ドキュメントをレビューして」「md を出す前にチェック」等）。呼び出し元が上記 2 skill に限られるため、それ以外の場面で md を触ったときに明示的に通せる入口として置く。呼ばれなければ誰も気づかないという弱点は残るが、入口を塞ぐ理由にはならない。

## `doc-enricher` との能力境界

`doc-enricher` は、code reading やタスク遂行後に、永続性が高くレバレッジの高い知識を既存 README へ提案する（提案の採否は Gate A〜G で「残す価値があるか」を判定する）。この skill は、書かれた文が観点（濃さ・記法・命名）を満たすかだけを見る。判定対象が違うため重複しない。

`plugins/tumeda-dev/docs/` 配下は、出所（`doc-enricher` が書いたか、他の workflow が書いたか）を問わずこの skill の対象に含める。出所を問わず当てることで境界が単純になる。
