# コードレビュー

## 目的とモデル

利用者が各指摘を独立して読み、採否を判断し、修正結果を追跡できる状態を作る。
テストの通過報告をレビュー結果の代わりにしない。

レビューは [runtime-model-profiles.md](../runtime-model-profiles.md) の
`high-reasoning-review` を使用する。利用者が指定したモデルを優先する。
モデルを選択できない場合は現在モデルと制約を明示する。
モデルの切替・独立レビューを行っていないのに、行ったと記載しない。
修正実行に同じ推論能力を必須とせず、レビューと適用の担当を区別してよい。

repository固有の指示・テスト・公開条件が必要な場合は
`maintenance-plugin-context`へconsumer=`code-review`として必要factを依頼する。
既存の合意と利用者の明示指示を保持し、不要な再承認を求めない。

## 入力

自然言語でも次のparameter相当でも受け取る。

| 入力 | 意味・既定値 |
| --- | --- |
| `repository` | 対象Git root。省略時は起動位置から確認する |
| `working_dir_parent` | 成果物配置の親。省略時は起動時のcurrent directory |
| `create_working_dir` | default `true`。`false`なら指定directoryを直接使う |
| `scope` | `full` / `paths` / `diff`。範囲・差分指定なしは`full` |
| `paths` | レビュー対象のファイル・directory。相対pathはrepository基準 |
| `base` / `head` | 差分の両端。branch、commit、PR指定から解決可能 |
| `diff_mode` | `endpoints` / `merge-base` / `working-tree` |
| `model` | 利用者指定があれば優先 |
| `apply` | 既定はレビューのみ。適用済みの合意があればその範囲を継続 |

出力先とレビュー対象のpathを取り違えない。directory指定がどちらか不明な場合だけ確認する。

## 出力先の確定

task-designと同じparameterの意味を使う。
`create_working_dir=true`なら既存の親directoryの下へ`YYYYMMDD-code-review`等の作業directoryを作る。
日付は利用者のtimezoneを使う。同名の既存成果物を上書きせず、再利用か別名かを確認する。
`create_working_dir=false`は存在する`working_dir_parent`自体を使う。未指定なら場所を確認する。
相対pathは起動時のcurrent directoryから解決し、確定した絶対pathを利用者へ伝える。
既存レビューの続行ならそのdirectoryと固定IDを使い、状態を初期化しない。

配置:

```text
<working_dir>/
  README.md
  coverage.md
  findings/
    CR-001-<slug>.md
  evidence/          # 必要な再現コード・証拠だけ
  application.md    # 適用の合意・順番・検証・commit記録。適用時だけ
```

## 対象を固定する

Git status、HEAD、既存commit、staged/unstaged/untrackedを確認する。
全体なら現行スナップショットの入口から追い、直近差分だけに縮めない。
指定範囲ならその範囲を主対象とし、呼出元・関連先・テストを根拠確認のため読む。
差分なら指定された比較の意味を保持する。

- `endpoints`: 解決したbaseとheadの二点を比較する。
- `merge-base`: baseとの分岐点からheadまでを比較し、PR差分と整合させる。
- `working-tree`: 指定baseと作業treeを比較し、staged/unstaged/untrackedの包含を記録する。

比較元が曖昧ならGitとPR情報で解決し、解けない場合だけ確認する。
base/headは完全SHA、作業treeは対象fileの内容hash・一覧で固定する。
開始後に対象が変わったら変更範囲を識別し、旧スナップショットの判定と混ぜない。
差分レビューでは既存問題と導入された問題を区別する。指定された全体レビューでは既存問題も対象となる。

## レビュー

1. 指示・設計契約・入口・テストから期待動作を確認する。
2. 入口から業務処理、永続化、外部I/O、応答、画面へ追う。
3. 正常系に加え、認可と関連ID、異常入力、部分失敗、状態遷移、並行操作、依存境界、重複と責務を確認する。
4. 疑いを呼出元・契約・再現で検証する。推測だけの問題を確定指摘にしない。
5. [指摘テンプレート](templates/finding.md)を使い、独立して採否・修正できる単位で保存する。

指摘だけをテンプレートに沿って記す。良かった点や網羅した観点で指摘を水増ししない。
同じ原因・修正を重複計上せず、独立する原因を巨大な1項目へまとめない。
指摘数の目標を設けない。改善案が未確定なら不足材料を明示する。
以前のレビューの結論を根拠にせず、現物で再確認して旧IDとの対応を残す。

READMEは対象、結論、優先順と個別指摘への索引に限定する。
coverageは読んだ範囲、除外、未確認、静的確認と実測の区別を記す。
テスト成功は問題がない証拠とは限らない。問題挙動を期待する再現テストは、成功が「再現できた」を意味すると記す。
公開物へ認証情報・実環境の非公開情報・過剰なログを含めない。

## 合意と適用

レビュー依頼だけでアプリケーションを修正しない。
具体的な指摘と修正案を読める状態にしたうえで、適用するID、除外、挙動変更の許容範囲を合意する。
利用者が既に「全件修正」「この範囲を適用」と指示していれば、その指示を合意として記録し再承認を求めない。
当初の「挙動維持のみ」と後続の適用指示が競合する場合は、直近指示の範囲を確認し記録する。
「対象外」はレビュー対象外・修正不要と混同せず、どの合意から外れるかを書く。
未確認の業務判断だけを質問し、それに依存しない確定事項を先に進める。

適用は1指摘ずつ行う:

1. 現行コードでも指摘が成立するか確認する。誤指摘なら根拠付きで撤回する。
2. 必要な回帰テストを追加・更新し、当該指摘の修正を実装する。
3. 関連自動テストと必要な型検査・lintを実行する。失敗を直してから次へ進む。
4. 指摘ファイルに結果を記録し、**1指摘1コミット**で保存する。messageに固定IDを含める。
5. applicationへcommit SHA・実行検証・残りを追記する。

依存順を先に決め、複数指摘をまとめて1commitにしない。共通基盤が必要なら最初に必要とする指摘へ含め、後続の依存を明示する。
誤指摘の撤回・適用保留もその指摘の記録だけを独立commitにする。
実装を伴わない調査結果を「修正完了」と数えない。
最後に必要な全体回帰を行い、再発防止のドキュメント更新案を提示する。
push・PR更新は既存の公開許可に従い、要求済みなら完了まで実行する。

## 実行中の障害と返却

外部取得・権限要求・書込み・テストの受付は、呼出し全体に60秒以下のdeadlineを設ける。
commandのtimeoutだけでは実行前の承認待ちを制限できないため、呼出し側にもdeadlineを置く。
テスト等の長時間処理はsession IDを受け取って非同期監視し、1回の待ちを60秒以内にする。
タイムアウトは取消成功を意味しない。書込み・branch作成等は完了した可能性を照合してから再試行する。
一時障害なら回数を限って再試行し、同一の権限拒否・設定不足なら原因を直すか正規の別手段へ切り替える。
待ちの原因、期限到達、次の対処を利用者へ報告し、5分間無言で待ち続けない。
環境障害では原因を切り分け、利用可能な正規の別手段を確認する。権限拒否を迂回しない。
同じ失敗する呼出しを無制限に繰り返さず、権限が必要な部分と独立に完了できる部分を区別する。
未完了を完了と称さず、必要な環境・入力が復旧したら既存成果物から続ける。
状況質問は継続中の作業を中止する指示と解釈しない。

最終返却は結論と優先指摘、索引path、未確認範囲、適用した場合のID/commitと検証結果を示す。
レビュー結果の代わりに「テストが全部通った」だけを返さない。
