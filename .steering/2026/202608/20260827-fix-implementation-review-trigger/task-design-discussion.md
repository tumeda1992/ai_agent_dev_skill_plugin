# 議論記録

## 論点1: 適用範囲と実行者固定の書き分け方

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 一文が担う二役を分離する

#### 提案0

`steering/SKILL.md` の `## 実装完了後review` 冒頭を、適用範囲の段落と実行者固定の段落へ分ける。

```diff
-実装、review、validation、ユーザー動作確認でfeedback・漏れ・追加要件・不具合を直接受け取ったworkflow ownerが、同じworking directoryでpluginの`facilitate-discussion`を適用する。steeringが直接受け取った場合はsteering自身が行い、議論だけを別childへ再委譲しない。
+実装、review、validation、ユーザー動作確認でfeedback・漏れ・追加要件・不具合が判明したら、同じworking directoryでpluginの`facilitate-discussion`を適用する。ユーザーから受け取ったものも、agent自身が見つけたものも同じ扱いにする。
+
+適用するのは、それを直接受領したworkflow ownerである。steeringが直接受領した場合はsteering自身が行い、議論だけを別childへ再委譲しない。
```

`直接受領`は実行者を固定する段落へ残す。`tasklist-design.md`と`templates/tasklist.md`の三箇所が同じ語を実行者固定の文脈で使っており、語法を揃える。

validatorへのassertionは追加しない。理由は提案背景に置く。

#### 提案背景

##### 今回満たす必要のある条件

適用範囲を定める記述と実行者を固定する記述が別の文として読めること、自己発見の`漏れ`・`不具合`が適用対象だと解釈に依存せず読めること、実行者固定の意図が失われないこと、既存三箇所の`直接受領`と語法が矛盾しないこと。

##### 各変更がどの条件を満たすか

一文目の主語を`workflow owner`から事象へ移し、述語を`直接受け取った`から`判明したら`へ変えることで、適用範囲の文から実行者が抜ける。`判明した`は出所を含意しないため、自己発見も他者からの受領も同じく満たす。

二文目として出所を問わないことを明示する。分離だけでも曖昧さは消えるが、実際に誤読が起きた事実があるため、読み手が抱きうる誤解へ先回りする一文を残す。既存文へ足すだけの対症療法と異なり、分離とセットで機能する。

実行者固定は独立した段落へ移し、`直接受領`という語をそこで使う。他三箇所の語法と揃い、`特定caller名へ固定しない`という併記の意図とも一致する。

##### validatorへassertionを追加しない理由

このrepositoryのvalidatorは固定文字列の存在を検査する。今回の変更は既存文の言い換えであり、新しい契約を追加しない。固定文字列を足すと、将来の文言改善のたびにvalidatorが偽陽性で落ちる。

検査したいのは「適用範囲と実行者が別の文になっていること」という構造であり、固定文字列では表現できない。表現できない対象へassertionを足さない。

### 決定

`steering/SKILL.md` の `## 実装完了後review` 冒頭を二段落へ分ける。一段落目が適用範囲と出所非依存、二段落目が実行者固定である。`直接受領`は二段落目へ残し、他三箇所と語法を揃える。

validatorへassertionを追加しない。今回の変更は既存文の言い換えであり新しい契約を追加しない。検査したい対象は文の構造であって固定文字列ではない。
