# Discussion entry形式の帰納的調査

## 調査目的

`discussion_entry.md`の見出し構造を先に設計せず、過去のdiscussion結果から、議論中の当事者がiterationの展開と現在地を見失う条件、追いやすさを生んだ表現、合意前の具体像が不足した条件を抽出する。

第一の評価者は、同じ論点を現在進行形で議論している当事者とする。session外から後で読む人の理解しやすさは、その次に検証する。

## 調査範囲

- discussion系file 20件
- 明示された論点見出し 130件
- iteration記録 53件
- file・directory・README・配置を判断対象に含む論点
- 固定`ネクストアクション`field 123件
- iterationのない短い論点を対照例として確認

この母集団には、現在template固有の`現在の合意対象`を使ったentryはなかった。したがって、現在templateの利用結果を直接評価したものではなく、現在formatへ至る経緯と、discussionで蓄積した実際のproblemを調べた結果である。

## 観測1: 問題の中心は、過去情報の量ではなく、議論展開の索引がないこと

53件のiteration見出しのうち45件は、`イテレーション1`のように番号しか持たなかった。この形式では、当事者がiteration 4へ戻った時に、候補変更、診断の深掘り、scope分割、外部制約による撤回のどれが各段階で起きたかを見出しから判断できない。本文を最初から再読して展開を再構築する必要がある。

対照的に、次のような表現を持つ事例は追いやすかった。

- iteration見出し自体が「候補Aの検討」「外部制約の発覚により候補Bへ変更」のように判断変化を表す
- 複数decisionへ分解した後、A / B / Cと順番を付ける
- 各段階で`現在の焦点`を明示する
- 分解したdecisionを最後に一つの結論へ再統合する

ここから、iterationは保存された過去ではなく、議論中の当事者が使うnavigationでもあると分かる。

## 観測2: iterationで起きる変化は「前案との差分」一種類ではない

複数iterationの論点では、少なくとも次の変化が観測された。

- 提案の具体項目だけを修正する
- 原因診断を一段深くし、提案の根拠を変える
- 一つの論点へ混在したdecisionを分解する
- 現在扱う焦点を次のdecisionへ移す
- 外部制約の発覚で、採用済み候補を撤回する
- 後続の別論点が、前の論点で使った語彙や具体像を置き換える

現行表示は、これらを同じ`検証 / 修正先の判断 / 根本原因N + 提案N`で包む。そのため情報は保存されていても、何が起きたiterationかをscanできない。

単純に「現在案」と「過去差分」へ二分すると、診断の更新、decision boundaryの再編、topic間の置換関係が落ちる。必要なのは、履歴を短くすることより、各iterationが議論全体へ与えた作用を判別できることだと考えられる。

## 観測3: 現formatの各意味要素には、具体的な発生理由がある

現在の`事象 / 原因 / 検証 / 総論 / 各論 / ルール / 適用例`は、一度に導入された装飾ではなかった。過去の5 iterationの議論で、次の失敗へ順番に対処した結果だった。

1. 提案だけを弄り、診断へ戻らない
2. 一行の総論だけを出し、具体的な変更内容を利用者へ判断させる
3. 診断の質と提案の質の因果を説明しない
4. discussionに思考結果の中身を保存せず、認識差異を振り返れない
5. 抽象ルールだけ、または特定事例だけに偏る

したがって、固定見出しの反復が読みにくいことと、そこに保存された意味が不要であることは別である。

特に、総論と各論、抽象ルールと具体例の往復は維持する価値が実例から確認できる。一方、異なる契約をすべて`ルール`と呼ぶと、内容の境界がscanできなくなる。改善方向は、抽象と具体を削ることではなく、具体契約を内容固有の名前で識別できるようにすることにある。

## 観測4: 合意に必要な具体像は、変更対象ごとに異なる

file・directory変更には、良い例と不足例の両方があった。

機能した表現:

- directory配置: 完成後のtreeと、既存directoryの移動箇所
- codeまたはUI挙動: 必要箇所だけのbefore / after
- 複数moduleの関係: 型やcall flowを示す小さな構造図

不足した表現:

- README作成: 保存pathと責務layerだけを決め、見出しoutlineと代表本文がない
- docs整備: 「作成する」「整理する」だけを決め、何を含め、何を含めないかが実装時判断として残る
- file移動: pathだけを合意し、移動後の周辺treeや作らないfileを示さない

この差から、previewを一種類の固定fieldにするのではなく、合意しようとしている変更に応じてtree、outline、代表本文、before / after、state transition等を選ぶ必要がある。previewは説明用の付録ではなく、実装時へ流出する未合意判断を発見するgateとして働く。

## 観測5: `ネクストアクション`の大半はnoiseだが、一部は現在地そのもの

固定field 123件には、空欄28件のほか、既定のdesign反映、tasklist作成、完了済み、なし等が多かった。これらはstatus、decision、consumer handoffと重複し、論点固有情報としての価値が低い。

一方、次のような記述は当事者のnavigationとして機能した。

- 次のiterationへ進む
- 分解した次のdecisionを扱う
- 複数の子論点を上位から順に解消する
- 外部調査または別steeringの結果を待つ

したがって、結論は`ネクストアクション`を一律に残す・消すではない。既定のhandoffを毎回繰り返さず、非defaultな停止位置または次の焦点を、議論の現在地として表す必要がある。

## 観測6: iterationのない新規提案は、現形式でも比較的読みやすい

事象、原因、提案、決定が一方向に進む短い論点では、思考順と理解順の差が小さく、現形式の負担は目立たなかった。読みにくさは主に、iterationが累積し、診断・提案・scope・焦点が異なる仕方で変わる時に顕在化した。

このため、全entryを一律に大きなsnapshot構造へ変えることより、iterationが増えた時にも議論の筋と累積した判断を追える構造を先に解くべきである。

## 帰納された上位要件候補

見出し構造を決める前の要件候補は、次のとおりである。

1. entryは、議論中の当事者が、現在の判断対象だけでなく、ここまでの議論がどの判断変化を経て現在地へ来たかを短い探索で再構築できる。
2. iterationは従属的なarchiveではなく、議論の展開を表すnavigationとして扱う。
3. 各iterationは、その段階で何が変わったかと、その変化が診断・提案・scope・焦点のどこへ作用したかを識別できる。
4. 現在の具体的な判断内容と、それを形成したiterationの接続を、どちらか一方を通読しないと他方が分からない形にしない。
5. 原因の追跡、総論と各論、抽象と具体の往復は維持する。ただし、異なる内容を同じ`ルール`labelで平坦化しない。
6. file・directory・文書・code・UI等の変更は、対象に適したpreviewで、合意後の具体像と非変更範囲を判断できる。
7. 既定handoffは固定fieldとして反復せず、非defaultな停止位置・次の焦点・外部依存だけを議論の現在地として残す。
8. 後から読む人にも同じentryから背景と論理を復元できることを、上記を満たした構造への第二の検証軸とする。

## この調査だけではまだ決めないこと

- exactなトップレベル見出し
- 現在案を論点上部へ一つだけ複製・集約するか
- iteration本文を完全案、差分、decision summaryのどれにするか
- 現在の判断内容と議論の展開を分離表示するか、相互参照するか、統合表示するか
- 非defaultな進行位置をどのfieldで表すか
- 変更種別ごとのpreview必須条件

これらは上位要件から演繹して決めない。壊れ方が異なる具体caseについてbefore / afterと局所修正方針を作り、仮の共通骨子とcase別variantを全iteration論点へ展開する。未対応caseがあればキュレーションを増やしてafterを更新し、既存caseの改善を壊さず全体をcoverできた時に固定する。
