# 議論記録

## 論点1: `2.1.1` を迂回させない導線の修正範囲

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 修正する箇所の集合を確定する

#### 提案0

**推奨:** A・B・D を採り、C は採らない。

##### A. routing表の直後に、`2.1.1` を全経路が通ることを明示する（必須）

`2.1` の routing表（8行）の直後、`#### 2.1.1` の直前へ次を挿入する。

```markdown
表で対象論点を決めた後、`2.2`または`2.3`へ進む前に必ず`2.1.1`を通る。`2.1.1`で原因を分類するのは
認識齟齬または修正要求を扱う場合だけだが、**該当するかどうかの判定自体は全経路で行う**。
表の「次に行うこと」列が指す遷移先は、この判定を終えた後の行き先である。
```

表の8行は変更しない。各行末へ「`2.1.1`を経て」を足すと8箇所へ同じ文言が散り、行の主眼である
「どの論点を選ぶか」が読みにくくなる。表の外に一度だけ置けば、表全体を支配できる。

##### B. `2.3.1` の「この分類」という語の衝突を解く（必須）

`2.3.1 iterationの入口gate` の現在の記述:

> feedbackを受けた時は、iterationを追加する前に必ずこの分類をやり直す。

この「分類」は**所属論点の判定**を指すが、`2.1.1` の「原因を分類する」と語が衝突している。
feedbackを受けた読み手が「分類はやり直した」と認識し、原因ownerの分類を済ませたと誤認できる。

次へ置き換える。

```markdown
feedbackを受けた時は、iterationを追加する前に必ず所属論点の判定をやり直す。この判定は`2.1`が所有し、
原因ownerの分類（`2.1.1`）とは別のものである。両方を通る。
```

##### C. `種別` fieldの再評価契機を足す（採らない）

論点の`種別`は作成時に決まり、途中で性質が加わっても更新契機がない。しかし A と B が通れば
`2.1.1` は必ず実行され、原因分類の結果は `2.1.1` の contract により
`doc-enricher` 起動または具体ケース修正として現れる。`種別` fieldの更新は記録の精度を上げるが、
迂回そのものは防がない。

このsteeringのMUSTは「迂回できなくする」ことであり、C はそこへ寄与しない。
記録精度の改善として独立に扱うべきで、導線修正へ混ぜない。

##### D. 認識齟齬かどうかを判定できる問いを `2.1.1` へ足す（必須）

`2.1.1` の冒頭は「選んだdecisionが認識齟齬または修正要求を扱う場合は」と条件を置くが、
**該当するかどうかを判定する基準がない**。gateを通っても「これは選好の変更であって認識齟齬ではない」と
判断すれば、迂回したのと同じ結果になる。

`2.1.1` の冒頭条件の直後へ次を挿入する。

```markdown
認識齟齬に該当するかは次で判定する。

> このfeedbackは、提案の選好を変えたのか。それとも提案が依拠していた前提知識の誤りを正したのか。

後者なら認識齟齬である。assistantが「より良い案へ差し替えた」と感じている時ほど、
実際には前提が誤っていた場合がある。差し替えた提案の内容ではなく、
**差し替える理由になった知識がどこから来たか**で判定する。その知識をassistantが持っていなかったなら、
成果物固有ではなくrepository知識またはskillの不足である。
```

##### 変更対象の集合

| file | 変更 | 採否 |
| --- | --- | --- |
| `skills/facilitate-discussion/SKILL.md` `2.1` 末尾 | A: 全経路が`2.1.1`を通る旨を挿入 | 採用 |
| `skills/facilitate-discussion/SKILL.md` `2.3.1` 入口gate | B: 「この分類」を「所属論点の判定」へ置換し、`2.1.1`と別である旨を明示 | 採用 |
| `skills/facilitate-discussion/SKILL.md` `2.1.1` 冒頭 | D: 認識齟齬の判定基準を挿入 | 採用 |
| `skills/facilitate-discussion/templates/discussion_entry.md` | C: `種別`の再評価契機 | **採らない** |

本文を図へ合わせる修正であり、逆ではない。

#### 提案背景

##### この提案が満たす必要のある条件

design.md の MUST は「既存論点へのfeedbackを扱う経路から `2.1.1` を迂回できなくする。図と本文が
同じ導線を示す」である。迂回を防ぐには、gateへ到達させることと、到達後に正しく判定できることの
両方が要る。片方だけでは迂回と同じ結果になる。

##### 調査で分かった、報告時より広い事象

escalation時の報告は「routing表の1行が `2.1.1` を経由しない」だった。実際に `SKILL.md` を読むと
**routing表は8行あり、そのどれ一つとして `2.1.1` に言及していない**。特定の行の欠落ではなく、
表全体が `2.1.1` を素通りする構造である。したがって修正も特定行ではなく表全体へ効く位置へ置く。

##### D を必須に含める理由

A だけでは今回の失敗を防げない可能性が高い。gateへ到達しても、assistantは自分の提案差し替えを
「より良い案を出した」と認識しやすく、「認識齟齬ではない」と判定して素通りできる。

今回の実例がまさにそれである。assistantはテーブル名に関する自分の反論が否定された時、
それを「提案の改善」として処理した。実際には、状態遷移で行が別テーブルへ移るという
**前提知識を持っていなかった**ことが原因だった。判定を提案の内容ではなく
「差し替える理由になった知識がどこから来たか」へ向ける問いがあれば、この取り違えは防げる。

##### C を採らない理由

`種別` fieldの更新契機は、記録の精度に関わるが迂回の防止には寄与しない。
A・B・D が通れば `2.1.1` は必ず実行され、その結果は `doc-enricher` 起動または具体ケース修正として
外形に現れる。`種別` が古いままでも導線は機能する。

導線修正と記録精度改善を1つのdecisionへ混ぜると、片方への反対がもう片方を止める。
記録精度の改善が必要なら独立の論点として扱う。

**A. `2.1` routing表の直後へ、全経路が `2.1.1` を通ることを明示する**

表の8行は変更しない。各行末へ同じ文言を散らすと、行の主眼である「どの論点を選ぶか」が読みにくくなる。
表の外へ一度だけ置けば表全体を支配できる。

**B. `2.3.1 iterationの入口gate` の「この分類」が何を指すかを直後で明示する**

`2.1.1` の「原因を分類する」と語が衝突しており、feedbackを受けた読み手が
「分類はやり直した」と認識して原因ownerの分類を済ませたと誤認できる。両者が別のものであり、
両方を通ることを明示する。

ピン留めされた契約文（`feedbackを受けた時は、iterationを追加する前に必ずこの分類をやり直す`）は
そのまま残し、直後の一文で「ここでいう分類は所属論点の判定であり、原因ownerの分類とは別」と補う。

記録の精度は上がるが、迂回そのものを防がない。A・B・D が通れば `2.1.1` は必ず実行され、

導線修正と記録精度改善を1つのdecisionへ混ぜると、片方への反対がもう片方を止める。
記録精度の改善が必要なら独立の論点として扱う。

**D. `2.1.1` の冒頭条件の直後へ、認識齟齬の判定基準を追加する**

`2.1.1` は「認識齟齬または修正要求を扱う場合は」と条件を置くが、該当するかを判定する基準がなかった。
gateへ到達しても「これは選好の変更であって認識齟齬ではない」と判断すれば、迂回したのと同じ結果になる。

判定は「差し替えた提案の内容」ではなく「差し替える理由になった知識がどこから来たか」へ向ける。
今回の失敗がまさにこの取り違えだった。assistantは自分の反論が否定された時それを「提案の改善」として
処理したが、実際には前提知識を持っていなかったことが原因だった。

**修正範囲を導線に限定した理由**

このsteeringのMUSTは「迂回できなくする」ことである。迂回を防ぐには、gateへ到達させること（A）と、
到達後に正しく判定できること（D）の両方が要る。片方だけでは迂回と同じ結果になる。
B は、到達したgateを「済ませた」と誤認させる語の衝突を除く。

## 論点2: 知識1・2・4 の置き場所と、知識4 の汎用化可否

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 4件の知識をどのfileへどう配置するかを確定する

#### 提案0

**推奨:** 知識3 は `naming.md` へ追加、知識1・2 は新規file `entity_modeling.md` へ、知識4 は**採らない**。

##### 配置

| 知識 | 配置先 | 理由 |
| --- | --- | --- |
| 3. 名詞形と形容詞形 | `development_standards/naming.md` に `### 名詞形と形容詞形を選ぶ` を新設 | 命名の判断であり、既存の §1 基本 に属する。エンティティ名に限らずmethod名・file名にも効く |
| 1. 状態遷移の表現方法 | 新規 `development_standards/entity_modeling.md` | 命名ではなくデータモデリングの判断。`naming.md` には収まらない |
| 2. テーブル名は集約の同一性を主張しない | 同上（知識1と同じfile） | 知識1の判断を下した後に必ず来る問いであり、分けると片方だけ読まれる |
| 4. ドメイン名前空間と永続化名の対応 | **採らない** | 下記 |

##### 知識3 を `naming.md` §1 へ置く理由

`naming.md` は §1 基本 / §2 ファイル名 / §3 メソッド名 の構成で、§1 が命名全般に効く原則を持つ。
「A の B」と「B の A」の違いは、テーブル名に限らずmethod名・file名・module名すべてに効くため §1 に属する。
§1 の既存項目（初見で自明 / 宣言的なwhat・why / 具体性 / 命名後のレビュー）と同じ粒度で並ぶ。

##### 知識1・2 を1つの新規fileへまとめる理由

`documentation_standards/README.md` は「各標準は基本1ファイル」と定める。知識1と2は
「エンティティをどう切るか」という1つの標準の表と裏である。

- 知識1: 状態が変わるとき、同じテーブルに置くか別テーブルへ移すか
- 知識2: 別テーブルへ移した結果、テーブル名が既存と似ることを恐れなくてよい

知識1の判断で「別エンティティ方式」を選んだ読み手は、必ず知識2の問いに直面する。
分けると、知識1だけ読んで名前で詰まる読み手が出る。

file名は `naming.md` §2 の「同階層の存在と足並みを揃える」「直上ディレクトリのコンテキストを継承する」
に従う。同階層は `naming.md`（広い標準の粒度、接頭辞なし、snake_case）であり、
親ディレクトリが `development_standards` を語るため、file名に `standard` を重複させない。
`entity_modeling.md` は同じ粒度・同じ表記で並ぶ。

##### `docs/README.md` の指し先

`development_standards/` が2 fileになるため、`docs/README.md` の「5群への入口」の1行を
`development_standards/naming.md` から `development_standards/` へ変える。
同READMEの「収録fileが1つならそのfileを、複数ならdirectoryを代表fileの代わりに指す」という規約に従う。

##### 知識4 を採らない理由

知識4は「永続化層のモデル名はドメイン名前空間を平坦化した形にする」というもので、次の2点で
このpluginの標準として成立しない。

**第一に、これは規約であって判断基準ではない。** 他の3件は「〜のとき、どちらを選ぶか」という
判断の問いを持つ。知識4は「こう命名せよ」という取り決めであり、そう決めた利用先repositoryでのみ有効で、
別の対応規則を採るrepositoryには適用できない。`naming.md` §2 が「表記は所属ツリーの慣習に従う。
どちらが正しいではなく、周囲に合わせる」と述べているのと同じ構造で、**規則の中身はrepository側が持つ**。

**第二に、汎用化すると内容が消える。** 「対応規則を持ち、逸脱時は理由を記録する」まで薄めると、
残るのは「一貫性を保て」「例外は記録せよ」という、どの標準にも書ける一般論になる。
`migration.md` は「汎用化を理由にfunctionを薄めることを許可しない」と定めており、
薄めなければ載せられない知識はpluginへ載せない。

代わりに、利用先repositoryのarchitecture文書へ残すことを提案する。今回の逸脱
（平坦化した語順が成立しないため語順を反転した）も、利用先の該当ドメインREADMEへ記録する。
これは利用先側のsteeringで扱う。

#### 提案背景

##### この提案が満たす必要のある条件

design.md の MUST は「エンティティ設計・命名の判断基準が `docs/development_standards/` 配下から辿れる」
「追加する記述にrepository固有情報を含めない」である。加えて `documentation_standards/README.md` の
「各標準は基本1ファイル」と、`naming.md` §2 のfile命名規約を満たす必要がある。

##### 判断の軸

4件を「命名の判断」と「データモデリングの判断」で切った。知識3だけが命名であり、
知識1・2はエンティティの切り方である。同じfileへ混ぜると、`naming.md` が命名以外を含み始め、
§1〜§3 の構成が崩れる。

##### 知識4の扱いで迷った点

escalation時は「汎用化できるか判定してほしい」という依頼だった。汎用化の可否ではなく、
**汎用化した後に判断能力が残るか**を基準にした。残らないなら、載せる意味がない。

#### 提案0へのフィードバック

**結果:** 知識4の不採用と知識3の`naming.md`配置は承認。知識3を`entity_modeling.md`へも置くことと、`naming.md`のscope方針明記を追加要求

> 知識4は別に入れなくてもいい。3についてはnamingに置くの賛成。そのうえでentity_modeling自体にもリンク付きで書いてほしい。というのも、大抵これがテーマになるのはエンティティの名付けの時。そして、この取り違えはは致命的な意味の取り違えとつながるからentity特有の記載が必要になる。またnaming.mdは、どのnamingにも当てはまる汎用的な内容について書いて、特定の文脈のnamingについてはこのファイルに入れないことを記載しておいて。汎用の積集合を扱って、取り扱い方針が濁る和集合運用はしない

提案0は知識3を`naming.md`へ置いて完結させたが、これは不足だった。この判断が実際に問われるのは
大半がエンティティの名付けの場面であり、そこでの取り違えは命名の不味さにとどまらず致命的な意味の
取り違えへつながる。一般則を`naming.md`に置いたうえで、`entity_modeling.md`にもエンティティ固有の
記載をlink付きで置く。

あわせて`naming.md`のscope方針を明記する。扱うのはどの命名にも当てはまる汎用的な内容（積集合）だけとし、
特定文脈の命名は入れない。和集合運用にすると取り扱い方針が濁る。

### イテレーション1: `naming.md` のscope境界を定義し、二箇所配置の分担を決める

#### 提案1

##### 先に解く必要がある衝突

`naming.md` へ「特定の文脈の命名はこのfileに入れない」と書くと、**既存の §2 ファイル名 と §3 メソッド名が
その規定に抵触する**。ファイル名もメソッド名も特定の対象種別に限った命名だからである。

境界を次のように定義する。

> `naming.md` が扱うのは、**どのプロジェクトにも存在する成果物**（file、method 等）の命名と、
> それらすべてに共通して効く原則である。

##### file名から `naming` を外す理由

現 `naming.md` §2 は「直上ディレクトリのコンテキストを継承する」と定め、

**この標準自身が定めた規則に、この標準のfile名が違反する**ことになる。

したがって `naming/method.md`、`naming/file.md` とする。`development_standards/naming/file.md` は
path全体で「命名標準のファイル名編」と読める。

`documentation_standards` であり、`file_naming` は親の文脈を重複していない。

`core` 単体では中身を示さないが、`file.md` / `method.md` と並ぶことで
「対象を問わず効く部分」という意味が立つ。§1 が禁じる `data` / `manager` / `info` / `util` は
**siblingと並べても意味が立たない**名前であり、`core` はこれに当たらない。採用する。

#### 提案背景

##### この提案が満たす必要のある条件

feedbackは「namingは扱うスコープが広いのでdirectory化し、`core.md` で共通部分、対象種別ごとに分け、
それぞれの守備範囲を明確にし、`README.md` で取り回し方針を立てる」ことを求めた。

加えて、既存の規約を満たす必要がある。`documentation_standards/README.md` は
「1つの標準を説明するのに複数ファイルが要る場合はディレクトリ化してよい」と定めており、
directory化は許可されている。`docs/README.md` は「群のREADMEが入口になる」と定めており、
`README.md` を置く構成と整合する。

##### file名でfeedbackと異なる案を出す理由

feedbackは `method_naming.md` / `file_naming.md` を挙げたが、この命名は
`naming.md` §2 が定める「直上ディレクトリのコンテキストを継承する」に違反する。
命名標準のfile名が命名標準に違反する状態は、標準の説得力を直接損なう。
規則を曲げるか名前を変えるかの二択であり、名前を変える方を選んだ。

##### 分割を function migration として扱う理由

分割は「見出しだけが移り、理由、例外、失敗例が落ちる」という失敗を起こしやすい。
`function_migration_policy.md` の §9 失敗pattern が最初に挙げているのがまさにこれである。
policyが用意されている作業に対して、policyを使わない理由がない。

### 決定

`naming.md` を削除し、`development_standards/naming/` へ4 fileとして分割する。

```text
docs/development_standards/
  naming/
    README.md   取り回し方針、各fileの守備範囲、対象種別fileを増やすときの規則
    core.md     名前を付ける対象が何であっても成立する原則（旧 §1 基本）
    file.md     ファイル名に固有の規則（旧 §2）
    method.md   メソッド名に固有の規則（旧 §3）
  entity_modeling.md
```

**file名から `naming` を外す。** 旧 §2「直上ディレクトリのコンテキストを継承する」は、親が語ることを
ファイル名に重複して持たせないことを求めている。`naming/` 配下で `method_naming.md` とすると、
この標準自身が定めた規則にこの標準のfile名が違反する。規則を曲げるか名前を変えるかの二択であり、
名前を変える方を選んだ。

`documentation_standards/file_naming.md`（ポインタfile）は改名しない。そちらの親は
`documentation_standards` であり、`file_naming` は親の文脈を重複していない。

**`core.md` を採用する。** `core` 単体では中身を示さないが、`file.md` / `method.md` と並ぶことで
「対象を問わず効く部分」という意味が立つ。`core.md` 自身が禁じる `data` / `manager` / `info` / `util` は
siblingと並べても意味が立たない名前であり、`core` はこれに当たらない。

**scope宣言の移設。** 論点2で `naming.md` 冒頭へ置いたscope宣言は `README.md` へ移し、群構成に合わせて
「`core.md`」「対象種別のfile」「この群の外」の3分岐へ細分した。積集合のみを扱い和集合運用をしない方針は
そのまま維持する。
