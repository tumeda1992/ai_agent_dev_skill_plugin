# 議論記録

## 論点1: `entity_modeling/` の分割軸と、`README.md` が持つ判断の問い

**ステータス:** 分解済み

**種別:** TBDヒアリング

### イテレーション0: 群の分け方を確定する

#### 提案0

**推奨:** `naming/` の形（README + core + 対象別file）は借りるが、**判断の問いと読む順の規定は変える。**
両者は分割軸が異なり、`core` と個別fileの関係も異なるため。

##### `naming/` と `entity_modeling/` は分割軸が違う

| | 分割軸 | `core` と個別fileの関係 |
| --- | --- | --- |
| `naming/` | **対象種別**（何に名前を付けるか。file、method） | **加算的。** `file.md` は `core.md` の原則に、ファイル名固有の規則を足す。`core.md` の内容は打ち消されない |
| `entity_modeling/` | **状況**（そのエンティティがどう生まれ、どう消えるか） | **上書き的。** `evacuation.md` は `core.md` のフィールド追加の既定を**逆転させる** |

`naming/README.md` の判断の問いは「この規則は、名前を付ける対象が何であっても成立するか」である。
これは加算的な分割に対応した問いであり、そのまま持ち込むと `evacuation.md` の性質を表せない。

`evacuation.md` は「退避エンティティにも当てはまる追加の規則」ではなく、
「退避エンティティでは `core.md` の既定が逆になる」という上書きである。
加算の問いで分けると、読者は `core.md` の opt-in を適用したまま `evacuation.md` を読み足し、
矛盾する2つの既定を同時に持つことになる。

##### `entity_modeling/README.md` の内容

```markdown
# エンティティ設計

エンティティをどう切るか、切った結果をどう名付けるかの標準。命名の一般則は
[naming/](../naming/README.md) が持ち、ここではエンティティを前提にしないと成立しない判断だけを扱う。

## この群の置き方

- `core.md`: エンティティがどう生まれ、どう消えるかを問わず成立する判断
- 状況ごとのfile（`evacuation.md`）: 特定のライフサイクルを前提にする判断

判断の問い: **「この判断は、そのエンティティがどう生まれ、どう消えるかを問わず成立するか」**

- 成立する → `core.md`
- 特定のライフサイクルを前提にしないと成立しない → その状況のfile

## 読む順と、既定の優先関係

MUST: `core.md` を読んだうえで、扱っているエンティティが状況fileに該当するかを確認する。
該当する場合、**状況fileの既定が `core.md` の既定に優先する。**

これは `naming/` と構造が違う。`naming/` の `file.md` や `method.md` は `core.md` へ規則を足すだけで、
`core.md` の内容を打ち消さない。一方 `entity_modeling/` の状況fileは既定そのものを逆転させることがある。

やってしまいがちな失敗: `core.md` の判断基準を適用して設計を終え、状況fileを読まない
→ 該当する状況では既定が逆であるため、結論が逆になる。実際に、退避エンティティへ `core.md` の
  フィールド追加基準（opt-in）を適用し、退避のたびに情報が失われる設計を作った事例がある

## 各fileの守備範囲

| file | 扱うもの | 扱わないもの |
| --- | --- | --- |
| [core.md](./core.md) | ライフサイクルを問わず成立するエンティティ設計の判断 | 特定の状況でだけ成立する判断 |
| [evacuation.md](./evacuation.md) | 元データを削除して別エンティティへ移す状況に固有の判断 | ライフサイクルを問わない判断（`core.md` を参照） |

状況fileを増やすときは、まずその判断が `core.md` へ入らないことを確認する。
`core.md` へ入る判断を状況fileへ書くと、他の状況から見えなくなる。
```

##### `naming/README.md` のリンク修正

`naming/README.md` は現在 `../entity_modeling.md` を指している。移動先へ追随させる。

```diff
- （例: エンティティ固有の命名判断は [entity_modeling.md](../entity_modeling.md)）
+ （例: エンティティ固有の命名判断は [entity_modeling/](../entity_modeling/README.md)）
```

directoryを指すのは、エンティティ固有の命名判断が `core.md` の §2 と `evacuation.md` の両方に
分かれる可能性があるためである。入口であるREADMEを指せば、増減へ自動的に追随する。

#### 提案背景

##### この提案が満たす必要のある条件

design.md の MUST は「退避エンティティの判断基準が `docs/development_standards/` 配下から辿れ、
`core.md` の既定と対比できる」である。**対比できることが要件に含まれている。**
単に2 fileへ分けるだけでは、読者が両方を読む保証も、どちらが優先するかを知る手段もない。

##### `naming/` の形をそのまま借りない理由

引き渡し時の提案は「`naming/` と同じ形（README + core + 対象別file）に揃える」だった。
file構成としてはそのとおりだが、READMEの中身まで同じにすると誤りになる。

`naming/README.md` は積集合／和集合という語で「core は共通部分だけを扱い、個別規則を足していかない」
と述べている。これは加算的な分割を前提にした表現であり、既定が逆転する関係を表せない。

今回の失敗そのものが、この違いを見落とした結果である。`core.md`（当時の `entity_modeling.md`）の
フィールド追加基準を退避型へ適用し、既定が逆であることに気づかなかった。
README が優先関係を書いていなければ、次の読者も同じ経路をたどる。

##### この提案で決めないこと

- `evacuation.md` の file名を確定するか（暫定採用のままにするか）
- `entity_modeling.md` → `entity_modeling/core.md` の移動を function migration として扱い、
  ledger を作るか
- `core.md` の内容変更。移動時は中身を変えない

#### 提案0へのフィードバック

**結果:** 提案0を受諾

> ok

### 決定

`entity_modeling/` は `naming/` の**file構成**（README + core + 個別file）を借りるが、
**READMEの判断の問いと読む順の規定は別にする。**両者は分割軸が異なるためである。

| | 分割軸 | `core` と個別fileの関係 |
| --- | --- | --- |
| `naming/` | 対象種別（何に名前を付けるか） | 加算的。`core.md` の内容を打ち消さない |
| `entity_modeling/` | 状況（どう生まれ、どう消えるか） | **上書き的。`core.md` の既定を逆転させることがある** |

**`entity_modeling/README.md` が持つもの:**

- 判断の問い「この判断は、そのエンティティがどう生まれ、どう消えるかを問わず成立するか」
- **既定の優先関係。** `core.md` を読んだうえで状況fileに該当するかを確認し、
  該当する場合は状況fileの既定が `core.md` の既定に優先する（MUST）
- `naming/` と構造が違うことの明示。`naming/` の個別fileは規則を足すだけだが、
  `entity_modeling/` の状況fileは既定そのものを逆転させることがある
- やってしまいがちな失敗として、`core.md` だけを適用して状況fileを読まない経路と、
  それによって退避のたびに情報が失われる設計を作った実例
- 各fileの守備範囲表と、状況fileを増やすときの確認

**`naming/README.md` のリンク修正:** `../entity_modeling.md` → `../entity_modeling/README.md`。
directoryの入口を指すのは、エンティティ固有の命名判断が `core.md` の §2 と状況fileの両方へ
分かれる可能性があり、入口を指せば増減へ自動的に追随するためである。

**採らなかった案:** `naming/README.md` の積集合／和集合の表現をそのまま持ち込む案。
加算的な分割を前提にした表現であり、既定が逆転する関係を表せない。この違いを見落としたことが
今回の失敗そのものであり、READMEが優先関係を書いていなければ次の読者も同じ経路をたどる。

## 論点2: `evacuation.md` の file名確定と、`entity_modeling.md` 移動の扱い

**ステータス:** 決定

**親論点:** 論点1

**種別:** TBDヒアリング

### イテレーション0: file名と移動の検証手段を確定する

#### 提案0

**推奨:** file名は `evacuation.md` で確定する。移動は full ledger を作らず、
`diff` による同一性確認で全量保存を示す。

##### file名を `evacuation.md` で確定する

引き渡し時は「暫定採用。より適切な語が見つかれば改名を妨げない」としていた。
論点1で分割軸が「状況（どう生まれ、どう消えるか）」だと確定したため、改めて検証する。

この状況の本質は「元データを削除し、その内容を別の形へ移す」ことである。
`evacuation`（退避）はこれを直接指す。日本語のユビキタス言語「退避」とも一致する。

`naming/file.md` の規則（直上ディレクトリの文脈を継承する）にも従う。
親が `entity_modeling` を語るため、file名に `entity` や `modeling` を重複させていない。

##### 移動は full ledger を作らず `diff` で検証する

`entity_modeling.md` → `entity_modeling/core.md` は**内容を変えない純粋な移動**である。
前回の `naming.md` 分割は1 fileを4 fileへ分け、内容の再配置を伴ったため二層ledgerを作った。
今回は性質が違う。

| | 前回（`naming.md`） | 今回（`entity_modeling.md`） |
| --- | --- | --- |
| 操作 | 1 file → 4 file の分割。章を再配置し、一部をADD | 1 file → 1 file の移動。内容不変 |
| 検証手段 | 構造ledger + contract ledger + 代表句照合 | **`diff` で同一性を直接確認** |

**`diff` のほうが ledger より強い証拠である。** ledger は「代表句が新fileに存在する」ことしか示せないが、
`diff` は全行の一致を示す。純粋な移動では `diff` が空であることが全量保存の直接の証明になる。

`function_migration_policy.md` が二層ledgerを要求するのは、内容が再配置されて一対一対応が
機械的に取れなくなる場合である。`git mv` 相当の移動では、その前提が成立しない。

新規追加される `README.md` と `evacuation.md` は移動ではなく `ADD` であり、
根拠は論点1の決定と引き渡された提案1である。

##### 検証手順

```text
1. entity_modeling.md の内容を entity_modeling/core.md へ移す
2. diff で移動前後が完全一致することを確認する（差分ゼロ）
3. entity_modeling.md を削除する
4. 旧pathへの参照が repository 全体でゼロであることを grep で確認する
   （既知の依存: naming/README.md）
```

#### 提案背景

##### file名を確定させる理由

暫定のまま実装へ進むと、`README.md` の守備範囲表、`naming/README.md` のリンク、
`core.md` からの参照がすべて暫定名を含むことになる。後で改名すると同じ箇所を再度触る。
論点1で軸が確定した今が、名前を検証して確定させる時点である。

##### ledger を作らない判断の根拠

`function_migration_policy.md` §8 は「validatorや文字列assertionも補助である。重要なanchorの消失や
path不整合は検知できるが、文脈、順序、理由、例外まで同じ意味で働くことは通読とledger照合でしか
確認できない」と述べる。

これは**内容が変わる移行**を前提にした記述である。内容が1バイトも変わらない移動では、
文脈・順序・理由・例外もすべてそのまま移る。`diff` の空が、それらの保存を同時に証明する。

ledger を作ること自体を目的にすると、`diff` で足りる場面でも形式を踏むことになり、
「ledgerを書いたから安全」という誤った安心が生まれる。

**結果:** 提案0を受諾

> ok

**file名は `evacuation.md` で確定する。** 論点1で分割軸が「状況（どう生まれ、どう消えるか）」だと

`naming/file.md` の「直上ディレクトリの文脈を継承する」にも従い、`entity` や `modeling` を重複させない。

**移動は full ledger を作らず `diff` で検証する。**

| | 前回（`naming.md`） | 今回（`entity_modeling.md`） |

`diff` のほうが ledger より強い証拠である。ledger は代表句の存在しか示せないが、`diff` は全行の一致を示す。

## 論点3: 差し込み点の適用対象をどう判定し、既存 migration 原則をどこまで一般化するか

**ステータス:** 分解済み

**種別:** TBDヒアリング

### イテレーション0: 判定基準と一般化範囲を確定する

#### 提案0

**推奨:** 対象actionを列挙ではなく一つの問いで判定する。既存「migration phaseの原則」の
section名を一般化し、migration をその代表例として残す。二つのMUSTの文面は変えず、適用対象だけを広げる。

##### 判定の問い

> **このphaseで起きる変化は、この作業を破棄しても残るか。**

- 残る → 対象action
- 残らない → 対象外

##### なぜ列挙ではなく問いにするか

引き渡された提案4は対象を「DB migration、公開contractの破壊的変更、データ移行等」と列挙した。
列挙は利用先が自分の環境のactionを照合できない。「等」に自分のケースが入るかを判断する基準が
どこにもないため、判断は結局その場のassistantの裁量になる。

`破壊的` `後方互換性がない` も判定に使えない。カラム追加のmigrationは破壊的でも後方非互換でもないが、
共有DBを持つrepositoryでは対象にしたい。逆にbranch内で完結する大規模な削除は破壊的だが対象ではない。
判定を左右しているのは**変化の性質ではなく、変化が及ぶ範囲**である。

「作業を破棄しても残るか」はこの範囲を直接問う。git で言えば working tree と branch を捨てて
元に戻せるかであり、利用先は自分の運用に当てはめて答えられる。

##### 呼称

| 案 | 評価 |
| --- | --- |
| a. 破壊的action | 提案4の語。削除・上書きを連想させ、カラム追加のmigrationを含めにくい。判定の問いとも一致しない |
| b. 不可逆action | 判定の帰結を名前にしている。down migration を持つ場合に「不可逆ではない」と読まれ、判定を誤らせる |
| c. 作業の外へ残るaction（推奨） | 判定の問いをそのまま名前にしている。長いが、section見出しで一度定義すれば本文中は`対象action`で足りる |

`docs/development_standards/naming/core.md` の「本質的に何であるか」で見ると、本質は
「効果がこの作業単位の外側に出ること」である。a は現象の一部、b は帰結、c は本質を指す。

##### 既存「migration phaseの原則」の差分

| | 現行 | 変更後 |
| --- | --- | --- |
| section見出し | `### migration phaseの原則` | `### 作業の外へ残るactionを含むphaseの原則` |
| MUST 1（単独phase切り出し） | DB migrationを含むphase | 対象actionを含むphase |
| MUST 2（末尾に停止・確認task） | migration結果をユーザーに確認 | 対象actionの結果をユーザーに確認 |
| 理由 | schema変更は後続作業すべての前提になる | 同左に加え、作業破棄で戻せないため、適用の事実を独立に確認する必要がある |
| migration の位置づけ | 唯一の対象 | 代表例として本文へ残す |

提案4は「既存の migration phaseの原則は維持する」としており、二つのMUSTの内容は変えない。
変えるのは適用対象の範囲だけである。これにより、これまでmigrationだけに掛かっていた
「単独phaseとして切り出す」MUSTが他の対象actionにも掛かる。理由が同じ（適用可否を独立に検証したい）ため、
拡大を意図したものとして受け入れる。

##### 判定例

| action | 作業破棄後に残るか | 判定 |
| --- | --- | --- |
| DB migration の適用 | 残る | 対象 |
| deploy / release | 残る | 対象 |
| 外部serviceの設定変更 | 残る | 対象 |
| 本番データの移行・削除 | 残る | 対象 |
| 公開APIのcode変更（未release） | 残らない | 対象外 |
| 通常のcode変更・test追加 | 残らない | 対象外 |

提案4が例示した「公開contractの破壊的変更」は、この判定では**対象外**になる。code変更だけならbranch内で
完結し、作業を破棄すれば残らないためである。実際に外へ出るのは release の時点であり、release 自体が
対象actionになるため取りこぼしは生じない。周知が必要な時点は「codeを書いた時」ではなく「外へ出した時」であり、
判定はその実態と一致している。

##### 受け入れる帰結

同じactionでも repository の運用によって判定が変わる。開発DBが開発者ごとに分離されていれば、
migration の適用は環境ごと捨てられるため対象外になりうる。plugin側は問いだけを持ち、
答えは利用先が自分の環境で出す。差し込み宣言の有無と同じ構造である。

判定が利用先依存であることは弱点ではない。plugin が全repositoryの運用を列挙できない以上、
列挙を持つほうが誤りを固定する。

#### 提案背景

design.md の「3. 完成後の姿 / workflow」は TBD であり、その内容は
「差し込み点の contract（`maintenance-plugin-context` への要求の形、返却がない場合の扱い、
tasklist初稿reviewでの問い方）」の確定を待っている。

この三つのうち、**適用対象の判定が最上位**である。何を対象とするかが決まらなければ、
利用先へ何を宣言させるかも、review時に何を問うかも決まらない。よってこの論点を先に置く。

引き渡された提案4の該当箇所は次のとおり。

> plugin（`tasklist-design.md`）| 差し込み点。後方互換性を壊す可能性のあるaction
> （DB migration、公開contractの破壊的変更、データ移行等）を含むphaseについて、
> `maintenance-plugin-context` へ consumer=`task-design` として差し込み宣言を要求する。

提案0はこの「後方互換性を壊す可能性のあるaction（…等）」という規定を、判定可能な一つの問いへ置き換える。
分担（plugin が枠、利用先が中身）と、宣言が返らなければ何も差し込まない既定は変えない。

現行 `tasklist-design.md:19-23` の実測は次のとおり。

```text
### migration phaseの原則
- **MUST**: DB migrationを含むphaseは必ず単独phaseとして切り出す。
- **MUST**: migration phaseの最後に「ここで作業を停止し、migration結果をユーザーに確認する。次phaseへは進まない」というtaskを置く。
- 理由: schema変更は後続作業すべての前提になる。ユーザーが実際に適用されたことを確認する前に後続へ進むと、誤った前提上へ変更が積み上がる。
```

この論点で決まると、次の論点（要求の形とreview時の問い方）が一意に定まる。

#### 提案0へのフィードバック

**結果:** 提案0を受諾

> ok

### 決定

**対象actionを列挙ではなく一つの問いで判定する。**

> このphaseで起きる変化は、この作業を破棄しても残るか。

残るなら対象action、残らないなら対象外とする。判定を分けているのは変化の性質ではなく
変化が及ぶ範囲であり、`破壊的` `後方互換性がない` はこの範囲を指さない。カラム追加のmigrationは
破壊的でも後方非互換でもないが共有DBでは対象であり、branch内で完結する大規模削除は破壊的だが対象外である。

**呼称は「作業の外へ残るaction」（案c）とする。** section見出しで一度定義し、本文中は`対象action`で参照する。
案aは現象の一部、案bは帰結を指す。案bの`不可逆`は down migration を持つ場合に
「不可逆ではない」と読まれ、判定を誤らせる。

**既存「migration phaseの原則」を一般化する。** 二つのMUSTの文面は変えず、適用対象だけを広げる。

| | 現行 | 変更後 |
| --- | --- | --- |
| section見出し | `### migration phaseの原則` | `### 作業の外へ残るactionを含むphaseの原則` |
| MUST 1 | DB migrationを含むphase | 対象actionを含むphase |
| MUST 2 | migration結果をユーザーに確認 | 対象actionの結果をユーザーに確認 |
| 理由 | schema変更は後続作業すべての前提になる | 同左に加え、作業破棄で戻せないため適用の事実を独立に確認する必要がある |
| migration | 唯一の対象 | 代表例として本文へ残す |

これまでmigrationだけに掛かっていた「単独phaseとして切り出す」MUSTが他の対象actionにも掛かる。
理由が同じ（適用可否を独立に検証したい）ため、拡大を意図したものとして受け入れる。

**提案4が例示した「公開contractの破壊的変更」はこの判定では対象外になる。**
code変更だけならbranch内で完結し、作業を破棄すれば残らない。実際に外へ出るのは release の時点であり、
release 自体が対象actionになるため取りこぼしは生じない。周知が必要な時点は「codeを書いた時」ではなく
「外へ出した時」であり、判定はその実態と一致する。

**判定が利用先の運用に依存することを受け入れる。** 開発DBが開発者ごとに分離されていれば、
migration の適用は環境ごと捨てられるため対象外になりうる。pluginは問いだけを持ち、答えは利用先が出す。
差し込み宣言の有無と同じ構造である。pluginが全repositoryの運用を列挙できない以上、
列挙を持つほうが誤りを固定する。

## 論点4: 差し込み宣言の受け口の形と、tasklist初稿reviewでの問い方

**親論点:** 論点3

**種別:** TBDヒアリング

### イテレーション0: 受け口・問い方・gateを確定する

#### 提案0

**推奨:** 受け口を context instance の `## task-design` 配下へ H3 として置く。宣言は

tasklist設計時にだけ使う利用先固有factだからである。`## 共通` は
「2つ以上のconsumerが同じ意味・粒度で直接使うrepository fact」の置き場所であり、これは該当しない。

`## 選択的読取` 末尾の実測は次のとおり。

##### 3. 宣言の二形態

引き渡された提案4の workflow 表は「中断時にどう振る舞うかをユーザーへ併せて問う」とし、
**常に問う**ことを前提にしていた。ここを二形態へ分ける。

| 宣言の形 | 記述例 | review時 | 停止・確認taskへ書くもの |
| --- | --- | --- | --- |
| actionを定める | 「対象action適用後、commitとpushを行う」 | 問わない | 宣言された内容 |
| 問いを定める | 「対象action適用後、commit・pushの要否をユーザーへ問う」 | review依頼へ併せて出す | ユーザーの回答 |
| 宣言なし | — | 問わない | 既定の停止・確認taskのみ |

常に問う設計にすると、利用先が「常にこうする」と決めている運用でも毎回ユーザーの手番が発生する。
task-design の目的は「実装中に新しい判断が生まれない状態を作る」ことであり、
利用先が既に決めている判断を毎回問い直すのはその逆である。

毎回問いたい利用先は、宣言を「問いを定める」形で書けばよい。どちらを選ぶかは利用先の判断であり、
plugin は両方を受けられる形にする。これは「宣言がなければ何もしない」という既定と同じ構造である。

##### 4. 問うタイミングと実行時の扱い

| 時点 | 行うこと | owner |
| --- | --- | --- |
| tasklist初稿作成 | 対象actionを含むphase末尾へ既定の停止・確認taskを書く。宣言があれば内容を反映する | task-design |
| tasklist初稿のreview依頼 | 宣言が問いを定めている場合だけ、その問いをreviewへ併せて出す | task-design |
| review後 | ユーザーの選択を停止・確認taskへ書き込む | task-design |
| 実行時（停止） | 記録済みの選択に従う。問い直さない | tasklist-executor |

設計段階で決められる判断を実行時まで持ち越さない。実行中に問うと executor の停止回数が増える。

**`tasklist-executor` 側の変更は不要である。** 実測したところ、executor に migration 固有の分岐は無く、
`../runtime-execution-contracts.md` の checkpoint / confirmation 契約に従って
「tasklist に書かれた停止task」で止まる。停止・確認taskは通常のtaskとして書かれるため、
executor は既存契約のまま動く。

##### 5. 自己レビューgateへの追加

`## 自己レビューgate` へ一項目を足す。

```markdown
- [ ] **対象actionを含むphaseで、差し込み宣言を要求したか**:
      `maintenance-plugin-context` へ要求し、返却の有無に応じて停止・確認taskを書いたか。
  - 宣言が返らなければ既定の停止・確認taskだけを置く。要求自体を省略しない。
  - やってしまいがちな失敗: 宣言が無い前提で進める。この契約は「宣言がなければ何もしない」ため、
    要求を忘れてもtasklistは正常に見え、差し込みが黙って落ちる。
```

**gate が要る理由は、この契約の失敗が silent だからである。** 要求を忘れても tasklist は完成して見え、
実行時に何も起きないことでしか気づけない。宣言が返らない場合と要求を忘れた場合が、
成果物の上で区別できない。区別できない失敗は、成果物の検査では捕まらず gate でしか捕まらない。

## 論点5: `design.md` template の見出し順変更と章番号廃止の適用範囲

### イテレーション0: 見出し順・追随範囲・既存design.mdの扱いを確定する


`元の依頼内容` と `上位roadmap制約` を付録へ送らず先頭へ残す。`前提とする既存仕様` と役割が違うためである。

##### 3. `steering/SKILL.md:142` は置換ではなく併記にする

現行の実測は次のとおり。

> `## 1. TL;DR`本文の最初の段落を優先し、なければ`## 目的`の最初の段落、それもなければ
> `{slug}（概要抽出不可、design.md 参照）`とする。

引き渡された提案2はこれを `## 1. TL;DR` → `## TL;DR` の**置換**としていた。**これでは壊れる。**

summary生成が読む対象は「実行月の一か月前」のsteering directoryにある design.md であり、
それらは**旧templateで書かれた過去のfile**である。提案2自身が「既に存在する design.md は書き換えない」と
定めているため、旧形式 `## 1. TL;DR` は将来にわたって残り続ける。

置換した場合の挙動は次のようになる。

```text
## TL;DR        → 旧design.mdにはマッチしない
## 目的          → マッチしない
fallback        → 「{slug}（概要抽出不可、design.md 参照）」
```

errorは出ない。summaryは生成され、概要欄だけが全件「抽出不可」になる。**silent degradation である。**

正しい変更は併記である。

> `## TL;DR`または`## 1. TL;DR`本文の最初の段落を優先し、なければ`## 目的`の最初の段落、…

現行が既に `## 目的` という旧形式を併記していることが、この扱いの先例になっている。
formatを変えた側が旧formatの読み取りを残す、という同じ判断が一度行われている。

##### 4. `validate-plugin.mjs` の forbid 句も番号を外す

345行目付近の実測は次のとおり。

```javascript
for (const forbidden of [
  "## 4. 設計判断",
  "### 選択した原則と理由",
  "### 代替案と棄却理由",
]) {
  forbidText(taskDesignTemplate, forbidden, "撤去済みの固定設計判断format");
}
```

これは撤去済みsectionの再導入を防ぐgardである。番号を外した後は `## 4. 設計判断` という文字列が
template へ現れる余地が無くなり、forbid が空振りする。誰かが `## 設計判断` を書き戻しても検出されない。
`## 設計判断` へ変える。残る2句は番号を持たないため変更不要。

require 側とforbid側で対処が違うのではなく、どちらも「番号に依存した文字列一致が、番号廃止で意味を失う」
という同じ問題である。require側は落ちて気づけるが、forbid側は**落ちないまま無力化する**。
落ちない方を見落としやすい。

##### 1. 提案5の項目（DoD検査）


| DoDの各項目に、それを担保するtaskがあるか | 各phaseにtest作成・変更があるか | 同じtestを別の角度（存在 / 網羅）から見る |
| 対象actionを含むphaseで、差し込み宣言を要求したか | 完了後actionがrepository contextへ従うか | どちらも repository context の返却に従うかを問う |

**gate全体の構造化は行わない。** 16項目へ伸びるが、見出しで群へ分けない。
gate は上から順に全部確認するためのlistであり、群へ分けると「この群は今回関係ない」と
飛ばす余地が生まれ、漏れの検出という目的と逆を向く。項目数が問題になるなら、
分類ではなく項目の統合で減らすべきであり、今回のscopeではない。

## 論点8: `validate-plugin.mjs` のピン留め追随を、どこにどう書くか

**ステータス:** 決定

**種別:** 認識齟齬の原因routing

### イテレーション0: 原因ownerと置き場所を確定する

#### 提案0

**推奨:** 原因は「ルールの不在」ではなく「既存ルールの守備範囲」である。`README.md` の
`## 変更時の検証と前提` を、assertionの**追加**だけでなく**追随**を含む形へ改める。
一般則への昇格は行わない。併せて、既に腐っている行数の記述を落とす。

##### 1. 事象

論点5と論点6で、追随すべき箇所として `scripts/verification/validate-plugin.mjs` を二度落とした。
どちらも引き渡された提案が申告した追随件数に含まれておらず、私が実測して初めて出た。

##### 2. 原因

**ルールは既に存在した。** `README.md` の `## 変更時の検証と前提` に次がある。

> skillを追加・変更したら、対応するassertionをこのfileへ追加する。

この文はassertionの**追加**しか言っていない。二度落としたのは**既存assertionの追随**である。

| | 対象 | 現行ruleが覆うか |
| --- | --- | --- |
| 追加 | 新しいskill・sectionに対して新しいassertionを足す | 覆う |
| 追随 | 既にピン留めされた文字列（`## 4. リスクと対策`、`### Step 0.5.`）が変更で成立しなくなる | **覆わない** |

原因owner は repository知識である。ただし「知識が無かった」のではなく「書かれている知識の
守備範囲が狭かった」ため、新しいruleを足すのではなく既存ruleを広げる。
不在だと誤認して新ruleを足すと、同じ対象を指す二つの規定が並ぶ。

##### 3. `README.md` の変更

**現行:**

> このrepositoryの検査正本は `node scripts/verification/validate-plugin.mjs` である。926行のassertion
> （`requireText` / `requireExists` / `requireFrontmatter` / `requireAbsent` 等）でskillとdocsの内容を検査する。
> test framework、lint、formatter、CI設定は他に存在しない。skillを追加・変更したら、対応するassertionを
> このfileへ追加する。

**変更後:**

> このrepositoryの検査正本は `node scripts/verification/validate-plugin.mjs` である。
> assertion（`requireText` / `requireExists` / `requireFrontmatter` / `requireAbsent` / `forbidText` /
> `requireOrderedText` 等）でskillとdocsの内容を検査する。test framework、lint、formatter、CI設定は
> 他に存在しない。
>
> - skillまたはdocsを追加・変更したら、対応するassertionをこのfileへ追加する。
> - **既存assertionがピン留めしている文字列を変更したら、そのassertionも追随させる。**
>   見出し、step番号、章番号、契約文の変更はすべてこれに当たる。
> - **`forbidText` を先に確認する。** `requireText` は追随を怠ると検査が落ちて気づけるが、
>   `forbidText` は落ちないまま無力化する。禁止した文字列が新formatで出現不能になると、
>   その禁止は何も守らなくなる。注意は、自動で検出できない側へ割く。

##### 4. 行数の記述を落とす

現行は「926行のassertion」と書いているが、実測は **950行** であり既に腐っている。今回の変更でさらに増える。

読者がこの数字から得る判断は無い。必要なのは「このfileが検査の正本である」ことと
「他に検査機構が無い」ことであり、規模の数字ではない。腐る数値を残すと、
他の記述の信頼性まで下げる。

##### 5. 一般則へ昇格させない

「否定形の検査は、禁止対象が構造的に出現不能になると、失敗せずに無効化する」は
このrepositoryに限らず成立しうる。lint rule、test assertion、type guard のいずれにも当てはまる。

それでも昇格させない。今回観測した実例は二つとも同じ `validate-plugin.mjs` であり、
一repositoryの一機構に閉じている。`naming/core.md` の将来進化テストが
「異なる方向に3〜4つ」を求めるのと同じ理由で、一方向の実例だけで抽象化すると金属疲労する。
別の文脈（lint、test framework等）での二例目が出てから昇格を判断する。

置き場所を `README.md` とするのは、`validate-plugin.mjs` がこのrepository固有の機構であり、
`docs/development_standards/` と `docs/think_standards/` がrepository非依存の標準を置く場所だからである。

#### 提案背景

論点6の提案背景で「二度続いたため、これが個別の見落としではなく確認手順の不足である
可能性を、後続の論点で扱う」と述べた。論点7で design.md の

`facilitate-discussion` の原因owner分類に従い、具体ケース（論点5・6での見落とし）の修正より先に
原因ownerを分類した。分類の結果、repository知識の守備範囲不足だった。

調査で分かった重要な点は、**原因が「ルールの不在」ではなかった**ことである。
不在だと考えたまま新しいruleを足すと、`## 変更時の検証と前提` に同じ対象を指す二つの規定が並び、
どちらが正本か分からなくなる。既存ruleを広げるのが正しい対処である。

行数の腐りは、この調査の過程で `wc -l` を実行して判明した副産物である。
