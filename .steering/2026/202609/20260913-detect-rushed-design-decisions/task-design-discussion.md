**# ユーザーから指摘・提案を受領した**

**主軸: 問うか自分で埋めるかは、情報の持ち主で決まる**

受領した指摘・提案を処理するとき、埋めなければならない空白が必ず出る。その空白を自分で埋めるか相手へ問うかは、好みでも礼儀でもなく、**その情報を誰が持っているか**で決まる。

- 外部にある情報（既存code、既存docs、標準、論理的帰結）: 自分で取りに行く。取りに行かずに問うのは、相手へ思考を投げ返している
- 相手の内部にしかない情報（経験、痛み、優先順位、好み、制約）: 相手から引き出す。引き出さずに推論で埋めるのは、相手の答えを自分で書いたことにしている

どちらの失敗も「その情報を誰が持っているか」を確かめずに動いたことが根である。片方だけを守ると、もう片方へ倒れる。

**## 外部にある情報を、自分で取りに行かずに問わない**

テーマ・情報が少しでも与えられた状態で「どうお考えですか？」と問うことは禁止。思考フォーマットは[考え始め](./starting_to_think.md)（事象→原因→提案→検証）を使う。

やってしまいがちな行動:
- 論点が与えられた瞬間に「〜についてどうお考えですか？」と返す
- 選択肢を列挙して「どれが良いですか？」と問う（自分の見解なし）
- 提案を出した後、提案だけを弄り続ける（前段の診断が浅いまま）
- 各段階を 1 行で済ませ、「考えた形跡」だけ見せて中身を省く

それをやると何が起きるか:
- ユーザーが Claude に思考を任せたいのに、逆にユーザーが考えさせられる
- ユーザーの初見コメントが「Claude の初案」になってしまい、議論が浅くなる
- 提案の質は診断の鋭さで決まるため、診断が浅いまま提案を弄っても根本原因が残る

[考え始め](./starting_to_think.md) のフォーマットで思考した結果を、繰り返しの過程ごとユーザーに渡す。ユーザーへの問いは「自分では〜と考えたが、この認識で合っているか？」という確認の形にする。

**## 相手の内部にしかない情報を、推論で埋めない**

相手の経験、痛み、優先順位、好み、制約は、外部のどこを読んでも出てこない。これらを推論で埋めると、埋めた内容が相手の答えとして扱われ、その上に下位の判断が積み上がる。後で相手の実際の答えが出たとき、積み上げた下位が全部崩れる。

推論で埋めやすいのは、**その空白を埋めないと次へ進めないとき**である。相手に問えば待ちが発生するが、自分で埋めれば進める。この「進める」が判断を歪める。

やってしまいがちな行動:
- 相手しか持たない前提を仮置きし、その上に具体案を書く。仮置きしたことは明示するが、合意は取らない
- 自分の推論で埋めた内容を、確定した前提として扱って下位を書く
- 相手が答えられないレイヤの質問を出し、答えが返らないまま同じ質問を繰り返す
- 相手が答えやすい形に整えることより、自分が次へ進めることを優先する

それをやると何が起きるか:
- 相手の答えが出た時点で、その上に積んだ判断が全部やり直しになる。推論が当たっていた場合は何も起きないため、外れたときだけコストが出る
- 「仮置きだと明示した」ことが免罪符になり、仮置きの上に確定的な下位が積まれる
- 答えられない質問を繰り返すと、相手は「この人は前提を理解していない」と判断し、説明のコストを負う

正しい進め方は、埋める前に「この情報は外部のどこかにあるか」と問うことである。無いなら相手から引き出す。引き出すまでは、その空白を推論で埋めず未決として残す。

- 「自分の推論で埋めた内容を、合意されたものとして下位の前提にしていないか？」

#### 提案背景

##### 起点

`task-design` skill へ二つの失敗形を組み込む作業の設計中、`think_standards/` の既存fileを調査した。`receiving_feedback.md` の主軸「自分で考えてから問う」が、今回の知見「相手しか持たない情報を自分の推論で埋めない」と一見矛盾することが分かった。

観測された失敗の原文は次である。

> 決して、フォーマットが決めやすいから飛びつかないで（プロジェクト名も同様）、やることやwhy、whatが合意できて初めてhowが話せるという土壌を忘れないでね

ユーザーから示された一般則は次である。

> ある物事を決めるのに、それを答えられる土壌が揃って初めてお互い自明な答えを自然合意できる。
> その土壌はwhyから始めてやっとhowが語れる土壌となる。
> 今回みたいにwhyレイヤと合意してない中でhowレイヤの答えを求められると性急に答えを急ぐコンサルに感じる。インタビュイーが答えられる量もそんな多くないから、その人との合意レイヤでその人が答えるのに急さない質問をする必要がある。
> task-designもそうだけど、think-throughにも入るものだな。ディープダイブというよりディープインタビューか。ディープって言葉もいらないかな

##### この論点を先に扱う理由

`think-through` は毎ターン適用される。`receiving_feedback.md` と矛盾する内容を `task-design` 側へ書くと、同じagentが両方を読む状態になる。したがって、置き場所の分担を決める前にこの関係を確定させる必要がある。

##### 二案が満たすべき条件

`think_standards/core.md` の「既存記述と競合する修正の扱い方」は次を定める。

> - 競合しない（追加・補完）→ 追記する
> - 競合する（既存の方針・構造と矛盾が生じる）→ 競合する節・ブロック全体を「変更後の前提」で再構築した案を提示して合意を得る
>
> やってしまいがちな行動: 競合しているのに既存記述を残し、「補足」「例外」「ただし書き」として追記する

したがって「競合しているか」の判定が案の選択を決める。

assistantの判定は「競合している」である。根拠は、**観測された失敗が主軸に違反していない**ことである。assistantは自分で考えてからWHYを書いており、「どうお考えですか？」とは問っていない。主軸を守った結果として失敗が起きている。これは主軸の射程が足りていないことを意味し、単なる未記載ではない。

主軸を守って失敗できるなら、補助節を足しても同じことが起きる。主軸を読んだ読み手は「守った」と判定して補助へ到達しない。これが案Aを推す理由である。

##### 主軸の文言について

「問うか自分で埋めるかは、情報の持ち主で決まる」とした。候補として「情報のsourceを確かめてから動く」も検討したが、「動く」が何を指すか曖昧であり、この場面で分岐する行動（問う／自分で埋める）を名指していない。持ち主という語を使うのは、外部と相手の内部という二つの所在を一語で対比できるためである。

#### 提案0へのフィードバック

**結果:** 案Aを採用

> A

案Aの主軸文言、既存本文を前半側の節として保持する構成、後半側の新設、波及するfileの範囲がそのまま受け入れられた。競合判定（主軸を守った結果として失敗が起きているため、単なる未記載ではなく競合である）への異論はなかった。

### 決定

`receiving_feedback.md` の主軸を「問うか自分で埋めるかは、情報の持ち主で決まる」へ置き換える。

- 埋めるべき空白を自分で埋めるか相手へ問うかは、その情報を誰が持っているかで決まる
- 外部にある情報（既存code、既存docs、標準、論理的帰結）は自分で取りに行く。既存本文「自分で考えてから問う」はこちら側であり、本文を変えずに節として保持する
- 相手の内部にしかない情報（経験、痛み、優先順位、好み、制約）は相手から引き出す。推論で埋めない。この側を新設する
- 推論で埋めやすいのは、その空白を埋めないと次へ進めないときである。「進める」ことが判断を歪める点を帰結として明記する

`think_standards/core.md` の競合ルールに照らして「競合している」と判定した。根拠は、観測された失敗が主軸に違反していないことである。主軸を守った結果として失敗が起きるなら、主軸の射程が足りていない。補助節として足すと、主軸を読んで満足した読み手が補助へ到達せず、同じ失敗が再発する。

波及として `think_standards/README.md` の収録一覧の一行説明を新しい主軸へ合わせる。`task-design/SKILL.md` `3-6` への追加シグナルの要否は、この論点では決めず別論点で判定する。

#### 提案背景

##### 判定の対象になった既存記述

`building_a_prototype.md` の `## 単位を決めることと、選び方を決めることは別` は次を持つ。

> 最小単位の定義（1 件を何とするか）と、複数を束ねる単位の定義（何を 1 ブロックとするか）は別である。
> 前者が決まっていると、後者もそれで決まったように錯覚する。

そして次の現物を持つ。

> ケースの最小単位を「1 つの API の 1 つのレスポンスパターン」と定義した作業で、
> 複数ケースを束ねる単位も API だと 3 回続けて提案した。
> 破綻したのは、データ状態が API に閉じないからだった。
> ある状態を 1 回作れば、一覧の API にも詳細の API にも同時に現れる。
> API を単位にすると、同じ状態を作る手順が複数の定義へ重複する。
> 束ねる単位は状態であって、API ではなかった。

##### 重複しているか

**記述のレベルでは重複しない。場面が違う。** `building_a_prototype.md` は「叩き台を選ぶ」場面であり、今回は「対象を分ける」場面である。

**ただし、上に引いた現物は今回の失敗2と同型である。** 「API で束ねられる」という仮定を検証せずに束ね、データ状態が API に閉じないため破綻した。今回の「上流と下流に切れる」という仮定を検証せずに切り、相互に判断材料を供給し合うため切れなかったのと同じ形である。

この同型性が案Aを支える。`writing_abstraction.md` は、抽象を書くとき「今の文脈を完全に離れた別ドメインの具体例をもう一つ書く」ことを求める。今回の原則は、設計対象の分割（今の文脈）と、API 移行作業での束ね単位（別ドメイン）という二つの具体例を持つ。直前の命名標準の作業で `think_standards/` への昇格を見送った理由はこの条件を満たさないことだったが、今回は満たす。

##### 案Cを推さない理由

`building_a_prototype.md` は前日に追加されたfileであり、file名が約束する範囲は「叩き台を作る」である。射程を「構造を仮定する」へ広げると、`content_density.md` が扱う射程の問題の逆（章名より中身が広い状態）になる。読み手は叩き台を作る場面でこのfileを引くため、分割一般の記述がそこにあることを想起できない。

##### 案Bを推さない理由

今回の失敗2は設計タスクに限らない。実装中に処理を分ける、議論で論点を分ける、作業を工程へ切る — どれも同じ動機が働く。`task-design` に閉じると、設計以外の場面で発火しない。

一方で、`task-design/SKILL.md` 側にも設計場面に固有の現れ方（`3-5` の段階分割との関係）が残るため、案Aを採っても `task-design` 側への追加は別途必要になる。案Aと案Bは排他ではなく、案Aは「原則の正本をどこに置くか」を決める。

##### file名について

`structuring_a_subject.md` とした。命名標準の宣言性（outcome を名指す）を当てると、このジョブの outcome は「与えた構造が対象の実際の構造に沿っている状態」である。`dividing_and_grouping.md` は手段の羅列であり、分割と統合という二つの手段が変わると名前も変わる。`structuring` は両方を覆い、手段が変わっても名前が変わらない。

同階層の足並みは動名詞形（`starting_to_think`、`advancing_discussion`、`building_a_prototype`）であり、`structuring_a_subject` はこれに沿う。

>
