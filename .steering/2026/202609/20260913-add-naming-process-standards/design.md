# Design: 命名プロセスの手段集と逆翻訳レビューと宣言性の理論を組み込む

## 元の依頼内容

`tumeda-dev` pluginへ、命名プロセスの手段集と、逆翻訳レビューという評価手法と、宣言性の理論を組み込む。

利用先repositoryでのsteering作業中に、リポジトリ名・ディレクトリ名・ファイル名を決める議論が発生し、assistantの提案が繰り返し却下された。その過程で、命名が詰まったときに引ける手段と、命名案を評価する手法と、宣言性とは何かという理論が得られた。これらがpluginに無かったために、同じ失敗を13イテレーション繰り返した。

議論ログ全文は `naming-discussion-full.local.md`（2751行）が持つ。利用先repository固有の情報は `migration.md` に従って総称へ置換済みである。

---

## TL;DR

既存の `naming/` は「どういう名前が良いか」の判断基準を持つが、「良い名前へどう辿り着くか」を持たない。そのため命名が詰まったとき、assistantは場当たりに案を出しては落とすことを繰り返し、13イテレーションを要した。

このsteeringは、命名が詰まったときに引ける手段集と、命名案を評価する逆翻訳レビューと、宣言性とは何かの理論を追加する。終了時には、同じ状況でassistantが引ける手段が文書として存在し、どの手段がどういう場面で有効かをメタ情報から選べる状態になる。

## 完成後の姿

### documentationによって成立する知識体系

#### 形式知化する対象

**暗黙知・散在知識・pain**

既存の `naming/core.md` は「初見でも自明にわかる名前にする」「手続き的な how でなく宣言的な what / why を表す」という判断基準を持つ。しかし次が欠けていた。

- その基準を満たす名前へ**どう辿り着くか**の手段。基準を読んでも、案が全部落ちたときに次に何をすればよいかが分からない
- 案を**どう評価するか**の手法。「初見でも自明か」を判定する具体的な方法がない
- 「宣言的とは何か」の**定義**。`core.md` は宣言的 what / why を表せと言うが、何をもって宣言的とするかを定義していない

この欠落により、実際の議論で次が起きた。語数を2〜3語に自分で制約してそこから出られなくなる。予約語と重なった時点で案ごと落とし、構造が良い案を取りこぼす。レビュー結果を方向性の抽出へ回さず、残った候補の中の相対優位を出し続ける。100点基準で65点の案を落とし、重箱の隅の指摘が並ぶ。手続き的な名前を出しては却下される。

**再利用可能な原則へ引き上げたもの**

四つに分けて記述した。それぞれの置き場所は下記「知識構造」に示す。

##### 1. 宣言性の定義（`core.md` へ統合）

宣言的であることは、ジョブを「input に処理を与えて out が出る（out な状態になる）」と抽象化した上で、どれを名指すかで決まる。

out は output（そのジョブが生み出す成果物）と outcome（そのジョブを経た状態変化。なぜその output を返すのか、それによって何を得るのか、どういうゴールに至るのか、何が変わるのか、何が分かるのか）に分かれる。

優先順位は outcome、output、input、処理の順とする。判定は「手段が変わっても名前が変わらないか」で行う。

手続き的な命名を禁止する規則ではない。同列に並ぶ要素を差別化するために処理を名前へ表す場合がある。優先順位3と4は、outcome と output だけでは区別がつかないときに降りる先である。

具体例を二つ持つ。単体のジョブ（ユーザーの退会処理。`withdraw` が outcome、`create_withdrawal_record` が output、`destroy_session_and_delete_data_and_send_mail` が処理の羅列）と、判断の場が同列に並ぶケース（新規事業を検討する四つの文書。`market.md` 等が output、`is-there-a-market.md` 等が outcome）である。

output を名指すと必ず落ちるわけではない。成果物を置くだけの場所か、既に確立した名前がある場合は output でよい。差が出るのは、判断を下す場所であり、かつ既存の確立した名前がない場合である。

outcome で名付けられないと判断する前に、その判断が特定の語形の制約によるものでないかを確認する。`decided-items`（過去分詞）は決定済みだけに読めるが、`decisions`（名詞）なら進行中を含められる。

##### 2. 名前空間に関する二つの追加（`core.md` へ統合）

**名前空間が同じで意味が一致するなら、その語を使う。** 既存節「表現が同じでも、名前空間が違えば別の意味を持つ」は、出会う場合の扱いを意味が違うときだけ書いていた。出会う場合に問うべきは「被っているか」ではなく「意味が同じか」である。意味が同じなら、その語こそが正しい名前であり、避けて別の語を作らない。避けると読み手は確立した語との差を探す。差がないのに別名を与えると、差があるという誤った示唆を与える。

**名前を単独で評価しない。** 親がある場合は `親/自分` の形で読み、同列に並ぶ要素を列挙して抽象度と表記が揃うかを確認する。この原則は `file.md` と `method.md` が対象種別ごとに持つ観点を、対象種別を問わない形へ引き上げたものである。

##### 3. 逆翻訳（`reverse_translation.md`）

`core.md` の「初見でも自明にわかる名前にする」を検算する手段。初見の人がその名前を見たとき、中に何が入っていて何をする場所だと想像するかを書き出し、実態と照合する。

語義の言い換えと区別する。語義は名前だけから導けるが、逆翻訳は「予想」と「実態」の二つを並べて初めて成立する。

名前空間の中で読む。二つの名前を並べたときに構造が読めることを根拠にしない。それは構造を既に知っている人の読み方であり、初見の人はそれぞれを単独で読む。

書き出した結果の判定と記述は `review.md` が持つ。

##### 4. レビューの書き方と判定基準（`review.md`）

観点の中身は持たない。`core.md` を常に当て、他は対象と場面に応じて見る、という当て方だけを持つ。中身を写すと二重管理になる。

記述形式として二つを要求する。一言コメントで済ませず、良い点と足りない点を分けて段落で書く。点数のグラデーションを出す。一言コメントは減点法になり、どう直せばよいかを含まない。グラデーションが見えないと、残った候補の中の相対優位を出して終わる。

判定基準として、誤解の方向で判定する。完璧に伝わることを求めず、方向が同じ誤解は許容し、方向が違う誤解（読み手が別のドメインの話だと受け取る）だけを落とす。

評価基準を到達可能な水準へ合わせる。粒度が上がるほど完璧な含意の難易度は上がる。1〜2語で決まるのはユビキタス言語が既にあるからであり、新しい概念には短い語がない。長さを理由に落とさない。

レビュー結果を方向性の抽出へ回す。落ちた理由をまとめ、通る方向性を帰納的に抽出し、その方向で案を出し直す。

##### 5. 索引と、他fileに属さない手段（`what_to_try.md`）

状態から引くものを引く索引と、他のどのfileにも属さない四つの手段を持つ。

索引は状態・引くもの・手間の三列を持つ。他fileが本体を持つものは参照だけを書く。

**手間を持つのは、毎回通す手順ではないためである。** 使わずに良い名前ができるなら、それでよい。引くかどうかは、得られるものと手間のトレードオフで決める。命名の機会は多く、すべての場面で全部を通すことはできない。

四つの手段は、実態を一文で説明する、役割の言語化が中身を覆っているか確認する、予約語との衝突を解く、語数を上げる、である。いずれも判断基準でも評価手法でもレビューの書き方でもないため、他fileへ置けない。

#### 読者と成立させる判断

| 読者 | 利用場面 | 再調査せず可能になる判断・action | 入口 |
| --- | --- | --- | --- |
| assistant（`task-design` の設計前調査を通る） | 命名が必要になったとき | 何をもって宣言的とするか、名前空間が同じで意味が一致する場合にどうするか、名前を単独で評価しないこと | `naming/core.md` |
| assistant（行き詰まったとき、または名前をより良くしたいとき） | 案が出ない、偏る、予約語と衝突する、短い案が伝わらない | 状態から引くものを選び、手間とトレードオフで採用するかを決める | `naming/what_to_try.md` |
| assistant（案を評価するとき） | 案が出たが良し悪しを判定できない | 初見の人が何を想像するかを書き出し、実態と照合する | `naming/reverse_translation.md` |
| assistant（レビューを書くとき） | レビューが重箱の隅になる、相対優位で選んでしまう | 段落で書く、グラデーションを出す、誤解の方向で判定する、方向性の抽出へ回す | `naming/review.md` |

#### 知識構造

```text
docs/development_standards/naming/
├── README.md                 # 二つの軸（判断基準 vs 手段、対象を問わない vs 対象種別ごと）と守備範囲
├── core.md                   # 判断基準（対象を問わない）
├── file.md                   # 判断基準（ファイル名）
├── method.md                 # 判断基準（メソッド名）
├── what_to_try.md            # 手段（索引＋他fileに属さない四つ）
├── reverse_translation.md    # 手段（検算）
└── review.md                 # 手段（レビューの書き方と判定基準）
```

判断基準と手段を分ける軸を `README.md` へ追加した。判断の問いは「この内容は、名前の良し悪しを判定するものか。それとも良い名前へ辿り着くための行動か」である。

各fileは自分が本体を持つものだけを書き、他fileの内容を写さない。`what_to_try.md` の索引は参照だけを持ち、`review.md` の観点の当て方も参照だけを持つ。

#### 規範の根拠と適用境界

- **MUST**: `core.md` の判断基準は、名前を付けるあらゆる場面で守る（既存の位置づけを変更しない）
- **SHOULD**: `review.md` の記述形式は、命名のレビューを書くときに従う
- **MAY**: `what_to_try.md` の手段は、得られるものと手間のトレードオフで採用を決める。毎回通す手順ではない

適用対象は命名に限る。`think_standards/` へは置かない。今回得た知見は命名の文脈でしか検証されておらず、別ドメインで同じ失敗が起きることを観測していないためである。`writing_abstraction.md` が求める「今の文脈を完全に離れた別ドメインの具体例」を持たないまま思考一般の標準へ置くと、命名の文脈に縛られた抽象が思考一般の顔をして並ぶ。`think_standards/` は毎ターン適用される想定であり、影響が大きい。

将来、別の文脈で同じ失敗が観測された時点で昇格を検討する。

#### snapshotと維持規律

| 正しいsnapshot | single source of truth | 更新owner | 更新trigger | 腐敗signal・同時確認先 |
| --- | --- | --- | --- | --- |
| 判断基準と手段が分かれており、各fileが自分の本体だけを持つ | 各file | 命名の標準を変更する者 | 命名で新しい失敗パターンが観測されたとき | `what_to_try.md` の索引が指す先が存在しない、同じ内容が複数fileにある |

`development_standards/README.md` の「配下をすべて読む」契約は変更しない。契約の目的が「判定を挟まないこと」にあり、手段fileを除外すると「詰まっているか」の判定が入る。詰まっていることに気づいていない状態こそが問題である。

維持規律の記述を 11 file・約 56KB へ更新した。7 file・約 36KB からの増加である。

## 要件（Requirements）

### MUST（必達）

- 命名が詰まったときに引ける手段が、どういう場面で有効かというメタ情報とともに文書化されていること
- 逆翻転レビューの手法が、語義の言い換えと区別できる形で記述されていること
- 宣言性の定義（outcome / output / input / 処理のどれを名指すか）と、その優先順位が記述されていること
- 議論ログ全文から得た失敗の質感が、抽象化の過程で失われていないこと

### SHOULD（できれば）

- 既存 `think_standards/` との重複が解消されていること
- `naming/` の「配下をすべて読む」契約が維持されるか、維持できないなら契約自体が見直されていること

### MAY（あれば嬉しい）

- 追加後の file 数と分量で「配下をすべて読む」契約が成立するかの判定が、別のsteeringで扱われること

### 非目標

- `task-design` の失敗（WHY・WHAT未合意のままHOWへ進む、構造を単純化できると仮定する）の組み込み。これは別のsteeringで扱う
- 既存 `naming/core.md`、`file.md`、`method.md` の判断基準そのものの変更

### 受け入れ基準

- 命名が必要になった場面で、`naming/` を読んだだけで「何をもって宣言的とするか」を判定できる。`core.md` の外へ問い合わせる必要がない
- 案が全部落ちた場面で、`what_to_try.md` の索引から次に引くものを選べる。選ぶ際に手間が判断材料として得られる
- 案を評価する場面で、`reverse_translation.md` の手法と、語義の言い換えとの区別が読める
- 各fileが本体を持つ内容が一意であり、同じ内容が複数fileに書かれていない

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 手段集が手順として読まれ、毎回全部通される | `what_to_try.md` の冒頭へ「これらは毎回通す手順ではない」を明記し、索引に手間を持たせた。手間は引くかどうかの判断材料であり、手間が大きい手段は短い名前で足りる場面では引かない |
| `naming/` の読み込み量が増え、命名判断を含まないタスクの設計前調査が重くなる | 7 file・約 36KB から 11 file・約 56KB へ増えた。契約の目的が「判定を挟まないこと」にあるため例外は設けない。「読み切れるか」の判定は別のsteeringで扱う |
| 既存 `think_standards/` と重複し、どちらを読むべきか分からなくなる | 今回は命名に閉じ、`think_standards/` を変更しない。別ドメインで同じ失敗が観測された時点で昇格を検討する |
| 議論ログを抽象化する過程で、失敗の質感が失われて原則だけが残る | 各原則へ「やってしまいがちな失敗」と「判断の問い」を添えた。失敗の具体例は、議論で実際に落ちた案（`planning` と Sprint Planning の衝突、`decided-items` の語形制約など）から取った |

## テスト方針

成果物はcodeを含まないため自動テストはない。次の観点で検証する。

- 作成・更新した各fileを `document-review` skill へ通し、内容の濃さ・記法・命名の観点を当てる
- `what_to_try.md` の索引が指す先（`core.md` の節、`reverse_translation.md`、`review.md` の節）が実在することを確認する
- 同じ内容が複数fileに書かれていないことを確認する。特に `review.md` の観点の当て方と、各判断基準fileの中身
- `core.md` の第一節と最終節から新fileへの参照が張られていることを確認する

## （付録）この標準の出所

利用先repositoryでのsteering作業中に行われた命名の議論から得た。リポジトリ名、ディレクトリ名、ファイル名を決める過程で、assistantの提案が繰り返し却下され、13イテレーションを要した。

議論ログ全文（約2750行）は利用先repositoryの `.steering/` 配下が正本として持つ。このrepositoryへは、そこから抽出した原則と、原則を検知可能にする具体例だけを取り込んだ。生ログをこのrepositoryへ置かないのは、公開配布物であること、および正本が二つになることを避けるためである。

具体例の一部は議論で実際に落ちた案から取った。`planning` とスクラムイベントの衝突、`decided-items` の語形制約、`questions/` と `answers/` をペアで設計した失敗などである。
