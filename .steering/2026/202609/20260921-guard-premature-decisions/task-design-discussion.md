# 議論記録

## 論点1: 提案を出す前に何を確かめるか

<!-- この論点は当初「段をどこが所有するか」という how を問う形で開始した。イテレーション0 の feedback により、how より先に what を決める必要があると判明したため、タイトルを現在の decision 範囲へ合わせた。イテレーション0 の履歴は当時の判断対象として残す。 -->

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: owner を決める

#### 提案0

三案から選ぶ。

##### a. `facilitate-discussion` の提案保存 gate へ置く

既存の不変条件が持つ「提案を保存する前に、その提案が含む decision を数える」の隣へ、判断材料を確かめる問いを足す。

```text
facilitate-discussion の不変条件
├── ユーザーへ合意を求める前に、proposal・提案背景・空のfeedback見出しを保存する
├── 提案を保存する前に、その提案が含むdecisionを数える        ← 既存の gate
└── 提案を保存する前に、判断材料が揃っているかを確かめる        ← 足す
```

`think_standards` は変えない。`task-design` Step 3 も変えない。

##### b. `think_standards/presenting_options.md` へ補助を足す

「選択肢を提示する」場面の補助として、既存の「選択肢に畳めたことは、議論が不要になったことを意味しない」の隣へ置く。

```text
presenting_options.md
├── 主軸: a/b/c または 1/2/3 で答えられる形式
├── 補助: 選択肢に畳めたことは、議論が不要になったことを意味しない  ← 既存
└── 補助: 畳む前に、判断材料が揃っているかを確かめる               ← 足す
```

`facilitate-discussion` と `task-design` は変えない。

##### c. `think_standards` を正本にし、`facilitate-discussion` から参照する

b の補助を正本として置き、a の位置には「この判断は `presenting_options.md` が持つ」という参照だけを置く。

**推す案は a。**

#### 提案背景

**この論点が扱う範囲。** 親 phase の DoD は「段の owner が一つに決まり、対象 file へ反映されている」を含む。他の三つの未決事項（既存 2 file との関係、併合提案の扱い、`仮決定`・`再開条件` への接続）は、この decision に従属する。

**調査で確定した事実。**

第一に、**`think_standards` は場面判定を挟む。** `think-through` の hook が毎ターン注入するのは短い要約（「唯々諾々禁止 / 修正前合意 / 事象→原因→提案→検証 / 上位から再帰 / 抽象と具体ワンショット / 型更新前に今のファイルで合意 / エラー消す前に原因特定 / 工程の切れ目で ready 再評価」）だけであり、`think_standards` 本体ではない。本体の指示は「該当する場面を判定し、その場面の file を読む」である。判定を誤れば、その file は読まれない。

第二に、**`facilitate-discussion` は既に同じ位置へ gate を持つ。** 不変条件のひとつが「提案を保存する前に、その提案が含む decision を数える。数え方は、ユーザーが『ここは良いがここは違う』と言える箇所がいくつあるかである」と定めている。手順に埋め込まれた gate であり、提案を保存する限り必ず通る。

第三に、**`think_standards` の維持規律は場面駆動モデルを崩さないことを求める。** `evolution_policy.md` は「各場面の主軸は 1 個に絞る」「削除より再分類」「補助節の追記」は変えてよいと定める。新しい場面 file を立てるより、既存場面へ補助を足す方が規律に沿う。今回の内容は「選択肢を提示する」場面の直前にあたるため、`presenting_options.md` が候補になる。

**a を推す理由。**

既存 2 file が発火しなかった原因は、場面が合っていなかったことにある。`choosing_between_options.md` は「選べない」と感じた場面で発火し、今回の誤りは「選べた」と感じた場面で起きた。`presenting_options.md` の補助は畳んだ後の記録判断に効き、畳む前には効かない。

ここで b を採ると、**同じ構造の risk を負う。** 場面判定が正しく働けば発火するが、働かなければ発火しない。そして「判断材料が揃っていない」ことに気づいていない agent は、その場面を「選択肢を提示する場面」と正しく判定できたとしても、`presenting_options.md` を引く動機を持たない。自信を持っているからである。

a は場面判定を挟まない。提案を discussion file へ保存する手順の中に gate があり、保存する限り必ず通る。既存の decision を数える gate と並ぶため、「保存前に二つ確かめる」という形で読める。

**併合提案（`task-design` Step 3）が a で覆えるか。**

覆える。Step 3 は「不確実性を選ぶ → 解消手段を選ぶ → 実行する」の順序を持ち、解消手段に discussion を選べば `facilitate-discussion` が起動する。そこで提案を保存する際に a の gate が発火する。

併合提案が求めた「1 と 2 の間に判定を置く」形とは位置が違うが、結果として止まる場所は同じである。ディレクトリ構造を 3 案提示した実例では、Step 3 の 1 で対象を選び、discussion を開始し、提案0 を作る段で「全容が見えていない」と判定できる。discussion を開始したコスト自体は発生するが、材料を集めることは discussion の中でもできる。

解消手段に「調査」または「技術検証実装」を選んだ場合は `facilitate-discussion` を通らないが、その経路では提案を出さないため今回の誤りは起きない。

**c を採らない理由。** 正本を `think_standards` へ置き `facilitate-discussion` から参照する形は、「同じ判断を複数の正本が持たない」という親 design の方針は満たす。しかし読み手にとっては、gate の位置で参照を辿って別 file を読む手順が増える。`facilitate-discussion` の既存 gate（decision を数える）は判定内容をその場に書いており、片方だけ参照にすると非対称になる。

**a を採った場合に残るもの。** `think_standards` は変わらないため、discussion を使わない場面（たとえば chat だけで方向性を相談する場面）では発火しない。この範囲を許容するかは、a を選ぶかどうかの判断に含まれる。

#### 提案0へのフィードバック

**結果:** how を先に問うた誤り。what が飛ばされているという指摘。

> というかこの話も同じ構造。howの前にwhat。失敗した時、何が問題だったのか、どこでどうすればよかったのか。それが振り返れて初めてそれを効かせるのにどうすればいいかわかる。提案を出す時、裏ではwhy,what,howの設計,howの順で下支えするものが決まっているときに初めて上澄みが提案できる。なんだったら、それぞれの選択肢に決めるときに何を大事にするかを翻って聞くこともできる。選択肢を出している時、なぜその提案をしているのかをwhyからそのレイヤまで引いて説明できないなら、立ち戻らなければならない

提案0 は「どこへ置くか」という how を三案で問うた。しかし親 phase の DoD は「段が発火する条件と、発火したときに何を確かめるかが具体的に書かれている。原則名だけを置いていない」を含んでおり、**何を確かめるかが決まらなければ置き場も決まらない。** 確かめる内容が「提案が依拠する前提の列挙」なら提案を書く手順の中が適切であり、「今決める時期か」なら不確実性を選んだ直後が適切になる。位置は内容に従属する。

加えて、提案0 は失敗の分析を飛ばしていた。実例を「判断材料が揃う前に決めた」と一語で括り、それぞれで何が問題だったか、どこでどうすればよかったかを分けていない。分析がないため、確かめる内容を導けていなかった。

### イテレーション1: 失敗を分析し、何を確かめるかを決める

#### 提案1

観測された失敗 6 件を、それぞれ「何が問題だったか」「どこでどうすればよかったか」へ分解する。

| # | 何が起きたか | 何が問題だったか | どこでどうすればよかったか |

| 1 | 事実を一つ見つけた時点で三案へ畳んだ（利用先の論点3） | その三案が依拠する前提を疑わなかった | 三案を作る前に「この三案は何を前提にしているか」を問う |
| 2 | 全容が見えていない段階で器の完成形を 3 案提示した（ディレクトリ構造） | 中身が出ていないのに器を確定させようとした | 案を作る前に「この判断は今決める時期か」を問う |

5 と 6 は個別対処が済んでいる。残る 1〜4 から、確かめるべきことを導く。

##### 確かめること

**主軸。この提案は、why からこのレイヤまで引いて説明できるか。**

1〜4 はすべてこの問いで捕まる。

- 1 と 4 は、前提が確定していないため why から引けない。前提が未確定なら、そこから何も導けない
- 2 は、what（中身に何が入るか）が確定していないのに how（器の形）を決めている。レイヤを飛ばしている
- 3 は、why からではなく既存成果物から導いている。引いてくる出発点が違う

**補助。主軸が抽象で発火しないときに当てる三つ。**

- この提案が依拠する前提は確定しているか（1・4 の形）
- この判断は今決める時期か。材料を集める段階と決める段階を区別しているか（2 の形）
- この案をどこから導いたか。既存成果物からの演繹だけになっていないか（3 の形）

##### 選択肢を出すときに併せて行うこと

提案を出す側は、**その選択肢を選ぶときに何を大事にするかを問うてもよい。** 判断基準を先に共有すれば、選択肢の評価軸が揃う。

提案0 はこれを行わなかった。三案を並べ「a を推す理由」を述べたが、**何を基準に選ぶかは示していない。** 読み手は assistant の推奨を受け入れるか、自分で基準を立てるかを選ばされる。

#### 提案背景

**直前の feedback から今回満たす必要が生じた条件。**

feedback は二つの条件を課した。第一に、how より先に what を決めること。第二に、what を決める前に失敗の分析を行うこと。分析が無ければ確かめる内容を導けず、内容が無ければ置き場も決まらない。

**前の診断の何を維持し、何を置換したか。**

維持するもの: 既存 2 file が発火しなかった原因の分析（`choosing_between_options.md` は「選べない」場面、`presenting_options.md` の補助は畳んだ後に効く）。この調査結果は提案0 の背景で確定しており、置き場を決める段で再び使う。

置換するもの: 「owner をどこにするか」を最上位の問いとした構成。これを「何を確かめるか」の下位へ移す。

**この提案が扱う範囲。** 主軸と補助までを決める。置き場（どの file のどこへ書くか）は、確かめる内容が決まってから別の decision として扱う。

**主軸を抽象な一問にした理由。** 1〜4 は具体の形が違うが、いずれも「引いてくる出発点が無い、または違う」という同じ構造を持つ。補助の三つだけを並べると、四つ目の形が現れたときに捕まらない。主軸を置けば、補助に該当しない形でも「why から引けるか」で検知できる。

**補助を三つ残す理由。** 主軸は抽象であり、それだけでは「引けている」と自己判定してしまう。`writing_abstraction.md` が「抽象だけ書いていないか。具体例を添えれば、読んだ人が自分のケースで判断できるか」と定めるとおり、具体の形が要る。三つは観測された形であり、推測で足したものではない。

**判断基準を問う点を併せて置く理由。** feedback が「それぞれの選択肢に決めるときに何を大事にするかを翻って聞くこともできる」と述べた部分にあたる。これは提案を出す側の行為であり、主軸・補助と同じ場面で発火する。別の decision として切り出すと、同じ場面の指示が二箇所へ分かれる。

### イテレーション2: 主軸が why の有無だけを問う形になっている

#### 提案2

##### 現在の記述

```text
## 提案を出す前に確かめる三つ

中心の問いは一つである。**この提案は、why からこのレイヤまで引いて説明できるか。**

引けない提案は、どこかの層を飛ばしている。飛ばした層は後から必ず問われ、
そこで前提が覆れば案全体が崩れる。
```

##### 修正案

```text
## 提案を出す前に確かめる四層

提案は四層の上に乗る。

    why        なぜこれをやるか
    what       何を作るか、何を確かめるか、何が問題だったか
    how の設計  どういう性質を満たせば解けるか。案を評価する基準
    how        具体的にどうするか、どこへ置くか

中心の問いは、**いま出している層の一つ上は埋まっているか**である。

頭が詰まると how へ飛びつく。why は既に決まっているため、
「why から説明できるか」と自問しても説明できてしまい、検知が働かない。
**飛ばされるのは中間の what と how の設計であり、why ではない。**

how の設計が空のまま how を並べると、案の比較軸が定まらない。
どの案も「置ける場所」ではあるため、置けることを根拠に順に提案でき、
一つずつ否定されるまで基準が姿を現さない。
```

`やってしまいがちな行動` へ次を足す。

```text
- why が決まっているため上位は埋まっていると判断し、what と how の設計を飛ばして how の選択肢を並べる
- 案が否定されるたびに別の how を出し、否定の理由から共通の基準を取り出さない
```

#### 提案背景

**直前の feedback から今回満たす必要が生じた条件。**

> 回答は論点1の提案1へのフィードバックに書いてあるよ

提案0 への feedback にある利用者の原文が答えを持っていた。

> 提案を出す時、裏ではwhy,what,howの設計,howの順で下支えするものが決まっているときに初めて上澄みが提案できる

**四層である。** イテレーション2 の初版は三層（why / what / how）で書いており、`how の設計` を落としていた。原文を引用しながら層の数を減らしていた。

**この phase 自身が、落とした層の実例になっている。**

論点10 と論点11 で六案を出した。

```text
不変条件へ置く / 三箇所へ一文 / SKILL に新設節 / template へ / 番号なし節へ / 三箇所へ直接
```

すべて how である。why（材料が揃う前に決めない段が要る）は決まっており、what（何を確かめるか）は論点1 で決まっていた。**空だったのは how の設計、すなわち「どこに置けば発火するか」という評価基準である。**

基準を持たなかったため、どの案も「置ける場所」として提案でき、否定されるたびに別の位置を出した。基準は否定の理由から事後的に現れた。注入されるか、実手順から離れていないか、実行順序を誤読させないか。これらを先に立てていれば、六案のうち五案は出す前に落ちていた。

**修正の方向。** 層を四つ明示し、問いを「いま出している層の一つ上は埋まっているか」とする。why を主語にすると why の有無だけで通過するため、主語を「いま出している層」へ移す。

### 決定

提案を出す前に確かめることを、四層の問いと補助三つで定める。

```text
why        なぜこれをやるか
what       何を作るか、何を確かめるか、何が問題だったか
how の設計  どういう性質を満たせば解けるか。案を評価する基準
how        具体的にどうするか、どこへ置くか
```

中心の問いは「いま出している層の一つ上は埋まっているか」である。why を主語にすると、why が決まっていることだけを確認して通過できる。飛ばされるのは中間の what と how の設計であり、why ではない。

補助三つ（前提の確定 / 今決める時期か / 導出元）と「選ぶときに何を大事にするかを問う」は、イテレーション1 の decision から維持する。

### 旧決定（イテレーション1）

提案を出す前に確かめることを、主軸一つと補助三つで定める。

**主軸。この提案は、why からこのレイヤまで引いて説明できるか。**

観測された四つの失敗はすべてこの問いで捕まる。前提が確定していないため引けない形（実例1・4）、what が未確定なのに how を決めてレイヤを飛ばす形（実例2）、why ではなく既存成果物から引いて出発点が違う形（実例3）である。

**補助。主軸が抽象で発火しないときに当てる三つ。**

- この提案が依拠する前提は確定しているか
- この判断は今決める時期か。材料を集める段階と決める段階を区別しているか
- この案をどこから導いたか。既存成果物からの演繹だけになっていないか

三つは観測された形であり、推測で足したものではない。

**併せて置くもの。選択肢を出す側は、その選択肢を選ぶときに何を大事にするかを問うてよい。** 判断基準を先に共有すれば評価軸が揃う。同じ場面で発火する行為であるため、主軸・補助と同じ場所へ置く。

置き場は論点2 で決める。

## 論点2: 確かめる段をどこが所有するか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 判断基準を示したうえで owner を決める

#### 提案0

##### 先に、何を大事にして選ぶか

四つの基準を示す。**この基準そのものへの異議があれば、案の選択より先に扱う。**

| 基準 | 内容 | なぜこれを見るか |
| --- | --- | --- |
| 発火の確実性 | 場面判定を挟まず、手順として必ず通るか | 既存 2 file が発火しなかった原因が場面判定のズレだった |
| 適用範囲 | discussion を使わない場面でも効くか | 失敗の一部は discussion の外（chat での相談）でも起こりうる |
| 既存構造との整合 | `think_standards` の場面駆動モデル、`facilitate-discussion` の gate 群を崩さないか | `evolution_policy.md` が「場面駆動を崩さない」「主軸は 1 個」を求める |
| 重複の回避 | `task-design` 3-1（WHY→WHAT→HOW の順序）と同じ判断を二箇所に持たないか | 親 design の方針が「同じ判断を複数の正本が持たない」 |

##### a. `facilitate-discussion` の不変条件へ置く

既存の「提案を保存する前に、その提案が含む decision を数える」の隣へ、主軸・補助・判断基準を問う行為を足す。

| 基準 | 評価 |
| --- | --- |

## 論点9: `think_standards` 全体の命名見直しをどこで扱うか

**ステータス:** 決定

**種別:** TBDヒアリング

#### 提案0

##### 調査結果 — 場面名の形式は 5 つ混在している

```text

─────────────────────────────────────────────────────────
file 名のまま   core.md / evolution_policy.md
名詞            考え始め / 議論進行中
動詞句（行為）  抽象を書く / 既存のものを消す・残すを判断する
```

場面名の機能は「いま自分はこの場面か」を判定する入口である。判定のトリガーには二種類ある。

- **出来事**（外から何が来たか）: エラーが出た、指摘を受領した

この二分は場面の性質から来るため、両方あること自体は正しい。揺れているのは**同じ種類の中での表記**である。`考え始め`（名詞）と `抽象を書く`（動詞句）はどちらも行為トリガーだが形式が違う。`型・スキル・テンプレートを直したい` だけが願望形を採る。`core.md` と `evolution_policy.md` は場面名を持たず file 名のまま並んでいる。

この phase は統合後の file だけを扱い、全体の命名見直しは独立した phase にする。

##### b. この phase の scope を広げ、ここで全体を扱う

##### c. 今は扱わない

**推す案は a。**

**b を採らない理由。** 統合後の file 名 `making_and_choosing_options.md` と場面名 `案を作る・提示する・選ぶ` は論点6 で決定済みである。全体の命名規約を先に作るなら、その規約に照らして再評価すべき対象になる。**b を採ると論点6 が再開する。** 手戻りの大きさに対し、得られるものは「全体と同時に決められる」ことだけである。論点6 で当てた基準（`naming/core.md`）は全体見直しでも同じ基準になるため、個別に決めた結果と全体で決めた結果が食い違う確率は低い。

**c を採らない理由。** 揺れは実在し、場面判定の入口という機能に直接効く。`型・スキル・テンプレートを直したい` の願望形は、他のどの場面名とも形式が違う。利用者が許可を出した時点が、扱うべき時期として最も適している。

**a を採った場合の handoff。** 親 roadmap への phase 追加は、この子 steering の権限外である。`steering` は「roadmapのphase identity、目的、scope、scope外、DoD、依存が変わる場合は task-design の roadmap plan 構造へ戻す」と定める。この decision は提案までとし、実際の phase 追加は親 steering の task-design へ返す。
