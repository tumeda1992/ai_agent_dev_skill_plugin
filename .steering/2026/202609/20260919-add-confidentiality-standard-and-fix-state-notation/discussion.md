# 議論記録

## 論点1: 不在判定の失敗を再発防止先へ書くか

**ステータス:** 決定済み

**種別:** 再発防止 review（steering の Ready result 後の必須 gate 4-2）

### イテレーション0: 書くかどうかを決める

#### 提案0

**事後記録である。** この論点は、discussion file へ proposal を保存する前に chat で合意を求めた。通常は保存が先であり、順序を守れていない。以下は chat で実際に提示した内容と、それに対する判断の記録である。

steering の必須 gate 4-2 が定める三問を、今回の議論へ当てた結果を示す。

**1. 根本原因は何か**

「規則が存在しない」を grep のヒット 0 で判定した。今回の作業中に 2 回起きている。

- 1 回目: `facilitate-discussion` が図の記法規則を持っていないと判断した。実際は `templates/proposal-sections/process-flow.md` が持っていた。検索語を `mermaid` としたが、同 file の表記は `Mermaid` であり、case が一致せずヒットしなかった。
- 2 回目: `document-review/SKILL.md` が適用境界を持っていないと判断した。実際は「呼び出し経路」節が「docs と skill 本体の作成・更新を行った後」と定めていた。検索語を `steering`、`対象`、`境界`、`作業記録` としたが、同節はそのいずれも含まずに境界を述べていた。

**2. どの層の不足か**

process 不足である。code を読めば分かる事実でも、code を読んでも分からない設計意図でもない。調査の作法にあたる。

**3. どこに書けば次回この議論が不要になるか**

`think_standards/` に不在判定を扱う file は無い。`questioning_existing.md` は既存のものを消すか残すかの判断であり、存在するかどうかの判定ではない。候補は `starting_to_think.md` への追記になる。

**この提案の弱点**

今回の失敗は知識の欠如ではなく注意の欠如である。「語の検索は、その語を使っていない記述を捕まえない」は書かれていなくても成立する事実であり、書いても実行時に落ちる可能性が残る。

一方で `think_standards/` の既存項目にも同じ性質のものがある。「唯々諾々の禁止」「エラーは消す前に原因を特定する」は、知識としては自明でありながら実行で落ちるものを明文化している。file の性質としては合う。

#### 提案0へのフィードバック

**結果:** 見送る。

### 決定

不在判定の失敗を `think_standards/` へ書かない。

判断の根拠は、三問の 3 問目に対する答えが弱いことである。書いても次回この失敗を防げるという見込みが立たない。必須 gate 4-2 は「解決策より先に原因を特定する」と定めており、原因の特定までは行った。原因が特定できたことと、書く先が定まることは別である。

原因の記録はこの論点に残る。同じ失敗が再発した場合、ここが 2 回目の証拠になり、そのときは書く先を改めて検討する材料が増えている。
