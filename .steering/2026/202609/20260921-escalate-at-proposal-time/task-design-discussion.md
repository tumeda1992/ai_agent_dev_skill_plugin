# 議論記録

## 論点1: 遅らせる理由と、それに対する方針

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 例外の有無を決める

#### 提案0

##### 先に、何を満たせば解けるか

| 基準 | 内容 |
| --- | --- |
| 経路を塞ぐ | 後回しにする経路が残らないか |
| 既存思想との整合 | この skill が既に持つ設計思想と揃うか |
| 安全側 | 中断できない状態で強行しないか |

##### 既存の設計思想

```text
起動gate
  今いるrepositoryがplugin repositoryかどうかは、起動条件に含めない。
  その判定は起動後にこのskill自身が行う。
  判定を起動条件に混ぜると、判定を誤った経路がこのskillへ到達しなくなり、
  結局同じ事故が形を変えて再発する。起動は広く、判定は内側で行う。

plugin repositoryの判定
  Git rootが取得できない、またはこの判定だけでは確定できない場合は、
  そのまま進めず停止する。提案は現在のsessionに残したまま、
  ユーザーへplugin repositoryのpathを尋ねる。推測で判定しない。
```

**起動は広く、判定は内側で行う。** 確定できない場合は停止してユーザーへ返す。この形が既に二箇所で採られている。

##### a. 例外条件を作らない。起動は常に行い、進められない場合は起動後に停止する

```text
起動   提案が生じた時点で常に起動する。session の長さ、元 task の進捗、
       提案が複数あることを理由に遅らせない

内側   移れない事情（利用先の作業を中断できない等）がある場合は、
       起動後に停止してユーザーへ報告する。提案は現在の session に残す
```

##### b. 例外条件を列挙する（本番障害対応中、デプロイ実行中など）

##### c. 例外条件を作らず、停止もしない。必ず plugin repository へ移る

**推す案は a。**

#### 提案背景

**この論点が扱う範囲。** 親 phase の scope は「後回しを許す例外条件があるか。あるならその条件」を含む。ここが決まらないと、起動 gate へ何を書くかが決まらない。

**a を推す理由。**

既存の設計思想と揃う。この skill は「起動は広く、判定は内側で行う」を明示しており、その理由として「判定を起動条件に混ぜると、判定を誤った経路がこのskillへ到達しなくなり、結局同じ事故が形を変えて再発する」を挙げている。例外条件を起動 gate へ書くと、「今は例外に当たるか」という判定が起動の前に入る。判定を誤れば skill へ到達しない。

停止の形も既に存在する。plugin repository の判定が確定できない場合、「そのまま進めず停止する。提案は現在のsessionに残したまま、ユーザーへ尋ねる」としている。移れない事情も同じ扱いにできる。

**b を採らない理由。** 例外を列挙すると、列挙に無い事情が現れたときに「これは例外か」の判断が生じる。judgment が起動の前に入る構造そのものが、この skill が避けようとしたものである。

**c を採らない理由。** 利用先の作業を中断できない状態が実在する。本番障害の対応中に plugin repository へ移ると、対応が止まる。停止して報告する経路が要る。

**session の長さを例外にしない根拠。** 起点となった利用者の発言が明示している。

> 長くなったセッションで別トピックだけど、それでも、問題があったからescalateされているわけで、その問題をわざわざ説明しなくても同じ視点で見てる人と解決を図りたいから長くなっても同じセッションで片付ける方針にしたい

**提案が複数あることを例外にしない根拠。** 溜めた結果がこの steering である。6 件を一括で引き渡し、roadmap を作って 6 phase へ分割する作業が発生した。1 件ずつなら各件が独立した steering で完結した。

### イテレーション1: 認識合わせ

案を出さない。防ぐ対象の整理が先であり、それが決まらなければどの論点を先に扱うかも決まらない。

#### 後回しが起きる経路

```text
経路1  skill が起動タイミングを本文で縛っていない
       → assistant が「今 escalate しましょう」と提案しない

経路2  利用者が「後で」と指示する
       → assistant が従う

経路3  移れない事情がある（利用先の作業を中断できない等）
       → 強行するか、止まるか
```

#### この steering で実際に起きたのは経路2

利用者が「後でescalate」と述べ、assistant がそのまま保留した。これが 5 回繰り返され、作業中に 1 件加わって 6 件になった。

**例外条件の有無は、この経路に効かない。** 例外が無くても、利用者が「後で」と言えば後回しになる。提案0 は経路3 への対処を先に問うており、最も起きた経路を後回しにしていた。

#### 三つの経路と、親 DoD の対応

```text
経路1  起動 gate または「引き渡し後」に、提案が生じた時点で片付ける方針を明示する
       → 親DoD「起動gateまたは引き渡し後の記述に、提案が生じた時点で片付ける方針が明示されている」

経路2  溜めた場合に何が起きるかを書く
       → 親DoD「溜めた場合に何が起きるかが読み取れる」
       利用者が「後で」と言ったとき、assistant が提示できる材料になる

経路3  後回しを許す例外条件があるか決める
       → 親DoD「後回しにしてよい例外条件が決まっている。無いなら無いと書かれている」
```

**三つとも親 DoD に対応している。** どれか一つを選ぶのではなく、三つとも塞ぐ。

#### 経路2 が最も効く理由

経路1 は assistant 側の不作為であり、本文へ書けば塞がる。経路3 は判断の分岐であり、条件を決めれば塞がる。

経路2 は利用者の指示に対する応答であるため、規律だけでは塞がらない。`think_standards/core.md` は「唯々諾々の禁止」を既に持つが、この steering では発火しなかった。**発火しなかったのは、後回しにすると何が起きるかを assistant が持っていなかったためである。** 帰結が書かれていれば、「後で」と言われたときに「溜めると文脈を説明し直す作業が加わります」と提示でき、利用者が判断材料を持ったうえで決められる。

#### 確認したいこと

この整理で合っているか。合っている場合、論点を次の順序で扱う。

```text
論点2  溜めた場合に何が起きるかを、どう書くか     （経路2）
論点3  起動タイミングを、どこへどう書くか         （経路1）
論点1  後回しを許す例外条件があるか（再開）       （経路3）
```

経路2 を先に扱うのは、そこで書く帰結が、経路1 の「なぜ遅らせないか」の根拠にもなるためである。

#### 起点の発言を分解する

```text
「提案されたリポジトリのセッションで直す」          やりたいこと
「後回しにされることもおおいから」                  現状
「問題があったからescalateされているわけで」        理由
```

**目的は「提案が生じた文脈を共有したまま解決すること」である。**

#### 文脈の共有が失われる形

```text
後回し        同じ session 内でも、時間が経てば何が問題だったかを説明し直すことになる
session跨ぎ   新しい session では context が空になる。記録から再構成する
一括引き渡し  複数の提案が絡み、個々の文脈が薄まる
```

三つとも「説明し直す作業が発生する」点で同じである。後回しはそのうちの一つにすぎない。

#### この steering で実際に失われたもの

6 件を一括で引き渡した結果、次が起きた。

```text
引き渡し時    各提案の根拠を discussion から再構成した。
              記録は残っていたが、なぜその提案に至ったかの温度が落ちた
roadmap作成   互いに独立した 6 つの問いを同時に扱うため、
              phase 分割の設計が必要になった
phase実行時   各 phase で「何が問題だったか」を design へ書き直した。
              この phase の design にも「元の依頼内容」として再掲している
```

**説明し直す作業が三段階で発生した。** 提案が生じた時点で扱っていれば、いずれも不要だった。

#### 既に skill が持っているもの

```text
description   提案が生じた瞬間に起動する
引き渡す内容   提案の内容 / それが必要だと分かった具体例 / 提案の根拠
利用先へ残す   正本で扱う旨 / steering basename / 提案要旨 1 行
```

**引き渡す内容は三点に要約される。** 文脈を共有したまま扱えない場合の最善が、この要約である。要約で足りるなら後回しでも構わないが、実際には足りなかった。

#### 確認したいこと

目的を「提案が生じた文脈を共有したまま解決すること」と置く。この読解で合っているか。

合っている場合、skill へ書くべきは次の三つになる。

```text
1  いつ起動するか          提案が生じた時点。文脈が context にある間に扱う
2  なぜ遅らせないか        遅らせると、説明し直す作業が発生する。
                           引き渡す内容は三点に要約されるため、文脈は要約でしか残らない
3  扱えない場合どうするか  起動したうえで停止し、提案を現在の session へ残す
```

イテレーション1 で洗った三経路（skill の不作為 / 利用者の指示 / 移れない事情）は、この三つのどこへ効くかとして整理し直せる。

### 決定（認識合わせ）

**目的は「提案が生じた文脈を共有したまま解決すること」である。** 後回しはそれを妨げる一つの形であり、防ぎたいものそのものではない。

**遅らせる理由は二つある。**

```text
1  目下の課題を中断したくない        正当なコスト。実在する
2  記録すれば文脈も残ると思っている   誤解。引き渡し時に要約三点
                                     （提案の内容 / 具体例 / 根拠）へ落ちる
```

1 について、利用者は「長くなっても同じセッションで片付ける方針にしたい」として、中断コストを払う側へ倒す判断を既に示している。

2 はこの steering で実際に起きた。「論点にして後でescalate」「これもescalate論点だな」と、discussion へ記録する前提で保留した。記録は残ったが、引き渡し時に各提案の根拠を再構成する作業が発生し、roadmap 作成と各 phase の design で合計三段階の説明し直しが生じた。

**したがって skill へ書くのは次の三つになる。**

```text
1  いつ起動するか          提案が生じた時点
2  なぜ遅らせないか        中断コストを理由に遅らせない。
                           文脈は要約でしか残らないため、記録は代替にならない
3  扱えない場合どうするか  起動したうえで停止し、提案を現在の session へ残す
```

#### 提案背景

**直前の認識合わせから今回満たす必要が生じた条件。** 遅らせる理由二つのうち、1（中断コスト）が例外になりうるかを決める。

**新しい例外を作らない理由。**

利用者は 1 について既に判断を示している。「長くなっても同じセッションで片付ける方針にしたい」は、中断コストを払う側へ倒す判断である。中断コストを例外条件にすると、この判断を覆すことになる。

**b を採らない理由。** 「本番障害対応中か」の判定が起動の前に入る。この skill は「判定を起動条件に混ぜると、判定を誤った経路がこのskillへ到達しなくなり、結局同じ事故が形を変えて再発する。起動は広く、判定は内側で行う」を明示しており、その思想に反する。

加えて、列挙に無い事情が現れたときに「これは例外か」の判断が生じる。中断コストは常に存在するため、例外を一つでも認めると「今回もそれに近い」という拡張が起きやすい。

**c を採らない理由。** 既存の停止条件は変えないため、実質的に提案1 と同じである。ただし c は「何も書かない」形であり、方針（中断コストを理由に遅らせない）も書かないことになる。それでは遅らせる理由 1 への対処が無い。

### 決定

新しい例外条件を作らない。既存の停止条件（Git root が取得できない、plugin repository かどうかを確定できない）で足りる。

中断コストを例外にしないのは、利用者が「長くなっても同じセッションで片付ける方針にしたい」として、中断コストを払う側へ倒す判断を既に示しているためである。加えて中断コストは常に存在するため、例外を一つ認めると拡張が起きやすい。

新たに書くのは「中断コストを理由に遅らせない」という方針と、記録が文脈の代替にならない根拠である。

## 論点2: 起動を遅らせない方針を、どこへどう書くか

**ステータス:** 取下げ

**種別:** TBDヒアリング

### イテレーション0: 書き場所と文面を決める

#### 提案0

##### 調査結果 — 既に書かれているが、理由が届いていない

```text
description
  提案が生じた瞬間に起動する

目的と成果
  このskillは「提案が生じた時点で、記録を始める前にplugin repositoryへ移る」ことを徹底し、
  移設という工程自体をなくす。
  ← 理由は直前の文にある「移設は記録の採番衝突、発言原文の意図しない改変、
     利用先固有情報の混入という事故を生む」

このskillが絶対にやらないこと
  plugin repositoryかどうかの判定を保留したまま、あるいは推測だけで、
  利用先repositoryのまま議論や記録を進めない。
  ← 条件が「判定を保留したまま」。起動していなければ当たらない
```

**「記録を始める前に移る」は既にある。** 守られなかったのは、理由が移設の事故に限られているためである。この steering で行ったのは利用先の discussion へ記録することだけで、移設はしていない。採番衝突も原文改変も固有情報混入も起きないため、**自分には当てはまらないと判断できた。**

**根本は、起動しなければどの規律も当たらないことである。** 起動条件（提案が生じた）は満たしていたが、「後でescalate」という指示が起動を止めた。skill には指示を却下する記述が無い。

##### a. 起動gateへ「遅らせない」を書き、目的と成果へ理由を足す

```diff
 ## 目的と成果

 このskillが存在しない状態では、提案は生まれた場所（多くは利用先repository）で議論が進み、合意してからplugin repositoryへ手作業で移設することになる。移設は記録の採番衝突、発言原文の意図しない改変、利用先固有情報の混入という事故を生む。このskillは「提案が生じた時点で、記録を始める前にplugin repositoryへ移る」ことを徹底し、移設という工程自体をなくす。
+
+移設の事故を避けることとは別に、提案が生じた文脈を保つ目的がある。提案は、それが生じた文脈と一体で価値を持つ。後回しにすると、引き渡す時点で残るのは提案の内容・具体例・根拠の三点だけになり、なぜその提案に至ったかは要約からの再構成になる。**記録を残すことは文脈を保つことの代わりにならない。**

 ## 起動gate

 起動条件は「このpluginのskill、docs、template、scriptに対する修正提案が生じた」という観測可能な行為だけである。

+起動を遅らせない。目下の課題を中断したくないことは、遅らせる理由にならない。提案を控えて後で扱うという指示を受けた場合は、そのまま従わず、後回しにすると文脈が要約でしか残らないことを示したうえで判断を仰ぐ。
+
 - 今いるrepositoryがplugin repositoryかどうかは、起動条件に含めない。…
```

##### b. 起動gateへ理由も含めて書く

##### c. 「このskillが絶対にやらないこと」へ「起動を遅らせる」を足す

**推す案は a。**

#### 提案背景

**この論点が扱う範囲。** 論点1 で例外を作らないことが決まった。方針と理由をどこへどう書くかを決める。

**a を推す理由。**

既存の役割分担に沿う。目的と成果は「なぜこの skill が要るか」を持ち、起動 gate は「いつ起動するか」を持つ。理由を目的と成果へ、方針を起動 gate へ置けば、どちらも既存の役割の中に収まる。

理由を目的と成果へ足すのは、既存の理由（移設の事故）が「記録だけして後で運ぶ」経路を覆っていないためである。同じ場所へ並べれば、二つの理由が揃う。

起動 gate へ「指示を受けた場合の扱い」を書くのは、起動を止めたのが指示だったためである。起動条件を満たしているのに起動しない経路は、ここでしか塞げない。

**b を採らない理由。** 起動 gate が長くなる。同 gate は既に「起動は広く、判定は内側で」という原則と、起動しない二例を持つ。理由まで入れると、起動条件を読む人が理由の段落を通過することになる。

**c を採らない理由。** 「絶対にやらないこと」は起動後の行為を列挙している。起動そのものを遅らせる行為は、起動前に起きる。加えて同 section は理由を書かない形式であり、今回必要な「なぜ遅らせないか」を置けない。

**指示を却下しない理由。** 「そのまま従わず、判断を仰ぐ」としている。中断できない事情が実在する場合があり、それを skill が一律に却下すると、利用者の判断を奪う。示すべきは判断材料であって、結論ではない。

#### 提案0へのフィードバック

**結果:** 正当な理由を「理由にならない」と否定していた。

> さっきの「まず、なぜ遅らせるかわかる？ 」という回答、反語だからね。正当な理由を持って遅らせてるの

提案0 は起動gateへ「目下の課題を中断したくないことは、遅らせる理由にならない」と書いた。中断コストは正当な理由であり、否定する対象ではない。

## 論点3: 「引き渡し後」をどう直すか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 記述を決める

#### 提案0

```diff
 ## 引き渡し後

 - 利用先repository側の元taskは中断したまま残る。plugin repository側の作業が終わってから、その続きに戻る。
-- plugin repositoryで対象のskillを修正しても、それは今実行中のsessionには反映されない。skill内容はsession開始時にcacheされるため、修正後のskillで動くには新しいsessionを開始する必要がある。
-- 元taskを旧版のskillのまま続けるか、新しいsessionを開始して修正後のskillで再開するかは、ユーザーが選ぶ。このskillが代わりに決めない。
+- 修正したskillは、今実行中のsessionへは反映されない。skill内容はsession開始時にcacheされるためである。**元taskは旧版のskillのまま続ける。** 修正の効果は次のsessionから現れる。
+- session切替を促さない。切り替えると、元taskと進行中の議論の両方でcontextが失われ、何をしていたかを説明し直すところから始まる。修正後のskillで動くことより、contextを保つことを優先する。
+- 修正後のskillで直ちに動く必要がある場合だけ、利用者へ切替を提案する。必要の判断は利用者が行い、このskillが代わりに決めない。
```

#### 提案背景

**この論点が扱う範囲。** 認識合わせで問題の所在が「引き渡し後の session 切替の促し」と決まった。その記述をどう直すかを決める。

**現在の記述が切替を促す理由。**

```text
現在の二つ目   修正後のskillで動くには新しいsessionを開始する必要がある
現在の三つ目   元taskを旧版のskillのまま続けるか、新しいsessionを開始するかは、ユーザーが選ぶ
```

二つ目が「必要がある」と述べ、三つ目が選択を委ねている。順序として「必要がある」が先に来るため、assistant は切替を既定として提示しやすい。加えて、修正を行った直後は、その修正を活かしたいという動機が働く。

**直す方向。**

第一に、既定を「旧版のまま続ける」と明示する。現在は選択肢を並べるだけで既定が無い。既定が無ければ、その場の動機で決まる。

第二に、切替のコストを書く。現在は「反映されない」という事実だけがあり、切り替えた場合に何を失うかが無い。失うものが書かれていなければ、反映されないことだけが判断材料になる。

第三に、切替を提案してよい条件を限定する。「修正後のskillで直ちに動く必要がある場合」だけとし、その判断を利用者へ残す。skill が一律に禁じると、必要な場面で提案できなくなる。

**三つ目を残す理由。** 「このskillが代わりに決めない」は維持する。必要性の判断は利用者が持つ。変えるのは、既定が無い状態と、コストが書かれていない状態である。

#### 提案0へのフィードバック

**結果:** 方向は採用。ただし resume を落としていた。

> ok。あと、セッションの切り替えは言い間違えかも。セッションの新規作成を促される。セッションは切ってもresumeできるしそうすればskill変更も反映できる。だけどescalateを別セッションで立ち上げたらcontextが失われる

### イテレーション1: 新規作成と resume を分ける

#### 提案1

**三つの記述が分担するもの。**

既存記述の「修正後のskillで動くには新しいsessionを開始する必要がある」は resume を落としており、context を捨てる経路しか見えない書き方になっていた。

#### 提案背景

**この論点が扱う範囲。** 論点3 で skill の修正が決まり、実装も済んだ。親 roadmap の phase 定義が誤読に基づくため、実態と合っていない。訂正の範囲を決める。

**a を推す理由。**

`escalation-without-deferral` という identity は「後回しなしの escalate」を意味し、扱った内容（session の新規作成を避ける）と一致しない。identity は phase を指す名前であり、内容が変われば名前も変わる。

目的・scope・DoD も、すべて「後回しを防ぐ」を前提に書かれている。部分的に直しても、前提が残る。

**b を採らない理由。** identity が内容と食い違ったまま残る。roadmap を読む人は identity から phase の内容を予測するため、食い違いは誤読を招く。この phase 自身が、誤った定義から誤った設計を導いた例になっている。

**c を採らない理由。** 扱う提案（提案6）は変わらない。親 DoD coverage の対応も変わらない。phase を作り直すと、完了済みの作業を新 phase へ移す操作が必要になる。

**identity を変えることの影響。** `roadmap-design.md` は stable phase identity を求めている。ただしこれは「runtime 都合で変えない」という規律であり、設計の誤りを訂正する場合は該当しない。親 steering の task-design を再開して直す手続きになる。

**この decision は親の権限に属する。** `steering` は「roadmapのphase identity、目的、scope、scope外、DoD、依存、親DoD coverageが変わる場合は、task-designのroadmap plan構造へ戻す」と定める。この子 steering では提案までとし、適用は親 steering の task-design で行う。
