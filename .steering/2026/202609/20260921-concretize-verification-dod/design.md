# Design: 動作確認の DoD を具体で書かせる段を置く

## 元の依頼内容

利用先 repository から `escalate-plugin-skill-fix` で引き渡された提案のうち、提案5 を扱う。

動作確認の DoD が抽象的なまま tasklist へ載り、実行時に利用者から問われて初めて具体化した。

> 動作確認はreview環境に悪さをしない適当な環境変数をamplifyに入れる修正入れて、pushしたらplanが動き、workflow_dispatchでapplyしたらamplifyにその値が入ってるって確認にする？ 確認できたらその記述消すって感じで。 tasklistで動作確認が自明じゃない場合にちゃんとユーザに提案して合意するというフロー必要

利用者が具体案を出して初めて、何を変更し何を観測すれば満たすかが決まった。

## 調査で確定した事実

**template の動作確認 section が、具体を書かせない形になっている。**

```text
templates/tasklist.md の `## 動作確認`

### DoD
ユーザーが実際に機能または契約を使い、意図どおりであることを確認した。

### Tasks
- [ ] ユーザーに動作確認を依頼する
- [ ] feedbackがあれば、…facilitate-discussion を implementation_review.md へ適用し…
```

DoD は「意図どおり」で止まり、それが何かを書かせる欄が無い。Tasks も「依頼する」だけで、何を確認してもらうかが無い。**この template をそのまま埋めると、抽象的な DoD が生成される。**

**`tasklist-design.md` は動作確認の存在を求めるが、具体を求めていない。**

```text
- 自動testとscreenshotは機械的確認であり、ユーザーが実際に触る動作確認を代替しない。
  commit・push・PRより前にユーザー動作確認を必須にする。

自己レビューgate
- [ ] **commit・push・PRより前にユーザー動作確認があるか**:
      自動test・screenshotをユーザー確認の代替にしていないか。
```

どちらも「動作確認があるか」を問い、「何を観測すれば満たすか」を問わない。

**実行時の契約も具体を要求しない。**

```text
tasklist-executor   ユーザー動作確認がtasklistにある時は user_confirmation_required で停止し、
                    確認前にcommit・pushへ進まない
                    11. ユーザーに動作確認を促す（「動作を確認していただけますか？」と伝えるのみ）
```

停止して促すところまでを定め、何を促すかは tasklist に書かれた内容に委ねている。

## 失敗の分析

| 起きたこと | 何が問題だったか | どこでどうすればよかったか |
| --- | --- | --- |
| 動作確認 DoD を「意図どおりであることを確認した」のまま tasklist へ載せた | **何を観測すれば満たすかが決まっていない。** 実行時まで誰も気づかない | tasklist を作る段階で、何を変更し何を観測すれば満たすかを書く |
| 実行時に利用者から「動作確認って何をもってしたといえればいい？」と問われた | 問われるまで気づかなかった。gate が「動作確認があるか」しか問わない | 具体が書けない場合に、その場で提案して合意する段を通る |
| 利用者が具体案を出し、それを採用した | **利用者が設計を肩代わりした。** 本来は案を出して合意を得る側 | 自分から案を出し、合意を得る |

**共有されていなかった前提。** 動作確認の DoD は、他の phase の DoD と同じく「満たしたかを判定できる」必要がある。「意図どおり」は判定基準ではなく、判定を後回しにする語である。

**塞ぐ経路は一つに絞れた。** 設計時に具体で書く MUST も、決まらない場合に design へ戻る受け皿も既に存在する。発火しなかったのは、動作確認 section だけが埋めるべき内容を固定文で持っており、埋める行為が発生しなかったためである。

---

## TL;DR

動作確認の DoD は「何を変更し、何を観測できれば満たすか」で書く。書けない場合は、実行前に提案して合意する段を通る。

終了時には、抽象的な DoD がそのまま tasklist へ載る経路が塞がれている。

## 完成後の姿

### skillの役割と方針

`templates/tasklist.md` の動作確認 section が、具体を書かせる形を持つ。`tasklist-design.md` と `tasklist-executor` は変えない。

`tasklist-design.md` へ規則を足さないのは、既に「各phaseのDoDを具体で書く」MUST があり重複するためである。自己レビューgateへ項目を足さないのは、固定文が文面上 gate を満たすため同じ理由で通過するためである。**gate は書いた後の確認であり、書かせる仕組みの代わりにならない。**

`tasklist-executor` を変えないのは、Tasks に具体があれば executor が Tasks をそのまま実行するだけで具体が伝わるためである。

### workflow

**設計時に決める。** 既存の MUST と受け皿がそのまま効く。

```text
tasklist を作る時点   Tasks へ「どの操作をしてもらい、何を観測できれば満たすか」を書く
書けない場合          既存 MUST が当たる。
                      「DoDが抽象的なままreviewへ進むことを禁止する。
                        具体化できない時はdesignへ戻る」
                      design へ戻れば facilitate-discussion が走り、提案して合意する
```

新しい段は置かない。起点の失敗で利用者が具体案を出したのは、これらが発火しなかったためであり、規則が足りなかったためではない。

### documentation以外のfile deliverable

対象 file は一つ。

| file | 変わる内容 |
| --- | --- |
| `skills/task-design/templates/tasklist.md` | 動作確認 section の DoD と Tasks |

```diff
 ### DoD

-ユーザーが実際に機能または契約を使い、意図どおりであることを確認した。
+Tasks に挙げた確認をユーザーが行い、期待どおりであることを確認した。

 ### Tasks

-- [ ] ユーザーに動作確認を依頼する
+- [ ] ユーザーに動作確認を依頼する（{どの操作をしてもらい、何を観測できれば満たすか}）
```

## 要件（Requirements）

### MUST（必達）

- owner が一つに決まり、対象 file へ反映されている
- 動作確認の具体をいつ決めるかが、設計時・実行前のどちらか、または両方として確定している
- 具体が自明でない場合に何をするかが書かれている。抽象的な DoD がそのまま残る経路を塞いでいる

### SHOULD（できれば）

- 修正で増える記述を最小に留める

### MAY（あれば嬉しい）

- 利用先で実際に合意された具体案を例として使う

### 非目標

- git / GitHub の資源の対応。`branch-pr-issue-correspondence` が扱う（完了済み）
- 提案の出し方に関する 3 phase の内容

### 受け入れ基準

- `node scripts/verification/validate-plugin.mjs` が `plugin validation passed` を出力する
- この phase 完了時点で、触った skill が単独で利用可能である
- 起点となった実例以外の具体 case を二つ以上当て、設計時に書けるか実行前に提案するかが判定できることを確認する

#### 検証結果

四つの case を、変更後の placeholder `{どの操作をしてもらい、何を観測できれば満たすか}` へ当てた。

**設計時に書ける三件。**

1. **既存機能の非破壊確認。** 「一覧画面を開いたとき、既存の 3 件が従来どおり表示されること」。操作も観測も設計時に決まる。
2. **外部連携の追加。** 「同期を実行したとき、Notion 側に対象ページが作られ、再実行しても重複しないこと」。再実行時の挙動まで観測対象に含められる。
3. **起点となった実例。** 「workflow_dispatch で apply したとき、Amplify の環境変数に検証用の値が入っていること」。検証のための変更は操作の一部として現れる。

**設計時に書けない一件。**

4. **未開拓の実行基盤を伴う作業。** 外部 service へ初めて接続する phase で、何が観測できるかが実行するまで分からない場合。placeholder を埋めようとして書けないため、既存 MUST「具体化できない時はdesignへ戻る」が当たる。`tasklist-design.md` は「未開拓の実行基盤を伴う作業では、基盤を立てるphaseを最初に置き、そのphaseのDoDへ実測結果を含める。完了後は実測結果を入力として`design.md`へ戻る前提でplanを作る」を既に持つため、この case は基盤 phase として扱われる。

四件とも、placeholder を埋められるかどうかで判定できた。埋められない場合は新しい段へ行くのではなく、既存の経路（design へ戻る、基盤 phase を置く）へ接続する。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 具体を求めても「動作を確認する」程度の記述で通ってしまう | 何を変更し何を観測するかの両方を求める。片方だけでは判定できない |
| 実行前の提案の段を置くと、設計時に書けたものまで先送りされる | 新しい段を置かず、既存の「具体化できない時はdesignへ戻る」へ接続する。先送りの経路自体を作らない |
