# 議論記録

## 論点1: 動作確認の DoD が抽象のまま残る経路をどう塞ぐか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 塞ぎ方を決める

#### 提案0

##### 先に、何を満たせば解けるか

| 基準 | 内容 |
| --- | --- |
| 経路を塞ぐ | 抽象的な DoD がそのまま tasklist へ載る経路が残らないか |
| 既存との非重複 | 既にある規則と同じことを二箇所へ書かないか |
| 肩代わりの防止 | 利用者が具体案を出す形にならないか |

##### 調査結果 — 規則も受け皿も既にある。template だけが例外を作っている

```text
tasklist-design.md
  MUST: 各phaseのDoDを「ユーザーが一つの操作をした時、何を確認できるか」の形で書く
        DoDが抽象的なままreviewへ進むことを禁止する。具体化できない時はdesignへ戻る

templates/tasklist.md
  Phase 1   ### DoD  - {一つの操作として実測できる完了条件}      ← placeholder
  Phase 2   ### DoD  - {一つの操作として実測できる完了条件}      ← placeholder
  Phase 3   ### DoD  - 全testがgreen / lintにerrorがない / …      ← 内容が確定した固定文
  動作確認   ### DoD  ユーザーが実際に機能または契約を使い、        ← 埋めるべきなのに固定文
                     意図どおりであることを確認した
```

**動作確認 section だけが、埋めるべき内容を固定文で持っている。** placeholder なら埋める必要が生じ、既存の MUST が効く。固定文だと埋める必要が無く、そのまま残る。Phase 3 の固定文は内容が確定しているため問題にならないが、動作確認は phase ごとに変わる。

Tasks も同じ形である。

```text
### Tasks
- [ ] ユーザーに動作確認を依頼する        ← 何を確認してもらうかが無い
```

##### a. template の固定文を placeholder へ変える

```diff
 ## 動作確認

 ### DoD

-ユーザーが実際に機能または契約を使い、意図どおりであることを確認した。
+- {何を変更し、何を観測できれば満たすか。ユーザーが実際に操作して判定できる形で書く}

 ### Tasks

-- [ ] ユーザーに動作確認を依頼する
+- [ ] ユーザーに動作確認を依頼する（{確認してもらう操作と、観測される値や状態}）
```

##### b. `tasklist-design.md` へ動作確認 DoD 固有の規則を足す

##### c. 自己レビューgate へ項目を足す

##### d. a と c を組み合わせる

**推す案は a。**

#### 提案背景

**この論点が扱う範囲。** 親 phase の scope は「設計時に決めるか、実行前に提案して合意する段を置くか、両方か」を含む。調査の結果、設計時に決める規則も、決まらない場合の受け皿も既に存在することが分かった。したがって問いは「いつ決めるか」ではなく「既にある規則が効かなかった経路をどう塞ぐか」になる。

**既に存在するもの。**

```text
設計時に具体で書く     MUST: 各phaseのDoDを「ユーザーが一つの操作をした時、
                             何を確認できるか」の形で書く
決まらない場合の受け皿  具体化できない時はdesignへ戻る
                       （design へ戻れば facilitate-discussion が走り、提案して合意する）
```

起点となった失敗で利用者が具体案を出したのは、これらが発火しなかったためである。新しい規則を足すのではなく、発火しなかった経路を塞ぐ。

**a を推す理由。**

固定文が placeholder になれば、埋める行為が発生する。埋めようとして書けなければ、既存の MUST「DoDが抽象的なままreviewへ進むことを禁止する。具体化できない時はdesignへ戻る」が当たる。**新しい規則を足さずに、既存の規則へ接続できる。**

他の phase の DoD が placeholder であることとも揃う。動作確認だけが例外になっている状態を解消する。

**b を採らない理由。** `tasklist-design.md` には既に「各phaseのDoDを具体で書く」MUST がある。動作確認固有の規則を足すと、同じことが二箇所に書かれる。`modify_description_policy.md` が戒める「指摘された箇所ほど厚くなる」形にあたる。

**c を採らない理由。** 自己レビュー gate には既に「各phaseにDoDがあるか」「DoDが一つの操作で検証できるか」がある。固定文は文面上これらを満たすように見えるため、gate を足しても同じ理由で通過する。**gate は書いた後の確認であり、書かせる仕組みの代わりにならない。**

**d を採らない理由。** a が効けば c は不要である。a が効かない場合に c が効く見込みも薄い（上記の理由）。

**この提案が扱わないこと。** 「何を変更し、何を観測できれば満たすか」という placeholder の文言そのものが適切かは、独立して却下できる。a の方向が決まってから詰める。

#### 提案0へのフィードバック

**結果:** a を採用。

> ok

### 決定

`templates/tasklist.md` の動作確認 section が持つ固定文を placeholder へ変える。

設計時に具体で書く MUST も、決まらない場合に design へ戻る受け皿も既に存在する。発火しなかったのは、動作確認 section だけが埋めるべき内容を固定文で持っており、埋める行為が発生しなかったためである。placeholder にすれば埋める行為が生じ、書けなければ既存の MUST が当たる。

`tasklist-design.md` への規則追加と自己レビューgateへの項目追加は行わない。前者は既存 MUST との重複であり、後者は固定文が文面上 gate を満たすため同じ理由で通過する。

## 論点2: DoD の placeholder をどう書くか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 文言を決める

#### 提案0

##### 他の phase の placeholder

```text
Phase 1/2   - {一つの操作として実測できる完了条件}
Phase 3     - 全testがgreen / lintにerrorがない / screenshotで目視確認済み（内容が確定した固定文）
```

##### 起点となった実例の構造

```text
利用者が出した具体案
  review 環境に悪さをしない環境変数を一つ足す修正を入れる     ← 検証のための変更
  push したら plan が動く                                      ← 操作と観測
  workflow_dispatch で apply したら値が入っている              ← 操作と観測
  確認できたらその記述を消す                                   ← 後始末
```

##### a. `- {どの操作をしたとき、何を観測できれば満たすか}`

```text
### DoD

- {どの操作をしたとき、何を観測できれば満たすか}
```

観測できるものを書かせる。検証のための変更が要る場合は、操作の一部として現れる。

##### b. 他の phase と同じ `{一つの操作として実測できる完了条件}` に揃える

##### c. 三要素を明示する `{何を変更し、どの操作をしたとき、何を観測できれば満たすか}`

**推す案は a。**

#### 提案背景

**この論点が扱う範囲。** 論点1 で固定文を placeholder へ変えることが決まった。その文言を決める。Tasks の文言は独立して却下できるため別に扱う。

**a を推す理由。**

起点の失敗で欠けていたのは「何を観測すれば満たすか」である。「意図どおりであることを確認した」には操作も観測も無い。操作と観測の二つを求めれば、書けたかどうかを書き手自身が判定できる。

**b を採らない理由。** 「実測できる完了条件」は、動作確認 phase では「意図どおり動いた」と書いても文面上満たせる。他の phase は実装の完了条件であり、何を作ったかが自明なため「実測できる」で足りる。動作確認は利用者が何を見るかが決まっていないため、観測対象を名指しさせる必要がある。

**c を採らない理由。** 検証のための変更は常に要るわけではない。既存機能が壊れていないことを確認する場合、変更は無い。三要素を固定すると、変更が無い場合に空欄か「なし」が生じる。変更が要る場合は操作の一部として自然に現れる（「環境変数を足して push したとき」）。

**実例を当てる。**

```text
起点の実例     workflow_dispatch で apply したとき、Amplify の環境変数に
               TF_APPLY_VERIFICATION の値が入っていること
既存機能の確認  一覧画面を開いたとき、既存の 3 件が従来どおり表示されること
外部連携       同期を実行したとき、Notion 側に対象ページが作られ、
               再実行しても重複しないこと
```

三件とも操作と観測で書けた。

#### 提案0へのフィードバック

**結果:** a を採用。

> ok

### イテレーション1: 具体が Tasks へ移った前提で DoD を決め直す

#### 提案1

```diff
 ### DoD

-ユーザーが実際に機能または契約を使い、意図どおりであることを確認した。
+Tasks に挙げた確認をユーザーが行い、期待どおりであることを確認した。
```

##### 対案

- **a. 固定文をそのまま残す。** 「意図どおりであることを確認した」のまま
- **c. placeholder にして、Tasks へ書いた場合は省略できると明示する**

**推す案は上の形（b）。**

#### 提案背景

**再開させた feedback。** placeholder を Tasks へ置くことが決まり、DoD 側は任意になった。

**無効になった判断。** イテレーション0 の decision「DoD の placeholder を `- {どの操作をしたとき、何を観測できれば満たすか}` とする」を取り下げる。具体は Tasks が持つ。

**維持する判断。** 操作と観測の二つを求める形は維持する。置き場が DoD から Tasks へ移るだけである。

**既存 MUST との整合を取る必要がある。**

```text
tasklist-design.md の MUST
  各phaseのDoDを「ユーザーが一つの操作をした時、何を確認できるか」の形で書く
  DoDが抽象的なままreviewへ進むことを禁止する
```

固定文「意図どおりであることを確認した」はこの形を満たさない。動作確認 phase だけが MUST の適用外になる状態が残る。

**推す形の理由。** 「Tasks に挙げた確認をユーザーが行い、期待どおりであることを確認した」は、何を確認するかを Tasks へ委ねていることを明示する。DoD を読んだ人は Tasks を見ればよいと分かり、具体が二箇所に分かれない。MUST との関係でも、確認内容が同じ phase 内に具体として存在することが読み取れる。

**a を採らない理由。** 「意図どおり」が残る。Tasks に具体があっても、DoD 単体では何が満たされたか分からない。既存 MUST との食い違いもそのまま残る。

**c を採らない理由。** 省略可の placeholder は、省略するか書くかの判断を毎回発生させる。具体の置き場が Tasks に決まったなら、DoD 側は迷いが生じない形にする。

#### 提案1へのフィードバック

**結果:** 採用。

> ok

### 決定

DoD を「Tasks に挙げた確認をユーザーが行い、期待どおりであることを確認した。」とする。

具体は Tasks が持ち、DoD は Tasks へ委ねていることを明示する。固定文「意図どおりであることを確認した」を残すと、DoD 単体では何が満たされたか分からず、`tasklist-design.md` の MUST「各phaseのDoDを『ユーザーが一つの操作をした時、何を確認できるか』の形で書く」との食い違いも残る。

### 旧決定（イテレーション0）

DoD の placeholder を `- {どの操作をしたとき、何を観測できれば満たすか}` とする。

操作と観測の二つを求めれば、書けたかどうかを書き手自身が判定できる。三要素（変更・操作・観測）を固定しないのは、検証のための変更が常に要るわけではなく、要る場合は操作の一部として自然に現れるためである。

## 論点3: Tasks と実行時の伝え方を変えるか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 変更の要否を決める

#### 提案0

##### 現在の形

```text
templates/tasklist.md
  ### Tasks
  - [ ] ユーザーに動作確認を依頼する

tasklist-executor/SKILL.md
  11. ユーザーに動作確認を促す（「動作を確認していただけますか？」と伝えるのみ。
      次の行動は促さない）
```

##### a. どちらも変えない

DoD に操作と観測が書かれていれば、利用者は tasklist を読んで何を確認するか分かる。

##### b. Tasks へ具体を書く placeholder を足す

##### c. `tasklist-executor` が DoD を示して促すようにする

```diff
-11. ユーザーに動作確認を促す（「動作を確認していただけますか？」と伝えるのみ。次の行動は促さない）
+11. ユーザーに動作確認を促す（動作確認phaseのDoDを示し、「動作を確認していただけますか？」と伝える。
+    次の行動は促さない）
```

**推す案は a。**

#### 提案背景

**この論点が扱う範囲。** 論点1・2 で DoD の placeholder が決まった。Tasks と実行時の伝え方を変えるかを決める。

**a を推す理由。**

起点となった失敗は「DoD が抽象だった」ことであり、伝え方ではない。利用者が「動作確認って何をもってしたといえればいい？」と問うたのは、tasklist を読んでも書かれていなかったためである。DoD が具体なら、同じ問いは起きない。

親 phase の DoD は「抽象的な DoD がそのまま残る経路を塞いでいる」を求めており、伝え方は含まない。

**b を採らない理由。** DoD に書いた内容を Tasks へ再掲することになる。`modify_description_policy.md` が戒める重複にあたる。

**c を検討した理由と、採らない理由。**

`tasklist-executor` の「伝えるのみ」は「次の行動は促さない」とセットであり、急かさないことが意図である。DoD を示すことは急かすことではないため、c は既存の意図と矛盾しない。利用者が tasklist を開かずに何を確認するか分かる利点もある。

ただし親 phase の DoD に含まれず、起点の失敗の原因でもない。**この phase で扱うと、解いていない問題への対処を混ぜることになる。** 伝え方の摩擦が実際に観測されたときに、その時点で扱う。

#### 提案0へのフィードバック

**結果:** b を採用。論点2 の decision を覆す。

> あー、論点2を覆しちゃってごめん。プレースホルダーはbの通りtaskにあったほうがわかりやすい。DoDのほうがオプショナル

### 決定

placeholder は Tasks へ置く。

```diff
 ### Tasks

-- [ ] ユーザーに動作確認を依頼する
+- [ ] ユーザーに動作確認を依頼する（{どの操作をしてもらい、何を観測できれば満たすか}）
```

`tasklist-executor` は変えない。**Tasks に具体があれば、executor は Tasks をそのまま実行するだけで具体が伝わる。** 提案0 が c として検討した「executor が DoD を示す」変更は不要になる。

動作確認 phase では「やること（依頼する）」と「満たした状態（確認された）」がほぼ同じであるため、DoD へ具体を書くと繰り返しになる。何を依頼するかは Tasks が持つ。

DoD の扱いは論点2 を再開して決め直す。
