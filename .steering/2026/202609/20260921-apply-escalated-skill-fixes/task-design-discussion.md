# 議論記録

## 論点1: 引き渡された 5 件を leaf として扱うか、composite として phase 分割するか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 5 件の扱いを決める

<!-- このイテレーションは事後記録である。assistant が提案を discussion file へ保存する前に chat へ三択を出し、ユーザーの feedback を受けた。`facilitate-discussion` が定める「合意を求める前に proposal を保存する」順序を守らなかったため、確認できる履歴から再構成している。 -->

#### 提案0

引き渡された 5 件の扱いとして、次の三択を提示した。

- **a.** 5 件を 1 つの steering で扱う
- **b.** 2 つに分け、今回は A（提案1・2・3）だけを扱う。B（提案4・5）は別 steering
- **c.** roadmap（composite）にして phase 分割する

assistant は **b** を推した。根拠は次の二点。

第一に、A と B は依存しない。A は議論の作法、B は実行の契約であり、片方を先に入れても他方の設計が変わらない。

第二に、A を先にする利益がある。提案1 は `task-design` の Step 3 にも及ぶ。この steering 自身が task-design で動いているため、直せば B の steering がその改善された skill で動く。逆順にこの利益は無い。

**c を却下した。** 根拠は「5 件に共通の親 DoD が無い」「phase 間の依存も無い」の二点である。親 DoD について、「利用先から来た 5 件の提案を適用する」は提案が 5 件あるという事実の集合であって一つの目的ではない、と述べた。依存が無い phase を roadmap で束ねると、独立した 2 つの作業を無理に一つの木にすることになる、と述べた。

#### 提案背景

利用先 repository から `escalate-plugin-skill-fix` で 5 件が引き渡され、`design.md` の初稿を作った段階で、ユーザーから「これら1つのsteeringで扱う？」と scope の問いを受けた。

この問いは `design.md` の骨格合意より上位にある。leaf か composite かで design の粒度が変わり、一つの `design.md` に 5 件分の完成後の姿を収めるのか、各 phase へ独立した design を持たせるのかが決まるためである。

assistant は 5 件を性質で 2 群へ分類した。A（提案1・2・3）は `facilitate-discussion` の中核で提案の出し方を扱い、B（提案4・5）は実行フェーズの契約を扱う、という分類である。この分類を根拠に b を構成した。

#### 提案0へのフィードバック

**結果:** c を吟味対象へ戻すよう指示を受けた。加えて、A を 1 まとまりで扱えるかへの懸念が示された。

> bでもいいんだけどcも吟味対象として考えられる？ Bが別というのもいいけどそれ以上にAは触る場所が同じだけれども全部根本に関わる話を1まとまりで扱えるのかという不安

この feedback を受けて再検討した結果、**提案0 が依拠していた前提に誤りが見つかった。**

assistant は A の 3 件を「触る場所が同じ（`facilitate-discussion`）」という理由で束ねた。しかし提案1 の owner は未決であり、`think_standards` へ置く可能性が残っている。そうなれば提案1 は `facilitate-discussion` に閉じない。**owner が決まっていない段階で「同じ場所」と決めつけていた。**

c を却下した根拠のうち「phase 間の依存が無い」も、この誤った前提から導かれていた。実際には依存がある。提案1 を `facilitate-discussion` へ置くなら、提案3 の `認識合わせ` はその段の直後に来て同じ場所を触る。`think_standards` へ置くなら提案3 は `facilitate-discussion` に閉じて独立する。**提案1 の decision が提案2・3 の設計を変える。**

この誤り自体が、提案1 が扱おうとしている誤りの実例である。判断材料（提案1 の owner）が揃う前に選択肢へ畳み、その選択肢が依拠する前提を疑わなかった。

### イテレーション1: 依存関係を確認したうえで扱い方を決め直す

#### 提案1

三択の構成は維持し、**c を推す**。

##### a. leaf として 5 件を一つの design と tasklist で扱う

一つの `design.md` へ 5 件分の完成後の姿を収め、一つの `tasklist.md` を作る。

成立する条件は「一つの tasklist で scope 全体を着手可能な task、検証、ユーザー確認まで落とせる」ことである。file 数や task 数が多いだけでは composite にしない、という判定基準からは leaf が既定になる。

この案の弱点は、提案1 の decision が提案2・3 の設計を変えるという依存を、一つの design の内部で順序として扱うことになる点にある。design は完成後の姿を一つ持つため、「提案1 の結論次第で提案2・3 の記述が変わる」という状態を design 内に抱えたまま合意を進めることになる。

##### b. 2 つの独立した steering へ分け、今回は A（提案1・2・3）だけを扱う

A を今回の steering で扱い、B（提案4・5）を別 steering として後で立てる。

この案の弱点は二つある。第一に、A の内部に提案1 → 提案2・3 の依存が残るため、A を一つの design で扱う限り a と同じ問題を持つ。第二に、B をいつ扱うかが記録に残らない。別 steering として立てると決めても、その約束を保持する場所が無い。

##### c. composite として roadmap を作り、3 phase へ分割する

親 DoD を「引き渡された 5 件それぞれについて、所有する skill または docs が一つに決まり、対象 file へ反映され、同じ判断を複数の正本が持たない」とする。

phase の構成と依存は次になる。

```text
Phase 1: いつ決めてよいかの段を、どの skill / docs が持つか（提案1）
   │
   └──> Phase 2: discussion の提案・背景・iteration の形式（提案2・3）

Phase 3: 実行フェーズの契約（提案4・5）   ← Phase 1・2 に依存しない
```

- **Phase 1**: 提案1 を扱う。`facilitate-discussion` の提案保存 gate、`task-design` section 5 Step 3、`think_standards` の新しい場面 file のどこが所有するかを決め、既存の `choosing_between_options.md`・`presenting_options.md` との関係を確定する
- **Phase 2**: 提案2・3 を扱う。`提案背景` の定義と、iteration の中身を `提案N` に固定しない形式を決める。Phase 1 の owner decision を入力として受け取る
- **Phase 3**: 提案4・5 を扱う。branch・PR・issue の対応と、動作確認の具体化を、`task-design` の plan 設計・`tasklist-executor` の実行契約・`steering` の orchestration のどこが所有するかを決める

composite の判定条件との照合は次になる。

- 二つ以上の相互に区別できる子 scope: Phase 1 は思考の作法、Phase 2 は記録形式、Phase 3 は実行契約。区別できる
- 各子が親より厳密に狭い: 各 phase は 5 件のうち 1〜2 件だけを扱う
- 子全体で親 DoD を満たす: 3 phase で 5 件すべてを覆う
- 依存が DAG: Phase 1 → Phase 2 の一本だけ。Phase 3 は独立

#### 提案背景

**直前の feedback から今回満たす必要が生じた条件。**

feedback は二つの条件を課した。第一に、c を却下した根拠が誤っていたため、c を判断材料の揃った状態で再提示する必要がある。第二に、A の 3 件を 1 まとまりで扱えるかという懸念へ答える必要がある。

**前の診断の何を維持し、何を置換したか。**

維持するもの: A（議論の作法）と B（実行の契約）が性質として異なり、B が A へ依存しないという判断。これは提案0 の分類のうち正しかった部分である。

置換するもの: 「A の 3 件は触る場所が同じだから一まとまりで扱える」という前提。提案1 の owner が未決である以上この前提は立たない。代わりに、提案1 → 提案2・3 の依存を明示し、それを phase 境界の根拠に置いた。

**c を推す理由。**

第一に、feedback が示した懸念に直接答える。「A を 1 まとまりで扱えるか」への答えは「扱えない」であり、その理由は依存にある。提案1 は既存標準の盲点、`task-design` Step 3 の構造問題、別 repository から併合した提案、四つの具体例を持つ。これ単独で一つの design に値する重さがある。Phase 1 と Phase 2 を分ければ、提案1 の owner decision を確定させてから提案2・3 の設計へ入れる。

第二に、b の弱点である「B をいつ扱うかが記録に残らない」を解消する。roadmap が 3 phase すべてを保持し、status と完了日で進捗が追える。

第三に、依存が実在する。「依存が無い phase を roadmap で束ねるな」という制約は、Phase 1 → Phase 2 の依存がある以上この case には当たらない。Phase 3 が独立していることは、DAG が一本鎖でなくてよいため問題にならない。

**a を採らない理由。** 依存を design の内部に抱える。提案1 の結論が出るまで提案2・3 の完成後の姿を書けず、TBD を抱えたまま design 合意を進めることになる。

**b を採らない理由。** A の内部の依存が解消しないため、a と同じ問題を持ち続ける。加えて B の扱いが記録に残らない。

#### 提案1へのフィードバック

**結果:** phase の束ね方が文脈ではなく owner の近さに依拠している、という指摘。

> 2,3と4,5はそれぞれ別文脈じゃない？ たまたま同じところをいじるだけで

提案1 は Phase 2 を「discussion の記録形式」、Phase 3 を「実行フェーズの契約」というラベルで束ねた。しかしこのラベルは、提案2 と 3、提案4 と 5 のそれぞれに共通点を後から与えたものである。実際に共通しているのは owner 候補が重なることだけで、問いは別である。

**この誤りは提案0 と同型である。** 提案0 は「触る場所が同じ」で 3 件を束ねた。提案1 はそれを「性質が同じ」と言い換えただけで、判定の中身は変えていなかった。

加えて、**assistant は `design.md` の初稿で既に提案2 と 3 を分ける根拠を書いていた。**

> 提案2 との関係。提案2 は「提案へ流れ込んだ調査結果を、背景側へ正しく置く」修正であり、提案は出せる前提に立つ。提案3 は「そもそも提案を出せない段階がある」ことを認める修正である。同じ具体例から導かれるが、片方を採ってもう片方を却下できるため、独立した decision として分ける。

自分で書いた「独立した decision として分ける」を、phase 構成では適用しなかった。

### イテレーション2: 各提案の文脈を分けたうえで、依存の確定手段を決める

#### 提案2

**各提案を独立した phase とする。** 5 件それぞれが別の問いを持つため、5 phase になる。

| phase | 扱う提案 | この phase が答える問い |
| --- | --- | --- |
| A | 提案1 | 判断材料が揃う前に選択肢へ畳まないための段を、どの skill / docs が持つか |
| B | 提案2 | 提案自体の背景（調査結果・思考記録）をどこへ書くか |
| C | 提案3 | 提案を出せない段階の受け皿をどう作るか |
| D | 提案4 | git / GitHub の資源（branch・PR・issue）の一対一対応をどう保つか |
| E | 提案5 | 動作確認の DoD を設計時に決めるか、実行時に具体化する段を置くか |

**依存は現時点で確定できない。** 確実に言えるのは次だけである。

- D と E は、A・B・C のどの結論にも依存しない。互いにも依存しない
- A は B・C のどちらかへ影響しうるが、**向きが決まっていない**

A と B の依存の向きが決まらない理由は次にある。提案1 の owner が `facilitate-discussion` の提案保存 gate になる場合、その gate は「提案背景に判断材料が書かれているか」を見る形になりうる。その場合、提案背景の定義（提案2）が先に決まっている必要がある。逆に、提案1 が `think_standards` の思考標準として置かれるなら、提案背景の定義とは独立する。**提案1 の owner decision が出るまで、A → B なのか B → A なのか、あるいは独立なのかが決まらない。**

A と C の関係も同じ構造を持つ。提案1 が `facilitate-discussion` へ入るなら、`認識合わせ` を置く段（提案3）は提案1 の段と同じ場所に来る。`think_standards` へ入るなら C は独立する。

したがって、**依存を確定させる手段として A を最初に実行する。** A の owner decision が出た時点で、B と C の依存と実行順が確定する。D と E は A の結果を待たずに実行できる。

```text
A（提案1）
 │
 ├─> B（提案2）   A の owner decision を受けて依存と順序が確定する
 └─> C（提案3）   同上

D（提案4）   A・B・C のどれにも依存しない
E（提案5）   同上
```

roadmap 上では、A を最初の phase とし、B と C の依存は A の完了時点で確定させる。D と E は依存なしとして最初から並列に置ける。

#### 提案背景

**直前の feedback から今回満たす必要が生じた条件。**

feedback は「phase の束ね方が文脈ではなく owner の近さに依拠している」ことを指摘した。したがって、束ねる根拠を文脈へ戻す必要がある。各提案が答える問いを並べると 5 つとも異なるため、束ねる根拠が無い。5 phase が帰結になる。

**前の診断の何を維持し、何を置換したか。**

維持するもの: composite（roadmap）を採るという判断と、その根拠である「提案1 は単独で一つの design に値する重さがある」「b では B の扱いが記録に残らない」。feedback はこの部分を否定していない。

置換するもの: phase を 3 つに束ねた構成。および、その根拠であった「Phase 2 は記録形式、Phase 3 は実行契約」という分類。

**この提案で新たに扱う問題。**

提案1 を書いた時点では、依存を「A → B」と断定して DAG を描いた。feedback を受けて各提案を分けた結果、**その依存の向きが確定していないことが露呈した。** 提案1 の owner が決まるまで、提案2・3 との前後関係は決まらない。

ここで取れる形は二つある。一つは、依存の向きを今決めてしまう形。もう一つは、依存が確定していないことを roadmap の構造として認め、A を最初に実行して確定させる形である。前者は判断材料が揃う前に決めることになる。後者を採った。

これは提案1 自身が扱っている問題と同じ構造である。材料が揃っていない依存関係を、roadmap を完成させたいという理由で確定させない。

**結果:** 採用。

### イテレーション3: 依存の向きを確定させる

#### 提案3

phase 構成（一提案一 phase の 5 phase）と親 DoD は提案2 のまま維持する。**依存関係だけを確定させる。**

```text
B（提案2）──> A（提案1）──> C（提案3）

D（提案4）   独立
E（提案5）   独立
```

**B → A。** B は「提案へ至った調査結果と思考記録を `提案背景` へ書く」という定義を作る。この定義は、判断材料を確かめる段があろうとなかろうと単独で成立するため、A に依存しない。一方 A は、提案が判断できる案かを確かめる方法として「`提案背景` に調査結果が書かれているか」を使える。その形を採るなら B の定義が先に要る。したがって B を先に置く。

**A → C。** C は「提案を出せない段階の受け皿」を作る。認識合わせの記法だけを決めても、いつそこへ分岐するかが無ければ使えない。分岐の判定は A の段が持つ。記法だけを作って使用条件を欠いた状態は、roadmap-design が禁じる「後続 phase がなければ成立しない壊れた状態」にあたる。したがって A を先に置く。

**D と E は独立。** git / GitHub の資源の対応も、動作確認の DoD の具体化も、提案の出し方とは無関係に決められる。互いにも依存しない。

依存 phase の確定結果を子 task-design へ渡す形は次になる。

| 依存 | `dependency_results` として渡すもの | 受け取る子 design で解消する上位制約 | 想定範囲外だった場合 |
| --- | --- | --- | --- |
| B → A | `提案背景` の確定した定義と、それがどの file のどこに書かれたか | A の段が `提案背景` を判定材料に使えるか。使えるなら判定基準をその定義へ接続し、使えないなら別の確かめ方を設計する | B が `提案背景` を持たない形（別 file へ分離等）に着地した場合、A の判定材料の候補が変わるため、親 roadmap へ戻って A の scope を見直す |
| A → C | A の段が置かれた file と位置、および「提案を出せる状態か」の判定基準 | C が認識合わせへ分岐する条件を、A の判定基準のどの分岐へ接続するか | A が `think_standards` へ置かれ、`facilitate-discussion` の実行手順へ分岐点を持たない形に着地した場合、C は分岐条件を自前で設計する必要があるため、親 roadmap へ戻って C の scope を見直す |

#### 提案背景

**再開させた evidence。**

`roadmap-design.md` を読んだ結果、二つのことが判明した。

第一に、構造 TBD が明示的に禁止されている。「前 phase の実行結果によって後続 phase の詳細が決まる場合も、親 roadmap の構造 TBD として残さない。後続 phase の目的、scope、scope外、DoD、依存を親 roadmap で確定し、どの依存 phase の確定結果を `dependency_results` として渡すか、その結果で解消する上位制約は何か、想定範囲外なら構造変更として親へ戻る条件は何かを明記する」と定めている。提案2 の「A を実行して依存を確定させる」は、依存を構造 TBD として残す形にあたる。

第二に、依存の向きを精査したところ、**提案2 で書いた向きが逆だった。** 提案2 は A → B と書いたが、B は A に依存せず単独で成立し、A が B を判定材料として使いうる。B → A が正しい。

**無効になった判断。**

提案2 の「A と B、A と C の依存は向きが決まっていない」「A を最初に実行して確定させる」を取り下げる。向きは精査で決まり、確定させるための先行実行は不要である。

**維持する判断。**

composite を採ること、一提案一 phase の 5 phase、親 DoD、各提案が答える問いの割り当ては提案2 のまま維持する。feedback はこの部分を否定していない。

**なぜ提案2 の時点で向きを決められなかったか。**

提案2 は「A の owner が `facilitate-discussion` なら gate が `提案背景` を見るため B が先に要る。`think_standards` なら独立する」として、A の owner decision を待つ形を採った。これは A の側からだけ依存を見ていた。B の側から「B は A の結論を必要とするか」を問えば、必要としないことが分かる。**依存の向きは、両端から問わなければ決まらない。** 片側からだけ見ると「相手の結論次第」という形に見え、未確定と誤認する。

#### 提案3へのフィードバック

**結果:** 採用。

### 決定

引き渡された 5 件を composite として扱い、`roadmap.md` を作る。各提案が別の問いを持つため、**一提案一 phase の 5 phase** とする。

| phase identity | 扱う提案 | この phase が答える問い |
| --- | --- | --- |
| `proposal-decidability` | 提案1 | 判断材料が揃う前に選択肢へ畳まないための段を、どの skill / docs が持つか |
| `proposal-background-scope` | 提案2 | 提案自体の背景（調査結果・思考記録）をどこへ書くか |
| `non-proposal-iteration` | 提案3 | 提案を出せない段階の受け皿をどう作るか |
| `branch-pr-issue-correspondence` | 提案4 | git / GitHub の資源（branch・PR・issue）の一対一対応をどう保つか |
| `verification-concreteness` | 提案5 | 動作確認の DoD を設計時に決めるか、実行時に具体化する段を置くか |

親 DoD は「引き渡された 5 件それぞれについて、所有する skill または docs が一つに決まり、対象 file へ反映され、同じ判断を複数の正本が持たない」とする。

依存は次で確定する。

```text
proposal-background-scope ──> proposal-decidability ──> non-proposal-iteration

branch-pr-issue-correspondence   独立
verification-concreteness        独立
```

`proposal-background-scope` を先に置くのは、`提案背景` の定義が判断材料の gate の有無に関わらず単独で成立し、逆に gate 側が `提案背景` を判定材料として使いうるためである。`non-proposal-iteration` を後に置くのは、認識合わせの記法だけを決めても分岐条件が無ければ使えず、分岐の判定を gate が持つためである。

依存 phase の確定結果と、それを受け取る子 design で解消する上位制約、想定範囲外だった場合に親 roadmap へ戻る条件は、`roadmap.md` が構造 field として持つ。

**この論点で三度繰り返した誤りを記録する。** 提案0 は「触る場所が同じ」で 3 件を束ねた。提案1 は同じ判定を「性質が同じ」と言い換えて 5 件を 3 phase へ束ねた。提案2 は依存の向きを A の側からだけ見て「未確定」と判定した。いずれも、判断材料を揃えずに構造を確定させようとした形である。三件とも phase `proposal-decidability` が扱う誤りの具体例として使える。

## 論点2: `escalate-plugin-skill-fix` の working directory 制約を今回の scope に含めるか

**ステータス:** 決定

**種別:** TBDヒアリング

**事後記録である。** 提案と合意が chat 上で成立したため、`facilitate-discussion` の `2.3.5` に従って記録する。

### イテレーション0: scope への出入りを決める

#### 提案0

`escalate-plugin-skill-fix` は「working directory を plugin repository へ移す。切り替えだけが、これから行う作業対象を `steering` へ伝える唯一の手段である」と定めている。しかしこの引き渡しを実行した session では、shell の working directory を変更できなかった（`cd` しても利用先 repository へ reset される）。そのため絶対 path を明示する形で代替した。

この制約を roadmap の 6 番目の phase として扱うか、今回の scope から外すかを決める。

**scope から外し、非目標へ置く。**

#### 提案背景

引き渡された 5 件は、いずれも利用先 repository での実作業から見つかった skill の穴であり、`escalate-plugin-skill-fix` を通じて正式に引き渡された。一方この制約は、その引き渡しを実行する最中に assistant が踏んだものであり、出自が異なる。

外す根拠は二つある。第一に、5 件は利用先での実運用から複数の具体例を伴って上がってきたが、この制約は一度観測されただけで、再現条件（どの実行環境で working directory が固定されるか）が確認できていない。第二に、`escalate-plugin-skill-fix` は今回の引き渡し自体を完了させており、代替手段（絶対 path の明示）で機能した。phase を立てて塞ぐべき穴として扱う前に、再現性の確認が要る。

含める根拠として考えうるのは、skill が「唯一の手段」と断定している記述が実際には成立しない環境があると判明した点である。ただしこれは記述の強さの問題であり、5 件と同じ重さで扱うと roadmap の焦点がぼやける。

#### 提案0へのフィードバック

**結果:** 採用。

> ok

### 決定

`escalate-plugin-skill-fix` の working directory 制約を、この roadmap の phase に含めない。`design.md` の非目標へ「この escalate の実行中に見つかった別出自の課題であり、5 件とは扱いが異なる」として記載する。

再現条件が確認できた時点で、別の escalate または別 steering として扱う。

## 論点3: この steering 自身で踏んだ失敗から、既存 docs へ何を足すか

**ステータス:** 決定

**種別:** レビュー指摘

**事後記録である。** steering の必須 gate 4-1（`doc-enricher` を提案モードで起動）を chat 上で実行し、提案と合意が成立した。`facilitate-discussion` の `2.3.5` に従って記録する。

### イテレーション0: 既存 docs への追記候補を決める

#### 提案0

この steering の論点1 で三度踏んだ失敗（提案0 の「触る場所が同じ」、提案1 の「性質が同じ」、提案2 の「依存の向きが未確定」）から、既存 docs へ足す候補を二件に絞る。

**候補A: `think_standards/ordering_parallel_items.md` の「やってしまいがちな行動」へ追記。**

```markdown
- 依存の有無や向きを一方の事項からだけ問う。相手側へ同じ問いを当てれば決まる場合でも、「相手の結論次第」として未確定と判定する
```

**候補B: `task-design/roadmap-design.md` の自己レビュー gate へ追加。**

```markdown
- [ ] 複数の対象を一つのphaseへ束ねている場合、束ねる根拠が「答える問いが同じ」であるか。「触るfileが近い」「owner候補が重なる」で束ねていないか。同じ対象についてdesignで既に分離・結合の判断を下していれば、それを先に引いたか。
```

#### 提案背景

**既存 docs の確認で判明したこと。**

依存の向きを判定する手順は、既存標準が既に持っていた。`ordering_parallel_items.md` の「正しい判断のための問い」がそれである。

> 「この事項を今完了するために、未決事項の答えが一つでも必要か？」

この問いを両方の事項へ当てれば向きが決まる。提案背景の定義（B）へ当てれば「判断材料の gate（A）の答えは要らない」、A へ当てれば「B の答えが要る（判定材料に使うなら）」となり、B → A が確定する。assistant はこの file を読まずに依存を判定していた。

したがって候補A は原則の追加ではなく、既存原則を知らずに踏んだ失敗の具体例として添える形を採る。`doc-enricher` の抽象化ラダーが定める止まり方のうち「既存ドキュメントに同じ原則があるが、このセッション中にその原則を知らず誤った前提・提案をした場合は、既存ドキュメントの『やってしまいがちな失敗』に具体例として追記する」に該当する。

**候補B が既存と重複しない理由。**

`roadmap-design.md` の既存の禁止事項は「一つだけの子、工程数が多いだけの分割、backend / frontend 等の layer 名だけで切った分割」であり、すべて分けすぎ方向を向いている。束ねるときの根拠を問う項目が無い。

`think_standards/designing_for_variations.md` は「case 間に同じ判断が成立するからまとめているか。一つの output 方式を維持するためにまとめていないか」という近い問いを持つ。ただしあちらは「広く variation のある対象へ適用方針を作る」場面の標準であり、roadmap の構造分割とは場面が違う。

**候補B が二つの失敗を統合していること。**

提案1 の「owner 候補が重なることで束ねた」と、「`design.md` 初稿に自分で書いた『提案2 と 3 は独立した decision として分ける』を phase 構成へ適用しなかった」は、どちらも束ねる判断の根拠に関する失敗である。後者を独立した原則として立てる案は、抽象化ラダーで「自明すぎて置き場がない」に落ちたため、候補B の後半へ吸収した。

#### 提案0へのフィードバック

**結果:** 二件とも採用。

> ok

### 決定

候補A と候補B を適用した。`node scripts/verification/validate-plugin.mjs` は `plugin validation passed` を出力する。

| 対象 | 追記内容 |
| --- | --- |
| `plugins/tumeda-dev/docs/think_standards/ordering_parallel_items.md` | 「やってしまいがちな行動」へ、依存の向きを一方からだけ問う失敗を追加 |
| `plugins/tumeda-dev/skills/task-design/roadmap-design.md` | 自己レビュー gate へ、束ねる根拠を問う項目を追加 |

どちらも roadmap の 5 phase が扱う範囲とは独立しており、phase の実行を待たずに反映できる。phase `proposal-decidability` が所有するのは「判断材料が揃う前に決めない」という原則そのものであり、この二件はその周辺にある別の判断（依存の向きの判定手順、束ねる根拠の判定）を扱う。

## 論点4: escalate の起動タイミングを roadmap の phase として扱うか

**ステータス:** 決定

**種別:** TBDヒアリング

**事後記録である。** 提案と合意が chat 上で成立したため、`facilitate-discussion` の `2.3.5` に従って記録する。

### イテレーション0: 扱う場所を決める

#### 提起

利用者から次の提案があった。

> escalateスキルについて基本的に提案されたリポジトリのセッションで直す。提案したリポジトリの目下の課題解決してから、と後回しにされることもおおいから、長くなったセッションで別トピックだけど、それでも、問題があったからescalateされているわけで、その問題をわざわざ説明しなくても同じ視点で見てる人と解決を図りたいから長くなっても同じセッションで片付ける方針にしたい

扱う場所については「どこかでついでに扱うか、個別 steering にしてもどっちでもいい」として判断が委ねられた。

#### 提案0

**この roadmap の 6 番目の phase として追加する。** 別 steering にしない。

#### 提案背景

**現状の skill が何を定めているか。**

`escalate-plugin-skill-fix` の起動 gate は「このplugin のskill、docs、template、scriptに対する修正提案が生じた」という行為だけを条件にしており、**いつ起動するかを縛っていない**。「引き渡し後」の節も、元 task の中断と再開、skill cache の扱い、旧版で続けるか新 session かの選択を定めるだけで、起動タイミングには触れていない。この空白が「目下の課題を片付けてから」という後回しを許している。

**後回しの帰結が、この steering 自身で観測できる。**

利用先 repository で論点28 を立てたのは設計中、実際に escalate したのは実装完了後だった。その間に論点29・30 が追加され、実装中にさらに提案4・5 が出た。**5 件が溜まった結果、roadmap を要するほど大きな引き渡しになった。** 1 件ずつ escalate していれば、各々は小さい leaf steering で済んだ可能性が高い。

説明コストも上がる。5 件を引き渡す際、各提案の背景・実例・ユーザー原文を長文で再構成する必要があった。提案が生まれた直後であれば、同じ session 内の文脈で足りる。利用者が述べた「問題をわざわざ説明しなくても同じ視点で見てる人と解決を図りたい」はこの点を指している。

**既存の思想との整合。**

`steering` の必須 gate 4-2 は「設計議論の context が最も熱い時点を逃すと『なぜ変えるか』が薄れ、更新品質が下がる」として、再発防止の更新提案を実装 task へ先送りしないことを定めている。escalate はこの思想が及ぶ範囲にありながら、skill 側に同じ記述を持っていない。

**別 steering にしない理由。**

第一に、他の 5 件と出自が同じである。いずれも利用先の実作業で見つかった skill の穴であり、親 DoD を 5 件から 6 件へ広げるだけで収まる。

第二に、別 steering にすると、いま指摘された「後回しにされる」構造をそのまま踏むことになる。この提案自体を後回しにする形は、提案の内容と矛盾する。

**論点2 との関係。**

論点2 は `escalate-plugin-skill-fix` の working directory 制約を scope 外と決めた。今回の提案は**同じ file を触るが別の問い**である。working directory 制約は「作業対象をどう伝えるか」、今回は「いつ直すか」を問う。前者は再現条件が未確認のため scope 外のまま維持し、後者を独立した phase として立てる。

#### 提案0へのフィードバック

**結果:** 採用。

> ok

### 決定

親 roadmap へ 6 番目の phase `escalation-without-deferral` を追加する。既存 5 phase のどれにも依存しない独立 phase とする。親 DoD の対象を 5 件から 6 件へ広げる。

論点2 で scope 外とした working directory 制約は、scope 外のまま維持する。
