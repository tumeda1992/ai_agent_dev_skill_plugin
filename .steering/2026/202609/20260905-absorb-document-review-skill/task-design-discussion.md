# 議論記録

## 論点1: 参照する標準のうち plugin に存在しないものの扱い

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: content_density.md をどう扱うかを決める

#### 提案0

**推奨:** a。固有情報の除去と意味保存は両立できる見込みが立ち、plugin には同じ手法で汎用化された前例があるため。ただし `writing_module.md` への依存が残るので、そこは参照の読み替えで閉じる。

##### 依存の実測

吸収対象の skill が参照する 3 標準のうち、`expression_notation.md` と `file_naming.md` は plugin 内で参照が閉じる。欠落は `content_density.md` だけである。

その `content_density.md` を読むと、さらに依存がある。

| 参照先 | plugin 側 | 用途 |
| --- | --- | --- |
| `core_readers.md` | あり | 隣接トピックの担当を示すポインタ |
| `expression_notation.md` | あり | 隣接トピック、および平準化の検知で箇条書きの並列性を参照 |
| `information_structuring/README.md` | あり | 隣接トピックの担当 |
| `information_structuring/writing_module.md` | **なし** | 隣接トピック 1 箇所と、具体例の「現物」3 箇所 |

`writing_module.md` は 253 行あり、利用先固有語の出現が 27 箇所。`content_density.md` はこの file の改稿履歴を具体例として使っている（旧「切る軸」の項が 2 行で測り方が無かった件、思想 1 と思想 2 の濃度差、思想 2 が射程縮小した件）。

##### 固有情報の分布

`content_density.md` 240 行のうち、利用先固有の情報は 2 種類に分かれる。

**事業ドメインの具体例**（汎用化の対象）

- 支払方法の動的切替を 1 文で書いた例。4 条件、コンビニ端末は期限切れなし、請求書は請求月末超過、電子バーコードは翌月 10 日以降、口座振替は端末番号を発行できる状態
- 階層の基準を請求金額に当てると 2 束に割れるが損金化に当てると割れない。貸倒と雑損失は対象条件も相殺区分も違うが、同じ改修で一緒に触る
- `billing_amount/` は 2 本柱に割り、同じ実質量の `payment_and_receipt/` は 7 ファイルをフラットに並べた

**doc 標準自身の改稿履歴**（固有ではないが file 名が固有）

- この標準の草案で「抽象と具体を往復する」を 2 バレットで済ませた件
- 平準化を 3 回繰り返した件（同型バレット 4 連 → 5 つの同型節 → 5 行の表）
- 指摘のたびに前版の要素を落とした振動の件

後者は doc を書く作業そのものの例であり、どの repository でも成立する。固有なのは `writing_module.md` という file 名だけである。

##### a. `content_density.md` を汎用化して plugin へ新設し、`writing_module.md` への参照を読み替える

事業ドメインの具体例を、業務構造を保ったまま汎用の題材へ置換する。「支払方法ごとに期限切れ判定が違う」という構造は、`PaymentMethod` のような一般的仮名と抽象化された条件で書ける。置換で失われるのは業務固有の語彙であって、「読者が下駄を履くとはどういうことか」を示す機構ではない。

`writing_module.md` を現物として使う 3 箇所は、plugin 内で成立する題材へ差し替える。この plugin は skill 本体と docs の両方を持ち、改稿履歴も `.steering/` に残っているため、同種の現物を取れる。隣接トピックのポインタ 1 箇所は、plugin の `information_structuring/README.md` へ向ける。

前例がある。plugin の `expression_notation.md` は利用先版と同じ骨格を持ちながら、図の例が「与信」ではなく「在庫確認」になっている。事業ドメイン語を汎用例へ置換する手法が、この標準体系では既に使われている。

**この案の弱点**: 汎用化した版が、`content_density.md` 自身の基準で「薄い」と判定される可能性がある。業務の具体性が持っていた検知力（読者が自分の作物と照合できる度合い）は、仮名化で目減りする。差し替える現物を plugin 内から実際に取れるかは、書いてみないと確定しない。

##### b. `content_density.md` と `writing_module.md` の両方を汎用化して吸収する

`content_density.md` の具体例をそのまま活かせる。`writing_module.md` の改稿履歴を現物として引用している 3 箇所が、参照先ごと plugin 内で閉じる。

ただし `writing_module.md` は 253 行で固有語 27 箇所あり、それ自体の汎用化が別の作業になる。今回の依頼は `document-review` の吸収であり、標準 2 本の移植はその範囲を超える。`writing_module.md` は `information_structuring/` の下にあり、plugin 側の同 directory には `README.md` / `README.template.md` / `writing_overview.md` があるため、体系上どこへ収まるかの判断も要る。

##### c. `content_density.md` への参照を外し、記法と命名の 2 標準だけのゲートにする

skill 本体だけを持ち込める。plugin に無い file を新設しない。

ただし回し方の contract が成立しなくなる。「薄い（濃さ不足）は微細でない。1 行足して繕わず、そのトピックを読者が実行できる形まで降ろすか、親へ畳む」という記述は、濃さ観点があって初めて意味を持つ。この contract は「微細な指摘は直して再度回す／微細でない指摘は生成をやり直す」という二分岐の判断基準そのものであり、濃さを外すと残るのは記法と命名だけの表層チェックになる。

`function_migration_policy.md` は合意済み差分を除く全量維持を求めるため、濃さ観点の `RETIRE` は明示合意を要する。

##### d. 吸収を保留する

`migration.md` の「固有情報の除去と意味保存を同時に満たせない contract は移植を停止する」に従う。

ただし両立不能はまだ証明されていない。固有情報は事業ドメインの具体例に集中しており、標準の骨格（濃さの定義、抽象と具体の役割分担、実行できる形まで降ろす、比較で見つかる 4 つの崩れ、厚さと濃さの区別、検知方法）は固有情報を含まない。停止を選ぶ前に、汎用化を試す余地が残っている。

#### 提案背景

`document-review` は「各標準の当て方はその標準ファイルが正本であり、ここに内容を写さない」という構造を持つ。skill 本体は薄く、参照先の標準が厚い。この構造のため、参照先が揃うかどうかが skill の成立条件になる。

##### 提案0 が満たす必要のある条件と、それを満たす内容

「持ち込めるか」を判断するには、固有情報がどこにどれだけあるかと、それを除いて意味が保てるかの見込みが要る。`content_density.md` 240 行を通読し、固有情報を事業ドメインの具体例と doc 標準自身の改稿履歴へ分類した。前者は汎用化の対象、後者は file 名だけが固有と判明した。

加えて、この標準自身が `writing_module.md` へ依存していることが読んで分かった。隣接トピックのポインタだけなら読み替えで済むが、具体例の「現物」として 3 箇所で使われているため、差し替えるか参照先ごと持ち込むかの判断が必要になる。これが a と b を分ける。

`migration.md` は除去と意味保存が両立しない場合の停止を定めるが、両立の可否は実際に置換してみないと確定しない部分がある。d を残しているのはそのためで、a を試して薄くなると判断された時点で d へ戻る経路は保たれる。

##### この論点で決めないこと

汎用化後の `content_density.md` の本文そのものは、この論点では決めない。範囲が決まった後に、書いた結果を review する。`expression_notation.md` の双方向ドリフト（利用先だけにある「小見出し」の記述）を逆輸入するかも、`document-review` の吸収とは独立した別 decision として扱う。

#### 提案0へのフィードバック

**結果:** 案 a を選択。

> a

### 決定

`content_density.md` を汎用化して `plugins/tumeda-dev/docs/documentation_standards/content_density.md` へ新設する。`writing_module.md` は吸収しない。

**汎用化の対象**

事業ドメインの具体例を、業務構造を保ったまま汎用の題材へ置換する。支払方法ごとに期限切れ判定が違うという構造、階層の基準が一方の軸では割れて他方では割れないという対比、同じ実質量を持つ 2 つの module が異なる粒度で書かれたという比較は、いずれも業務語彙を外しても機構が残る。置換で失われるのは語彙であって、「読者が下駄を履くとはどういうことか」を示す機構ではない。

plugin の `expression_notation.md` が同じ手法で作られている。利用先版と同じ骨格を持ちながら、図の例が「与信」ではなく「在庫確認」になっている。事業ドメイン語を汎用例へ置換する手法は、この標準体系で既に使われている。

**`writing_module.md` への参照の扱い**

4 箇所ある参照のうち、隣接トピックのポインタ 1 箇所は plugin の `information_structuring/README.md` へ向ける。具体例の「現物」として使っている 3 箇所は、plugin 内で成立する題材へ差し替える。この plugin は skill 本体と docs の両方を持ち、改稿履歴が `.steering/` に残っているため、同種の現物を取れる。

**保存する骨格**

濃さの定義（読者が下駄を履く / 深く知る・十全に実行できる・アンチパターンを踏まない）、薄さが書き手と読者の満足条件の非対称から生まれること、抽象と具体の役割分担と往復が閉じる条件、トピックを実行できる形まで降ろす 3 要素、比較で見つかる 4 つの崩れ（薄い節・平準化・射程縮小・振動）とそれぞれの検知方法、厚さと濃さの区別、検知の 3 問と比較 4 本。これらは固有情報を含まないため原文の意味を保つ。

**この決定が生む制約**

汎用化後の版は `content_density.md` 自身の基準で判定する。業務の具体性が持っていた検知力は仮名化で目減りするため、差し替える現物が plugin 内から取れず薄くなると判断された場合は、吸収の保留（提案0 の案 d）へ戻る経路を残す。

## 論点2: plugin 側で誰がこのゲートを呼ぶか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 呼び出し契約を決める

#### 提案0

**推奨:** b。plugin で md を emit する場面のうち、この skill の観点が有効なのは docs と skill 本体であり、steering の作業記録ではないため。呼び出しをその 2 つに限定する。

##### この論点を先に扱う理由

吸収対象は「doc を書く／直す workflow が、各成果物を emit する前のゲートとして呼ぶ」ことを前提にしている。利用先ではその呼び出し元が実在した。plugin 側に呼び出し元が無ければ、この skill は「単独起動できるレビュー skill」という別のものになり、役割と判断方針（論点3 で扱う）も変わる。したがって役割より先に呼び出し契約を決める。

##### plugin で md を emit する場面

| 場面 | 成果物 | 読者 | 既存の品質 gate |
| --- | --- | --- | --- |
| steering の作業記録 | `design.md` / `tasklist.md` / discussion file / `summary.md` | 次に同じ steering を読む人 | `task-design` の完成設計書チェック（Stage 1 grep / Stage 2 目視通読）、`facilitate-discussion` の entry 形式契約、`steering` の summary exact format |
| skill 本体 | `SKILL.md`、`templates/` 配下 | skill を適用する agent | `outcome-sections/` の各 MUST と判断基準、`skill-policy.md` の記述 MUST |
| docs | `documentation_standards/` `think_standards/` `development_standards/` 配下 | skill を書く人と agent | なし |
| 既存 README への追記 | 利用先 repository の README | その repository の読み手 | `doc-enricher` の Gate A〜G |

plugin の全 skill が何らかの gate を持つが、性質が違う。`task-design` の完成設計書チェックは design.md 固有の議論色を見る。`facilitate-discussion` と `steering` の契約は形式を定める。`doc-enricher` の Gate A〜G は「その知識を残すべきか」を判定する。いずれも「濃さ・記法・命名」を当てるものではない。

##### a. 単独起動できる skill として置くだけにする

呼び出しを既存 skill へ書き込まない。ユーザーが「ドキュメントをレビューして」と明示したときだけ起動する。

既存 skill を変更しないため、吸収の影響が `document-review` の新設と `content_density.md` の新設に閉じる。ただし「emit 前のゲート」という位置づけは失われ、通せば通る任意のレビューになる。書き手が呼ぶことを覚えていないと機能しない。

##### b. docs と skill 本体を書く場面から呼ばせる

`document-review` を emit 前ゲートとして呼ぶ場面を、docs（`documentation_standards/` 等）と skill 本体（`SKILL.md`、`templates/`）の作成・更新に限定する。steering の作業記録には当てない。

この 2 つは読者が「その doc を読んで作業できるようになる」ことを期待する成果物であり、`content_density.md` の濃さの定義（深く知る・十全に実行できる・アンチパターンを踏まない）がそのまま当たる。docs には現在どの gate も無く、skill 本体の gate は `outcome-sections` の観点別 MUST であって濃さ・記法・命名を横断的に見るものではない。

steering の作業記録を外すのは、読者と目的が違うためである。`design.md` は合意済みの完成後状態を記録する場所で、読者は次にその steering を読む人に限られる。既に `task-design` が議論色ゼロを 2 段階で確認する gate を持っており、そこへ濃さの観点を重ねると、作業記録に「読者が下駄を履く」水準を要求することになる。

呼び出しの書き込み先は、docs と skill 本体を実際に書く工程を持つ `tasklist-executor` になる。加えて `task-design` が `documentation` outcome を設計する場面でも参照させる。

##### c. md を emit する全場面から呼ばせる

steering の作業記録を含め、plugin が生成する md すべてに当てる。

品質基準が一本化される。ただし `design.md` や discussion file にも濃さの基準が当たるため、作業記録を書くたびに「読者が下駄を履くか」を判定することになる。既存 gate との重複も生じる。`task-design` の完成設計書チェックと `document-review` の両方を通す順序と、指摘が競合したときの優先順位を決める必要がある。

#### 提案背景

論点1 で参照先の揃え方が決まったため、次に skill の成立条件を左右するのは呼び出し契約である。利用先ではこの skill が「呼ばれるゲート」として設計されており、単独起動は補助的な入口だった。plugin 側で呼び出し元を持たせないなら、skill の性質そのものが変わる。

##### 提案0 が満たす必要のある条件と、それを満たす内容

判断には、plugin が md を emit する場面と、そこに既存 gate があるかの一覧が要る。全 skill を調べ、md 成果物を 4 種類へ分類し、各々の読者と既存 gate を確認した。その結果、既存 gate はいずれも濃さ・記法・命名を横断的に見るものではなく、docs にはそもそも gate が無いと分かった。

3 案は「どこまで当てるか」で分かれる。判断の分かれ目は、steering の作業記録に濃さの基準を当てるかどうかである。

##### この論点で決めないこと

呼び出しを書き込む具体的な文言と挿入位置は決めない。既存 skill のどの節へどう書くかは、範囲が決まった後に扱う。

#### 提案0へのフィードバック

**結果:** 案 b を選択。

> b

### 決定

`document-review` を emit 前ゲートとして呼ぶ場面を、docs と skill 本体の作成・更新に限定する。steering の作業記録には当てない。

**当てる対象**

`plugins/tumeda-dev/docs/` 配下の標準 doc と、`plugins/tumeda-dev/skills/` 配下の `SKILL.md` および `templates/`。どちらも読者が「読んで作業できるようになる」ことを期待する成果物であり、`content_density.md` の濃さの定義がそのまま当たる。docs には現在どの gate も無く、skill 本体の gate は `outcome-sections` の観点別 MUST であって濃さ・記法・命名を横断的に見るものではない。

**当てない対象**

steering の作業記録（`design.md` / `tasklist.md` / discussion file / `summary.md`）。読者が次にその steering を読む人に限られ、合意済みの完成後状態を記録する場所であるため、「読者が下駄を履く」水準を要求する対象ではない。`task-design` が議論色ゼロを 2 段階で確認する gate を既に持つ。

利用先 repository の README への追記は `doc-enricher` の Gate A〜G が担う。この skill の対象にしない。

**呼び出しの書き込み先**

docs と skill 本体を実際に書く工程を持つ `tasklist-executor`。加えて `task-design` が `documentation` outcome を設計する場面でも参照させる。

## 論点3: skill の役割と判断方針

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 完成後の policy を決める

#### 提案0

論点1 で参照先、論点2 で呼び出し場面が決まったため、残るのはこの skill が何を成立させ何を拒むかである。選択肢を並べるより完成後の policy を直接示す。判断が分かれうる 2 点は末尾に明示する。

##### 完成後の document-review

`document-review` は、md を emit する前に、読者がその doc で作業できる状態に達しているかを判定し、達していないものを出させない。書き手が自分では見えない薄さを検知させ、指摘の性質に応じて直すか書き直すかを判断させる。

###### 要素の充足ではなく観点の充足で判定する

書き手は「載せた」で満足でき、読者は「使える」でしか満足しない。この非対称があるため、トピックが挙がっていることや節が揃っていることを完了条件にすると、薄い doc がそのまま通る。判定は常に「観点を満たしたか」で行い、満たさないなら出さない。

違反の兆候は、指摘を返すときに「触れてはいる」「抜けは無い」を根拠にすることである。これが出たら、その節を読み終えた読者が何をできるようになるかを 1 文で言えるかへ戻す。言えないなら濃さの目標が定まっていない。

###### 薄さは微細な指摘ではない

指摘は 2 種類に分かれ、対処が違う。記法の一部・命名・言い回しは微細であり、直してレビューを最初から回し直す。指摘が尽きるまで繰り返すのは、直した結果が別の観点を崩すことがあるためである。

骨子・構造・実質の破綻は微細でなく、書く工程へ戻って生成をやり直す。パッチで繕わない。濃さ不足はこちらに属する。1 行足すと書き手の基準では満たされるが、読者は依然として何も持ち帰れないためである。正しい対処は、そのトピックを読者が実行できる形まで降ろすか、親へ畳むかのどちらかになる。

###### 観点の当て方は標準 file が正本

この skill は観点の名前と、いつ当てるかだけを持つ。当て方の中身は `content_density.md` / `expression_notation.md` / `file_naming.md` が正本であり、skill 本文へ写さない。写すと二重管理になり、標準を直しても skill 側が古いまま残る。

新規作成は「作成＝更新でもある」ため、作成時観点と更新時観点の両方を当てる。更新時の濃さ観点では、書き足した箇所だけでなく前の版から削った要素も見る。指摘を受けて書き直すと、指摘された点だけを直して前版に成立していた要素を無自覚に捨てることがあるためである。

###### 能力境界

何を書くべきかという知識の取捨選択は `doc-enricher` が担う。この skill は書かれたものが観点を満たすかだけを見る。逆に、観点を満たさない doc を「残す価値がある知識だから」という理由で通さない。

対象は docs と skill 本体に限る。steering の作業記録には当てない。利用先 repository の README への追記は `doc-enricher` の Gate A〜G が担う。

##### 判断が分かれうる 2 点

**単独起動を受け付けるか**

利用先版は「ドキュメントをレビューして」「md を出す前にチェック」でも起動する、と description に書いている。emit 前ゲートとしての呼び出しと、ユーザーが明示する単独起動の 2 経路を持つ形である。

plugin でも 2 経路を維持する案を推す。呼び出し元が `tasklist-executor` と `task-design` に限られるため、それ以外の場面で md を触ったときにユーザーが明示的に通せる入口が要る。ただし単独起動を残すと、呼ばれなかった場合に誰も気づかないという弱点は残る。

**`doc-enricher` が plugin 自身の docs へ追記する場合の扱い**

`doc-enricher` は利用先 README への追記提案を担うが、plugin 自身の docs を対象にすることもある（この steering でも plugin の docs への提案が出うる）。その場合、追記内容が `document-review` の対象になるかが決まっていない。

対象に含める案を推す。plugin の `docs/` 配下であれば出所を問わず当てる、とすれば境界が単純になる。`doc-enricher` の Gate A〜G は「その知識を残すべきか」を判定するもので、書かれた文が観点を満たすかは見ないため、重複しない。

#### 提案背景

論点1 と論点2 で外側の条件が固まったため、この skill 自身が何を判断するかを確定できる状態になった。

##### 提案0 が満たす必要のある条件と、それを満たす内容

`skill-policy.md` は、原則名だけでなく誤適用を防ぐ理由・違反signal・帰結・判断質問を残すことを MUST とし、「skill 名と workflow を残したままこの section を削除したとき、実装者が別の思想を持つ skill へ作り替えられるか」を判断基準に置く。そこで各 policy に、なぜそれが効くのかと、外れているときにどう見えるかを添えた。

利用先版が持っていた contract は全量を保存対象とした。要素充足でなく観点充足で判定すること、微細と微細でないの二分岐、薄さは微細でないこと、標準を正本として写さないこと、更新時に削った要素も見ることは、いずれも原文の判断能力である。

判断が分かれうる 2 点は、利用先の記述からは一意に決まらない。単独起動は description に書かれているが plugin では呼び出し元が違う。`doc-enricher` との関係は利用先に対応する状況が無かった。この 2 点だけを明示して合意を求める。

##### この論点で決めないこと

`SKILL.md` の見出し構成と本文そのものは決めない。policy が確定した後に書き、書いた結果を review する。

### 決定

`document-review` は、md を emit する前に読者がその doc で作業できる状態に達しているかを判定し、達していないものを出させない。書き手が自分では見えない薄さを検知させ、指摘の性質に応じて直すか書き直すかを判断させる。

**要素の充足ではなく観点の充足で判定する。** 書き手は「載せた」で満足でき読者は「使える」でしか満足しないため、トピックが挙がっていることを完了条件にすると薄い doc が通る。違反の兆候は「触れてはいる」「抜けは無い」を根拠に返すことであり、その節を読み終えた読者が何をできるようになるかを 1 文で言えるかへ戻す。

**薄さは微細な指摘ではない。** 記法の一部・命名・言い回しは微細であり、直してレビューを最初から回し直す。直した結果が別の観点を崩すことがあるため、指摘が尽きるまで繰り返す。骨子・構造・実質の破綻は微細でなく、書く工程へ戻して生成をやり直す。濃さ不足は後者に属し、1 行足すと書き手の基準では満たされるが読者は依然として何も持ち帰れない。正しい対処はトピックを実行できる形まで降ろすか親へ畳むかである。

**観点の当て方は標準 file が正本。** skill は観点の名前といつ当てるかだけを持ち、当て方の中身を写さない。写すと二重管理になり、標準を直しても skill 側が古いまま残る。新規作成は作成時観点と更新時観点の両方を当て、更新時の濃さ観点では書き足した箇所だけでなく前の版から削った要素も見る。

**能力境界。** 何を書くべきかという知識の取捨選択は `doc-enricher` が担い、この skill は書かれたものが観点を満たすかだけを見る。観点を満たさない doc を「残す価値がある知識だから」で通さない。

**呼び出し経路は 2 つ持つ。** `tasklist-executor` と `task-design` からの emit 前ゲートとしての呼び出しに加え、ユーザーが明示する単独起動も受け付ける。呼び出し元が 2 skill に限られるため、それ以外の場面で md を触ったときに明示的に通せる入口が要る。呼ばれなければ誰も気づかないという弱点は残るが、入口を塞ぐ理由にはならない。

**`doc-enricher` が plugin 自身の docs へ追記する場合も対象に含める。** `plugins/tumeda-dev/docs/` 配下であれば出所を問わず当てる。Gate A〜G は残すべき知識かを判定するもので、書かれた文が観点を満たすかは見ないため重複しない。
