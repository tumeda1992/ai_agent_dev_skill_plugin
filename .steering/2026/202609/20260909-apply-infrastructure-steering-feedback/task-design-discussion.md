# 議論記録

## 論点1: 実環境依存の論点を基盤構築後へ回す経路をどう作るか

**ステータス:** 分解済み

**種別:** TBDヒアリング

### イテレーション0: 既存契約を壊さずに段階的designとして表す

#### 提案0

**案 a: 新機構を作らず、designの対象範囲を段階的に確定する運用として表す。**

`design.md` の scope を「基盤を立てるところまで」に限定し、その範囲で TBD をゼロにして合意する。実環境依存の論点は、そもそも今回の design scope へ含めない。基盤phase を実行して実測を得たあと、同じ `working_dir` で `task-design` を `create_working_dir=false` で再開し、`design.md` を拡張して残りを設計する。

既存契約を一つも壊さない。`task-design` の完了条件（未解消TBDがゼロ）は各段階で満たされ、`steering` の「plan合意を実行開始の承認と読み替えない」も維持され、`tasklist-executor` は各段階の合意済み tasklist を受け取る。再開経路も `create_working_dir=false` として既に存在する。

足りないのは判断だけである。「この不確実性を今回の design scope へ含めるか」を問う基準が無く、実環境依存の論点まで机上で潰そうとしてしまう。

**案 b: TBD へ「実環境依存」区分を導入し、design合意の必須解消対象から外す。**

`design.md` には最終形を最初から描き、実環境依存の TBD を残したまま plan phase へ進む。`task-design` の完了条件を「未解消TBDが無い、または残る TBD が実環境依存として基盤phase の後へ明示的に委ねられている」へ緩める。

一つの `design.md` に最終形が最初からある点は読み手に利く。ただし `task-design` の中核である「実装中に新しい判断が生まれない状態を作る」を担保しているのが完了条件であり、そこへ例外区分を入れると、実環境依存かどうかの自己申告で TBD を先送りできるようになる。

**案 c: `spike/` の定義を拡張し、捨てられない検証を許す。**

現行の `spike/` は「書いたコードは捨ててよい。残るのは事実だけ」と定義されている。基盤構築はこの定義から外れる。定義を拡張して捨てられない検証を含める。

ただし `tasklist-design.md` は既に「作業の外へ残るactionを含むphaseの原則」を持ち、「このphaseで起きる変化は、この作業を破棄しても残るか」を判定の問いにしている。`spike/` を拡張すると、残る変化を扱う仕組みが二つになる。

**推す案と、その具体的な修正内容**

案 a を推す。案 b は完了条件という担保そのものを緩めるため副作用が読めず、案 c は残る変化の扱いを二重管理にする。案 a が足すのは判断基準だけであり、既存の機構をそのまま使う。

案 a を採る場合、次の三箇所を変更する。

**(1) `plugins/tumeda-dev/skills/task-design/SKILL.md` の section 3 へ、思想を一つ追加する**

`3-4 不確実性のためならコードを書く` の直後、`3-5 設計は対話であり転記ではない` の前へ挿入する。section 3 の既存の型（思想 / 違反シグナル / 帰結 / 問い）を崩さない。

```markdown
### 3-5. 実環境依存の論点は、基盤を立ててから設計する

**思想:**

未開拓の実行基盤を伴う作業では、机上で決めた前提が実測で崩れる。崩れた前提の上に積んだ下位の合意はすべてやり直しになる。だから「その論点の答えが実環境の挙動に依存するか」を先に問い、依存するなら今回の design scope へ含めない。基盤を立て、実測を得てから設計する。

scope から外すのは先送りではない。今回の design は「基盤を立てるところまで」を対象として完結させ、TBD をゼロにして合意する。基盤phase を実行したあと、同じ working directory で task-design を再開し、実測を入力として残りを設計する。

含めるか外すかは二問で決める。

1. その論点の答えは、実環境の挙動に依存するか。依存するなら基盤を立てた後へ回す。
2. その論点の答えは、作るものそのものを変えるか。変えるなら基盤より前に決める。

二問が両方 Yes の場合は基盤より前に決める。作るものが変わる論点を後回しにすると、基盤そのものが不要になりうるためである。

**違反シグナル:**
- 実行してみないと分からない挙動について、複数案を比較して優劣を論じている
- 外部serviceの設定範囲、認証の適用単位、build環境の挙動を、documentだけを根拠に design へ書いている
- 一つの論点で三回以上 iteration を重ね、実測が一度も入っていない
- 「基盤を立てるのに必要な合意」と「機能を完成させるのに必要な合意」を分けずに、全部を一度に決めようとしている

**帰結:**

決着した論点の前提が実測で崩れ、design を訂正し、下位の合意をやり直す。実測が入るまで、どの論点が生き残るか分からないまま議論が続く。設計時間が増えるだけでなく、何が決まっているのかが読めなくなる。

**問い:**
- 「この論点の答えは、実環境を動かさずに確定できるか?」
- 「いま決めようとしていることは、基盤を立てるのに必要か? それとも基盤が立ってからでよいか?」
- 「今回の design は、どこまでを対象として完結させるのか?」
```

既存の `3-5 設計は対話であり転記ではない` は `3-6` へ繰り下がる。番号を持つ節の追加であるため、`SKILL.md` 内の相互参照（`→ 3-5` 等）も併せて更新する。

**(2) `plugins/tumeda-dev/skills/task-design/SKILL.md` の Step 3 へ、scope判断を足す**

Step 3 の 2 番目「不確実性の解消手段を選ぶ」の表の直前へ、次を挿入する。解消手段を四つへ増やすのではなく、表へ入る前の分岐として置く。

```markdown
手段を選ぶ前に、その不確実性を今回の design scope へ含めるかを判定する。答えが実環境の挙動に依存し、かつ作るものそのものを変えないなら、今回の scope から外す（3-5）。外した不確実性は `design.md` の非目標へ「基盤の実測後に設計する」と明記し、基盤phase 完了後の再開で扱う。
```

**(3) `plugins/tumeda-dev/skills/task-design/tasklist-design.md` の phase分割の方針へ、基盤phase の指針を足す**

`### phase分割の方針` の箇条書きの末尾へ、次を追加する。

```markdown
- 未開拓の実行基盤を伴う作業では、基盤を立てる phase を最初に置き、その phase の DoD へ実測結果を含める。基盤phase の完了後、実測を入力として design へ戻る前提で plan を作る（`SKILL.md` 3-5）。
```

`steering/SKILL.md` は変更しない。実測後の再開は既存の `create_working_dir=false` による task-design 再開と、`実装完了後review` の戻り先指定で表現できる。新しい gate も禁止事項の緩和も要らない。

#### 提案背景

提案0 が満たす必要のある条件は二つある。

一つは、実環境依存の論点を机上で決めさせないこと。今回の起点となった作業では、外部serviceの設定適用単位、監視対象の設定、build image の挙動、secret store の機構が、いずれも実測で初めて判明した。このうち二つは design の記述を訂正させ、一つは最初の phase を実行できない状態を生み、一つは既に決着していた論点の前提を崩した。

もう一つは、既存契約を壊さないこと。調査で次の三つの衝突が確定している。`task-design` の完了条件は未解消TBDがゼロであり、TBD を残して plan を実行する経路を持たない。`steering` は「plan合意を実行開始の承認と読み替えない」「必須gateを飛ばして自動で次工程へ突入しない」を禁止事項に持つ。`tasklist-executor` は合意済み tasklist を single writer として実行する。

案 a は前者を「scope に含めない」という判断で満たし、後者を「各段階で完了条件を満たす」ことで満たす。案 b は前者を満たすが後者の一つ目を緩める。案 c は前者を満たすが、`tasklist-design.md` の「作業の外へ残るaction」原則と重複する仕組みを作る。

修正内容を三箇所へ限定したのは、追加するものが判断基準だけだからである。思想は section 3 が所有し、適用する手順は Step 3 が所有し、plan への落とし込みは `tasklist-design.md` が所有する。この三層は既存の責務境界どおりであり、新しい owner を作らない。

#### 提案0へのフィードバック

**結果:** 提案0 は HOW の階層で並んでおり、選ぶ根拠が示されていない。思想の合意から始め直す。

> 私の頭が良くなくて、このデカ論点に対して、howレベルの選択肢が並んでもどれを選べばいいかわからなくて、何がどうだからどれかを選べる根拠となる、と思えるものがまだない。
> 思想面の合意から必要になるのかな

提案0 の三案は、機構の違い（scope を段階化する / TBD へ区分を足す / `spike` を拡張する）で並んでいる。機構は思想から導かれるものであり、思想が未合意のまま機構を比べても、どの代償を受け入れるかの判断ができない。`task-design` 自身の `3-1 WHY→WHAT→HOW` に反している。

### イテレーション1: 「設計を尽くした」と言える単位を決める

#### 提案1

**何が衝突しているか**

`task-design` は「実装中に新たな設計決定が生まれない状態」を作ることを目的にしている。設計を尽くしてから実装する、という前提に立っている。

一方で、実行しなければ確定しない事実がある。この skill はそれを既に認めていて、`3-4 不確実性のためならコードを書く` で「議論・調査・技術検証実装」の三手段を持つ。技術検証実装は `spike/` へ置き、「書いたコードは捨ててよい。残るのは事実だけ」と定義されている。

つまり現行の思想はこうである。

> 実行しないと分からないことは、**捨てられる形で**動かして事実を取り、設計へ戻す。

提案2 が突きつけているのは、この「捨てられる形で」が成立しない領域があることである。基盤は捨てられない。S3 bucket、hosting app、DNS record は、作れば残る。捨てられない実行によってしか得られない事実がある。

**決めること**

衝突の解き方は二つに分かれる。どちらを採るかは「設計を尽くしたと言える単位」をどこに置くかで決まる。

- **思想A: 設計の完結単位を「実行可能な一段階」に置く。** 一つの作業に対して design を一度完結させる、という前提を手放す。段階ごとに「その段階を実行するのに十分な設計」を完結させ、実行し、実測を得て、次の段階を設計する。「実装中に新しい判断が生まれない」は各段階の内側で守られる。
- **思想B: 設計の完結単位を「作業全体」に置いたまま、確定できない前提を明示して持ち越す。** design は最初から最終形を描く。実環境依存の部分は「未確定の前提」として印を付けて残し、実測で確定する。「実装中に新しい判断が生まれない」は、印を付けた箇所については保証しない。

**何がどう変わるか**

| | 思想A | 思想B |
| --- | --- | --- |
| design.md が示すもの | 各時点では、その段階までの完成後の姿 | 最初から最終形。ただし一部が未確定 |
| 完了条件 | 段階ごとに TBD ゼロ。既存の完了条件をそのまま使う | 作業全体で TBD ゼロを求めない。完了条件に例外区分が要る |
| 基盤前に列挙する論点 | 基盤を立てるのに必要なものだけ | 最終形に必要なものすべて |
| 実装者への保証 | 各段階の実装中に新しい判断は生まれない | 印の無い箇所についてだけ保証される |
| 読み手のコスト | 最終形を知るには段階を追う必要がある | 一つの file で最終形が読める |

**判断の根拠になると考えるもの**

提起の原文にこの一文がある。

> 全体の整合性のための重箱の隅の話は基盤立てられて初めて、今後の成長にむけて大事な論点になる。それが決まることで他を安心して考えられるし、それが決まらない限り「今これ話している場合じゃないんだけどな」が続く

ここで言われているのは「基盤前と基盤後では、考えるべき論点の集合そのものが違う」ということである。論点の答えが変わるのではなく、その論点に取り組む価値が基盤の有無で変わる。

思想B は最終形を最初に描くため、基盤前に最終形の論点集合を列挙することになる。「今これ話している場合じゃない」論点が、印付きであっても design.md の上に並ぶ。実際に起きた事象――四イテレーションを費やした論点が、実測一つで前提ごと崩れた――は、論点が未確定だったから起きたのではなく、その論点を基盤前に扱ったから起きた。

思想A はその論点を design scope の外へ置く。基盤前の design.md には現れない。

これが assistant の見立てである。思想A を推す。

**代償として受け入れること**

思想A を採ると、途中の design.md は最終形を示さなくなる。「この design はどこまでを対象としているか」を明示しない限り、読み手は完成形と勘違いする。この明示を design.md の非目標へ書くことが、思想A の運用上の必須条件になる。

#### 提案背景

イテレーション0 のフィードバックが求めているのは、機構の比較ではなく、機構を導く思想の合意である。提案1 は、比較の軸を「どの file を変えるか」から「設計を尽くしたと言える単位をどこに置くか」へ移して、この条件を満たす。

イテレーション0 で確定した事実のうち、次は維持する。現行契約との衝突が三つあること（`task-design` の完了条件、`steering` の禁止事項、`tasklist-executor` の前提）、`spike/` が「捨ててよい」と定義されていること、`tasklist-design.md` が「作業の外へ残るaction」の判定軸を既に持つこと。これらは思想の選択後、機構を決める段階で再び使う。

置き換えたのは、それらから「どの機構を選ぶか」を直接導こうとした点である。イテレーション0 の案 a は思想A の機構、案 b は思想B の機構、案 c は「捨てられない実行も検証として扱う」という第三の位置にあたる。案 c を提案1 の選択肢へ残していないのは、それが思想の選択ではなく、思想A・B のどちらを採っても検討しうる機構だからである。思想が決まった後の機構比較で扱う。

**結果:** 思想A を採用。

### 決定

「設計を尽くした」と言える単位を、**実行可能な一段階**に置く。一つの作業に対して design を一度で完結させるという前提を手放す。

- 各段階では「その段階を実行するのに十分な設計」を完結させる。既存の完了条件（未解消TBDがゼロ、`分類保留` がゼロ）は緩めず、段階ごとにそのまま満たす
- 「実装中に新しい判断が生まれない」という保証は、各段階の内側で維持する
- 実環境の挙動に依存し、かつ作るものそのものを変えない論点は、その段階の design scope へ含めない。基盤を立て、実測を得てから次の段階で設計する
- 代償として、途中の `design.md` は最終形を示さない。この代償を受け入れる条件として、`design.md` に「この design がどこまでを対象としているか」を明示する。明示が無ければ読み手は完成形と誤読する

この決定は思想の単位を定めるものであり、skill のどの層へ何を書くかは論点2 が持つ。

## 論点2: 思想A を skill のどの層へ何として書くか

**ステータス:** 決定

**親論点:** 論点1

**種別:** TBDヒアリング

### イテレーション0: 判断・適用・段階の切り方を三層へ分けて置く

#### 提案0

論点1 で「設計を尽くした単位は実行可能な一段階」と決めた。これを skill 上で成立させるには三つのものが要る。

- **判断**: ある不確実性を、この段階の scope へ含めるか外すか
- **適用**: その判断を design phase のどの手順で行うか
- **段階の切り方**: 外した不確実性を、plan 側でどう段階として表すか

この三つを既存の責務境界どおり別々の owner へ置くか、一箇所へまとめるかで案が分かれる。

**案 a: 三層へ分けて置く。**

- 判断 → `task-design/SKILL.md` の section 3（思想の層）
- 適用 → 同 `SKILL.md` の Step 3（手順の層）
- 段階の切り方 → `tasklist-design.md` の phase分割の方針（plan の層）

既存の責務境界と一致する。section 3 は「なぜそうするか」、Step 3 は「いつ何を判断するか」、`tasklist-design.md` は「plan をどう割るか」を既に所有している。新しい owner を作らない。

三箇所に分かれるため、一箇所を読んだだけでは全体が見えない。相互参照で繋ぐ。

**案 b: `spike/` の定義を拡張し、捨てられない検証も spike として扱う。**

現行の `spike/` は「書いたコードは捨ててよい。残るのは事実だけ」と定義されている。この定義を「事実を得るための実行。捨てられる場合と、残る場合がある」へ広げ、基盤構築を spike の一種として扱う。

判断・適用・段階の切り方が `3-4` と「技術検証実装の配置・運用」の二箇所へ集まり、読む場所が減る。

ただし `tasklist-design.md` は既に「このphaseで起きる変化は、この作業を破棄しても残るか」を判定の問いとして持ち、残る変化を含む phase の扱いを規定している。spike を拡張すると、残る変化の扱いが `spike` 側と `tasklist-design` 側の二箇所に生まれる。どちらを読めばよいかが読み手に残る。

**案 c: 新しい section を一つ作り、三つをまとめて置く。**

`task-design/SKILL.md` へ「段階的に設計する」という独立 section を新設し、判断・適用・段階の切り方を一箇所へ書く。読む場所が一つになる。

section 3 は思想、Step は手順という既存の層構造から外れた section が一つ増える。以後、思想を足すとき section 3 とこの section のどちらへ置くかの判断が毎回発生する。

**推す案**

案 a を推す。理由は二つある。

一つは、論点1 の決定が「既存の完了条件を緩めない」ことを前提にしている点である。既存の層をそのまま使う案 a は、この前提と整合する。案 b は残る変化の扱いを二重にし、案 c は層構造そのものを増やす。

もう一つは、三つのものが実際に異なる読み手へ向いている点である。判断の根拠を必要とするのは設計を進める者、適用のタイミングを必要とするのは手順を追う者、段階の切り方を必要とするのは plan を作る者である。一箇所へまとめると、それぞれが自分に不要な二つを読むことになる。

案 a を採る場合に書く内容は次のとおり。

**(1) `task-design/SKILL.md` section 3 — 思想の層**

`3-4 不確実性のためならコードを書く` の直後へ挿入し、既存 `3-5` 以降を繰り下げる。section 3 の型（思想 / 違反シグナル / 帰結 / 問い）に従う。

#### 提案背景

## 論点3: 引き継ぎ可能性を、いつ誰が確認するものとして定義するか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 確認の主体と時点を決める

#### 提案0

**何が欠けているか**

起点となった作業の受け入れ基準は、すべて「作ったものが動くこと」で構成されていた。構成と構築結果を照合できる、公開 URL から機能が使える、access gate が要求される、主要操作が動作する、再適用で意図しない差分が出ない。

欠けていたのは「作ったものを、作った人以外が扱えること」である。更新手順、確認手順、復旧手順が無くても、上の基準はすべて満たせてしまう。

**決めること**

引き継ぎ可能性を担保する仕組みを、どこに持たせるか。これは「誰が、いつ確認するか」の選択である。

- **案 A: 設計の受け入れ基準として持つ。** `design.md` の受け入れ基準へ運用の観点を入れ、作業終了時に検証する。検証は「運用documentの手順だけを入力として、対象環境に対する確認操作が通る」形にすれば、一つの操作で検証できる DoD になる
- **案 B: 外部へ残るactionに伴う責務として持つ。** `tasklist-design.md` は既に「このphaseで起きる変化は、この作業を破棄しても残るか」を判定の問いとして持ち、対象actionを含むphaseへ停止・確認taskを置くことを MUST にしている。この停止・確認へ「残したものを後から更新・確認・復旧する手順がどこにあるか」を加える
- **案 C: 両方に持つ。** design の受け入れ基準にも、phase の停止・確認にも置く

**何がどう変わるか**

| | 案 A | 案 B |
| --- | --- | --- |
| 発火する条件 | design が受け入れ基準へ書いたとき | 外部へ残るactionを含むphaseがあるとき（既存の判定軸） |
| 適用範囲の決まり方 | 「infrastructure構築とは何か」を別途定義する必要がある | 「破棄しても残るか」で自動的に決まる |
| 確認する時点 | 作業終了時 | そのactionを残した直後 |
| 確認する主体 | 全phase完了を判定する者 | そのactionを実行した本人 |
| design を読んだ人が知れるか | 知れる | 受け入れ基準には現れない |

**推す案**

案 B を推す。理由は二つある。

一つは、適用範囲が既存の判定軸で自動的に決まることである。案 A は受け入れ基準へ書く条件として「infrastructure を新しく構築する作業」を定義する必要があるが、この境界は曖昧になる。外部serviceの設定変更だけの作業は含むのか、既存基盤への追加は含むのか。案 B は「この作業を破棄しても残るか」という既に運用されている問いへ乗るため、境界を新しく引かない。

もう一つは、確認の時点である。案 A は作業終了時に検証するため、基盤を作ってから何phaseも後になる。そのとき手順を書こうとしても、何を書くべきかの記憶が薄れている。案 B はそのactionを残した直後の停止・確認で問うため、実際に手を動かした本人が、手を動かした直後に書く。

案 C を推さないのは、同じ担保を二箇所へ置くと、片方だけ満たして通過する経路ができるためである。ただし案 B を採ると design を読んだだけでは引き継ぎ可能性の担保が見えなくなる。この不足は、案 B の停止・確認へ何を加えるかを `tasklist-design.md` が明示することで補う。

#### 提案背景

提案0 が満たす必要のある条件は二つある。

一つは、担保が実際に発火すること。起点の作業では、受け入れ基準に無かったために tasklist へ task が立たず、成果物が生まれなかった。仕組みが「書けば発火する」形だと、書き忘れがそのまま欠落になる。

もう一つは、`tasklist-design.md` の gate と両立すること。同fileは「各phaseのDoDを『ユーザーが一つの操作をした時、何を確認できるか』の形で書く」「DoDが抽象的なままreviewへ進むことを禁止する」を MUST にしている。「手順が文書として存在する」は存在確認であり、この gate を通らない。

案 A はこの二つ目の条件を「documentの手順だけを入力として確認操作が通る」という形で満たせるが、一つ目の条件については受け入れ基準へ書くかどうかが書き手に委ねられる。案 B は停止・確認taskが MUST であるため、対象actionがある限り必ず発火する。

論点1・論点2 で採った方針――新しい機構を作らず既存の層と判定軸へ乗せる――は、この論点でも同じ形で現れている。案 B はその一貫である。

#### 提案0へのフィードバック

**結果:** 案 C を、案 A を主とする形で採用。提案0 が案 B を推した根拠の一つが成立しない。

> A寄りのCかな。
> 方針や場合によっては設計時点の具体も設計で全然組める。
> 実装によって方針が変わった時に追随すればいい

提案0 は案 B を推す理由の一つに「案 A は作業終了時の検証になるため、何を書くべきかの記憶が薄れている」を挙げた。これは design が実測を経ずに運用documentの中身を推測で書く、という前提に立っていた。実際には引き継ぎの方針は設計時点で決められ、場合によっては具体も組める。実装で方針が変わったときに追随すればよい。前提が成立しないため、この理由は無効になる。

もう一つの理由――適用範囲を既存の判定軸で決められる――は維持する。

### イテレーション1: 案 A と案 B が何を持ち、どう噛み合うか

#### 提案1

案 C を採るうえで確定が要るのは、二つが同じ担保を重複して持たないことと、片方だけ満たして通過する経路ができないことである。次の形にする。

**案 A（主）が持つもの: 設計時点で決める方針と、可能なら具体**

`design.md` の受け入れ基準へ、引き継ぎの観点を入れる。運用documentに何を書くかは設計時点で決める。実測を待たずに決められるものは決め、実測でしか決まらないものだけを次の段階へ回す（論点1 の決定）。

受け入れ基準は操作で検証できる形にする。「運用documentが存在する」ではなく、「運用documentの手順だけを入力として、対象環境に対する確認操作が通る」と書く。これなら `tasklist-design.md` の「一つの操作で検証できるDoD」の gate を通る。

適用条件には、案 B が使っている既存の判定軸をそのまま使う。「この作業を破棄しても残る変化があるか」が Yes なら、引き継ぎの観点を受け入れ基準へ入れる。infrastructure という語で境界を引かない。

**案 B（従）が持つもの: 残した時点での実態との照合**

外部へ残るactionを含むphaseの停止・確認へ、設計時点で決めた運用documentが実態と合っているかの照合を加える。新しい担保を作るのではなく、案 A で決めた内容を対象にした照合である。

実装の過程で方針が変わっていた場合は、その場で document を書き換えるのではなく、design へ戻す。既存の `実装完了後review` の経路をそのまま使う。

**片方だけ満たして通過する経路ができない理由**

案 B は案 A の複製ではない。案 B が照合する対象は案 A が決めた内容であり、案 A が無ければ照合するものが無い。逆に案 A だけでは、実装で方針が変わったときに受け入れ基準の記述が実態から離れたまま残る。二つは重複ではなく、決める側と追随する側の関係にある。

**書く場所**

- 案 A → `plugins/tumeda-dev/skills/task-design/templates/design.md` の `### 受け入れ基準` の記入指示、および `tasklist-design.md` の `作業の外へ残るactionを含むphaseの原則`
- 案 B → `tasklist-design.md` の同じ原則の停止・確認taskの記述

二つが同じ原則の中で前後に並ぶため、読み手はどちらか一方だけを読んで済ませられない。

#### 提案背景

イテレーション0 のフィードバックが無効にしたのは「設計時点では中身が決められない」という前提である。この前提が外れると、案 A を主に置く形が成立する。方針と具体を設計で決め、実装で変わったら追随する、という順序になる。

このとき残る条件は二つある。一つは、二つの担保が重複しないこと。同じことを二箇所で確認すると、どちらが正かが読み手に残る。もう一つは、片方だけ満たして通過する経路ができないこと。提案0 が案 C を推さなかった理由がこれであり、案 C を採る以上はこの条件を満たす形を示す必要がある。

提案1 は、案 B の役割を「独立した担保」から「案 A で決めた内容と実態の照合」へ限定することで両方を満たす。照合は決めた内容が無ければ成立しないため、案 A を飛ばして案 B だけを満たすことができない。

適用条件に既存の判定軸を使うのは、イテレーション0 で維持された理由による。「infrastructure を新しく構築する作業」という境界は曖昧だが、「この作業を破棄しても残る変化があるか」は既に運用されている問いである。

### 決定

## 論点4: hookが注入すべきは規範の要約か、規範の所在か

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 要約を残すかどうかを決める

#### 提案0

**何が起きたか**

`.claude/hooks/` の二つの script が、毎ターン `think-through` の要約を注入していた。冒頭は「think-through skill 適用中（毎ターン常時注入）。」だった。受け手はこれを読んで skill の作法が適用済みだと扱い、`SKILL.md` も `docs/think_standards/core.md` も template も読み込まないまま、記録の形式だけを既存fileから真似て進めた。

文面から断定を外す変更は既に適用済みである。決めるのは、それで足りるとするかどうかである。

**確定している事実**

`.claude/hooks/` は配布対象ではない。`plugins/tumeda-dev/` の中身は `docs` と `skills` だけで、plugin manifest は hook を参照しない。利用先の hook は手動copyである。したがって、この repository の hook を直しても利用先へは伝播せず、新しい利用先には何も届かない。

**決めること**

- **案 a: 文面変更で足りるとする。** skill・docs は変更しない。この repository の hook が「これは要約であり、skill の起動ではない」と名乗る状態で終える
- **案 b: 要約を注入する運用そのものへの規範を docs へ置く。** hook は配布されないが、規範は配布される。利用先が hook を書くとき、または既存の hook を見直すときの参照先になる
- **案 c: hook から要約をやめ、規範の所在だけを注入する。** 「作法は `tumeda-dev:think-through` が持つ。適用するには起動する」だけを注入し、原則の列挙を載せない。要約が無ければ、要約を規範として扱う失敗が原理的に起きない

**何がどう変わるか**

案 c は失敗を原理的に消すが、代償が大きい。`think-through` は毎ターン適用する前提の skill であり、要約はそれを起動していない状態でも最低限の作法を効かせるために置かれている。実際、この起点の作業でも「唯々諾々禁止」「修正前合意」は要約から効いていた。所在だけにすると、起動しない限り何も効かなくなる。失敗の原因は要約の存在ではなく、要約が自分を本体と名乗っていたことである。

案 a は今回の repository では正しい状態になるが、同じ失敗が別の利用先で起きたときに参照できるものが残らない。hook が配布されない以上、伝播の手段は規範しかない。

**推す案**

案 b を推す。案 a に加えて、規範を docs へ置く。

書く内容は、hook のような常時注入で規範の要約を渡す場合、その注入が自分を規範そのものと名乗ってはならない、という一点である。要約であること、載っていない範囲があること、本体を適用するには起動が要ることを、注入文面自身が持つ。

案 c を採らないのは、要約の価値と失敗の原因が別だからである。要約は起動していない状態を救うために存在し、失敗は要約が自分を本体と名乗ったことで起きた。名乗りを直せば要約の価値は残る。

#### 提案背景

提案0 が満たす必要のある条件は、同じ失敗が別の利用先で起きたときに参照できるものを残すことである。この repository の hook を直すだけでは、hook が配布対象でないため他へ届かない。

案 b が置く規範は、`docs/documentation_standards/` が扱う範囲にあたる。同directoryは document の書き方の標準を持ち、`core_readers.md` のように「誰が読むか」を扱う file を含む。常時注入される文面は、読み手が選んで読むのではなく強制的に渡される document であり、その性質に応じた規範を持つ場所として整合する。

案 c を選択肢へ残しているのは、失敗を原理的に消す唯一の案だからである。採らない判断をする場合も、その理由（要約の価値と失敗の原因が別である）を記録に残す必要がある。

#### 提案0へのフィードバック

**結果:** 案 a を採用。文面変更で足りるとする。

> a

### 決定

hook の注入文面から断定を外す変更で足りるとし、skill・docs は変更しない。

適用済みの内容は次のとおり。

- `.claude/hooks/think_through_session_start.sh`: 冒頭を「think-through skill の要約（hook による毎ターン注入）。これは要約であり、skill の起動ではない。」とし、末尾に「この要約が載せているのは think-through の一部だけである。design・tasklist・discussion の記録形式、論点の立て方、合意の取り方は含まれていない。`.steering/` 配下を読み書きする前に、`Skill` で `tumeda-dev:task-design` を起動する。」を加える
- `.claude/hooks/think_through_user_prompt.sh`: 冒頭を「think-through 要約（起動ではない）。」とし、末尾に「`.steering/` を扱うなら `Skill` で `tumeda-dev:task-design` を起動する。」を加える

要約そのものは残す。`think-through` は毎ターン適用する前提の skill であり、要約は起動していない状態でも最低限の作法を効かせるために置かれている。失敗の原因は要約の存在ではなく、要約が自分を本体と名乗っていたことである。

`.claude/hooks/` は配布対象ではないため、この変更は利用先へ伝播しない。伝播させる規範を docs へ置くことは、この decision では行わない。

## 論点5: このrepositoryの自称に使う語を何にするか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 語を選ぶ基準と候補

#### 提案0

**何を直すか**

このrepositoryは自身を「正本」と名乗っている。名乗りは五箇所にある。

- `AGENTS.md:9`「このrepositoryが正本のskill plugin。実体は `plugins/tumeda-dev/`。」
- `README.md:7`「共有手順の正本はこのpluginに置く。」
- `README.md:11`「正本repository自身も…正本だけを例外にしない。」
- `README.md:15`「このrepositoryの検査正本は `node scripts/verification/validate-plugin.mjs` である。」
- `plugins/tumeda-dev/skills/escalate-plugin-skill-fix/SKILL.md`: description と本文に「正本repository」が計5箇所

対象外は、相対関係が文中に明示されている用法である。`runtime-execution-contracts.md` の「taskの完了状態の正本はtasklistの `[ ]` / `[x]` である」、`facilitate-discussion` の「discussion fileをsession外の正本とする」、`tasklist-executor` の「`./design.md` を設計の正本として必ず読む」、`steering` の成果物lifecycle、`information_structuring/README.md` の値辞書とcasesのID採番、`function_migration_policy.md` の「二重正本」。これらは何に対する正本かが同じ文の中にある。

**語を選ぶ基準**

1. 実体に即していること。このrepositoryは skill を共有するための plugin を持つ repository である
2. 相対関係を含まないこと。読み手が「何に対する」を補わなくても意味が通る
3. 既存の語彙と衝突しないこと。`利用先repository` という語が既に使われており、その対になる語として読める必要がある

**候補**

- **案 a: `plugin repository`。** 実体そのままで、相対関係を含まない。`利用先repository` と対になる。ただし「plugin を持つ repository」と「plugin である repository」のどちらとも読める
- **案 b: `このpluginのrepository`。** 所有関係が明示され、読み違えが起きにくい。`escalate-plugin-skill-fix` のように文脈が plugin の話で固定されている場所では自然に読める。一方 `AGENTS.md` や `README.md` の冒頭では、「この plugin」が何を指すかがまだ確定していない
- **案 c: 場所ごとに言い換える。** 単一の置換語を決めず、各箇所で意味が通る表現を選ぶ。`AGENTS.md:9` は「このrepositoryは `plugins/tumeda-dev/` の実装を持つ」、`README.md:7` は「共有手順はこの plugin に置き、利用先repositoryへ同じskill本文をコピーしない」、`escalate-plugin-skill-fix` は「plugin repository」

**推す案**

案 c を推す。理由は、五箇所が同じ意味で「正本」を使っていないためである。

`AGENTS.md:9` と `README.md:11` は repository の位置づけを述べており、置き換えるべきは語ではなく文である。`README.md:7` は「コピーを置かない」という規則の理由として使われており、規則そのものは相対関係を持つ（この plugin と利用先の関係）。`README.md:15` の「検査正本」は検査手段が一つであることを言っており、repository の自称ではない。`escalate-plugin-skill-fix` は利用先との対比で使われており、ここだけは対になる語が要る。

単一の語で置換すると、位置づけを述べている箇所が不自然になるか、規則の理由が消える。案 c は各箇所の役割に応じて表現を選ぶため、この不整合が起きない。

案 c を採る場合、`escalate-plugin-skill-fix` で使う対の語は `plugin repository` とする。`利用先repository` と対になり、相対関係を含まない。

#### 提案背景

提案0 が満たす必要のある条件は、指摘された性質を消すことである。指摘は「正本は相対的な言葉で、複写先があって初めて成立する。自身がその文脈において複写先の正本でないとき、またメインのトピックがその正本と複写の関係でないときに正本と呼ばれると、視点の向きが狂う。文脈に優先されて守られるべき存在と読まれてしまう」というものだった。

したがって判定は、置き換え後の語が単独で意味を持つかどうかで行う。`plugin repository` は「plugin を持つ repository」として単独で読める。`正本repository` は「何の正本か」を補わなければ読めない。

五箇所を実際に読み比べると、同じ語が四つの異なる役割で使われていた。repository の位置づけ、コピー禁止規則の理由、検査手段の一意性、利用先との対比である。この観察が案 c を導いた。単一置換の案 a・案 b を残しているのは、置換語を一つに決めた方が以後の判断が要らなくなるという利点があり、その利点と各箇所の自然さのどちらを取るかが判断対象になるためである。

`escalate-plugin-skill-fix` の description も対象に含まれる。description の変更は `docs/documentation_standards/modify_description_policy.md` の規約に従う必要があり、語の決定後にその規約を読んで適用する。

#### 提案0へのフィードバック

**結果:** 案 c を採用。単一の置換語を決めず、場所ごとに言い換える。

> c

### 決定

「正本」の自称を、五箇所それぞれの役割に応じて言い換える。単一の置換語は定めない。

役割は四つに分かれる。

- **repository の位置づけ**（`AGENTS.md:9`、`README.md:11`）: 語ではなく文を書き換える。このrepositoryが何を持つかを述べる形にする
- **コピー禁止規則の理由**（`README.md:7`）: 規則そのものは残す。理由の述べ方から自称を外す
- **検査手段の一意性**（`README.md:15`）: 自称ではない。検査手段が一つであることを述べる形にする
- **利用先との対比**（`escalate-plugin-skill-fix/SKILL.md` の description と本文）: 対になる語が要る。`plugin repository` を使う。`利用先repository` と対になり、相対関係を含まない

規模について、提案0 は「計5箇所」と書いたが誤りである。`grep -c` が行数を数えることを見落として集計していた。実測すると `escalate-plugin-skill-fix/SKILL.md` は26行に「正本」を含み、section見出し `## 正本repositoryの判定` を含むこの skill の中心語彙になっている。`README.md` は4行、`AGENTS.md` は1行である。決定の中身は変わらないが、escalate の書き換えは語の置換ではなく本文全体に及ぶ。

同fileには相対用法も混在する。`:47`「規約はこのskillが持たない。正本は `migration.md` である」と `:90`「次の判断・規約はそれぞれの正本に委ね、複製しない」は、何に対する正本かが文中にあるため変更しない。

相対関係が文中に明示されている用法は変更しない。`runtime-execution-contracts.md`、`facilitate-discussion`、`tasklist-executor`、`steering` の成果物lifecycle、`information_structuring/README.md`、`function_migration_policy.md` が該当する。

description の変更は `docs/documentation_standards/modify_description_policy.md` の規約に従う。

各箇所の完成後の文面は `design.md` の `documentation以外のfile deliverable` が持つ。

## 論点6: 用語の再発を検査で止めるか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 検査を足すかどうかと、禁止語の粒度

#### 提案0

**判断の対象**

`scripts/verification/validate-plugin.mjs` は `forbidText` assertion を持ち、廃止した見出しや固定fieldの再混入検査に9箇所で使っている。同じ仕組みで「正本」の自称の再混入を止められる。

止めるかどうか、止めるなら何を禁止語にするかを決める。

**論点5 の決定と実測が作る前提**

論点5 は、相対関係が文中に明示されている用法を残すと決めた。したがって語そのものを repository 全体で禁止することはできない。

実測した分布は次のとおり。

| file | 「正本」を含む行数 | 言い換え後に残るもの |
| --- | --- | --- |
| `AGENTS.md` | 1 | ゼロ |
| `README.md` | 4 | ゼロ |
| `plugins/tumeda-dev/skills/escalate-plugin-skill-fix/SKILL.md` | 26 | 2行（`migration.md` を規約の正本とする記述、判断・規約をそれぞれの正本へ委ねる記述） |

escalate だけは、言い換え後も相対用法が残る。file 単位で「正本」を禁止すると、この2行が落ちる。

自称が取る形も file によって違う。`AGENTS.md` は「正本のskill plugin」、`README.md` は「共有手順の正本」「正本repository」「検査正本」、escalate は「正本repository」「正本かどうか」「正本だった場合」である。

**候補**

- **案 a: file ごとに禁止語を変える。** `AGENTS.md` と `README.md` は「正本」を禁止し、escalate は「正本repository」だけを禁止する。自称の主要な形を捕まえつつ、escalate に残る相対用法を通す
- **案 b: 三つの file とも「正本repository」だけを禁止する。** 一つの禁止語で済む。ただし `AGENTS.md` の「正本のskill plugin」と `README.md` の「検査正本」は捕まえられない
- **案 c: 検査を足さない。** 言い換えを適用して終える

**推す案**

案 a を推す。

`AGENTS.md` と `README.md` は repository の位置づけと運用を述べる file であり、正当な相対用法がそこへ現れる見込みが低い。この二つでは語そのものを禁止できる。escalate は skill の責務境界を述べる中で規約の所在に触れるため、複合語だけを禁止する。

案 b は禁止語が一つで済むが、実際に存在した自称の三形のうち二つを取り逃がす。検査としての意味が薄い。

案 c を推さないのは、この失敗が「読めば分かるが読まれない」種類だからである。自称は文に自然に馴染み、読み手が違和感を持つまでに時間がかかる。

**受け入れる代償**

将来 `AGENTS.md` または `README.md` で正当な相対用法が必要になったとき、assertion を編集する手間が発生する。そのときは編集の理由を記録する。検査は「二度と書けない」ためではなく、「書くときに理由を残させる」ために置く。

#### 提案背景

提案0 が満たす必要のある条件は二つある。論点5 の決定（相対用法を残す）と両立すること、および実際に存在した自称の形を捕まえることである。

当初の版は「言い換える三つの file は言い換え後にこの語を持たなくなる」を前提に、三つとも「正本」を禁止する案を推していた。実測でこの前提が崩れた。escalate は26行にわたって「正本」を使い、そのうち2行は変更対象外の相対用法である。前提が誤っていたため、file 単位で同じ禁止語を使う案は成立しない。

禁止語の粒度を file ごとに変える形は、`validate-plugin.mjs` の既存の使い方と整合する。同scriptの `forbidText` は `forbidText(relativePath, forbidden, label)` の形を取り、file と禁止語の組を個別に登録する。新しい仕組みを持ち込まない。

#### 提案0へのフィードバック

**結果:** 案 a を採用。file ごとに禁止語を変える。

> a

### 決定

`scripts/verification/validate-plugin.mjs` へ `forbidText` を三件追加する。

- `AGENTS.md` に対し「正本」を禁止する
- `README.md` に対し「正本」を禁止する
- `plugins/tumeda-dev/skills/escalate-plugin-skill-fix/SKILL.md` に対し「正本repository」を禁止する

前二つは repository の位置づけと運用を述べる file であり、正当な相対用法が現れる見込みが低いため語そのものを禁止する。escalate は責務境界の中で規約の所在に触れ、`migration.md` を規約の正本とする記述と、判断・規約をそれぞれの正本へ委ねる記述が残るため、自称の形である複合語だけを禁止する。

将来これらの file で正当な相対用法が必要になった場合は、assertion を編集し、編集の理由を記録する。この検査は再記述を不可能にするためではなく、記述時に理由を残させるために置く。
