# discussion entryの記録形式

このfileは、論点・回・提示・応答・現在stateの保存骨子を定める。必要な部分だけを使い、説明の章見出しや未使用の骨子をdiscussionへ複製しない。
論点選択、採番、状態遷移、合意判定、保存先の範囲限定は `../SKILL.md`、通常の提示準備と応答処理は `../iteration.md`、未収録の履歴の回復は `../record-recovery.md` の手順に従う。

## 適用する表記と保存範囲

Tは論点番号、Iは提案と認識合わせに共通の外向きiteration番号、Mは親論点番号を表す説明用変数であり、保存時には実際の番号へ置き換える。新規論点の初回はI=0とする。論点番号を0から始める指示ではない。

新規discussion fileでは、以下の骨子の見出し深度と所属suffixを使う。既存fileへ論点・回を加える場合は、そのfileの識別表記とiteration兄弟の深度を維持し、配下の見出しも同じ段数だけ移動する。親子関係と読順を保ち、過去見出しを一括変換しない。
新方式で作成したfileは継続時もその方式を使う。内容固有の小見出しへsuffixや連番を一律に付けない。

新規論点を作る前に、結論が現在のdiscussion目的または指定parentの決定・実装範囲を変えるかを確認する。変わらない事項はactiveな論点にしない。
一括proposalから独立decisionを分ける場合は、同一論点内の枝labelではなく、次の論点番号を持つ別論点にする。childだけに親論点を置き、親statusはhandlerの親子規則で導出する。

statusの語彙は `応答待ち / 調査中 / 子論点待ち / 決定 / 保留 / 分解済み` とする。通常の作成中は調査中、提示後は応答待ち、外部条件等による停止は保留とし、親子関係がある場合はその導出を優先する。古いstatusも実際の本文・応答・会話と照合して読む。

書込みはhandlerの安全な更新規則に従い、論点→必要なら回→欄の範囲を一意に特定する。骨子の例やplaceholderを実在する論点・更新対象として扱わない。

## 論点と作成中の回

新規論点には次の骨子を使う。top-levelでは親論点の行を省略する。種別は該当するものを使い、複数なら併記できる。

```markdown
## 論点T: {判断内容を表すタイトル}

**ステータス:** 調査中

**親論点:** 論点M

**種別:** {TBDヒアリング / 認識齟齬 / レビュー指摘}

### イテレーションI（論点T）: {この回で進める内容}

#### 検討記録（論点T・イテレーションI）

{最初に使う目的別formatの実施前入力を保存する}
```

既存論点の次の回は、論点metadataを複製せずiteration以下だけを追加する。現在stateの欄があれば、その前へ置く。
提示種類がまだ決まらない段階では本文・応答欄を作らず、未成立の提案、空の認識合わせ、空の決定で埋めない。内部の調査や判断が増えても、それだけで外向きの回番号を増やさない。

## 検討記録を育てる

`consideration-records/README.md` で目的を選び、該当file全文を読んで記入する。目的変更時も選び直す。共通の読み取りcontractと用途ごとの記入形の詳細はそちらが所有し、このfileへ複製しない。

最初の回では、最初のuser input、finding、既存状態から、その回の提示が満たす必要のある条件を残す。
次の回では、直前の応答と今回の調査から生じた条件、条件を導いたfindingと整理を残す。応答で原因診断や修正scopeが変わったなら、前の診断の何を維持・置換・拡張したかを読み分けられるようにする。原文と評価結果は前の応答欄が所有し、ここへ複製しない。
外部evidenceが採用済み判断を無効にした場合は、evidence、無効になった判断、置換に必要な条件を内容固有の見出しで示す。これらを全回の固定fieldにしない。

実施前に問い・方法・評価軸等を保存し、結果・解釈・残る不足・次action・案への影響を得たら、次actionより前に追記する。具体的な手順と中断復帰は本体に従う。
最終的な提案では条件と案のどの内容が対応するか、認識合わせでは残る未共有前提と回答で進む判断が対応するかを辿れるようにする。

既に提示済みの回や過去の `提案背景` は改名しない。新しく準備する回は共通の検討記録を使い、作成中からの蓄積を提示種類の確定時に移動・再要約しない。

## 提示内容と対応する応答欄を加える

本体が提示可能と判断した同じ回へ、本文を検討記録の直前、対応する空の応答欄を検討記録の直後に加える。保存後の読順は「本文→検討記録→応答欄」とする。
検討記録を別の完成entryへcopyし直さず、同じ回にある蓄積を保持する。通常の提示では本文・検討記録・空の対応応答欄を保存してから提示する。

### 提案を提示する場合

検討記録の直前に置く。

```markdown
#### 提案I（論点T）

{その回の問いを判断できる案}
```

今回の判断に必要な範囲だけ既決内容を示し、完全性のために再掲しない。完全状態そのものが判断対象なら完全版を示す。
`proposal-sections/README.md` から判断対象の理解を助けるpatternを選び、必要なら組み合わせる。複数案なら選択肢patternをwrapperとして使い、各案の内部に別patternを置ける。該当しなければ内容から構成を決める。

独立した説明は「保存構造」「読み取り範囲」「fallback」等の固有見出しへ分け、短く同格な要素だけを箇条書きにする。`総論 / 各論 / ルール / 適用例`や箇条書きを固定しない。抽象と具体が必要でも、疑似箇条書きへ平坦化せず、意味関係を表す段落・見出し・表等を選ぶ。

新規fileで配置・周辺fileとの関係・作らないfileが判断対象なら `structure-tree.md`、新規documentの見出しと内容への合意には `document-heading-outline.md` を使う。合意後に実fileを作成してreviewし、作成前のdiscussionへ本文全文を複製しない。
既存fileの局所変更が読みやすい一つのunified diffへ収まるなら `existing-file-local-diff.md` を使い、全追加・削除行と必要contextを示す。変更hunkを省略せず、変更しない残部は再掲しない。
複数file、file間の対応、または一file内の複数hunkが一つのdecisionとして不可分に変わる場合は、`file-change-set.md` を使う。今回の変更へ含む対象を漏れなく列挙し、beforeからafterへの対応、変えてよい範囲、維持・削除・scope外、完了状態を判断できる変更集合にする。対応の主単位と内部表示はcaseに合わせ、file path、責務・contract、保持する意味等から選ぶ。各対象内部ではtree、機械的置換、完全diff、before / after、outline、flow等を使い分け、同じ表示方式へ揃えない。独立して採否を変えられる変更は、一つの変更集合へまとめず別decisionへ分ける。これらのpatternはすべて `proposal-sections/` 内にある。

検討記録の直後に置き、提示時の可視本文は空にする。

```markdown
#### 提案Iへのフィードバック（論点T）
```

### 認識合わせを提示する場合

検討記録の直前に置く。

```markdown
#### 認識合わせI（論点T）

{確認したい理解と、具体的に回答・訂正してほしい対象}
```

今は提案できない理由、何が共有できれば進めるかを示す。確認済み事実・自分の読解・未確定を区別し、回答によって進む判断を示す。調査結果と読解へ至った理由は検討記録に置く。
本文の構成は対象に合わせる。未提示の具体案や独立decisionの採否を一緒に問わず、調査可能な事実の問い返し・単なる調査報告・調査方針の承認依頼にしない。
初回からI=0で使える。提案と同じ番号系列を使い、別counterや形式だけの提案を加えない。

検討記録の直後に置き、提示時の可視本文は空にする。

```markdown
#### 認識合わせIへの回答（論点T）
```

## 受領した応答を一度保存する

提示時の空欄へ `未回答`、`結果: 未回答` 等のplaceholderを書かず、応答を推測しない。
応答対象と所属を本体で確認した後、対応する同じ番号の空欄へ必要な原文と結果を一度保存する。記入形は次を基本に、補足の段落・表等を内容に合わせる。

```markdown
**結果:** {その回の結果が分かる短い表現}

> {user feedback、review等を必要な範囲で原文のまま示す}

{原文だけでは分からない評価や、得た入力・訂正・残る不足}
```

提案へのfeedbackでは、何が受け入れられ、何が成立しなかったかを示す。結果は固定語彙へ限定しない。原因診断への影響が次の提案に必要なら、「修正要求」だけに丸めず、診断を維持するのか遡るのかを読み分けられる短い表現にする。
認識合わせへの回答では、確認対象に対して得た入力・訂正された理解・残る空白を示す。訂正・一部回答・回答不能も記録できるが、固定の三欄や結果enumにはしない。理解への了承を未提示案への合意へ広げず、経験を問う質問への `ok` を経験の取得とは扱わない。

別decisionや作業再開の指示だけなら、この回への回答として欄を埋めない。応答後に次の回へ進むか、decision確定・別論点・停止へ返すかは本体とhandlerが判断する。
応答が確定した過去の本文・検討記録・応答欄は変更しない。同じ評価結果を上書きせず、決定済みの同一decisionを変えるeventは新しい回へ接続する。

## 必要な現在stateを全iterationの後へ置く

以下は必要な時だけ使う。全entryへ空の欄を常設しない。現在stateは論点に属し、回番号を付けない。

### 仮決定を示す

議論中に現在成立する内容をまとめることが理解を助ける時だけ置く。

```markdown
### 仮決定（論点T）

{その時点で現在有効な仮の判断を自己完結して書く}
```

過去の部分判断を機械的に加算せず、方向転換で無効になった内容は外す。履歴は過去iterationへ保つ。判断の足跡が役立つ時だけ典拠iterationを添える。最終合意時は仮決定を外し、最終結論を決定へ書く。

### 外部条件による停止からの再開位置を示す

同じ未決decisionが外部event・user action・後続phase等を待ち、entryだけでは停止理由と再開位置を特定できない時だけ置く。

```markdown
### 再開条件（論点T）

{今足りないもの、解消を判断するevent・evidence・action、解消後に再開する未決判断}
```

固定の小fieldへ分けず、内容に合う文章・短い列挙・表等を使う。通常のuser応答待ち、consumerによるdecision反映、完了報告、直後の次iteration・次topicへの移動には置かない。
条件成立時は、その結果を新しい回の検討記録へ接続して現在の再開条件を外す。別steering化や後続phaseへの委譲自体が最終判断なら、再開条件ではなく決定へ書く。

### 現在有効な決定を示す

handlerで確定した、その論点の現在有効な最終結論を置く。未決時に確定したように書かない。

```markdown
### 決定（論点T）

{確定した内容と、現在の制約・選択理由を自己完結して書く}
```

過去iterationの判断を機械的に加算せず、`以前の決定`、`決定（更新）`、`決定（最終）`を並べない。userが弱点を受容した場合は、デバッグ経緯ではなく現在契約の制約・選択理由として含める。
別topicがdecision boundaryを保ったまま識別子・path・語彙等を具体化した場合は、過去iterationを変えず、現在の決定だけを典拠付きで同期する。置換理由・影響範囲は後続topicが所有する。decision自体が変わるなら、表現同期で済ませず再開・別論点へのroutingを行う。

固定のネクストアクションfieldは置かない。通常の合意待ち、consumerによる反映、完了を全entryへ反復しない。次の焦点は末尾のactiveな提示で示し、順序・委譲先が合意内容なら決定へ、同じ未決判断の再開位置が停止条件と不可分なら再開条件へ書く。consumerへの具体的なhandoffは維持する。

## 継続・再開・記録回復で保つもの

entry末尾の未決提示を現在の判断対象とし、同じ内容を上部へ複製しない。過去iteration・却下理由・当時の判断を変更・削除せず、「ここまでの議論」等の圧縮要約を作らない。
決定済みの同一decisionを変えるfeedbackやevidenceは、元の応答欄へ追記せず、新しい回の検討記録へ接続する。旧決定を現在表示から外す更新はhandlerの再開手順で行う。scope・情報ownerの移動が独立decisionなら同じ回へ累積しない。同じdecision内で移動前後やowner境界を示す場合は、flow・tree・対応表・散文等を内容に合わせて使う。

reparent・取下げ・chat合意済み記録・事後回復には、handlerと回復手順が判定した部分だけを使う。すべてを作成中→提示待ちの通常順序へ通したり、既に確認できる結果へ空の合意待ちを作ったりしない。
確認できる実際の変遷を時系列に残し、事後記録と確認不能な範囲を明示する。存在しなかった提案・回答・合意や、実施前に保存していたという履歴を創作しない。
