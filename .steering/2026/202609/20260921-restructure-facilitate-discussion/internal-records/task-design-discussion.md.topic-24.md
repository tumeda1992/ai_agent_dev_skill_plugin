## 開始context

このsteeringは、facilitate-discussionの既存能力を保全して構造を分け、判断材料確認・内部検討の逐次記録・認識合わせを組み込む設計である。
productionへの適用前に、三つの実行fileとtemplate群を `faciliate-discussion/` にprototypeとして作成した。
今回は [prototypeレビュー](../prototype-refinement/prototype-maintainability-review.md) の五指摘を扱う。

- ユーザーが承認した作業: レビュー実施と参照先をdiscussionへ記録し、自明な修正はprototypeへ反映する。新しい選択が必要なら論点を立てる。
- 維持する既決条件: 三fileの責務分担、独立したdecisionの分離、不可分な複数file変更の一括提示、二層の独立可読性、目的別記録、入力→実施→結果の保存順。
- scope外: production適用、commit、既存のレビュー原文・過去提示の改変。
- 不足: 各指摘が既決契約の明確化だけで閉じるか、採否基準を変える新しい判断かの区別。

#### 期待との差と原因候補

実行者が毎回同じ解釈へ到達でき、同じ規則を複数fileで保守せずに済むことを期待する。
レビューでは、長文へ埋まった手順、復帰規則の重複、目的別記録への暗黙の接続、図の規則の適用範囲、独立decision判定の広すぎる表現が指摘された。

現時点までの読取でレビュー対象と五指摘の位置を確認した。次に、既決契約との照合と修正を行う。

- 原因候補と確認先
  - 手順・variantが混在した表現: `SKILL.md` の安全書込み、`iteration.md` の回準備・file-change-setを照合する。
  - 正本ownerの重複: 論点22の決定と、handlerの戻り先・iterationの中断復帰表を照合する。
  - 共通記録への入口漏れ: 論点6・7・14・22の契約と、origin-review・六用途fallbackの接続を照合する。
  - 表示scopeの曖昧さ: 旧本文のdiscussion/chat限定と、二層化後の標準参照を照合する。
  - 独立decisionの意味のずれ: 旧本文の判定、不可分なfile-change-set、具体的な部分修正caseを照合する。
- 修正の境界
  - 同じ入力で同じ結論となり、既決のowner・順序を読み取れる形へ戻す変更は反映する。
  - 今まで分けていた案を一つに扱えるようにする等、判断結果が変わる変更は明確化と偽らず、合意を要する案として残す。
- 確認方法
  - 修正前後のcontract対応と、通常・legacy・失敗時の経路を限定して点検する。
  - 同じ意味の保持を静的照合し、独立decisionの基準だけは分割・非分割の具体caseで境界を示す。

この記録より前の読取を実施前保存したとは扱わない。ここから行う分類・修正の入力として保存する。

### 判断: decision分離の基準を、修正可能な箇所から採否の独立性へ置き換えるか

別の問いへの結論を分ける基準への置換を推す。局所修正の可否では、判断の単位を数えられないためである。
ただし旧基準の単なる表記修正ではないので、prototypeへは未反映とする。

#### 判断対象・必要条件・根拠

採否を別々に決めるべき内容を混ぜず、一つの採否を実現する不可分な変更は一緒に扱える基準を作る。
根拠は前の診断、レビュー指摘1、旧SKILLの一leaf一decisionの目的、現在のfile-change-set契約である。

- 必須条件
  - 一部だけの修正要求を、直ちに別decisionの証拠にしない。
  - ファイル数や作業数が複数でも、それだけでは分けない。
  - 独立した結論や、上位確定後にも選択が残る下位decisionは既存routingへ分ける。
  - event到着時と提案保存前の両方で、同じ基準を使う。
- 評価する案
  - 「各部分が別の問いへの答えで、採否を別々に決めた結論を定義できるか」で分ける。
  - 同じ採否の必然的な展開・参照更新と、同じ採否を満たすための局所修正は分けない。
- 確かめる境界
  - basename変更と参照更新、再試行回数と間隔、定義の採用と説明文の訂正、上位の保存方式とその方式内で選ぶ期間を当てる。
  - 局所例外を足して元条件を残す方法と比べ、基準を一箇所へ置く案の説明力と代償を検討する。

#### caseから定めた境界と代償

- basenameを `new.md` にする案と、参照hrefを `new.md` へ直す変更
  - 参照更新だけを却下すれば、改名後のlinkが壊れる。「何と呼ぶか」の採否を実現する必然的な追随であり、一つの変更集合にする。
  - 別名へ修正してほしいという応答も同じ命名decisionの継続である。
- 再試行を3回にする案と、間隔を1秒にする案
  - 回数を3回に確定しても間隔は別に選べる。異なる二つの問いとして分ける。
  - 一つの設定fileへ書くことは、一decisionの理由にならない。
- 用語定義の採用と、その定義を説明した文の誤解を招く表現の訂正
  - 意味を変えずに例や説明を直すなら、定義の採否を満たすための局所修正であり同じdecisionに留める。
  - 定義自体を別の意味へ変える要求も、同じ問いへの別案なら同じ論点の継続である。別の用語の採否まで持ち込まれた場合だけ別decisionになる。
- 保存先を決めた後、その保存先で何日保持するかを選ぶ
  - 上位を確定しても期間の選択が残る。依存があるから一つに束ねるのではなく、既存のchild routingへ分ける。

元条件へ「改名は例外」等を追加する案は採らない。新しい種類の局所修正ごとに例外が必要になり、判定正本を育てられない。
採否の意味を読解する負担は残るが、file数・文章中の修正可能箇所数という代理指標で機械的に分けるより、既存の一leaf一decisionの目的に合う。
主基準はSKILLの一節に置き、event所属判定とiterationの保存前・応答時から参照する。decisionを分けた後の親子routingは変更しない。

### 検証: 四件の明確化が元の経路を保ち、提案を単体で判断できるか

四件の明確化は、限定した静的検査と下記の経路照合で保持を確認した。
agentの実行安定性や、全旧能力の移行完了を保証する結果ではない。

#### claim・合格条件・方法

今回反映した四件について、参照・既存guard・各変更範囲の読み方を限定して検査する。
新しいagent評価や全量移行完了を主張する検証ではない。

- 実行する静的検査
  - integrationのvalidator置換断片をprototypeと既存consumerへ束縛して実行する。production validatorも別に実行し、変更対象外の状態を区別する。
  - 更新した三fileのMarkdown linkとanchor、保存形10+3部品、discussionの実論点番号重複を検査する。
- 意味と経路の照合
  - 安全書込みの新規・既存・重複、継続と決定済み再開、原文応答保存後・提示済み不明を点検する。
  - origin-reviewの追加検討と結果保存だけの場合、六用途fallbackの理由、discussion/chatと内部logの図のscopeを区別できるか読む。
  - 指摘1の変更案を、前の判断blockの四caseへ当てる。
- document-review
  - 作成・更新時の必須観点を当て、削った規則、指示対象、見出しの包含、未合意案と反映済み内容の区別を確認する。

既存ledgerの行位置・逆引き集計はレビュー前のsnapshotである。今回の修正へ無条件で有効とせず、差分の所有先と再照合待ちを明記する。

| 検査 | 結果と限界 |
| --- | --- |
| repository validator | `node scripts/verification/validate-plugin.mjs` は `plugin validation passed`。productionの既存状態を検査したもので、prototypeの意味検証ではない |
| prototype向けvalidator断片 | repositoryと同じhelperにintegration断片を渡し、実行fileとtemplateをprototype、metadataとcallerをproductionへ束縛した。失敗0。保存形10+3部品と既存guardを満たした |

#### 規則と経路の照合

- 安全書込み: 全体再読込→実論点走査→範囲限定→更新／未作成確認→差分確認を保持した。重複は全書込み停止、不在・不整合は対象更新停止、正常な未作成は追加可能という違いも残る。
- 回の準備: 新規・継続・決定済み再開を別項で引ける。旧決定の無効化と履歴保持、再開条件未成立でhandlerへ返す経路、同じeventから二回作らない規則を保持した。
- 復帰: 原文応答まで保存済みなら、iteration表から未完の確定・consumer反映・次準備へ戻る。提示済み不明なら同表で停止する。handlerに同じ具体判定は残さず、確定・同期・事後回復検出を残した。
- origin-review: 追加で比較する場合は判断formatの入力→比較→結果を記録し、handlerへ戻る。得た結果を保存するだけなら、新しい調査・外向き回を要求しない。
- 目的選択: 新しい目的に既存六用途が合わない理由をREADMEのfallbackで示す。見出し変更で表せるものと、必須file読取不能は未該当にしない。
- 図: 判断interfaceはraw text優先を保持し、内部logには標準のmermaid優先を使う。図そのものの必要性は情報関係から選ぶ。

#### document-reviewと今回の検証限界

作成・更新時の濃さ、記法、命名、指示対象、既存記述の更新方針、機密性を当てた。
実行者が停止条件・入口差分・共通保存順をそれぞれ引けること、削除した具体復帰分岐がiterationへ残ること、未合意の分割基準を反映済みと読めないことを確認した。
fallback条件がiterationとREADMEの二箇所へ重複していた点を検出し、READMEを正本、iterationを参照へ修正してからvalidatorを実行した。

レビュー前の独立A/B/C評価を今回の変更後の再実行結果とは呼ばない。
今は四件の明確化と一件の提案に検証範囲を限定し、指摘1の合意後に変更行のledger対応と逆引き位置を更新する。

### 調査: レビュー反映後、ユーザーが選ぶ必要のある設計事項が残っているか

#### 問い・探索範囲・方法

保留されていたユーザー質問へ、未決設計と実作業を区別して答える。
対象はdesign全文、全24実論点の現在status・decision・親子依存、変更のroutingとする。
予備読取では、古い「validator具体実装は未決」と現在の実装案への参照が併存していたため、単語の存在で未決と判定せず後続の確定内容を照合する。

1. code fence・引用・comment内の例を除外して実論点を抽出し、現在stateと全childの解決状態を確認する。
2. design全文の未決・未完成記述を、現在decision、具体化済みの保存設計・validator/caller設計・移管三件へ対応付ける。
3. 「ユーザーが選ぶ設計」「既決から進める整合・検証作業」「production適用等の未承認action」を区別する。

過去の提案や却下理由を改めて設計し直す調査ではない。
既決内容への同期漏れなら文書を同期し、真に残る意味選択が見つかった時だけ次論点にする。
このoriginのdoc-enricher reviewも提案modeで一度だけ確認し、既存skill・標準にある規則をREADMEへ重複させない。

#### 言える範囲と調査の終了

現時点で、ユーザーが新しく選ぶ必要のある設計上のtrade-offは見つからなかった。
以前のdecisionに残る「この合意には含めない」「未決」は、後続の決定・通常具体化と合わせて読むことで解決先を追える。
未適用・未検証を新しい設計選択として問い直す必要はない。

これは全量移行の完了判定ではなく、レビュー反映後の現在の未決確認である。
そのためこのturnでproduction適用や全面再検査へ広げず、保留されていたユーザー質問へ以上を返す。
将来の照合で新しい意味変更が必要と判明した場合は、その時点で通常の論点へ戻す。

origin単位のdoc-enricher reviewは提案modeで一度実施した。
今回のdecision粒度の規則はSKILL本文、記録の読み方はformat群と既存標準が所有し、prototype READMEも完成形と検証境界への入口を持つ。
新たにREADMEへ保存すべき独立した知識はなく、重複となるため追加提案は行わない。
