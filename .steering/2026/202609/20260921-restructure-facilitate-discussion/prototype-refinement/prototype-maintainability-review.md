# 仮構成の保守性・解釈安定性レビュー

## 判定と対象

責務分割と、判断材料を整えてから提示する内部loopの方向は成立している。
ただし、現在の本文を「今後も同じ境界と順序で実行でき、変更箇所も特定しやすい記述」としては合格にしない。
主な問題は、契約の欠落よりも、判断基準の境界、手順を表す記法、同じ規則の複数箇所への配置にある。

対象は [SKILL.md](../faciliate-discussion/SKILL.md) と [iteration.md](../faciliate-discussion/iteration.md)。
参照先の保存形・目的別format・回復手順も、二つの本文の意味を確認する範囲で読んだ。
レビューによる対象本文の変更は行っていない。

レビュー対象のSHA-256は次のとおり。

- `SKILL.md`: `f84a5aea731a270534363517afb3bb20bd6ed53dcd16d5fac804b12db96ec702`
- `iteration.md`: `94938440f341bf3d3d49ec11b22bce6b2bb542971bfba2cea7d9ab056ae420af`

重点標準は [expression_notation.md](../../../../../plugins/tumeda-dev/docs/documentation_standards/expression_notation.md) と
[content_density.md](../../../../../plugins/tumeda-dev/docs/documentation_standards/content_density.md)。
document-reviewの作成・更新観点として、命名、指示対象、既存記述の直し方、機密性も確認した。
旧production本文との比較では、移設前から残る判断基準や図の規則も今回の対象に含めた。
既存契約を保全できたことと、その契約を今後も安定して解釈できることは別に判定する。

## 指摘1: 部分修正と独立decisionの区別が判定基準から抜ける

優先度は高い。採番・論点分離・合意回数が読み手によって変わる可能性がある。

対象は `SKILL.md` の「workflow全体で守る不変条件」、レビュー時点の92行。
次の基準を独立decision数の判定に使っている。

> ユーザーが「ここは良いがここは違う」と言える箇所がいくつあるか

ユーザーは一つの案の表現、具体化、適用方法にも部分修正を求められる。
部分修正できる箇所の数だけでは、採否が独立したdecisionの数を判定できない。
現状は、そのあと直ちに「二つ以上あるなら……一つの提案へ入れない」と進むため、
読み手によって細部の修正まで論点を分離する解釈が成立する。

`iteration.md` の「提案または認識合わせを形にする」、90行では、
複数fileや複数hunkが一つのdecisionとして不可分に変わる場合を認めている。
二つの記述の接続を読者に推論させず、独立性の判定そのものへ不可分な変更との境界を含める必要がある。

修正の方向は、部分的な賛否ではなく、別々に採否を決めても各結論が成立するかを判定すること。
一つの判断対象に含まれる具体化・修正と、別の目的や契約を選ぶ判断を区別する。

- 分ける例: retry上限とretry間隔をそれぞれ採用・却下できる。
- 分けない例: basename変更と、その名前を参照する箇所の追随は、同じ変更を成立させる変更集合である。
  - 参照の直し方へfeedbackが出ても、それだけでbasename変更とは別の採否を持つdecisionにはならない。
- 既決事項の表記修正: 新しいscopeや方針を選ばない変更は、現在本文の機械的適用規則と接続する。

この判定の正本を一箇所に持ち、保存前の点検と応答routingから参照する。
「分離しすぎない」という禁止を追加するだけでは、独立性の定義が曖昧なまま残る。

## 指摘2: 手順・variant・終了条件が散文の中で混線している

優先度は中。文を読み終えれば要素は拾えるが、実行順と適用条件を読者が再構築する必要がある。

主な対象は次の三箇所。

- `SKILL.md` の「書込対象を範囲限定する」、125〜131行。
  - 全体再読込、実論点走査、更新範囲の限定、既存欄の異常、新規挿入、保存後の差分確認に加え、
    legacy見出し、番号変数、status優先順位まで一続きに置かれている。
- `iteration.md` の「作成中の回と検討記録を用意する」、28〜41行。
  - 新規・継続・再開の分岐、parent同期、回番号、作成中のstatus、保存順、旧記録への接続、原文の保持が段落で続く。
- `iteration.md` の「提案または認識合わせを形にする」、90行。
  - file-change-setの適用条件、必要情報、表示方法の選択、独立decisionの除外が一行の326文字に入っている。

これは改行だけの問題ではない。
順序、条件から行き先への対応、同格の保持条件、判断理由という異なる関係が、同じ記法に収まっている。
局所修正でも、どの条件がどの処理へかかるかを段落全体から読み直すことになる。

修正は関係に合わせて行う。

1. 「書込対象を範囲限定する」は、読込・識別・更新・差分確認の順序を番号付き手順にする。
2. 新規／継続／再開は、各variantの入口条件と準備する内容を分けて示す。
   短い対応は表、説明が育つvariantは個別見出しにする。
3. variant共通の保存順と完了条件を、その分岐の後に一箇所で置く。
4. legacy互換・変数の意味・status導出は、それぞれを変更する人が探せる規則として分離する。

例えば、安全な書込みの背骨は次の順序として取り出せる。

1. 対象file全体を再読込し、実論点の番号重複がないことを確認する。
2. 論点、必要なら回、更新欄の順に所属・役割・終端を照合する。
3. 既存更新なら対象欄の一意性、新規追加なら未作成と挿入位置の一意性を確認する。
4. 確認した範囲だけを書き込む。
5. 差分で、対象欄・必要な現在state・親status以外を変更していないことを確かめる。

ここに全variantの例外を詰め込むのでなく、異常時の停止範囲とlegacyの識別規則を別に参照する。
理由の説明は残す。長い段落を丸ごと箇条書きにしても、順序と並列の混線は直らない。

## 指摘3: 中断復帰の具体規則がhandlerと本体で二重管理される

優先度は中。現在は概ね同じ意味だが、保存境界の進化時に変更箇所が二つになる。

対象は `SKILL.md` の「共通本体へ接続する」、265〜268行と、
`iteration.md` の「保存境界から中断処理へ戻る」、114〜129行。

handler側にも、保存済み合意なら確定、修正応答なら次準備、未提示なら提示、提示済みか不明なら停止、という具体的な復帰規則がある。
本体側の表にも同じ境界を持ち、結果未保存や背景再構成からの復帰を加えている。
本体への参照はあるが、handler側の記述が単なる呼出条件なのか、それ自体も更新すべき正本なのかが明確でない。

修正の方向は、同じ中断処理の復帰表を `iteration.md` の正本とすること。
handlerは、通常の中断復帰へ渡す条件、record-recoveryへ渡す条件、返却された結果に応じて自身が行う確定・同期だけを所有する。
handlerの説明に必要な要約は残せるが、具体的な保存境界を独立した条件列として再定義しない。

保守時には、例えば「内部logの結果保存後、discussion背景保存前」の扱いを変更した時、
その復帰先の規定を一箇所で直せるかを確認する。
consumer反映のownerなど、異なる責務の規則まで本体へ集める必要はない。

## 指摘4: decision後reviewと目的別formatの接続が暗黙である

優先度は中。独立評価に適用の揺れが実際に出ている。

対象は `SKILL.md` の原因owner節、247行と、
`iteration.md` の「判断材料を確かめ、検討記録を育てる」、59〜67行。

本体は新しいblockの前に目的を選び、該当format全文を読む手順を持つ。
一方、handler内のdecision後 `doc-enricher` reviewは、候補の有無に応じた結果保存を直接規定している。
その検討過程も同じ目的選択・実施前入力・結果保存を通るのか、単なる適用結果として保存するのかを、読み手に判断させている。

独立評価Cでは、後続blockが「確認: 反映済みの決定から残す共有知識の有無」という独自形式になった。
六用途に当たらない理由は記録されていない。
ただし、この記録には対象・方法・候補を採らない根拠があり、内容全体を「説明不足」とは判定しない。
「確認」という語だけを禁止しても、接続の曖昧さは残る。

修正の方向は、handler側のreviewで実質的な調査・比較・一般化をする場合に、共通の記録手順へ明示接続すること。
既に得た結果を適用結果として一度保存するだけなら、不要な内部loopを作らない。
六用途のfallbackも、既存の目的では何を表せないのかを判定できるようにする。
既存formatに合うのに見出しが面倒という理由で自由形式へ移ることと、新しい目的があることを区別する。

この接続を正せば、同じ出来事を目的別formatへ落とすか独自形式へ落とすかという揺れを、禁止事項の増殖でなく責務境界から抑えられる。

## 指摘5: 図の優先順位と標準の例外関係が未整理である

優先度は中。読み手がどの規範を適用するかで記法が変わる。

対象は `SKILL.md` の95行・155行・327行。
skillはdiscussionとchatの図についてアスキーアートを第一選択とする。
毎回全文を読むよう要求する `expression_notation.md` は、図ならmermaidを第一選択とする。

raw textでも関係を読めることは、このskillの具体的な成果条件として成立している。
問題はその条件自体ではなく、標準の優先順位に対する例外の適用範囲と理由が明示されていないこと。
これは旧本文から保持した規則であり、移行によって新しく生じた欠落とは区別する。

修正の方向は、raw textを読むconsumerへ出す図の例外として、対象範囲と選択理由を明示すること。
内部log、discussion、chatのどこまで例外に含むかを定め、標準を適用する範囲との境界を示す。
一般標準の内容を再掲したり、reviewだけを理由に一律mermaidへ変更したりしない。
意味の関係から図・表・箇条書き・散文を選ぶ原則は、そのまま標準へ委ねる。

## 宣言的な成果と固定するworkflowの境界

宣言的な記述と手続き的な記述のどちらかへ全体を揃える必要はない。
このskillでは、異なる探索方法でも受け入れられる部分と、順序が変わると正当性を失う部分がある。

| 対象 | 本文が定めるもの |
| --- | --- |
| 保存・合意・復帰 | 必要な順序、証拠、状態遷移、停止条件 |
| 材料の充足・decision独立性・format適用 | 判断基準、成立条件、境界を区別できる具体例 |
| source探索・分析・背景構成 | 成果条件と限界の説明。方法は内容から選ぶ |

例えば、調査sourceを探す順番は対象によって変えられる。
しかし結果を次action前に保存する境界は、後から過程を再構成できるかに影響するので固定する。
探索方法の自由と、判断・保存の順序を守ることを同じ規則で縛らない。

背景再構成の101〜104行は、方法の固定ではなく到達状態を説明している。
問いになった理由、必要条件、案を規定した事実・反証、受容する代償まで扱うので、保持する価値がある。
ここを固定フィールドの消化に変えると、内容に応じた因果の説明を潰す。

逆に、保存前のdecision分離や中断復帰は、賢い読み手なら補えることを期待して曖昧に残せない。
合格条件と当たらない例を示し、別の読み手でも同じ境界を取れるようにする。
アンチパターンは、その境界を誤読しやすい箇所へ置く。
全見出しへ同じ「禁止」「悪い例」を機械的に付けることは求めない。

## 保持すべき構成と修正のまとまり

次の構成は、今回の指摘を直す時にも保持する。

- handler、本体、事後回復という責務分割。
- 本体の二入口と、自力で取れる不足を内部loopで解消する経路。
- 内部logとdiscussion背景の独立可読性。
- 実施前入力、結果保存、背景再構成、提示という保存境界。
- `iteration.md` の中断復帰表。
- 原文の応答と具体的な判断結果を分け、認識合わせの完了をdecisionの成立と扱わない規則。

修正のまとまりは三つに分けられる。

1. 判断基準: 指摘1の独立性と、指摘4のformat適用境界を具体化する。
2. workflow表現: 指摘2の関係別記法と、指摘3の正本整理を一緒に行う。
3. 規範接続: 指摘5の標準例外を明示する。

指摘2・3は、禁止や補足を一文ずつ追加して済ませる修正ではない。
対象節の実行関係を組み直し、旧契約を新しい手順・条件・理由へ対応させる。
それを既存ledgerへ戻して照合することで、可読性の改善で機能を落とす振動も防げる。

レビューは、強いmodelなら必ず成功するという保証や、model間の性能比較を行ったものではない。
同じ入力に対して本文から複数の実行解釈を取り出せる箇所と、その変更責務を特定した。
独立評価の三入力も、全経路の安定性を実証したものとは扱わない。
