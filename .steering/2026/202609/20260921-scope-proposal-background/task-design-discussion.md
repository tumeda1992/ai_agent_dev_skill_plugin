# 議論記録

## 論点1: `提案背景` の定義をどこへ書くか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 修正箇所を決める

#### 提案0

三案から選ぶ。

##### a. `2.3.1` の手順5 だけを直す

```diff
-5. 新しい`提案背景`へ、直前のfeedbackから今回満たす必要が生じた条件と、新proposalのどの内容がそれを満たすかを書く。feedback原文と評価結果は直前iterationが所有するため複製しない。原因診断または修正scopeが変わった時は、前の診断の何を維持、置換、拡張したかを読み分けられるようにする。
+5. 新しい`提案背景`へ、今回の提案が満たす必要のある条件、その案へ至るまでに確認したfindingと思考記録、新proposalのどの内容が条件を満たすかを書く。条件は直前のfeedbackから生じたものと、調査の結果として生じたものの両方を含む。イテレーションが起きた背景、feedback原文、評価結果は直前iterationの`提案N-1へのフィードバック`が所有するため複製しない。原因診断または修正scopeが変わった時は、前の診断の何を維持、置換、拡張したかを読み分けられるようにする。
```

`2.2` の手順4 は変えない。

##### b. `2.2` と `2.3.1` の両方を直す

a の変更に加えて、`2.2` 手順4 も次へ直す。

```diff
-4. `提案背景`には、最初のuser input、finding、既存状態を必要な範囲で示し、提案0が満たす必要のある条件と、提案0のどの内容がそれを満たすかを書く。原因追跡、discussion scopeへ属する理由、別decisionとして分けた理由等は、proposalを評価するために必要な時だけ内容固有の見出しや段落で示す。
+4. `提案背景`には、最初のuser input、findingと思考記録、既存状態を必要な範囲で示し、提案0が満たす必要のある条件と、提案0のどの内容がそれを満たすかを書く。原因追跡、discussion scopeへ属する理由、別decisionとして分けた理由等は、proposalを評価するために必要な時だけ内容固有の見出しや段落で示す。
```

##### c. 共通部分を一箇所へ集約する

`2. 論点を扱う` の「論点levelで守る契約」へ `提案背景` が持つものを定義し、`2.2` 手順4 と `2.3.1` 手順5 は差分だけを書く。

```text
2. 論点を扱う
└── 論点levelで守る契約
      「`提案背景`は、その提案が満たす必要のある条件、その案へ至るまでに
        確認したfindingと思考記録、提案のどの内容が条件を満たすかを持つ。
        イテレーションが起きた背景は`提案N-1へのフィードバック`が所有し、
        `提案背景`へ複製しない」
      ↑
      ├── 2.2 手順4      「提案0では、最初のuser inputと既存状態を起点として示す」
      └── 2.3.1 手順5    「提案1以降では、条件が直前のfeedbackから生じたものと
                          調査の結果生じたものの両方を含む」
```

**推す案は a。**

#### 提案背景

**この論点が扱う範囲。** 親 phase の DoD は「`2.2` と `2.3.1` のどちらを直すか、両方を直すかが決まり、反映されている」を含む。どこを直すかが決まらないと、何を書くか（TBD 2）と責務境界をどう書くか（TBD 3）の書き場所が決まらない。

**調査で確認した現在の定義。**

`提案背景` という語は `SKILL.md` に 13 箇所現れるが、定義しているのは 2 箇所だけで、残る 11 箇所は参照である（不変条件、論点levelの完了gate、`2.1.1`、`2.3.3`、`3.2` 等）。

二つの定義を並べると、共通部分と差分に分かれる。

| | `2.2` 手順4（新規論点） | `2.3.1` 手順5（iteration） |
| --- | --- | --- |
| 共通 | 提案0が満たす必要のある条件と、提案0のどの内容がそれを満たすか | 新proposalのどの内容がそれを満たすか |
| 材料 | 最初のuser input、**finding**、既存状態 | 直前のfeedbackから今回満たす必要が生じた条件 |
| 除外 | （明示なし） | feedback原文と評価結果は直前iterationが所有するため複製しない |
| 追加で書いてよいもの | 原因追跡、discussion scopeへ属する理由、別decisionとして分けた理由等を、proposalを評価するために必要な時だけ | 原因診断または修正scopeが変わった時は、前の診断の何を維持、置換、拡張したか |

**a を推す理由。**

第一に、縮退が起きているのは iteration 側だけである。`2.2` は材料として `finding` を挙げており、さらに「原因追跡...proposalを評価するために必要な時だけ内容固有の見出しや段落で示す」として、提案へ至った経緯を書く余地を明示的に持つ。一方 `2.3.1` は材料が「直前のfeedbackから生じた条件」だけで、調査結果の置き場が無い。引き渡された提案が挙げた実例（提案5）も iteration であり、`2.3.1` が適用される場面だった。

第二に、`modify_description_policy.md` が「修正で増えた分は、増えた理由を疑う。指摘された箇所ほど厚くなるのが自然な力学なので、厚みが読者の必要から来ているのか、指摘への応答から来ているのかを分ける」と定めている。両方を直す b は、`2.2` 側に問題が観測されていないまま厚くする形にあたる。

**b を採らない理由。** `2.2` へ「思考記録」を足す変更は、`finding` との差が読み手に伝わりにくい。`finding` が調査で確認した事実、思考記録がそこから案へ至る過程だとしても、両者が並ぶと「必要な範囲で示し」の対象が曖昧になる。iteration 側で必要なのは、feedback 起点しか材料に挙がっていない点を埋めることであり、`2.2` にその欠落は無い。

**c を採らない理由と、それでも検討した理由。**

`how_to_write_workflow.md` は「情報は、意味を欠かずに置ける最も狭い scope へ置く。狭すぎると、同じ意図や rule が複製され、適用範囲が分裂する。広すぎると、関係のない procedure まで縛り、局所条件から意味を切り離す」と定める。共通部分が二箇所にあることは、この基準では複製にあたりうる。

ただし今回の二箇所は、完全な複製ではない。`2.2` は「提案0が満たす必要のある条件」、`2.3.1` は「新proposalのどの内容がそれを満たすか」と、主語と focus が違う。集約すると、新規論点と iteration で材料が違うという実態を、集約先と差分の二箇所に分けて読ませることになる。手順を読みながら書く agent にとっては、その場で完結している方が読みやすい。

加えて、集約は `2.2` と `2.3.1` の両方を書き換える変更になり、b と同じく `2.2` 側を触る。観測されていない問題のために構造を変えることになる。

**a を採った場合に残る非対称。** `2.2` が `finding`、`2.3.1` が「findingと思考記録」となり、用語が揃わない。これを揃えるかどうかは TBD 2（何を書くか）で扱う。今回は修正箇所だけを決める。

#### 提案0へのフィードバック

**結果:** a を採用。

> a

### 決定

`2.3.1` の手順5 だけを直す。`2.2` の手順4 は変えない。

縮退が起きているのは iteration 側だけである。`2.2` は材料として `finding` を挙げ、さらに「原因追跡...proposalを評価するために必要な時だけ内容固有の見出しや段落で示す」として提案へ至った経緯を書く余地を持つ。`2.3.1` は材料が「直前のfeedbackから生じた条件」だけで、調査結果の置き場が無い。引き渡された実例も iteration であり `2.3.1` が適用される場面だった。

`2.2` 側に問題が観測されていない以上、そこを厚くすることは `modify_description_policy.md` が禁じる「指摘への応答で増やす」形にあたる。

`2.2` が `finding`、`2.3.1` が別の語になる非対称が残る。用語を揃えるかは論点2 で扱う。

## 論点2: `提案背景` が持つものをどこまでとするか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 範囲を決める

#### 提案0

`2.3.1` 手順5 が `提案背景` へ書かせる内容の範囲を、三案から選ぶ。

##### a. 条件を導いた finding とその整理まで

```text
提案背景が持つもの
├── 提案が満たす必要のある条件
├── その条件を導いた finding と、finding を整理した結果
└── 提案のどの内容が条件を満たすか
```

引き渡された実例に照らすと、提案5 の本体にあった「過去の実績から拾った 10 行の表」「実績三件の列挙」が finding、「それを束ね直した内訳」が整理にあたる。三つとも `提案背景` へ移る。

##### b. a に加えて、採らなかった案とその理由

```text
提案背景が持つもの
├── 提案が満たす必要のある条件
├── その条件を導いた finding と、finding を整理した結果
├── 検討したが提示しない案と、提示しない理由
└── 提案のどの内容が条件を満たすか
```

選択肢として提示する案は `提案N` が持つ。ここで扱うのは、検討したが選択肢に載せなかった案である。

##### c. a に加えて、前提の確認結果

```text
提案背景が持つもの
├── 提案が満たす必要のある条件
├── その条件を導いた finding と、finding を整理した結果
├── この提案が依拠する前提と、それを確認した結果
└── 提案のどの内容が条件を満たすか
```

**推す案は a。**

#### 提案背景

**この論点が扱う範囲。** 論点1 で修正箇所が `2.3.1` 手順5 に決まった。次は、その手順が `提案背景` へ何を書かせるかを決める。範囲が決まらないと文面が書けない。

**引き渡された提案が求めているもの。** 利用者の原文は次である。

> 提案と調査結果が混ざるなら提案背景側に書いてほしい。文字通りの背景、イテレーションが起きた背景しか書いてなくて、提案自体の背景としての調査結果や思考記録が提案側に寄ることがそこそこある

「調査結果」と「思考記録」の二つが挙がっている。調査結果は finding、思考記録は finding から案へ至る整理にあたる。a はこの二つを覆う。

**a を推す理由。** 実例で `提案N` から移すべきだったものが、a の範囲にちょうど収まる。提案5 の本体は表・列挙・束ね直しの三つで構成されており、どれも「条件を導いた finding とその整理」である。b が扱う「採らなかった案」も c が扱う「前提の確認結果」も、この実例には存在しなかった。観測された問題を解く範囲として a で足りる。

**b を採らない理由。** 採らなかった案の置き場は、既に別の場所が持つ。`proposal-sections/README.md` は複数案を提示する場合に `compact-options.md` または `detailed-options.md` を wrapper として使うと定めており、**選択肢として並べる案は `提案N` が持つ**。選択肢に載せなかった案については、`facilitate-discussion` の不変条件が「feedback確定後の過去iteration、却下理由、当時の判断内容を変更・削除しない」として過去 iteration に置くことを前提にしている。`提案背景` へ新たに置き場を作ると、同じ判断が複数の正本を持つ。親 design が phase 間で共有する方針として挙げた「同じ判断を複数の正本が持たない」に反する。

**c を採らない理由と、それでも検討した理由。** 「この提案が依拠する前提と、それを確認した結果」は、この roadmap の phase `proposal-decidability` が扱う領域と重なる。あちらは「提案が判断できる案になっているかを何で確かめるか」を設計する phase であり、前提の確認はその判定材料になりうる。いま `提案背景` の定義へ前提の確認結果を入れると、`proposal-decidability` が判定材料を設計する前に置き場だけが決まる。**この phase は `proposal-decidability` より先に実行されるため、後続の設計余地を先に狭めることになる。** 親 roadmap の依存は `proposal-background-scope → proposal-decidability` であり、こちらが渡すのは「`提案背景` の確定した定義」までである。前提の確認結果を含めるかは、後続が判定材料を決めたうえで必要なら戻ってくる形が筋になる。

**a を採った場合の用語。** 論点1 で残した非対称（`2.2` が `finding`、`2.3.1` が別の語）について、a では `finding` を使う。`2.2` と同じ語になり、非対称が解消する。「思考記録」という語は使わず、「finding を整理した結果」とする。整理が何を指すかは実例で地を作れる。

#### 提案0へのフィードバック

**結果:** a を採用。

> a

### 決定

`2.3.1` 手順5 が `提案背景` へ書かせる範囲を、次の三つとする。

```text
提案背景が持つもの
├── 提案が満たす必要のある条件
├── その条件を導いた finding と、finding を整理した結果
└── 提案のどの内容が条件を満たすか
```

採らなかった案は `提案背景` へ置かない。選択肢として並べる案は `提案N` が `proposal-sections` の wrapper で持ち、選択肢に載せなかった案は過去 iteration が持つ。新たな置き場を作ると同じ判断が複数の正本を持つ。

前提の確認結果も置かない。phase `proposal-decidability` が「提案が判断できる案かを何で確かめるか」を設計する際の判定材料になりうるため、先に置き場だけを決めると後続の設計余地を狭める。必要なら後続から戻る。

用語は `finding` を使う。`2.2` と同じ語になり、論点1 で残した非対称が解消する。「思考記録」という語は使わず「finding を整理した結果」とする。

## 論点3: 「イテレーションが起きた背景」を除外対象として明示するか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0: 除外の書き方を決める

#### 提案0

`2.3.1` 手順5 の除外部分をどう書くかを、三案から選ぶ。

##### a. 現在の記述のまま変えない

```text
feedback原文と評価結果は直前iterationが所有するため複製しない。
```

##### b. 「イテレーションが起きた背景」を並べて足す

```text
イテレーションが起きた背景、feedback原文、評価結果は直前iterationの
`提案N-1へのフィードバック`が所有するため複製しない。
```

##### c. 既存の語と同じものだと明示する

```text
feedback原文と評価結果は直前iterationの`提案N-1へのフィードバック`が所有する
ため複製しない。イテレーションが起きた背景はこの二つが持つ。
```

**推す案は a。**

#### 提案背景

**この論点が扱う範囲。** 親 phase の DoD は「イテレーションが起きた背景を `提案N-1へのフィードバック` が持ち、`提案背景` へ重ねて書かないことが読み取れる」を含む。現在の記述でこれが読み取れるか、書き足す必要があるかを決める。

**実例で起きたことを見直した結果、当初の見立てが変わった。**

design の初稿は「現在の `2.3.1` は『feedback 原文と評価結果は直前 iteration が所有するため複製しない』とだけ書いており、評価結果と『イテレーションが起きた背景』が同じものかが読み取れない」として、書き足す方向を前提にしていた。

しかし実例を精査すると、提案5 の `提案背景` が「提案4 から何を引き継ぎ、何を捨てるか」だったのは、**現在の記述が明示的に求めている内容**である。`2.3.1` 手順5 は「原因診断または修正scopeが変わった時は、前の診断の何を維持、置換、拡張したかを読み分けられるようにする」と定めており、提案5 の背景はこの指示どおりに書かれていた。

つまり実例で起きた問題は「イテレーション背景を重ねて書いた」ことではなく、**「finding を書く指示が無かったため finding が無かった」**ことである。これは論点2 の decision で解消する。

**a を推す理由。**

第一に、「イテレーションが起きた背景」は `提案N-1へのフィードバック` が持つ二つ（feedback 原文と評価結果）と同じものを別の語で呼んだものである。`naming/core.md` は「意味が同じなら、その語こそが正しい名前である。避けて別の語を作ると、読み手は確立した語との差を探すことになる。差がないのに別名を与えると、差があるという誤った示唆を与える」と定める。b は同じ構造の誤りにあたる。

第二に、`modify_description_policy.md` が「修正で増えた分は、増えた理由を疑う。指摘された箇所ほど厚くなるのが自然な力学なので、厚みが読者の必要から来ているのか、指摘への応答から来ているのかを分ける」と定めている。今回の追加は、指摘を受けた箇所へ指摘者の語彙をそのまま持ち込む形になる。

第三に、論点2 の decision によって `提案背景` が持つものが三つに確定した。持つものが確定すれば、それ以外を書かないことは定義から導かれる。除外の列挙を増やさなくても、書く側は「finding と条件と対応」を書けばよいと分かる。

**c を採らない理由。** 「イテレーションが起きた背景はこの二つが持つ」という一文は、読者が自分で抱く誤解ではなく、**この議論の経緯から生じた誤解**へ当てている。`modify_description_policy.md` の判定は「その否定を、doc しか読んでいない人が自分で思いつくか」である。`提案背景` の定義を読む agent が「イテレーションが起きた背景はどこへ書くのか」と自問するとは限らない。その語は skill 本文に存在せず、この議論で持ち込まれたものである。

**a を採った場合に残るもの。** 「原因診断または修正scopeが変わった時は、前の診断の何を維持、置換、拡張したかを読み分けられるようにする」は現在の記述のまま残る。これは条件付き（変わった時だけ）であり、毎回書くことを求めていない。論点2 で finding が加わることで、`提案背景` の中身は「条件・finding・対応」が主、「診断の変遷」が条件付きの従、という配分になる。

#### 提案0へのフィードバック

**結果:** a を採用。

> a

### 決定

`2.3.1` 手順5 の除外部分は現在の記述のまま変えない。「イテレーションが起きた背景」という語を skill へ持ち込まない。

この語は `提案N-1へのフィードバック` が持つ二つ（feedback 原文と評価結果）を別の語で呼んだものであり、並べると読み手が差を探す。論点2 で `提案背景` が持つものが三つに確定したため、それ以外を書かないことは定義から導かれる。

実例で `提案背景` がイテレーション背景だけだったのは、重ねて書いたためではなく finding を書く指示が無かったためである。論点2 の decision で解消する。
