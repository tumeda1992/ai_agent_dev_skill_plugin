# Design: `提案背景` が提案自体の背景を持つようにする

## 元の依頼内容

利用先 repository から `escalate-plugin-skill-fix` で引き渡された提案のうち、提案2 を扱う。

`facilitate-discussion` の `提案背景` の定義は二箇所にある。

- 新規論点（`2.2`）: 「最初の user input、finding、既存状態を必要な範囲で示し、提案0 が満たす必要のある条件と、提案0 のどの内容がそれを満たすかを書く」
- iteration（`2.3.1`）: 「直前の feedback から今回満たす必要が生じた条件と、新 proposal のどの内容がそれを満たすかを書く」

iteration 側は「直前の feedback から生じた条件」だけを指定している。結果、`提案背景` が「イテレーションが起きた背景」に縮退する。提案そのものの背景、すなわちなぜこの案へ至ったかの調査結果と思考記録は、置き場が定義されていないため `提案N` 側へ流れ込む。流れ込んだ提案は、選ぶべき案と、その案へ至った経緯が混ざり、判断対象が特定できなくなる。

加えて、イテレーションが起きた背景は `提案N-1へのフィードバック` が既に持っている。`提案背景` が同じことを書くと二重記録になる。

### 利用先 repository での実例

ある論点の提案5 は、本体の大部分が調査結果だった（過去の実績から拾った 10 行の表、実績三件の列挙、それを束ね直した内訳）。一方、同じ iteration の `提案背景` は「提案4 から何を引き継ぎ、何を捨てるか」であり、イテレーションが起きた背景だけを書いていた。調査結果と思考記録が提案側に寄り、背景側にイテレーション背景しか無いという形がそのまま現れた。この提案5 は feedback で「提案の形を取っていない」と確定した。

> この提案5は何を書いてるの？ 提案なの？

### 想定する修正の方向

`提案背景` の定義へ、提案自体の背景（この案へ至った調査結果と思考記録）を含めることを明示する。イテレーションが起きた背景は `提案N-1へのフィードバック` が持つため `提案背景` へ重ねて書かない旨も併せて示す。

## 上位roadmap制約

- 親roadmap: `.steering/2026/202609/20260921-apply-escalated-skill-fixes/roadmap.md`
- 親phase identity: `proposal-background-scope`
- 親phaseの目的: `提案背景` が「イテレーションが起きた背景」へ縮退している状態を解消し、提案そのものの背景（この案へ至った調査結果と思考記録）が置かれる場所を定義する
- 親phaseのscope: `facilitate-discussion` の `2.2` と `2.3.1` が定める `提案背景` の定義 / `提案N-1へのフィードバック` との責務境界 / `templates/discussion_entry.md` の `提案背景` の記述指示
- 親phaseのscope外: 提案が判断できる案かを確かめる段の設計（`proposal-decidability` が扱う）/ 提案を出せない段階の受け皿（`non-proposal-iteration` が扱う）/ `提案N` 本文の構成 pattern（`templates/proposal-sections/` は既に pattern catalog を持つ）
- 親phaseのDoD: 下記「受け入れ基準」へ展開する
- 依存phaseの確定結果: なし（この phase は依存を持たない）

**後続 phase への引き渡し。** `proposal-decidability` が「`提案背景` の確定した定義と、それがどの file のどこに書かれたか」を `dependency_results` として受け取る。`提案背景` を持たない形（別 file へ分離等）に着地した場合は、後続の判定材料の候補が変わるため親 roadmap へ戻る。

## TL;DR

`提案背景` の定義が iteration 側で「直前の feedback から生じた条件」に限定されているため、提案へ至った調査結果と思考記録の置き場が無く、`提案N` へ流れ込んで判断対象を曖昧にしている。定義へ「提案自体の背景」を含め、イテレーション背景は `提案N-1へのフィードバック` が持つことを明示する。

終了時には、`提案背景` に何を書き何を書かないかが定義の側から読み取れ、`templates/discussion_entry.md` の記述指示もそれと矛盾しない状態になる。

## 完成後の姿

### documentation以外のfile deliverable

**対象と読者:**

| file | 主な読者 | 読後または利用後にできること |
| --- | --- | --- |
| `plugins/tumeda-dev/skills/facilitate-discussion/SKILL.md` | discussion を進行する agent | `提案背景` へ何を書き、何を `提案N` や `提案N-1へのフィードバック` へ残すかを判断できる |
| `plugins/tumeda-dev/skills/facilitate-discussion/templates/discussion_entry.md` | 同上 | entry を書く時点で、`提案背景` の記述指示が本文の定義と同じことを指していると確認できる |

**現在の定義（変更対象）:**

`提案背景` という語は `SKILL.md` に 13 箇所現れるが、**定義しているのは 2 箇所だけ**で、残る 11 箇所は参照である。

```text
SKILL.md
├── 2.2 新規論点を作るvariant / 手順4        ← 定義その1
│     「最初のuser input、finding、既存状態を必要な範囲で示し、提案0が満たす
│      必要のある条件と、提案0のどの内容がそれを満たすかを書く。原因追跡、
│      discussion scopeへ属する理由、別decisionとして分けた理由等は、proposalを
│      評価するために必要な時だけ内容固有の見出しや段落で示す」
│
├── 2.3.1 同じdecisionへiterationを追記する / 手順5   ← 定義その2
│     「直前のfeedbackから今回満たす必要が生じた条件と、新proposalのどの内容が
│      それを満たすかを書く。feedback原文と評価結果は直前iterationが所有する
│      ため複製しない。原因診断または修正scopeが変わった時は、前の診断の何を
│      維持、置換、拡張したかを読み分けられるようにする」
│
└── 他 11 箇所                                 ← 参照のみ（不変条件、完了gate、
                                                  2.1.1、2.3.3、3.2 等）

templates/discussion_entry.md
└── 提案背景の記述指示                          ← 本文の定義と同期が要る
```

**修正箇所。** `2.3.1` 手順5 だけを直す。`2.2` 手順4 は変えない。

縮退が起きているのは iteration 側だけである。`2.2` は材料として `finding` を挙げ、さらに「原因追跡...proposalを評価するために必要な時だけ内容固有の見出しや段落で示す」として提案へ至った経緯を書く余地を持つ。`2.3.1` は材料が「直前のfeedbackから生じた条件」だけで、調査結果の置き場が無い。引き渡された実例も iteration であり `2.3.1` が適用される場面だった。`2.2` 側に問題が観測されていない以上、そこを厚くすることは `modify_description_policy.md` が禁じる「指摘への応答で増やす」形にあたる。

**`提案背景` が持つもの。** 三つとする。

```text
提案背景が持つもの
├── 提案が満たす必要のある条件
├── その条件を導いた finding と、finding を整理した結果
└── 提案のどの内容が条件を満たすか
```

採らなかった案は置かない。選択肢として並べる案は `提案N` が `proposal-sections` の wrapper で持ち、選択肢に載せなかった案は過去 iteration が持つ。新たな置き場を作ると同じ判断が複数の正本を持つ。

前提の確認結果も置かない。phase `proposal-decidability` が判定材料を設計する際に必要としうるため、先に置き場だけを決めると後続の設計余地を狭める。

用語は `finding` を使う。`2.2` と同じ語になり、非対称が解消する。

**除外の記述。** 現在のまま変えない。「イテレーションが起きた背景」という語を skill へ持ち込まない。この語は `提案N-1へのフィードバック` が持つ二つ（feedback 原文と評価結果）を別の語で呼んだものであり、並べると読み手が差を探す。持つものが三つに確定した以上、それ以外を書かないことは定義から導かれる。

**確定する文面。** `2.3.1` 手順5 を次へ置き換える。

```diff
-5. 新しい`提案背景`へ、直前のfeedbackから今回満たす必要が生じた条件と、新proposalのどの内容がそれを満たすかを書く。feedback原文と評価結果は直前iterationが所有するため複製しない。原因診断または修正scopeが変わった時は、前の診断の何を維持、置換、拡張したかを読み分けられるようにする。
+5. 新しい`提案背景`へ、直前のfeedbackと今回の調査から今回満たす必要が生じた条件、その条件を導いたfindingとその整理、新proposalのどの内容が条件を満たすかを書く。feedback原文と評価結果は直前iterationが所有するため複製しない。原因診断または修正scopeが変わった時は、前の診断の何を維持、置換、拡張したかを読み分けられるようにする。
```

増えるのは「その条件を導いたfindingとその整理」の一句と、条件の出所へ「今回の調査」を加えた部分だけである。除外の記述と、診断の変遷を読み分けさせる条件付きの指示は変えない。

`templates/discussion_entry.md` の `提案背景` 記述指示を、本文と同じ語で同期する。

```diff
-提案1以降では、直前の提案へのfeedbackから必要になった条件を扱う。
+提案1以降では、直前の提案へのfeedbackと今回の調査から必要になった条件と、その条件を導いたfindingとその整理を扱う。
```

**記載する原則と例:**

- `提案背景` は提案へ至る経緯を持ち、`提案N` は選ぶべき案そのものを持つ
  - 今回の具体例: 引き渡された実例では、過去の実績から拾った表・実績三件の列挙・それを束ね直した内訳が `提案N` 側にあった。三つとも「条件を導いた finding とその整理」であり `提案背景` へ移る
  - 意図に反する薄い記述: 「調査結果は背景へ書く」とだけ書くこと。何が調査結果にあたるかの地が無いため、表や列挙を提案本体へ置いたまま「これは提案の一部だ」と判断できてしまう

**配置・形式:**

- 配置: `plugins/tumeda-dev/skills/facilitate-discussion/SKILL.md` の `2.3.1` 手順5、および `templates/discussion_entry.md` の `提案背景` 記述指示
- 形式: Markdown。既存の番号付き手順の中で該当項目を置き換える
- 参照する既存 pattern: `2.2` 手順4 が `finding` という語を既に使う。同じ語を使い、二つの定義で用語が揃う
- 正本と重複防止: `提案背景` が持つものの定義は `2.3.1` 手順5 が持つ。`templates/discussion_entry.md` は記述指示として同じ語を使うが、定義を複製しない

## 要件（Requirements）

### MUST（必達）

- `提案背景` の定義が、提案自体の背景（調査結果・思考記録）を含むことを明示している
- イテレーションが起きた背景を `提案N-1へのフィードバック` が持ち、`提案背景` へ重ねて書かないことが読み取れる
- `templates/discussion_entry.md` の記述指示が本文の定義と矛盾しない
- 定義が複数箇所に残る場合、同じ判断を二つの正本が持たない形になっている

### SHOULD（できれば）

- 修正で増える記述を最小に留める。`modify_description_policy.md` が定める「指摘された箇所ほど厚くなる力学」を避ける

### MAY（あれば嬉しい）

- なし

### 非目標

- 提案が判断できる案かを確かめる段の設計。phase `proposal-decidability` が扱う
- 提案を出せない段階の受け皿。phase `non-proposal-iteration` が扱う
- `提案N` 本文の構成 pattern。`templates/proposal-sections/` が既に catalog を持ち、今回変えない

### 受け入れ基準

- `node scripts/verification/validate-plugin.mjs` が `plugin validation passed` を出力する
- この phase 完了時点で `facilitate-discussion` が単独で利用可能である。他 phase の結論を前提とする記述を残さない
- 起点となった実例以外の具体 case を二つ以上、確定した定義へ当て、`提案背景` と `提案N` のどちらへ落ちるかが判定できることを確認する

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 「提案自体の背景」の範囲が広がり、`提案N` が薄くなる | 持つものを三つへ限定し、採らなかった案と前提の確認結果を除外した |
| 修正で記述が増え、`modify_description_policy.md` が禁じる「指摘への応答で厚くなる」形になる | 三つの decision すべてで増やさない側を選んだ。増えるのは `2.3.1` 手順5 の一句と条件の出所の追加だけで、`2.2` と除外の記述は変えない |

## （付録）前提とする既存仕様

- `facilitate-discussion/SKILL.md` の `2.2` 手順4: `提案背景` の定義その1。「最初のuser input、finding、既存状態を必要な範囲で示し、提案0が満たす必要のある条件と、提案0のどの内容がそれを満たすかを書く。原因追跡、discussion scopeへ属する理由、別decisionとして分けた理由等は、proposalを評価するために必要な時だけ内容固有の見出しや段落で示す」
- 同 `2.3.1` 手順5: `提案背景` の定義その2。「直前のfeedbackから今回満たす必要が生じた条件と、新proposalのどの内容がそれを満たすかを書く。feedback原文と評価結果は直前iterationが所有するため複製しない。原因診断または修正scopeが変わった時は、前の診断の何を維持、置換、拡張したかを読み分けられるようにする」
- 同 `2.1.1`: 「原因の分類と追跡は、その修正案がなぜ必要かを示す`提案背景`が所有する」。`提案背景` が持つものを定義以外の箇所から規定している例
- 同 不変条件: 「ユーザーへ合意を求める前に、その回の問いを初見の読者が単独で評価できるproposal、提案背景、空のfeedback見出しをdiscussion fileへ保存する」
- `templates/discussion_entry.md`: `提案背景` の記述指示を持つ。「提案Nが満たす必要のある条件と、提案Nのどの内容がそれを満たすかを書く。提案0では、最初のuser input、finding、既存状態を必要な範囲で示し、そこから必要になった条件を扱う。提案1以降では、直前の提案へのfeedbackから必要になった条件を扱う」
- `documentation_standards/modify_description_policy.md`: 既存 doc を直すときの記述方針。議論の経緯や指摘への反論を本文へ持ち込まない。修正で増えた分は増えた理由を疑う。同じ趣旨の否定が 2 file 以上に現れたら過剰補正
- この repository は自動 test framework を持たず、検証は `node scripts/verification/validate-plugin.mjs` だけである

**受け入れ基準の検証結果。** 起点となった実例（引き渡された提案5）以外の case を二件当てた。

一件目は、この steering の論点1 提案0 である。a / b / c の diff は選ぶべき案そのものであるため `提案N` へ、`2.2` と `2.3.1` の定義を並べた表は条件を導いた finding として `提案背景` へ、各案を推す理由と採らない理由は finding の整理として `提案背景` へ落ちる。同じ論点の中で提案と背景に分かれることを、定義が判定できている。
