# 内部検討記録: 論点17 — 再開条件の成立後に確認を挟むか

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-16-20.md)

**論点:** 論点17

## 開始context

保留時の内容を固定し、追加情報を関連付けることが論点16で決定した。
保留の要求は利用者の明示を前提とし、agentの都合やrecordの存在から成立・解除させない。
handoff-input.mdには利用者が指定した条件による再開案があるが、その条件成立後に毎回確認するかはplugin側で未決である。
今回は、条件付き保留の再開時点だけを決める。保存path・schema・監視機構・暫定運用指示の解決は対象外とする。
対象を名指した直接の再開指示や確認待ち指示がある場合は、それを既定より優先する。

## イテレーション0: 条件に基づく再開と、その時点で選び直せる確認を比較する

<a id="iteration-0-record-1"></a>

### 判断: 明示された再開条件を、反復確認なしで実行できるか

#### 判断対象・必須条件・根拠

条件成立後の再開を、当初の条件付き指示で行うか、その時点の追加確認を標準にするかを比較する。
現行escalate-plugin-skill-fixの即時転送契約、handoff-input.mdの保留案、論点11の明示委任・利用者判断の境界、論点16の固定内容を根拠にする。
利用者の対象・条件・範囲を越えないこと、曖昧な条件や状態不明を成立扱いしないこと、実装・公開権限を新たに作らないことが必須である。
比較軸は、条件に従って進める連続性と、条件成立時点で作業の切替を選び直せることとする。
条件を実証できる場合、曖昧な場合、成立後に事情や提案範囲が変わる場合、条件がない場合、明示の再開・確認待ち指示がある場合を机上照合する。

#### 結果

現行escalate-plugin-skill-fixは、元taskを中断してplugin側へ移る経路を持つが、保留や再開条件の契約は持たない。
入力は明示条件による再開を提案している。
これに論点11を当てると、対象と再開条件を明確に指定した指示へ、毎回同じ採否を聞き直す案は成立しない。
再開を事前に指示した場合と、確認する時点だけを指定した場合を分ければ、利用者の切替判断も保持できる。

| 入力・観測case | 導かれる処理 |
| --- | --- |
| 「この設計が完了したら、この改善をescalateして」かつ完了を確認 | 元の条件付き指示を根拠に再開する |
| 「設計が終わったら、escalateするか聞いて」 | 条件成立後に確認する |
| 「落ち着いたら」など成立基準が不明 | 推定で解除せず、必要な意図を確認する |
| 条件なしの「今は保留」 | 明示の解除を待つ |
| 後の指示が保留継続を指定 | 古い条件だけを根拠に再開しない |
| 追加情報で対象範囲・必要権限が変化 | 元の指示で覆えるか評価し、越える部分だけ確認する |

新たな既定の好みではなく、明示された指示・委任の範囲を守る境界の具体化である。
同じ条件付き指示を再承認させる選択肢は提示せず、合意からの導出として個別記録する。
条件成立の証拠と再開指示の所在を記録する契約をescalate-plugin-skill-fixへ追加する完成形とする。
条件成立から実装・公開・commit権限を作らず、現在の実行で確認できたeventだけを扱う。
常時監視や新しいsessionの自動起動は含めない。

#### 次の処理

変更内容0として保存・報告し、次の作業応答後までdesignへの同期を待つ。
利用者による保留指定を提案ごとに要求するか、承認済みrepository方針も認めるかは、別の実質的判断なので論点18へ分ける。

### 検証: 報告した再開条件を、元の指示の範囲でdesignへ同期する

#### claim・合格条件・方法

論点18の説明し直しへの実際の応答「ok」を受け、報告済みの変更内容0をdesignへ同期する。
説明が分からないという前の応答時は同期を待ったが、今回は説明への了承であり、新しい訂正や権限拡張はない。
採否の再合意として扱わず、論点11・16を根拠とする変更として反映する。
明確な再開指示、確認待ち、曖昧な条件、条件なし、後の保留継続、範囲変化の六caseを、変更内容0とdesignの記述で照合する。
同期後の現在結果に、報告した版、応答の所在、対象がdesignだけであることを残す。
Nodeによる文書構造・相対link・過去履歴・plugin成果物不変の検査も行い、実行機構のtestとは区別する。

#### 結果

designの保留・再開節へ変更内容0を同期し、六caseの処理がそれぞれ一致した。
条件付き実行と条件付き確認、条件なしと曖昧な条件、後の指示と範囲変更を区別し、元の権限を広げていない。
実応答は論点18・変更内容1への応答欄の「ok」だけであり、論点17への架空の賛成は追加していない。
読取専用Nodeで25文書・63実相対link・18実論点・4範囲本文を検査し、索引、範囲、親、内部log、明示anchor、行末空白、機密候補の不整合はなかった。
開始snapshotとの比較ではdesign、本文16〜20、内部log17・18だけが変更され、既存fileの削除とplugin成果物の変更はなかった。
完了済みの過去iterationと内部log本文は残し、追加と現在結果の更新だけを行う。
反映対象はdesignであり、pluginの保留機構・条件監視・配布は未実装のままである。
