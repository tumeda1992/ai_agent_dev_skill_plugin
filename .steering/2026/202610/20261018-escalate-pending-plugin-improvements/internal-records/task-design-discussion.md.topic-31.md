# 内部検討記録: 論点31 — skill構造reviewの指摘と完了判定

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-31-35.md)

**論点:** 論点31

## 開始context

四領域の骨格のうち、skillの構造変化を確認するskill-update-reviewの役割を詰める。
目的は、SKILL.md一fileへ異なる状態の処理を抱え続ける窮屈さや責務の混在を、利用者の指摘を待たずに見つけることである。
作成・編集は開発AIのskill-creatorに残し、行数だけで分割を要求しない。
引き渡し入力は構造reviewをgateへする案を持つが、plugin側の完成形としては未合意である。
今回は、必要なreviewを実行した結果、機能不良ではないが保守性に問題がある構造を指摘した時の扱いを選ぶ。
いつ呼ぶか、具体的なreview基準、返却形式、編集方法、記録の保存先は別に詰める。

## イテレーション0: 構造上の負債を残して完了できるか

<a id="iteration-0-record-1"></a>

### 判断: 改善候補の報告にするか、解消まで完了を止めるか

#### 判断対象・必須条件・根拠

構造上の問題と改善案を返し、今回直すかは呼出元の設計・作業範囲へ委ねるaと、構造上の問題が未解消なら通常の更新完了を認めないbを比較する。
両案ともreview自体を省略せず、skill-creatorの編集責務、既存の機能検証・document-reviewのgate、合意・変更権限を維持する。
単に長いことと、別の進化理由を持つ処理が混在していることを区別し、分割すること自体を成功条件にしない。
引き渡し入力の構造reviewの節、現行document-reviewとtask-designの責務を照合し、設計時の案と更新後の実物の両場面で比較する。
独立状態の処理が同居するが現時点では動く場合、長いが一責務として成立する場合、分割が既存の動作を落とす場合、将来の可能性だけの指摘、review材料不足の五caseを机上検討する。
比較軸は構造負債の積み残しを防ぐ強さと、依頼された変更を将来向けの整理で止める負担である。
reviewの実行頻度と、指摘に合意するだけで未承認の編集を許可することは今回の採否に含めない。

#### 比較結果と推奨

bの、構造上の不合格を残して通常完了しない案を推す。
指摘を自動で見つけても、そのまま足し続けて完了できるなら、利用者が整理を求めるまで直らない形が残る。
引き渡し入力も、設計時と更新後に構造を検査するgateを提案している。
ただしplugin側の採用根拠はまだなく、この入力を既決扱いにはしない。

引き渡し入力197〜267行では、行数でなく独立した進化理由・状態・検証境界を見て、一file維持・内部file分割・別skill化を選ぶ案が示されている。
現行document-reviewは読者が文書で作業できるかのgateを持つが、skill内部の状態処理をどの単位へ置くかに特化した役割は持たない。
task-designは未決判断と変更の反映ownerを管理し、合意なしの本体編集を禁止する。
したがって新reviewの不合格から直接書き換えず、設計・作成を担当する既存の経路へ戻す必要がある。

| case | 改善候補にするa | 完了条件にするb |
| --- | --- | --- |
| 独立した状態処理が絡み、変更の影響が無関係な処理へ波及するが現時点では動く | 問題と整理案を返す。担当側が今は直さない理由を残して完了する余地がある | 問題が残る間は通常完了せず、構造案へ戻す |
| 長いが目的・状態・変更理由が一つで閉じる | 維持する判断も返せる | 分割せず合格できる |
| 分割案が既存の動作を落とす | その分割を採らず、既存の機能検証にも通す | 同左。分割しただけでは合格しない |
| 将来そうなる可能性だけがある | 将来の見直し候補として区別 | 現在の不合格にせず、将来の候補として区別 |
| reviewに必要な前後の内容を確認できない | 未確認を合格扱いにしない | 同左 |

aには、今回の変更と、今すぐ動作には響かない保守性の整理を分けられる利点がある。
review結果を返すことは必須でも、構造上の指摘だけを理由に完了を止める権限は新設しない。
代償は、問題を認識した構造のまま変更が積み重なる余地を残すことである。
既に満たすべき機能・安全・合意要件やdocument-reviewの不合格を、この案で無視できるわけではない。

bは、構造上の問題を解消してから完了する制約を追加するため、依頼された機能だけの変更でも整理が必要になり得る。
reviewが具体的な問題・根拠・成立する構造案を返し、担当側が必要な設計合意とskill-creatorによる編集・再検証へ戻す。
指摘が誤りなら根拠を示して再判定できるため、reviewの初見の感想を無条件の分割命令にはしない。
不合格と助言の境界を別途具体化する必要はあり、この段階で全ての改善案を必須修正と呼ぶものではない。

起動頻度・呼出位置・詳細な判定基準・返却schema・記録先は独立して残す。
両案ともskill-creatorの代替、無断の範囲拡張・編集・release、過去skill全件の一括reviewは許可しない。
これは五caseの机上比較と既存契約の照合であり、新skillの動作確認ではない。

### 検証: 動くが保守性に問題がある例から、reviewの強さを選べるか

#### claim・合格条件・方法

提案保存後、document-reviewで両案の差がreviewをするかどうかでなく、不合格の構造を残して完了できるかだと読めることを確認する。
長いだけ・将来の可能性だけの指摘を一律不合格にせず、bも分割自体を成功条件にしない。
aでも既存の機能・文書reviewを迂回せず、bでも編集権限や未合意の構造判断をreview担当が横取りしない。
Nodeで構造・link・採番・親・範囲・索引を検査し、論点30の履歴と実応答の一回保存、未合意の論点31のdesignへの非反映とplugin本体の不変を確認する。

#### 結果

document-reviewの作成・更新観点で、現在は動くが別々に育つ処理の変更が絡む例から、構造reviewの指摘と完了の関係を選べることを確認した。
aでもreview自体を省略せず、既存の機能・文書reviewを迂回しない。
bは不合格の解消を要求するが、単に長いことや将来の可能性だけを一律の不合格にせず、分割の実施そのものを成功としない。
編集と必要な合意は元の設計・作成担当へ残し、review結果から無断編集の権限を作っていない。
独立した起動頻度・具体的判定基準・返却形式・記録先は未決のまま区別した。
具体例、両案の差と代償を本文で読め、既存の履歴を削らず、新たな機密情報も記載していない。

Node検査は41文書、相対link 105件、31論点、7範囲fileで問題なしだった。
論点30は決定、論点31は応答待ち、親論点1は子論点待ちであり、論点31のfeedbackは空である。
開始snapshotの26〜30の本文は、論点30のstatus変更と論点26の現在決定への接続一文以外を保持して追記し、論点30の既存内部記録も保持した。
実応答「a」は論点30へ一度だけ保存されている。
今回の変更はdesign、索引、26〜30の本文、論点30の内部記録の更新と、新しい31〜35の本文・論点31の内部記録の追加である。
新しい範囲fileは実在する論点31の追加に伴うもので、未発生の次範囲は先行作成していない。
designへの反映は合意済みの論点30だけで、構造reviewの具体的な完成形は未決として残している。
file削除、plugin本体の変更、実指示の終了・切替、新skillの実装は行っていない。
これは文書検査と机上reviewであり、新review skillの動作確認ではない。

<a id="iteration-0-record-3"></a>

### 検証: bの不合格を残して完了しない契約を反映する

#### claim・合格条件・方法

実応答「b」を一度保存し、新iterationを作らず論点31を決定する。
不合格が残れば構造案・設計・編集へ戻すこと、動いていても整理が必要になる負担、reviewと編集の分担をdesignへ同期する。
長さや将来の可能性だけでの分割を要求せず、具体的な判定基準は未決として残す。
Nodeで構造・link・範囲・開始snapshotとの履歴保持・変更対象・実応答の一回保存とplugin本体の不変を検査し、document-reviewの作成・更新観点で採否の範囲を照合する。

#### 結果

実応答「b」を提案0へ一度保存し、新iterationなしで論点31を決定した。
document-reviewの作成・更新観点で、不合格が残れば構造案・設計・編集へ戻すことと、動いていても整理が必要になる負担をdesignへ反映したことを確認した。
reviewは問題・根拠・整理案を返し、編集・合意・既存機能の検証を代行しない。
全指摘を不合格にせず、長さや将来の可能性だけで分割を要求しない境界と、具体的な判定基準の未決を維持した。

Node検査は41文書、相対link 105件、31論点、7範囲fileで問題なしだった。
開始snapshotの本文は論点31のstatus変更以外を保持して追記し、既存の内部記録も保持した。
実応答「b」は論点31へ一度だけ保存された。
変更した既存fileはdesign、31〜35の本文、論点31の内部記録だけで、追加・削除はなかった。
plugin本体は不変で、新skillの実装や既存skillの編集・一括reviewは行っていない。
これは文書検査と机上reviewであり、新review skillの実行結果ではない。
