# 内部検討記録: 論点24 — 作業限定の暫定指示の保存先

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-21-25.md)

**論点:** 論点24

## 開始context

暫定指示はmaintenance-plugin-contextが管理し、一つの作業にだけ効かせると決まった。
事実だけを持つcontext instanceへ混ぜないが、暫定指示の物理保存先は未決である。
保留メモは元作業のpending-escalations配下にあるが、後回しにした改善内容の控えであって、動作指示そのものではない。
今回は暫定指示の保存先を元作業directory配下のtemporary-overridesへ分ける案を評価する。
指示fileの粒度・名前・項目、取得時点、競合・終了規則、実際の指示登録は別に残す。

<a id="iteration-0"></a>

## イテレーション0: 元作業内の専用保存先で必要な分離を保てるか

<a id="iteration-0-record-1"></a>

### 判断: 作業限定の指示をtemporary-overridesへ保存する案の成立条件

#### 必要条件と確かめる対応

対象は暫定指示の正本の保存先であり、効く作業の範囲や管理skillを決め直さない。
一作業の経緯と一緒に扱え、事実のcontext instanceと保留メモから指示を区別でき、指示がなければ余計な保存物を増やさないことを求める。
候補を元作業内の専用directory、repository共通の作業別保存先、discussion本文への直接保存として比較する。
根拠はdesignの作業限定と情報分離、既存context管理の安定factの境界、引き渡し入力のtemporary-overrides案である。
指示なし、指示あり、保留メモだけを引き渡す、同じ作業を再開するcaseで、指示と控えを取り違えずに扱えるか机上照合する。
一案の採否として提示できるかも判定し、directoryを選ぶために不成立の対抗馬を作らない。

#### 結果と案への影響

現行maintenance-plugin-contextの保存先はrepositoryの安定fact用であり、session議論・task状態・skill手順を混ぜない契約を持つ。
引き渡し入力は別のtemporary-overrides配下へ置く案を持つが、その親はrepository共通の.agentsである。
論点23では共通適用を作らず一作業限定と決めたため、その旧pathをそのまま採用せず、元作業のdirectory内へ置く案を評価した。
適用範囲と物理保存先は別なので、配置が既決から一意に決まったとは扱わない。

| 保存候補 | 得られるもの | 今回の評価 |
| --- | --- | --- |
| 元作業内のtemporary-overrides | 経緯と指示を一緒に扱い、控えと指示を区別できる | 推奨 |
| repository共通の作業別保存先 | 指示の場所をrepository全体で揃えられる | 今回は他作業を扱わず、別の共通場所を維持する利点が小さい |
| discussion本文への直接保存 | 別の指示保存物が要らない | 現行指示の取得を議論形式と更新ownerへ結び付ける |

discussionには既に提案・応答・過去案があり、指示の現行内容を取り出すには、その形式と状態を読む必要がある。
専用保存先なら議論の履歴と、maintenance-plugin-contextが管理する指示を区別できる。
代償は保存物と、根拠となる議論との参照関係が増えることであり、別保存を無償な改善とはしない。
この利点・代償から元作業内の専用保存先を一案として提示する。旧共通配置や議論への埋込みを、数合わせの選択肢にはしない。

| case | 専用保存先での扱い |
| --- | --- |
| 暫定指示なし | 空のtemporary-overridesを先行作成しない |
| 合意した暫定指示あり | 元作業のtemporary-overridesへ保存する |
| 保留メモをplugin側へ引き渡す | 指示の保存先は別のままで、引き渡しだけで消さない |
| 同じ作業を再開する | 同じ作業にある指示を参照できる |

元作業のdirectoryが特定できなければ、別作業やrepository共通の場所へ推測保存しない。
今回の案には保存先とその作成条件だけを含め、指示fileの粒度・basename・項目・resolverの詳細は未決に残す。
保留メモの引き渡しと指示の失効を分ける既決境界は維持する。
この結果は机上の配置比較であり、指示fileの新設、読み取り機構の実行、plugin成果物の変更は行っていない。

<a id="iteration-0-record-2"></a>

### 検証: 暫定指示と保留メモの保存先・役割の違いを判断できるか

#### claim・合格条件・方法

treeと具体例から、元作業のどこへ何を置く提案かをdocument-reviewする。
一指示一fileや項目のschemaを先取りせず、指示なしなら保存物を増やさないことと、保留メモの引き渡しで指示を消さないことを照合する。
一作業限定からpathが一意に導けるという説明にせず、別保存の負担も示す。
Nodeで論点・索引・親・範囲・内部log・相対link・anchor・空白・機密候補を検査する。
開始snapshotの本文とlogが保持され、designには論点23の決定だけが反映され、実際の暫定指示保存先やplugin本体が作成・変更されていないことを確認する。

#### 結果

document-reviewで、元作業内の二つの保存先をtreeと同じ議論分割の例から区別できることを確認した。
pending-escalationsは後で渡す改善の控え、temporary-overridesは今の動作へ渡す暫定指示であり、控えの引き渡しで指示を消さない境界を維持した。
事実用context instanceとrepository共通の置き場へ保存しない案、必要時だけ作る条件、議論とは別の保存物と参照が増える負担を示した。
file粒度・名前・記録項目・取得時点・競合・終了規則は未決として残し、未提示のschemaや実指示登録へ採否を広げていない。

Node検査は32文書、相対link 84件、24論点、5範囲fileを確認し、問題はなかった。
論点23は決定、論点24は応答待ち、親論点1は子論点待ちである。
開始時の本文は論点23のstatus変更を除いて保持され、論点23の既存内部logも保持されている。
論点23の実応答「a」は一度だけ保存され、論点24のfeedbackは空である。

今回の差分はdesign、索引、21〜25のdiscussion本文、論点23の内部記録の更新と、論点24の内部記録の追加だった。
designへの追加は合意済みの論点23だけであり、未合意の保存先案は反映していない。
既存fileの削除やplugin本体の変更はなく、この作業directoryに実運用のtemporary-overridesも作成していない。
これは文書の検査と机上reviewであり、暫定指示の保存・読取機構の動作確認ではない。

### 検証: 保存先へのokを決定とdesign同期へ反映する

#### claim・合格条件・方法

実応答「ok」を提案0へ一度だけ保存し、新iterationを作らず論点24を決定する。
元作業のtemporary-overrides、保留メモとの分離、必要時だけ作ること、安定factと共通配置へ保存しない境界がdesignと一致するか確認する。
粒度・schema・終了条件を確定せず、実運用のdirectoryや指示を作らない。
Nodeで論点・索引・link・anchor・履歴保持とplugin本体の不変を検査し、反映後に次の未決事項を選ぶ。

#### 結果

実応答「ok」を提案0のfeedbackへ一度だけ保存し、同じiterationのまま論点24を決定した。
保存先、保留メモとの分離、必要時だけ作る条件、共通配置と安定factへ混ぜない境界をdesignへ反映した。
指示fileの粒度・名前・記録項目・取得時点・競合・終了条件は未決に残っている。

Node検査は32文書、相対link 84件、24論点、5範囲fileを確認し、問題はなかった。
開始時のdiscussion本文は論点24のstatus変更を除いて保持され、既存内部記録も保持された。
今回の変更はdesign、21〜25のdiscussion本文、論点24の内部記録の三fileで、削除はなかった。
plugin本体に変更はなく、実運用のtemporary-overridesも作成していない。
文書上の合意反映を確認した結果であり、保存・読取機構の動作確認ではない。

次は暫定指示fileの粒度を比較する。
保存先の決定から一指示一fileまでは導けず、全指示を一度に見渡すことと、個別に更新できることのどちらを優先するかが残るためである。
