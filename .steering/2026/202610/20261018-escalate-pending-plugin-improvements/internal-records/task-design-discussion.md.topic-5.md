# 内部検討記録: 論点5 — 未分割・分割済みの入口解決

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-1-5.md)

**論点:** 論点5

## 開始context

分割は一記録が10論点を超えた時だけ行い、元の{stem}.mdと同階層の{stem}/へ同じbasenameの索引と範囲本文を置く。
旧入口には案内も残さず、短い記録と内部logの配置は変えない。
callerは既存のdiscussion_directoryとdiscussion_file_nameを渡し、物理的な保存形式の解決はfacilitate-discussionが所有する。
今回の対象は入口の発見と不整合時の停止であり、索引の中身、本文の読取範囲、分割実行・中断復帰は別に残す。

<a id="iteration-0"></a>

## イテレーション0: 二入力から正本の入口を一意に解決する

論点4で旧入口を残さない方針が決定した。
同論点の調査により、現行のfile解決は元pathがなければ新規作成し、
task-designのhandoff gateはdesignまたは元discussionの存在を見ていることが分かっている。
この既存findingを使い、同じ調査を再実行せず入口手順の状態網羅を机上照合する。

<a id="iteration-0-record-1"></a>

### 検証: 保存形式の存在組合せから新規・継続・停止を区別できるか

#### claim・合格条件・方法

作業directoryをW、discussion basenameをD={stem}.mdとし、未分割入口W/Dと分割先W/{stem}/を確認する。
両方がない時だけ新規候補とし、未分割入口だけなら従来形式、分割先の索引だけなら分割形式として継続する案を照合する。
両方がある、分割先に索引がない、必要なpathの型が違う、存在確認に失敗する場合は書込みを停止する案とする。

合格条件は、分割済み記録の新規扱い、二重正本の黙認、確認不能を不存在とみなすことがないこと、
短い記録の配置と既存の二入力を維持すること、catch-up前の本文読取禁止を破らないことである。
通常の四つの存在組合せに加え、不完全な分割先、取得失敗、既存の長い一file、
designなしで分割discussionだけある引き継ぎを、提案する条件に机上で当てはめる。
これは設計案のcase照合であり、未実装のresolverを実行して検証するものではない。

#### 存在組合せと照合結果

通常の四組合せは、入口を一意に決められる場合だけ継続する案と整合した。
本文の読取前に判定できる範囲と、その後の構造確認を分ける必要がある。

| 机上case | 入口判定の結果 |
| --- | --- |
| 未分割fileだけある | 一file形式として継続 |
| 分割先directoryと同名の索引だけある | 分割形式の入口として継続候補 |
| 元fileと分割先が両方ある | 正本を選ばず停止 |
| 元fileも分割先もない | 新規候補。既存記録の証拠がないことも確認する |
| 分割先だけあるが索引がない | 不完全な記録として停止。新規fileを作らない |
| 分割先がdirectoryでない、入口が通常fileでない | 想定形式と異なるため停止 |
| 存在や種類の確認に失敗する | 確認不能として停止。不在とみなさない |
| 従来の一fileに既に12論点ある | 既存記録として認識。移行の実施時点はここでは決めない |
| designがなく、分割discussionだけ残る | 既存設計としてhandoff gateへ渡す。新規設計へ進めず、design欠落時の既存停止条件を維持する |

「両方ない」だけで新規確定する案には反例がある。
同じdiscussionのinternal-records/{D}.topic-{N}.mdや会話上の既存記録の証拠が残る場合は、
入口だけが失われた可能性があり、新しい論点1を作ると履歴を別正本へ分断する。
そこで、既存記録の証拠と矛盾しない場合だけ新規作成を認める条件へ具体化した。
他discussionの内部logがあるだけでは同じ記録の証拠とせず、Dの一致を確認する。
catch-up前に必要ならfile名の存在だけを確認し、内部log本文まで読む経路は追加しない。

#### 保証できる範囲と残る設計

この案は、入口の保存形式を一意に判定し、不完全・競合・確認不能を新規作成で覆い隠さない手順として成立する。
分割先の索引を発見しただけでは、範囲本文の欠落、論点重複、索引内容の正しさまでは保証しない。
それらは読取可能になった後の構造検査へ渡し、書込み可能な完全状態とは区別する必要がある。
机上検証であり、productionの挙動が既に変わったこと、全保存形に対する実行検証が完了したことは主張しない。

callerに分割先のpathを再指定させる案は、既存の二入力と共通ownerという条件を崩す。
元file優先・分割先優先で競合を自動解消する案も正本性を保証できないため、比較用の選択肢にはしない。
今回は一つの入口解決案を提示し、索引内容、読取・構造検査、移行手順を独立した未決として残す。
