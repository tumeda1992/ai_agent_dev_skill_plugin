# 内部検討記録: 論点39 — skill構造reviewの実行担当の独立性

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-36-40.md)

**論点:** 論点39

## 開始context

skill-update-reviewは汎用skillの構造を設計時と編集後に確認し、不合格を残して通常完了しない設計である。
編集はskill-creator、設計・完了判断・保存は既存callerの責務に残す。
独立した内部処理を同じskill内の指示fileへ分ける基準と、結果を適切な既存作業記録へ残す原則は決まった。
ただし、reviewを設計・編集したagent自身が担当できるか、毎回別agentへ渡すかは未決である。

今回決めるのはreview担当の分離を必須にする強さであり、合否基準や二段階確認を弱める選択ではない。
別agentを使う案でも、review担当が編集・design・tasklistの正本を勝手に更新する権限は持たず、結果をcallerへ返す。
この設計比較のために現在の議論を別agentへ委譲することはしない。

## イテレーション0: 同じ担当の明示reviewと、毎回独立したreviewを比較する

<a id="iteration-0-record-1"></a>

### 判断: 別agentによる構造reviewを必須条件にするか

#### 判断対象・必須条件・根拠と照合方法

aは同じagentがskill-update-reviewを明示適用し、実物・構造案を改めて評価してよいとする。別agentを毎回の必須条件にはしない。
bは設計・編集したagentとは別agentによるreviewを、設計時と編集後の各確認で必須にする。
比較軸は、作成時の思い込みを持たない評価者を構造的に挟むことと、毎回の引き渡し・待機・実行基盤への依存を増やさないことである。
両案とも対象skill全体の根拠付き判定、既存owner、権限、記録、不合格と材料不足を合格にしない条件を維持する。

system skill-creatorの独立検証方針と、pluginのdocument-review、runtime-execution-contracts、runtime-model-profilesの該当本文を読み、別agent必須が既存契約から決まるのかを照合する。
設計案の確認、編集後の確認、同じ誤認の持越し、別agentを起動できない環境の四caseで、成立条件と追加負担を比べる。
確認するのは保存された指示と方針の机上比較であり、検出率・費用・所要時間の実測や、実際のchild起動・新review機能の実装は行わない。

#### 既存契約との照合

pluginのdocument-review本文全体を確認した。
同skillは作成・更新後のemit gateとして観点を当てるが、別agentによる実施を必須にはしていない。
これはaが既存のreview運用へ接続できる根拠にはなるが、新しい構造reviewも必ず同じ担当でよいという証明ではない。

system skill-creatorのIndependent Forward-Testing節は、複雑さ・riskに対して実際の動作検証が有意義で、委譲が利用可能かつ許可される場合に独立agentを使う。
期待する答えや疑っている不具合を不用意に渡さず、実要求と必要な生の成果物で評価させる考えはbの独立性を支える。
ただし、これは動作検証の方針であり、全ての構造reviewを毎回別agentへ渡す既存規則ではない。
どちらの案でも、この動作検証自体の必要性や独立実施条件を取り消す根拠にはしない。

runtime-execution-contracts.mdとruntime-model-profiles.mdは全文を確認した。
既存child契約の固有kindはtest-runnerとvisual-inspectorであり、新しい構造reviewのrequest/result契約や推論profileは未定義である。
したがってbでは、既存kindへ名前だけを混ぜず、起動・返却・停止・中断復帰等の接続を設計する必要がある。
aでもreviewの入出力とcallerへの接続は必要だが、その実施のために毎回childを起動する条件は増えない。
profileの既存fallbackはmodel選択に関するものであり、独立agent自体を用意できない場合の自己reviewへの切替を既に許可するものではない。

#### 四caseの比較と反証

以下は方針の机上比較であり、検出性能を実測した表ではない。

| case | a: 同じ担当も認める | b: 別agentを必須にする |
| --- | --- | --- |
| 設計時の構造案 | 設計担当がreview skillを明示適用 | 別agentへ構造案と要件を渡す |
| 編集後の現物 | 編集担当が現物全体を再評価 | 別agentが現物全体を評価 |
| 作成時の誤認がある | 同じ誤認を持ち越す弱点が残る | 作成時の推論と切り離して評価できる |
| 別agentを起動できない | 自身で必要なreviewを実施できる | 必須の独立reviewが未完として止まる |

同じ誤認のモデルとして、編集担当が「この二つは同じ状態の処理だから分けなくてよい」と思い込み、実際には別の完了条件を持つ場合を考える。
aではskillの基準と現物を照合し直すことを求めても、その誤認自体を持ち越す危険は消せない。
bでは、要件と現物を渡し、編集担当の期待する合否や結論へ誘導しなければ、その推論から切り離した評価を挟める。
ただし別agentも同じ誤りを犯し得るので、bを正しさや検出率の保証とは呼ばない。

bでも合意済み要件や制約を隠して独立させるのではない。
必要な設計根拠、対象skill全体、設計時の役割分担・接続等は渡し、review対象を理解できる入力を揃える。
編集後に前段の結論だけ渡して追認させる案ではない。
毎回違うmodelを要求する案でも、設計時と編集後で必ず別々のreviewerを新設する案でもない。
独立させる相手は当該構造案の設計・編集担当であり、選定modelや再review担当の継続方法はこの問いでは決めない。

#### 推奨と残る代償

aを推す。
起点の問題は、独立した実行処理を一fileへ抱え込むことを検知する観点と明示gateがなかったことであり、独立reviewerがいないことを原因と確認したわけではない。
合意した構造基準を明示適用し、根拠を残すgateをまず成立させ、全呼出しにagentの追加起動・待機を必須化しないことを優先する。
同じ担当が設計・編集時の誤認を持ち越す弱点を受け入れる判断であり、aでbと同じ独立性が得られるとは主張しない。

bは、見落としの理由が分からなくても、作成時の推論から切り離した評価者を必ず挟むことを優先する有力な対案である。
設計時と編集後の双方で入力の整備・起動・待機・返却の接続が必要になり、独立agentを使えなければ同じ担当の確認だけでは完了できない。
この追加負担を引き受けるかは、二段階確認や不合格を残さない既決方針から一意には決まらない。

どちらもreviewは結果と根拠を返し、既存callerが適切な作業記録へ保存する。
review担当へ設計・編集やtask完了の権限を移さず、明示要求や別途必要な独立した動作検証を免除しない。
具体的な入出力、呼出位置、停止・再開の詳細、modelやhost別接続は未決であり、この比較のためにchildを起動しない。

### 検証: review基準と実行担当の独立性を混同せず比較できるか

#### claim・合格条件・方法

保存したdiscussionと内部記録を全文読み、document-reviewの作成時・更新時観点で、aも明示的な根拠付きreviewを行い、bも正しさの保証ではないことを確認する。
設計時・編集後・誤認の持越し・起動不能の四caseで、担当と追加負担を区別して選べるかを照合する。
skill-creatorの独立した動作検証、既存の保存owner、権限、二段階確認、不合格と材料不足を通さない条件を変えていないことも確認する。
読み取り専用Node検査と今回開始時の49文書のbaselineで、索引・採番・親子・link、論点38の旧履歴と原文応答の一度保存、変更範囲、実行用pluginの不変を確認する。
検証は文書と方針比較に限り、独立reviewの検出性能や新機能の実行は対象外とする。

#### 結果・限界

保存後の論点36〜39を含む本文と、本内部記録を全文読んだ。
document-reviewの作成時・更新時観点で、読者が二案の実施担当と受け入れる弱点を判断できることを確認した。
aは同じ担当による明示的な根拠付きreviewであり、確認省略ではない。
bは別担当を必須にするが正しさは保証せず、起動不能時は未完となる。
例はモデルと明記し、実際の事故や検出性能の証拠へすり替えていない。
必要な要件を隠すことと独立性を混同せず、二段階確認、不合格・材料不足、保存owner、編集権限、別途の独立した動作検証も維持した。

選択肢を小見出しで分け、理由・代償・例は散文、四caseの対応は内部記録の表へ分担した。
指示対象は設計・編集担当とreview担当を区別し、既存の確定履歴を書き換えず、機密値を追加していない。
前版から削った合意事項はなく、論点39を未決の応答待ちとして保存した。
その独立性の方針は、合意前のためdesignへ反映していない。

読み取り専用Node検査は50文書、130相対link、39論点、8範囲本文を確認し、採番・索引・親子・link等の問題は0件だった。
今回開始時のbaselineとの比較では、論点38以前の本文は同論点の状態変更を除いて保持され、旧内部記録も保持されていた。
論点38の原文応答は一度だけ保存され、変更はdesign、論点38の内部記録、36〜40の本文、索引の4文書と、新規の論点39内部記録に限られた。
削除はなく、実行用pluginの内容は不変だった。
この結果は設計文書の整合確認であり、新review機能の実装・動作・検出性能の検証ではない。

### 応答処理: 同じ設計・編集担当による明示reviewを採用する

利用者の今回の応答は、保存済み提案0のaを選ぶ明示合意である。
前提訂正や別decisionの追加ではないため、新しいiterationや比較は作らず、対応するfeedback欄へ原文を一度保存して決定を確定する。
「別agentを必須にしない」と「別agentを使わない」を区別し、明示された独立review、別途の独立した動作検証、二段階確認、判定根拠、既存ownerと権限を保持する。

consumerはdesignのskill構造review節へ、同じ担当での明示適用、追加agentを必須にしない理由と受容する弱点、既存の独立確認を免除しない境界を同期する。
これは設計の更新であり、実行用skillの実装や新review機能の検証ではない。
今回開始時の50文書のbaselineと読み取り専用検査により、過去本文・内部記録の保持、原文の一度保存、変更範囲、実行用pluginの不変を照合してから次の未決事項へ進む。

保存後の比較では、旧本文は論点39の状態を決定へ変えた以外は保持され、旧内部記録もそのまま残っていた。
同論点の原文応答は一度保存され、変更はdesign、36〜40本文、本内部記録の3文書だけだった。追加・削除はなかった。
全体検査は50文書・130相対link・39論点・8範囲本文で問題0件、実行用pluginは不変だった。
設計へ同期した内容は採用されたaの範囲に限られ、別agent禁止や独立した動作検証の免除を追加していない。
このdecisionは設計の同期まで完了した。実行用skillへの反映は未実施であり、通常のdesign更新だけを理由にorigin-reviewを再帰起動しない。
