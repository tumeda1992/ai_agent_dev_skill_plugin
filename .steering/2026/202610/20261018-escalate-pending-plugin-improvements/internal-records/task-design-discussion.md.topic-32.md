# 内部検討記録: 論点32 — 構造上の不合格を支える証拠

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-31-35.md)

**論点:** 論点32

## 開始context

論点31で、skill-update-reviewの構造上の不合格を残して通常完了しない方針を採用した。
行数や漠然とした将来の可能性だけでは不合格にせず、具体的な判定基準は未決である。
今回は、機能・安全要件の不備ではなく、独立して育つ処理の混在や同期負担など保守性の構造問題を扱う。
実際の改訂で困った記録がない場合でも、現物の指示を具体的な変更caseで辿ることで不合格を裏付けられるかを選ぶ。
どこへ切り出すか、全ての不合格類型、reviewの頻度・返却schemaは対象外とする。

## イテレーション0: 改訂実績と現物を辿る検証を比較する

<a id="iteration-0-record-1"></a>

### 判断: 不合格の根拠に実際の改訂実績を必要とするか

#### 判断対象・必須条件・根拠

改訂履歴や実行記録から実際の連動修正・読み落とし等を確認した場合だけ保守性の構造問題を不合格にするaと、それに加えて現物に基づく具体的な変更caseの机上検証でも不合格を裏付けられるbを比較する。
両案とも、長さ・状態数・分割しやすさ・漠然とした将来機能の想像だけでは不合格にしない。
機能・安全・既存要件を満たさないものは別の既存gateへ返し、この証拠の選択で通過させない。
根拠は論点31と引き渡し入力の、独立した進化理由・検証境界を見て金属疲労を検知する要求である。
比較軸はAIの予想だけで不要な整理を必須化する危険と、履歴のない新規skillや未事故の構造を早く評価できることである。
実際の連動修正記録、履歴なしで同一ルールが複数箇所に重複している例、長いが一責務の例、将来の別用途の想像だけ、材料不足の五caseを机上比較する。
机上検証では何を変えるか、現物のどこへ波及するか、なぜ無関係な修正・重複同期が必要になるかを追える必要があり、存在しない実障害を創作しない。

#### 比較結果と推奨

現物に基づく変更caseの机上検証も証拠に認めるbを推す。
新規skillを含む設計段階でも、すでに存在する保守上の負担を評価できることが決め手である。
ただし、予測した負担を過大評価して、機能上は成立するskillへ不要な整理を要求する危険を引き受ける。
aはその危険を抑えられる成立する代替案であり、既存の機能不良を見逃す案ではない。

次の五caseは方針を比較するためのモデル例であり、今回調べた実skillの障害報告ではない。

| case | a: 実績を必須にする | b: 現物の机上検証も認める |
| --- | --- | --- |
| 改訂記録から不要な連動修正を確認できる | 不合格の証拠になる | 不合格の証拠になる |
| 改訂履歴はないが、同一ルールの二重管理を現物で辿れる | 保守面の改善候補に留める | 不合格の証拠にできる |
| 長いが一つの目的・変更理由で成立している | 長さだけでは不合格にしない | 長さだけでは不合格にしない |
| 将来は別用途から使うかもしれないという想像だけ | 不合格の証拠にしない | 不合格の証拠にしない |
| 現物や必要な記録を確認できない | 材料不足で判定を完了しない | 材料不足で判定を完了しない |

差が出るのは二番目である。
例えば、新規実行と再開の両方で同じ報告形式を使うskillが、その報告項目の正式な定義を各処理に全文で持ち、どちらも更新対象になっているとする。
報告項目を一つ変更するcaseを当てると、同じ要求を満たすために二つの定義を同期修正する必要がある。
bでは、その変更目的、定義の所在、両方への波及、共通定義への参照ではない理由を現物で示せれば、過去の同期漏れを創作せずに構造上の負担を論証できる。
aでは、実際の改訂でその負担が生じた記録がない間は、保守面の指摘を改善候補として返す。

同じ文が二度出てくること自体は、この例の証拠にならない。
一方が要約・使用例である場合や、似ていても別々に変わるべきルールの場合は、同じ定義を二重管理しているという前提が崩れる。
また、共有形式を変えれば複数の利用処理へ必要な変更が及ぶこと自体は不良ではない。
ルールの正本が重複し、同じ判断を複数箇所へ同期する負担と、要求上必要な波及を区別する必要がある。
実際のreviewでは該当箇所と理由を示し、反証が出れば判定し直す。

#### 提案へ反映する範囲と残る不足

提案0は、保守性の構造問題を不合格とする根拠に実績を必須にするかだけを選ぶ。
機能・安全・既存要件の不備は両案とも既存のgateで扱い、実績がないことを通過理由にしない。
この比較は全ての不合格類型を決定せず、ファイル分割も自動要求しない。
二重管理の例なら同一file内で定義を一つにして参照する整理も考えられ、切出し先の選択は別の判断である。
reviewの呼出頻度、正式な判定項目、返却schema、記録先は未決のまま残す。

### 検証: 論点31の採用と論点32の提示範囲が保存内容に一致するか

#### claim・合格条件・方法

論点31のb採用を反映したdesignと議論履歴を保ち、論点32だけを未決の提案として保存できているかを検証する。
保存後に対象discussionと内部記録を全文再読し、document-reviewで初見の読者がaとbの差、推奨理由、代償、モデル例と実測の違いを判断できるかを確認する。
読み取り専用Node検査で、論点採番・親子・索引・相対link・保存前からの履歴保持を照合する。
今回の変更はdesign、索引、31–35本文、論点31の内部記録と、新規の論点32内部記録に限り、pluginの実行用skill・docs・scriptは変えていないことを確認する。

#### 検証結果と射程

論点31の採用を保ち、論点32を応答待ちの提案として提示できることを確認した。
全文再読とdocument-reviewでは、同じ二重定義の例についてaなら実績ができるまで改善候補、bなら現物を辿る検討も証拠にできる、という差を確認した。
推奨理由に新規skillでの早期評価、代償にAIの予測による不要な整理の危険があり、モデル例を実測結果と取り違えない説明になっている。

初回の文書reviewでは「証拠不足を合格にしない」が、aで改訂実績がない場合まで判定未完了にする読みを生むと判断した。
未提示の提案0を、必要な現物を読めない材料不足と、実績がないと確認できた場合とに分けて説明し、全文再読でaの説明との矛盾がないことを確認した。
過去の合意や実装方針を変更する修正ではない。
記法は案ごとの見出しと理由の散文、五caseの比較表に分け、同じ対象の呼称を揃えた。
新規内部記録の命名と参照は既存の論点別形式に従い、秘密情報やユーザーを識別する新規情報は追加していない。
