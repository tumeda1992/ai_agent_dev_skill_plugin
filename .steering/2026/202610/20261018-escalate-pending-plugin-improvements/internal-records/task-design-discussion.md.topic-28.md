# 内部検討記録: 論点28 — 暫定指示を取得し直す時点

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-26-30.md)

**論点:** 論点28

## 開始context

対象skillに必要な暫定指示はmaintenance-plugin-contextが管理し、元作業のtemporary-overridesから選択的に返す。
実行version変更時は毎回継続を確認し、終了済みのfileは保持して適用候補から外す。
取得時点は未決で、引き渡し入力には起動・session再開・同じsession内の更新時に取得し、全user turnで定期scanしない案がある。
今回はこのイベント時の取得で足りるか、同じ作業を続ける利用者の各発話の処理前にも取得し直すかを比べる。
正式な入力・返却項目、全consumerへの具体的接続、競合・終了条件の設計は対象外とする。

## イテレーション0: 取得の繰返しと、通知されていない編集の発見時点を比べる

<a id="iteration-0-record-1"></a>

### 判断: 進行中のskillでも各user turnに指示を取得し直すか

#### 判断対象・必須条件・根拠

skill起動・作業再開・把握した指示変更時に取得するaと、それに加えて同じ作業の各user turnの処理前にも取得するbを比較する。
新規起動とsession再開で最新の指示を読むこと、同じsessionで把握した更新を放置しないこと、終了済み・別作業の指示を適用しないことを必須とする。
比較軸は継続会話で繰り返す読取の負担と、通知されていない手動編集を発見できる時点である。
根拠は論点22〜27の担当・範囲・version・状態の境界と、引き渡し入力の取得時点案である。
初回起動、同じsessionで指示更新、通知なしの保存file編集、明示的な読み直し依頼、session再開の五caseを机上比較する。
両案とも常時監視は行わず、通常の発話ごとに既存skillを新規起動したと数えて差を消さない。

#### 比較結果と推奨

起動・再開・把握した変更時に取得するaを推す。
同じsessionで管理担当が行った更新はその場で返せ、起動・再開でも読み直すため、毎回の返答で同じ保存先を読み直す処理を追加せずに済む。
代償は、通知されていない保存fileの編集を、進行中の会話が次の発話だけで必ず発見するとは約束できないことだ。

| case | イベント時に取得するa | 各user turnでも取得するb |
| --- | --- | --- |
| 初回のskill起動 | 取得する | 取得する |
| 同じsessionで把握した指示更新 | 更新後の内容を受け取り以後へ反映 | 同じくその場で反映 |
| 通知なしの保存file編集 | 次の起動・再開・読み直しまで発見を保証しない | 次の当該作業の発話を処理する前に確認する |
| 明示的な読み直し依頼 | 取得し直す | 取得し直す |
| session再開 | 取得し直す | 取得し直す |

bには、保存fileへの変更を会話へ知らせ忘れても、次の発話から発見できる利点がある。
その代わり、変更のない通常の応答でも作業内の保存先を読み直す処理が繰り返される。
常時監視ではないため、応答の途中の外部編集を直ちに検知する保証はbにもない。
両案とも取得した内容が有効かは管理担当が別に判定する。fileが変わったことだけを合意や適用権限にはしない。

頻度は保存先・version照合から一意には導けず、通知を伴わない編集の発見をどこまで自動で担うかという運用の選択である。
引き渡し入力のa相当の案をそのまま確定せず、毎回取得するbの実益も示して採否を求める。
同じ作業の指示だけを扱い、別作業の横断探索、background監視、指示fileのない時の空instance作成は加えない。
これは五caseの机上比較であり、読取の実測やconsumer接続の動作確認は行っていない。

### 検証: 通常の返信と再開を区別し、取得頻度を選べるか

#### claim・合格条件・方法

提案保存後、document-reviewで手動編集を会話へ通知しなかった例から二案の違いを判断できるか確認する。
同じsessionで把握した更新と明示的な読み直しは両案とも扱い、aを変更放置案にしない。
bにも常時監視や編集即適用の保証を持たせず、同じ作業の各発話の処理前という境界を明記する。
Nodeで論点・索引・範囲・link・anchor・内部logを検査し、論点27の履歴と二発話の一回保存、論点28の空feedback、plugin本体の不変を確認する。

#### 結果

document-reviewの作成・更新観点を当て、会話へ知らせずに指示fileを編集した例から、二案の発見時点と読取負担を判断できることを確認した。
通常の返信と起動・再開を区別し、aでも把握した更新と明示的な読み直しを扱う。
bも次の当該作業の発話前の取得であり、background監視や編集即適用を保証していない。
取得しただけで合意・有効性を認定せず、終了済みの除外とversion更新時の毎回確認を維持した。
既存の経緯を削らず、採否の範囲を明記し、新たな機密情報は記載していない。

Node検査は37文書、相対link 96件、28論点、6範囲fileを確認し、問題はなかった。
論点27は決定、論点28は応答待ち、親論点1は子論点待ちである。
開始時の本文は論点27のstatus変更を除いて保持され、論点27の既存内部記録も保持された。
論点27の最初の応答と訂正全文は順に一度ずつ保存され、論点28のfeedbackは空である。

今回の差分はdesign、索引、26〜30の本文、論点27の内部記録の更新と、論点28の内部記録の追加である。
designへ反映したのは合意済みの論点27だけで、未合意の取得頻度は反映していない。
既存fileの削除、plugin本体の変更、実運用のtemporary-overrides作成や指示の終了は行っていない。
これは文書の検査と机上reviewであり、取得機構やconsumer接続を実行した結果ではない。

### 検証: aの採用を決定とdesignへ反映する

#### claim・合格条件・方法

実応答「a」を一度だけ保存し、新iterationを増やさず論点28を決定する。
起動・再開・把握した変更時の取得と同じsession内の更新反映、通常返信を再開と数えないこと、通知されていない編集の発見限界をdesignと照合する。
取得時点を未決とする現在記述だけを整え、各ターンの定期読取や実機構の変更は加えない。
Nodeで構造・link・開始snapshotからの履歴保持・変更対象とplugin本体の不変を検査し、document-reviewで合意の反映範囲を確認する。

#### 結果

実応答「a」を提案0のfeedbackへ一度だけ保存し、論点28を決定した。
document-reviewの作成・更新観点から、通常返信を再開に含めず、通知されていない編集の発見限界も含めてdesignへ反映したことを確認した。
取得時点を未決とする現在記述だけを整え、競合・終了条件などの未決範囲は残した。

Node検査は37文書、相対link 96件、28論点、6範囲fileで問題なしだった。
開始snapshotとの照合では、本文は論点28のstatus変更以外を保持したうえでfeedbackと決定を追記し、既存の内部記録も保持していた。
変更した既存fileはdesign、26〜30の本文、論点28の内部記録だけで、削除はなかった。
plugin本体は不変で、実運用のtemporary-overridesも作成していない。
これは文書の照合と机上reviewであり、取得機構の動作確認ではない。
