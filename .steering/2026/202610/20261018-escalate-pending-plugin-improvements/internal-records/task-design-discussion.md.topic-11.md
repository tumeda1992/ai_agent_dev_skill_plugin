## イテレーション0: 未決の判断が残るかで利用者確認を分ける

<a id="iteration-0-record-1"></a>

### 判断: 導出と委任と新規の判断を区別できるか

#### 対象・根拠・照合方法

既存合意を参照するだけで採否が定まる変更と、AIが合理的だと判断した新しい選択とを混ぜない境界を考える。
handoff-input.mdの第二領域、facilitate-discussionの一対一の機械適用に関する現行条件、論点6・8の採否を根拠にする。
現行skillでは具体化に新しい判断を含めば提案・合意が必要であり、この設計合意前に運用を緩めない。

参照先を変えずに相対linkを直す変更、論理記録内の親参照を複数fileへ対応させる契約変更、
索引へ状態を追加する選択、明示的に任されたscriptの技術詳細、情報不足の五つを比較する。
一案しか思いつかなかったことやAIの確信が強いことだけで、利用者判断を不要にしないかを反例として確かめる。
先に、この記録が11論点になったことに伴う物理分割を行う。
分割中は提案作成を止め、移行完了後にこの判断を再開する。

#### 比較結果と境界の具体化

合意から導けることと、AIが良いと考えることを分ける必要がある。
根拠となる合意・確認済み制約を示せて、その意味を変えずに別の結果を選べない変更だけを導出とする。
一案だけ考えたこと、他案を調べていないこと、AIの確信が強いことは導出の根拠にならない。
一つの手段しか成立しなくても、新しい負担・公開・権限・運用方針を引き受ける判断が未合意なら確認を残す。

| 具体case | 分類と理由 |
| --- | --- |
| 本文を一段深く移したので、同じ内部logへの相対linkを直す | 機械的適用。参照先・合意内容・成果の意味を変えない |
| 分割した論点の親を別範囲本文にも置くため、「同じfile内の親」という契約を「同じ論理記録内の親」へ改める | 導出変更。分割と親子保持の合意から必要だが、契約の適用範囲を具体的に変えるので個別に辿れる記録が要る |
| 索引へstatusと親も常設する | 利用者判断。閲覧の利便性と同期負荷に差があり、所在だけの索引も成立する。論点6で実際に採否を確認した |
| 読取専用scriptの引数・schemaを、論点8の委任内で詰める | 委任された判断。複数の技術案からAIが選べるが、論理的に一意だったとは記録しない |
| 既存URLの利用状況が分からない | 情報不足。確認できる事実を先に調べ、それでも必要な利用者の意図・許容範囲だけを尋ねる |
| 一つの提案しか成立しないが、利用者の未合意の公開判断を含む | 利用者判断。案数ではなく、必要な権限が未充足であることが理由 |

導出の範囲を単なる転記だけに絞ると、契約へ具体化した必然的変更まで毎回採否を問うことになる。
逆に「AIが自明だと思った」を許すと、新しい好み・優先順位・許容範囲を黙って決められる。
その間を、導出元と反例の照合、個別変更の追跡、未決判断の利用者への返却で区別する案とする。

委任は第三の根拠である。明示された対象と範囲の中でAIが判断し、委任元と選んだ理由を残す。
対象外の運用方針や実装開始まで委任を拡張せず、利用者だけが持つ権限の条件も維持する。
論点8のscript詳細への委任から、論点9の既存記録の移行時点は決まらなかった事実が、この境界の具体例になる。

#### 既存契約との差分と残る判断

現行facilitate-discussionは一対一の機械適用以外に具体判断が入ると提案・合意を要求する。
変更案は、そのうち既存合意から結果が定まる具体化を個別の導出変更として残し、採否確認の反復から分離する。
利用者判断の条件はhandoff-input.mdの四条件を保つ。
原因ownerの診断を省いて局所修正を「自明」とする経路は追加しない。

今回は境界の設計を提示する。導出変更を何番のどの形式で残すか、委任判断との記録上の区別、
横断報告と成果物への反映時点、訂正時の差し戻しは後続の独立論点に残す。
返事がないことを合意とみなす規則や、報告前の一律反映は、この判断では採用しない。
机上で六caseを照合した結果であり、自動分類器や実装を検証した結果ではない。
次は、この境界を例付きの提案0としてdiscussionへ保存する。
