# 内部検討記録: 論点10 — 分割移行の確定と中断復帰

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-6-10.md)

**論点:** 論点10

## 開始context

10論点を超えた記録は5論点単位に分け、元fileと同名のdirectory内に索引と範囲本文を置く。
移行後に元fileや互換入口を残さず、確認できる参照を新しい正本へ付け替える。
導入前から長い一fileも次の更新時に移行し、読むだけの利用や過去記録の一括移行は行わない。
通常の入口解決は、元fileと分割先の両方があれば停止する。
この条件下で履歴を失わず切り替え、途中停止時にも正本を推測で選ばない手順を設計する。
読取専用scriptに修復や書込みを追加することは、検討対象にしない。

## イテレーション0: 元fileの除去を検証後の確定境界にする

<a id="iteration-0-record-1"></a>

### 判断: 原文保持・参照更新・中断復帰を一つの移行手順として成立させる

元fileを保持して移行先と参照を検証し、最後に元fileを外す手順を推す。
復帰は事前の移行記録と実fileが一致する範囲に限定し、通常の入口解決の競合停止は維持する。

#### 必要条件・根拠・照合方法

論点3〜9の現在決定、同じ議論ownerによるsingle writer、過去の応答とiterationを保持する契約を根拠にする。
移行先を検証する前に元fileを失わず、通常の議論記録と移行途中の候補を取り違えないことが必要である。
また、移行した本文の相対linkだけでなく、内部logやdesignからの参照も元と同じ内容へ到達する必要がある。

候補は、変更前の内容digestと移行対応を既存の論点別内部logへ保存し、
元fileを保持したまま移行先と参照を作り、検証後に元fileを外す手順である。
新しい常設の進捗fileは設けず、移行中には通常の議論追記を止める。
新旧の入口が共存する途中状態、移行先の一部だけができた状態、参照更新の途中、元file除去直後、
外部編集、曖昧なlegacy見出し参照をcaseとして、再開できる根拠と止める境界を照合する。
元fileを先に外す手順と、常に移行を最初からやり直す手順も比較し、原文喪失と無関係な変更の上書きを避けられるかを見る。
今回行うのは手順の設計と机上照合であり、fileの実移動やmigration実行試験ではない。

#### 手順の成立範囲と比較

元fileを先に外すと、本文の生成・参照更新・検証のいずれかが止まった時に、元の原文を通常pathから確認できなくなる。
保持したまま候補を作れば、移行元と照合できる期間を確保できる。
ただし新旧が一時共存するため、その間は通常の議論追記を禁止し、候補を正本として扱わないことが必要になる。

移行開始前に、保存する応答などがある場合はその原文を失わない保存境界を確保する。
今回の意味上の更新と物理移行を一括の通常追記として混ぜず、比較する移行元の版を確定する。
移行対応には、元fileのdigest、実論点と担当範囲、論点外の既存説明の保存先、変更する参照と限定差分を含める。
これを対象論点の既存内部logへ残し、別の常設journalや進捗flagは新設しない。
log自身には、保存後の自分自身の全体digestを埋め込む自己参照を作らず、既存部分と追記・参照変更の範囲で照合する。

参照更新は、移動後も同じ内容を指すためのhrefの変更に限定する。
過去の文章・採否・応答原文、例示code内のpathをまとめて置換しない。
内部logへの往復link、本文内の相対link、designなどから元fileへの参照を、実際の参照先に基づいて付け替える。
旧fragmentの対象が一意に分からなければ推測せず停止する。
本文の比較は、列挙したhref変更と必要な索引・範囲境界を区別し、それ以外の内容を保持したかで判定する。

移行先・参照・原文保持の検証結果を保存し、元fileが比較元の版から変わっていないことを再確認してから外す。
除去後は、新しい入口だけで同じ論点と根拠を辿れることを再検査し、その後に通常の議論へ戻る。
複数fileの変更全体がatomicであるとは仮定しない。

#### 中断caseの机上照合

| 実fileの状態 | 復帰の境界 |
| --- | --- |
| 移行先が未作成 | 比較元が不変なら、保存済み対応から作成を始める |
| 一部の範囲本文だけある | 保存済み内容と一致する自分の作成物だけ再利用し、未完分を続ける |
| 参照更新の途中 | 各対象が変更前か予定した変更後かを照合し、残りだけ更新する |
| 元fileと移行先が共存する | 通常入口は停止したまま、同じownerが移行記録に限定して復帰する |
| 元file除去後、完了記録前 | 新入口・全本文・参照・保持内容を再検証し、成功していれば結果だけ保存する |
| 外部編集、記録欠落、予定外fileがある | 上書き・削除・自動巻き戻しをせず、差分と不足を報告して停止する |

毎回最初から作り直す案では、途中で追加された内容まで消してやり直すriskがある。
fileの有無や更新時刻だけで移行途中とみなす案も、別の正本との競合を隠すため採らない。
復帰の根拠は、保存した対応と内容の一致であり、「新しい方だろう」という推測ではない。
別ownerは既存の引き継ぎgateを省略できず、必要な証拠を安全に読めなければ復帰を始めない。

#### 案への影響と限界

提案は、新しい配置への切替と中断復帰を同じ移行単位として示す。
移行候補を読む検証は正本解決とは区別し、読取専用scriptに書込みや正本選択を追加しない。
代償として、移行中は議論の通常追記を止め、予定外変更があれば利用者に状況を返す。
これは無停止・並行writer・障害後の無条件自動修復を保証する手順ではない。
実装時には保存境界ごとの中断と、原文・参照・未完入力の保持をfixtureで検証する必要がある。
次は、この確定境界と復帰条件を具体例つきでdiscussionへ提示する。

### 検証: この議論記録の11論点を履歴保持して分割する
