# 内部検討記録: 論点12 — 導出変更と委任判断の記録単位・形式

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-11-15.md)

**論点:** 論点12

## 開始context

論点11で、利用者判断、合意からの導出、明示的な委任、機械適用の境界が決定した。
導出や委任でAIが結論を出せても、契約・成果を変える内容は個別に追跡でき、利用者合意を捏造しない記録が必要である。
今回扱うのは、その記録単位、二層記録内の所属、通常の提案・応答との見分け方である。
報告前後の成果物反映、訂正による差し戻し、完了stateへの遷移は別論点として残す。
handoff-input.mdは利用先の要求であり、今回のplugin向けschemaへの合意とは扱わない。

## イテレーション0: 個別変更を通常の論点から辿り、結論の根拠を区別する

<a id="iteration-0-record-1"></a>

### 調査: 通常の論点形式へAIの変更判断を接続する時、どの契約が変わるか

#### 問い・探索範囲・方法

既存の番号・回・二層記録を使う場合、どこが利用者の合意を前提にしており、導出・委任を誤って合意済みと表示しうるかを調べる。
facilitate-discussion/SKILL.mdの二層所属、metadata、論点の分割、decision確定、通常同期と、
iteration.mdの準備・応答処理、discussion_entry.md・internal_record.mdの保存形を照合する。
既に読んだiterationとtemplateは既存根拠として使い、読み直しを新たな発見には数えない。
handoff-input.mdの第二領域と論点11の決定を合わせ、独立変更の単位、記録へ必要な内容、未合意の反映時点を区別する。
実装・parserの試験や過去記録の書換えは行わない。

#### 通常の論点形式は利用者の採否を中心にしている

facilitate-discussion/SKILL.mdの「decisionの境界を判定する」は、decisionを利用者が採否を決める問いと定義している。
「合意したdecisionを確定する」と返却gateは、具体案と明示合意が揃う場合だけ決定を確定する。
iteration.mdも通常提示へ空の応答欄を要求する。
したがって、AIが導出した変更へ同じ応答・決定欄を埋めるだけでは、存在しない利用者合意を作るか、不要な応答待ちになる。

一方、同SKILL.mdの「論点をreparentする」には、別decisionの機械反映を空の合意待ちにしない先例がある。
通常同期にも意味を変えない修正を新論点にしない条件がある。
すべての保存を採否待ちへ統一する必要はないが、この先例は導出・委任の新形式そのものではない。

#### 変更内容と検討過程を分ける既存の二層は使える

discussionは読者が内容を評価する正本、internal-recordsは問い・根拠・比較・検証・限界の正本である。
論点番号と同じ内部logの接続を、導出・委任にも使えば、別の台帳を増やさず変更理由へ到達できる。
ただし、根拠linkだけでは変更後の意味を理解できないため、変更内容と必要な理由はdiscussionにも自立して残す。

現行の「種別」はTBDヒアリング・認識齟齬・レビュー指摘を表し、起点の区別である。
導出か委任かは判断権限の区別であり、同じfieldへ足すとレビュー起点の導出などを表しにくくなる。
表示する場所は記録案で決め、過去の種別を新しい分類へ一括変換しない。

#### 入力が要求する単位と、未決のlifecycle

handoff-input.mdの第二領域は、導出元・契約owner・理由・単独差し戻しの影響範囲が異なる変更の個別記録と、
導出元、変更箇所、理由、前後、依存成果、変更後の完全な提案を要求する。
論点11はこれを個別追跡の境界として採用したが、保存形と成果物反映の時点は未決のまま残した。
したがって、この回は記録する内容・単位と見分け方を設計できるが、報告済み・反映済みを示す完了stateはまだ決めない。

今回はSKILL.md全文、既読のiterationと二template、入力の第二領域を照合した。
parserの挙動、全consumerの実装接続、既存記録を新形式へ移す必要性は調べておらず、成立済みと主張しない。
次は同じ採番・二層記録へ接続する案を、導出・委任・不可分変更・独立変更のcaseで評価する。

<a id="iteration-0-record-2"></a>

### 判断: 同じ採番の個別論点へ、AIが行った変更の根拠を明示する

#### 必須条件・評価軸・照合するcase

番号と内部logを通常の論点と共用し、変更内容blockで「合意からの導出」か「明示委任」かを示す案を評価する。
利用者の提案・応答と混同せず、既存の種別・親子・回の識別を変えず、一つだけ差し戻せる単位を保つ必要がある。
根拠、対象、理由、前後、影響先、変更後の完全な対象範囲がdiscussionから分かるかも確認する。

論点11と同じ回の調査結果を根拠にする。
導出と委任で別台帳を持つ案、内部logだけへ記録する案、通常の提案・空応答をそのまま使う案も、
正本の分散、利用者合意との誤認、現在結果の追跡という軸で比較する。
親参照の複数file対応、委任済みscriptの入出力選択、basenameと必須href追従、
別ownerの独立変更、変更の一部に新しい利用者判断が混ざる場合を机上照合する。
例は内容blockの保存形に限定し、反映時点・status・現在結果の確定見出しは後続の論点へ残す。

#### 評価結果と採る保存形

通常と同じ論点番号・iteration・二層記録を使い、AI側の本文を「変更内容I（論点N）」として保存する案を推す。
本文の冒頭へ「判断根拠: 合意からの導出」または「判断根拠: 明示委任」を置き、根拠となる合意・指示を特定する。
既存の種別は起点の分類として維持し、判断権限と混ぜない。
通常の利用者提案は今の「提案I」と応答欄を保ち、AI側の変更に空の利用者応答欄を自動生成しない。
実際に届いた応答は原文保存するが、届いていないokや合意結果は書かない。

独立した変更は新しい連番の論点とし、変更根拠・契約owner・理由・影響範囲の違いと、単独差し戻し可能性で分ける。
同じ変更を成立させるために不可欠な複数fileの修正やhref追従は、一つの変更集合に保つ。
「同じ元合意から導けた」という理由だけで別owner・別作用の変更をまとめない。
導出元が複数あることも、親を複数にする理由にはしない。親は構造上の一つ、根拠は本文中で複数参照できる。

discussionの内容blockは、根拠と対象を特定し、変更前後、理由、影響先、変更後の完全な対象範囲を自立して示す。
全fileの再掲は要求せず、変更する契約や提案のまとまりを、diffだけでなく変更後の意味として読める形にする。
委任では比較対象と選んだ理由を残し、なぜ一意かという導出の説明へ置き換えない。
詳しい比較・反例・調査範囲・検証結果は同じ番号の内部logに残す。
この保存形は内容の正本を定めるもので、保存したことを成果物への反映済みや利用者の合意としない。

#### 五caseの机上照合と不採用案

| case | この保存形で保持すること |
| --- | --- |
| 分割後の親参照契約 | 分割と親子保持の導出元、同一論理記録へ広げる前後、別記録を親にしない制約を本文へ記録できる |
| 委任されたscriptの入出力選択 | 委任元、候補、採る仕様、選定理由を示せる。入力fileを書き換えない等の元の制約も残せる |
| basename変更と必須href追従 | 一つの変更を成立させる集合としてまとめ、fileごとの不要な論点増加を避けられる |
| 別ownerで単独差し戻せる変更 | 別の連番と内部logへ分けられ、片方の訂正理由を他方へ転記せずに済む |
| 一部に未合意の利用者判断が混入 | その部分を導出・委任と表示せず、論点11の利用者判断へ返す。記録labelで権限を作らない |

別台帳にすると、通常の論点と変更の二つの番号体系を跨ぐことになり、同じ履歴から辿る要求への利点がない。
内部logだけの記録では、正本のdiscussionから変更内容が分からず二層の責務が逆転する。
通常の提案・空応答をそのまま使う案も、回答不要という境界とぶつかる。
これらは有効な対抗馬として利用者へ選ばせず、退けた理由をこの比較に残す。

共通の採番・履歴規則を再利用できる代わりに、提案と変更内容の二種類の本文をreaderとhelperが理解する必要がある。
追加するのはAI側の内容blockだけとし、別skill、統合確認論点、常設summary fileは作らない。
過去の形式・合意を一括変換せず、今回の例も導入後の形を示す架空の抜粋と明記する。

#### 残る設計と次action

状態表示、報告・反映・訂正時の遷移、consumer返却の確定条件はこの形だけでは決まらない。
それらは次の独立論点で設計し、helperの現在結果抽出にもその時点で接続する。
今回は内容blockの原型と五caseを机上照合した結果であり、parserや保存処理の実行試験ではない。
次は、この保存形、単位の判断基準、導出と委任の二つの記入例を提案0へ保存する。
