# 内部検討記録: 論点29 — 元作業の完了と暫定指示の終了

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-26-30.md)

**論点:** 論点29

## 開始context

暫定指示は一つの作業だけに適用し、終了後も元作業のtemporary-overridesに同じfileを残す。
通常の中断・再開でも読み直すが、それだけで指示を終了・再有効化しない。
まだ終了条件のない指示について、元作業の完了を終了条件に含めるかは決まっていない。
明示された期限や終了条件の遵守は比較対象にしない。

## イテレーション0: 実際の作業完了を暫定指示の終了境界にするか

<a id="iteration-0-record-1"></a>

### 判断: 完了後に同じ作業を再開した時の既定動作

#### 判断対象・必須条件・根拠

終了条件が指定されていない暫定指示について、作業担当が完了を判断・記録した時に終了扱いにするaと、完了だけでは終了させず同じ作業の正当な再開でも使える状態を保つbを比較する。
元の作業の完了判定を横取りせず、一回の返信終了・session終了・中断を作業完了と混同しないことを必須とする。
論点23の一作業限定、論点26の実行version変更ごとの確認、論点27の終了済みfile保持と自動再有効化禁止、論点28の取得時点を維持する。
比較軸は、作業境界で指示の役目を区切ることと、同じ作業の再開で指示し直す負担である。
進行中のsession再開、実際の作業完了、完了後の同じ作業の再開、新しい別作業、完了判定前の中断、明示された終了条件の六caseを机上照合する。
作業の再開自体を許可する仕組み、終了条件の全体設計、正式修正による終了の判定、記録項目・接続の詳細は対象外とする。

#### 比較結果と推奨

aの、元作業の完了で終了する案を推す。
一作業のために承認した例外は、その作業をやり終えた時点で役目を区切れる。
後日の再開時に昔の例外を自動で持ち越さずに済む一方、同じ作業でも指示し直す負担が生じる。
終了扱いの更新は、作業担当が記録した完了を根拠に管理担当が行う必要がある。
管理担当が独自に完了を宣言したり、新たな完了承認gateを追加したりする案ではない。

| case | 作業完了で終了するa | 完了だけでは終了しないb |
| --- | --- | --- |
| 進行中のsession再開 | 元の指示を取得する | 同左 |
| 実際の作業完了 | 完了を根拠に終了扱いを記録 | 終了させず、作業していない間は使わない |
| 完了後に同じ作業を正当に再開 | 元の指示を自動復活させず、新たな指示・合意が必要 | 他の適用条件を満たせば元の指示を使える |
| 新しい別作業 | 引き継がない | 引き継がない |
| 完了判定前の中断 | 中断だけでは終了しない | 同左 |
| 明示された終了条件 | その条件に従う | 同左 |

bは、同じ作業へ戻った時に合意済みの方法も戻せる点が強い。
作業完了ごとの終了更新も不要だが、完了した作業内に未終了の指示を残す。
何を同じ作業の正当な再開と認めるかは作業担当の既存契約に従い、この案だけで完了済み作業の再開を許可しない。
また、bでもversionが変わっていれば論点26の継続確認が必要であり、既に別の理由で終了した指示は復活しない。

作業内だけに閉じることは場所と範囲の制約であり、完了後の寿命までは一意に定めない。
そのため合意からの導出ではなく、再開時の再指示と例外の持越しのどちらを避けるかという運用判断として採否を求める。
両案ともfileは残し、別作業の探索、background監視、新しいsession、上位制約の迂回は加えない。
六caseの机上比較であり、完了時の接続や状態更新を実行した結果ではない。

### 検証: 中断と作業完了を混同せず、再開時の差を選べるか

#### claim・合格条件・方法

提案保存後、document-reviewで完了後に同じ作業へ戻る例から二案の違いを判断できるか確認する。
sessionの終了・中断と作業完了を区別し、明示された期限への服従を偽の選択肢にしない。
終了後のfile保持、version変更時の継続確認、同じ作業の範囲を維持する。
Nodeで文書構造・link・範囲・索引・内部記録を検査し、開始snapshotとの履歴保持、論点28の実応答の一回保存、未合意の論点29がdesignへ反映されていないこととplugin本体の不変を確認する。

#### 結果

document-reviewの作成・更新観点を当て、完了した作業を後日再開する例から、再指示が必要なaと元の指示を使えるbの差を判断できることを確認した。
中断・session終了・承認待ちを作業完了に数えず、管理担当に完了・再開の決定権や新しい承認gateを追加していない。
両案でfile保持、別作業への非継承、明示された終了条件、version変更時の毎回確認を維持した。
本文は具体例から採否・理由・代償を読める構成で、内部記録へのlinkだけに判断材料を委ねていない。
既存の議論を削らず、新たな機密情報は記載していない。

Node検査は38文書、相対link 99件、29論点、6範囲fileで問題なしだった。
親論点1は子論点待ち、論点28は決定、論点29は応答待ちである。
開始snapshotの本文は論点28のstatus変更以外を保持して追記し、論点28の内部記録も保持した。
論点28の実応答「a」は一回だけ保存され、論点29のfeedbackは空である。

今回の変更はdesign、索引、26〜30の本文、論点28の内部記録の更新と、論点29の内部記録の追加である。
designへの反映は合意済みの論点28だけで、終了条件は未決のまま残している。
file削除、plugin本体の変更、実運用のtemporary-overrides作成や指示終了は行っていない。
これは文書検査と机上reviewであり、完了時の状態更新やconsumer接続の動作確認ではない。

### 検証: aの採用を決定とdesignへ反映する

#### claim・合格条件・方法

実応答「a」を提案0へ一度保存し、新iterationを作らず論点29を決定する。
終了条件のない指示を元作業の記録済み完了で終了すること、fileを残すこと、後日の再開には新たな指示・合意が要ることをdesignと照合する。
中断・session終了を完了と扱わず、明示された条件と既存の完了判定を維持する。
Nodeで構造・link・範囲を検査し、開始snapshotとの履歴保持・変更対象・実応答の一回保存とplugin本体の不変を確認する。
document-reviewの作成・更新観点で、他の終了条件を未決として残し、実指示の終了や新しい完了承認を混入させていないか照合する。

#### 結果

実応答「a」を一度保存し、論点29を新iterationなしで決定した。
document-reviewの作成・更新観点から、終了条件のない指示を記録済み作業完了で終了すること、file保持、後日の再開では新たな指示・合意が必要なことがdesignと一致することを確認した。
同じ作業の再開に使うという現在記述は未完了の再開に限定し、他の終了条件は未決のまま残した。
中断・session終了・承認待ちを完了扱いにせず、明示された条件と既存の完了・再開判定を維持している。

Node検査は38文書、相対link 99件、29論点、6範囲fileで問題なしだった。
開始snapshotの本文は論点29のstatus変更以外を保持して追記し、既存の内部記録も保持した。
実応答「a」は論点29へ一度だけ保存された。
変更した既存fileはdesign、26〜30の本文、論点29の内部記録だけで、追加・削除はなかった。
plugin本体は不変で、実運用のtemporary-overridesの作成や実指示の終了は行っていない。
これは文書検査と机上reviewであり、完了時の接続や状態更新の動作確認ではない。
