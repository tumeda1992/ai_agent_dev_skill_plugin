## イテレーション0: 訂正を受けた変更と後続の根拠を再評価する

<a id="iteration-0-record-1"></a>

### 判断: 既存の原因owner・論点境界と、報告後の反映待機を接続する

#### 必要条件・根拠・方法

論点11〜13、facilitate-discussionのdecision境界・原因owner routing・履歴不変を根拠にする。
実際の応答とAI側の解釈を区別し、複数の変更への訂正は個別に追跡しながら、根拠のない全件停止を避ける必要がある。
反映前の訂正、訂正と次の選択が同時に来る場合、利用者が完成形を一意に指定した場合、
AIによる再導出が必要な場合、適用後に誤りが判明する場合、一般規則の不足が原因の場合を机上照合する。
追加ok、無断の一括巻き戻し、既存履歴の上書き、新しい前提への回答流用が生じないかを確認する。

#### 結果

訂正を受けた事実の保存、原因ownerの判定、影響範囲の特定、根拠の再評価、必要な反映という順で接続できる。
訂正を新たな全件承認として扱わず、同じ変更の後続iterationと独立した新decisionを分ける。

| 照合case | 続行条件 |
| --- | --- |
| 反映前の訂正 | 対象変更とその依存先を止め、根拠を再評価する |
| 訂正と次の選択が同時 | 選択の前提が維持される場合だけ、その回答を使う |
| 利用者が完成形を一意に指定 | 通常の明示指示として扱い、同じ採否を再確認しない |
| AIによる内容の再導出 | 新iterationの変更内容を報告し、論点13の訂正機会を改めて設ける |
| 反映後に誤りが判明 | 反映済み表示をそのまま信用せず、現物と影響先を再評価する |
| 一般規則の不足が原因 | 既存の原因owner routingを通し、局所成果物だけを直して覆わない |

利用者が一意に指定した訂正まで必ずもう一往復待たせると、通常の明示decisionを例外にした論点13と衝突する。
逆に、AIが訂正から別の具体内容を組み立てた場合まで明示指示扱いにすると、訂正機会を省略してしまう。
両者を区別すれば、追加okなしの方針と反映前の訂正機会を両立できる。

変更と無関係な確定作業は止めず、影響した前提を持つ後続だけ再評価する。
過去の記録を改変せず、適用後の修復では現物と利用者の変更を守る。
一括rollbackの許可を作る規則ではなく、state machineや回復scriptの実行検証でもない。

### 検証: 訂正処理をdesignへ同期し、判断と実行の境界を保つ

#### claim・合格条件・方法

論点16の提案0への応答「b」が届いたため、論点13に従って報告済みの変更内容0を同期する。
応答には論点15への訂正がなく、論点16のb自体を論点15への明示合意として保存しない。
design.mdへ訂正の保存・原因owner判定・影響範囲の停止・根拠再評価・反映と検証を記録する。
利用者が一意に指定した訂正、AIの再導出、未決の利用者判断、次の選択と訂正の同時受領、反映後の誤りを机上照合する。
追加ok、回答の自動流用、全件停止、過去履歴の改変を要求せず、consumerの適用gateを保てれば合格とする。

discussionの未完の変更内容0は、意味を保ったまま図の描画をraw textへ揃える。
この検証でplugin本体や回復scriptを実装・実行したとは扱わない。

#### 結果

変更内容0をdesign.mdへ同期した。
完成形の一意な指定は通常の明示指示、AIの再導出は新iterationの報告と次応答待ち、未決の利用者判断は個別提案へ分かれる。
訂正と選択の同時受領では前提を先に評価し、反映後の誤りでは現物と影響先を再確認する。
五caseとも、consumerの権限・依存・検証を省かず、追加ok、回答の自動流用、全件停止や過去履歴の改変を要求しない。

文字列照合で原文・解釈の区別、影響範囲だけの停止、明示指示と再導出の分離、回答流用禁止、rollbackの境界、原因owner routingを確認した。
