# 内部検討記録: 論点13 — 導出変更・委任判断の報告と成果物反映の時点

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-11-15.md)

**論点:** 論点13

## 開始context

論点11で利用者判断・導出・委任・機械適用の境界、論点12で個別変更を同じ採番・二層へ保存する形が決定した。
保存すること、利用者に報告すること、成果物へ反映することは、まだ同じeventとして決めていない。
入力は、次の利用者decisionまたは完了reviewの直前に未報告の変更をsessionで要約し、統合確認論点やsummaryへのokを増やさないことを求める。
どの案でも反映する権限は元の合意・委任から得るのであり、返事がないことを合意とみなさない。
今回決めるのは、報告後に利用者が内容へ応答できる機会を待ってから反映するかという運用の時点である。
成果物を変更するconsumerの権限・依存関係・検証gateは維持し、報告だけで実装・公開・commit・pushを許可しない。

## イテレーション0: 報告後に次の作業応答を待つ案と、そのまま反映する案を比べる

<a id="iteration-0-record-1"></a>

### 判断: 反映前に訂正できる機会を標準で設けるか

#### 判断対象・必要条件・比較方法

aは、変更内容を保存し、次の利用者decisionまたは完了reviewと一緒に報告した後、
その作業に対する次の利用者応答を受けて、影響する訂正を先に処理してから反映する案とする。
bは、同じ報告をsessionへ出した時点で、利用者の返事を待たず、元の合意・委任内でconsumerのgateを通して反映する案とする。
どちらもsummary自体への追加okを求めず、無関係な別件の発話を反映開始の合図にはしない。

論点11・12の決定、handoff-input.md第二領域、論点12の既存契約調査を根拠にする。
事実を調べ直す形式的な調査は作らず、既知のconsumerによる適用・再評価の責務を使う。
比較軸は、反映前の訂正機会、報告・成果物の一致、応答待ちによる後続への影響である。
次の判断が変更に依存する場合、利用者が変更へ訂正を返す場合、次の応答が来ない場合、
最後の完了review、委任だけで反映まで許可されていない場合を机上照合する。
明示された反映時点はどちらの既定より優先し、正常な待機と新しい承認の不足を混同しないかも確かめる。
status名や現在結果の保存形、訂正後の具体的な再開処理は、この選択から導く後続設計として残す。

#### 比較結果と推奨

aを推す。追加のokを求めず、通常どおり次の判断やreviewへの応答を受ける間に、反映前の訂正機会も持てる。
入力の「報告し、訂正があれば個別論点へ戻す」という順序を、実際に応答できる間隔として確保できることが決め手である。
ただし入力には待機を設ける具体的なeventまでは書かれていないため、aが既に合意済みとは扱わない。
未反映の変更を正本と区別する必要が増え、次の当該作業の応答が来なければ反映しないという代償もある。

bも成立する。反映権限が元の合意・委任で足りている場合、報告後にそのまま適用しても、無応答を新たな合意にするわけではない。
同じturnで成果物と報告内容を揃え、依存する後続を待たずに進められる。
一方、利用者が報告を読んで訂正する頃には反映済みになりうるため、訂正は反映後の見直しになる。
「報告を出した」と「利用者が読んで訂正できた」は同じeventではなく、この差は論点11・12から一意には決まらない。

#### 具体caseと成立条件

| case | a: 次の当該作業の応答後 | b: 報告したturnで反映 |
| --- | --- | --- |
| 次の判断が変更に依存する | 未反映の変更を使う提案であると明示して提示できるが、依存する実行は待つ。応答後に訂正を評価し、変更反映と検証を済ませてから後続へ進む | 報告後に適用・検証し、その結果を次の提案の前提にできる |
| 利用者が変更へ訂正を返す | 反映前に影響する変更を止め、個別論点へ戻せる | 既に反映済みなら影響成果を再評価し、必要な差し戻しを行う |
| 次の作業応答が来ない | 未反映のまま保つ。時間経過・別件の発話・無応答で進めない | 先のturnで適用可能な範囲は反映済みであり、応答待ちを増やさない |
| 最後の完了review | 最終同期待ちの内容を明示し、通常のreview応答を受けて反映・検証するまでは完了を宣言しない | 同期と検証を済ませてからreviewできる。後の訂正では成果物の再更新が要る |
| 委任が仕様の選定だけを許している | 選んだ仕様の記録・報告まで。次の応答を受けても実装開始の権限は増えない | 同じく仕様の記録・報告まで。報告しただけで実装へ進めない |

どちらも、明示された反映時点、consumerが持つ適用権限・依存関係・validationを優先する。
反映不可の理由が別にあれば、その条件を解消するまで適用可能な結果とは扱わない。
利用者が明示合意した通常のdecisionの反映や、意味を変えない機械適用まで、この待機の対象へ広げない。

aで次の判断への応答と変更訂正が一緒に来た場合は、変更訂正の影響を先に評価する。
提案の前提が変わるなら、受け取った選択を別の前提へ勝手に流用しない。
これは次の応答を合意の証拠として捏造することではない。適用の根拠は元の合意・委任で、待機は訂正機会を確保する手順である。

#### 判断の射程と次action

この比較は、適用可能な変更について確認機会を優先するか、同じturnの同期を優先するかという運用選択である。
無回答を承認とみなす案、summaryへの追加okを毎回求める案、権限のない実装を開始する案は含めない。
机上のcase比較であり、実装したstate machineやconsumerの動作試験ではない。
次は、両案の流れと具体例、代償、推奨理由を提案0へ保存する。
状態表示、現在結果の保存、訂正後の具体的な再開方法は採否後の設計へ残す。
