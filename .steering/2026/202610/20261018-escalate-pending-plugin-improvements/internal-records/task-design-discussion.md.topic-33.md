# 内部検討記録: 論点33 — skill構造reviewを挟む時点

**discussion:** [task-design-discussion.md](../task-design-discussion/task-design-discussion-31-35.md)

**論点:** 論点33

## 開始context

skill-update-reviewは構造上の不合格を残した通常完了を止め、編集自体はskill-creatorへ任せる方針が論点31で決まっている。
論点32では、実績だけでなく現物に即した具体的な変更の机上検討も、不合格を支える証拠に認めた。
引き渡し入力には設計時と作成・更新後の両方でreviewする案があるが、plugin側で呼出位置は未合意である。
今回はtumeda-devがskillの作成・更新を扱うworkflow内で、構造案を採用して編集へ進む前にもreviewするか、編集後の確認へまとめるかを決める。
設計時とは本文を完成させる前の責務分担・読取・返却の構造案、編集後とは実際に作成・更新したskill一式を扱う時点である。
軽微変更を含む対象範囲、正確な入力・返却、各callerへの接続、既存検証との細かな順序、不合格類型の全ては別に詰める。

## イテレーション0: 早い構造確認と、現物へ集約した確認を比較する

<a id="iteration-0-record-1"></a>

### 判断: 構造案の時点にもreviewを必須にするか

#### 判断対象・必須条件・根拠

構造案を採用して編集へ進む前と編集後の両方でreviewするa、編集後の実際のskill一式へ必須reviewをまとめるbを比較する。
両案とも、編集後の構造上の不合格を残した通常完了を許さず、既存の設計合意・document-review・機能検証を代替しないことが必須である。
根拠には引き渡し入力の呼出位置案と、task-designの構造設計・対象成果物反映・完了gateの既存契約を使う。
評価軸は構造上の手戻りを早く抑えることと、まだ本文がない段階の確認・重複reviewを増やさないことである。
構造案ですでに処理の抱え込みが見える例、編集して初めて読取条件の不備が出る例、単純な一責務、既存gateで構造問題を発見した例を机上比較する。
設計時の確認は実際のskillを検証した結果とは扱わず、bも設計中に既に発見した問題を無視する案にはしない。

#### 比較結果と推奨

構造案と編集後の両方で確認するaを推す。
引き渡し入力で問題になったのは、本文を細かく書いた後で、独立して育つ処理を一つへ抱えていたことに気づく手戻りである。
責務分担の時点に専用reviewを置くことが、その手戻りを早く抑える目的に合う。
代償は、構造に問題のない案でも確認が一段増え、まだ本文のない案を読んでも判定できるだけの説明が必要になることである。
bは既存の設計reviewを残したまま実際の完成形へ専用reviewを集約でき、意味のある代替案である。
その代わり、専用reviewで初めて見つかった構造問題は本文を作り直す段階まで残りうる。

引き渡し入力の「tumeda-dev workflowへの差し込み」には、設計でのready前と、skill-creatorによる作成・更新後の二箇所が提案されている。
一方、task-designのStep 3は、未決事項へ依存しない合意済み変更を設計中に対象成果物へ反映できる。
同skillの「skill / docs 改善が必要になったとき」も、次の論点より前の適用を認めている。
したがって、aの前段をexecution planのready直前だけに置くと、その前にskillの編集が済んでいる経路を覆えない。
提案では「構造案を採用して編集へ進む前」とし、task-design内での反映と後続の実行担当への引渡しの両方に意味が通る時点にする。
これは呼出位置の設計であり、既存task-designの権限を拡張する判断ではない。

四caseは方針比較用のモデルであり、新skillの実行結果ではない。

| case | a: 構造案と編集後 | b: 編集後へ集約 |
| --- | --- | --- |
| 構造案に独立処理の抱え込みが見える | 編集前に専用reviewで差戻せる | 既存設計reviewで扱い、専用reviewは編集後 |
| 編集後に読取条件の記述漏れが現れる | 編集後の確認で差戻す | 編集後の確認で差戻す |
| 単純な一責務として成立する | 前段の確認も通る負担がある | 必須の専用reviewを集約できる |
| 設計中に既存gateが構造問題を発見する | 元の設計判断へ戻す | 元の設計判断へ戻す |

前段の合格は後段の免除に使えない。
設計が成立していても、実際のSKILL.mdが指示fileを読む条件を落とすなど、編集で構造上の欠落が生まれうるためである。
逆に、bを選んでも、設計中に分かった問題を放置してよいという意味にはしない。
両案とも論点31の差戻しと既存gateを維持する。

#### 提案への反映と未決範囲

提案0はreviewを置く時点だけを選び、全ての更新・誤字修正を対象にするかなどの適用範囲は未決とする。
設計時は構造案の責務分担・読取・返却を確認し、編集後は実際のskill一式を確認する、という各時点の違いを示す。
設計reviewのために本文全文を先に完成させる規則や、各論点・各返信ごとのreviewは加えない。
正確な呼出元の修正箇所、入力・返却・記録先、既存validatorとの詳細な順序は後続の設計へ残す。
この採否だけで実行用skillを変更したり、汎用のskill-creator自体を書き換えたりはしない。

### 検証: 論点33の提示がreview時点の一decisionとして判断できるか

#### claim・合格条件・方法

構造案の合格を実物の合格としておらず、呼出頻度・適用範囲・返却schemaを同時に確定していないことも照合する。
読み取り専用Node検査で採番・索引・親子・相対linkを確認し、今回の保存前との比較で論点32の旧履歴保持、原文応答bが一度だけ保存されていること、変更fileの範囲を確認する。
pluginの実行用skill・docs・scriptが不変であり、今回の確認をskill-update-reviewの実行検証と混同していないことを合格条件にする。

#### 検証結果と限界

提案0はreviewを必須にする時点の一decisionとして判断できる。
全文再読とdocument-reviewで、aは構造案と実物の両段、bは既存の設計手順を残して実物へ専用reviewを集約する案と読み分けられることを確認した。

早い手戻り防止と確認が一段増える負担を両方示し、軽微変更を含む対象範囲や各callerの詳細接続は未決に留めている。

作成・更新時観点では、二案の見出しと理由・例・適用限界の段落から、読者がどこで何を確認する案か判断できることを確認した。
索引へ状態を複製せず、内部記録の命名は既存の論点別形式を維持し、過去本文の書換えも行っていない。
秘密情報や新たな利用者識別情報は加えていない。

### 判断: 対象を明示した説明が既存の汎用skill改善の範囲を保つか

#### 必要条件と使う既存根拠

対象は記事作成の成果物や執筆工程ではなく、tumeda-dev経由で作成・更新する汎用skillの構造である。
既知の根拠は、引き渡し入力のskill-creatorを補う構造reviewという要求と、skill-creatorのAnatomy of a SkillにあるSKILL.md・指示参照・script等の役割分担である。
提案0もskill作成・更新を対象と書いていたが、chatと説明に「本文」等の指示対象を明記しない語が残っている。
共有知識自体に記事限定の制約はなく、今回は成果物固有の説明の問題として扱い、汎用skillやrepository規約へ新たな禁止規則を追加しない。
対象ファイルと処理を明示し、汎用の具体例でaとbの差を説明できるかを照合する。
変更するのは説明であり、reviewの時点・必須性の採否、軽微更新を含む適用対象などの未決事項は勝手に確定しない。

#### 照合結果と説明の修正範囲

汎用skillの構造を対象とする範囲を維持し、提案1では「本文」をSKILL.md・補助指示file等の実行指示と明記する。
skill-creatorのAnatomy of a Skillは、SKILL.mdを入口として、必要に応じてscript・reference・asset等を持つ構成を扱っている。
引き渡し要求も、開発AIのskill-creatorに編集を任せ、独立して進化する処理を一fileへ抱え込まないためのreviewを求めている。
どちらも記事執筆へ用途を限定する根拠にはならず、記事執筆の工程をこのreviewの設計へ持ち込まない。

例えばデプロイskillで、通常実行と復旧の処理をどの指示fileが持ち、SKILL.mdがどの条件で読むかを判断するモデル例なら、記事用でなくても提案0のaとbの差を説明できる。
aはその役割分担を実装前にも確認し、実装後には実fileの接続を確認する。
bは既存の設計手順を維持し、専用reviewを実装後のskill一式へ集約する。
例の置換は構造reviewを挟む時点の選択を変えず、aの早い手戻り防止と二段階確認の負担、bの確認集約と遅い手戻りの負担も維持する。

指摘のうちどの語がきっかけだったかはユーザーから特定されていないため、「本文」だけが原因だったとは断定しない。
ただし、説明対象を明記せず記事の文脈と区別しづらくした記述は今回の提案内で修正できる。
既に汎用の対象が資料に明記されているので、共有skillやrepository知識の新規不足としては扱わない。
設計対象を変えたとはせず、元の汎用skill改善として対象を明示した未決の提案1へ進む。
