## 論点51: 暫定指示の記録・選択・競合・終了を具体化する

**ステータス:** 反映済み

**親論点:** 論点1

**種別:** TBDヒアリング

### イテレーション0（論点51）: 既決方針内の具体化をAIが担当する

#### 変更内容0（論点51）

**判断根拠:** 明示委任

直前の「具体化はAIが担当し、変更と理由は個別に記録・報告する」進め方への利用者のokを根拠とする。
委任は既決方針の具体化に限る。以下をdesignの該当部分へ反映し、その後の実装の基準とする。新たな採否や架空の利用者feedbackは作らない。

##### 保存fileと管理担当

maintenance-plugin-context内へ `temporary-overrides.md` と `templates/temporary-override.md` を加える。
SKILL.mdは安定factと暫定指示の依頼を独立して受け付け、暫定指示の処理時だけ内部指示を読む。
factを頼まれていない場合はinstanceの作成・更新へ進まない。配布templateにも作業固有指示を保存しない。

元作業の `temporary-overrides/001-<短いkebab-slug>.md` のように、一指示一fileで置く。
連番はそのdirectory内で最大値+1、3桁以上、再利用なしとする。
必要時だけ作成し、終了済みfileも同じ場所へ残す。pending-escalationsと参照できるが、メモの存在を指示の権限にはしない。

templateは `## 指示`、`## 適用状況`、`## 変更と終了の履歴` を持つ。
指示には元作業のidentity、実際の利用者指示と出典、対象skill・処理・条件、現行の動作、明示された終了条件を記す。
適用状況には有効・停止・終了、確認した実行pluginのversionと取得元、確認根拠、未解決事項を記す。
変更履歴には変更前後と指示・判断の根拠を追記し、古い指示の意味を消して「元から同じだった」ことにしない。

##### 入力・取得結果と例

自然言語の既存依頼へ、暫定指示の取得・登録・更新・終了の目的、元作業のexactな場所、consumer、対象処理、確認できる実行pluginの取得元を添える。
管理担当は元作業と実行版の不足を呼出し側へ返し、別作業を探索しない。
取得結果は安定factとは別節にし、状態、適用する指示のpathと改訂、対象と条件、実効指示、実行版の根拠、停止・終了理由を返す。
取得できないことを「指示なし」へ変換しない。

| 取得結果 | 意味 |
| --- | --- |
| `active` | 対象・条件・版を確認した指示を渡す |
| `none` | 元作業を確認し、該当する有効指示がない |
| `paused` | version更新・競合等で適用を止め、必要な判断を返す |
| `unavailable` | 所在・読取・版等を確認できない |
| `ended` | 終了を記録・通知した。実効指示には含めない |

架空例では、あなたが「この作業では議論の分割を暫定適用して」と指示した時、対象をfacilitate-discussionの保存処理、状態を有効、確認版を8.0.2と記録する。
実物は利用者指示の原文と出典・元作業・実行元を記し、8.0.2を固定defaultにはしない。
8.0.3へ変わった時は、無関係な修正でも停止し、変更を確認して継続を尋ねる。
一方、実行中の正式版が指示全範囲を既に満たしたと証明できれば、理由を記録して終了・報告し、継続の確認は求めない。

##### 競合・取下げ・再開の処理

同じ対象へ効く全指示を読み、上位指示・安全・権限・確認済みfactとの不整合を先に確認する。
利用者が旧指示の置換・取下げを明示していれば、その範囲で更新・終了する。
なお並立できない指示が残れば、矛盾箇所と影響を示して対象の暫定動作を止め、解決を求める。新しいfileだからという理由で自動優先しない。
一部の意味を勝手に切り取り、有効指示を合成しない。

実行versionは実際に用いるskillの取得元と同じ配布単位の宣言から確認し、repositoryの最新版とcacheを取り違えない。
確認不能なら停止し、version更新時の停止を終了と混同しない。
明示取下げ、指定条件の成立、元作業担当の完了記録、実行する正式版による全範囲の代替で終了する。部分代替は自動改訂・終了しない。
終了した指示は自動復活させず、必要なら新しい利用者指示を受ける。

内部指示の見出しは `## 元作業と依頼を確認する`、`## 記録を登録・改訂する`、`## 適用候補と実行版を照合する`、`## 実効指示または停止理由を返す`、`## 終了を記録する` とする。
停止中に通常動作へ黙って戻さず、無関係な作業・fact取得まで止めない。

##### consumerへの接続

変更対象は `plugins/tumeda-dev/skills/` 配下の現存する全 `*/SKILL.md` と、今回新設するskill-update-review/SKILL.mdの入口だけとする。他skillの個別workflowを再設計しない。
pluginの各SKILL.mdは、実際の新規起動・別session再開・resume・把握した変更時に、元作業の場所と対象処理を管理担当へ渡す短い導線を持つ。
詳細な選択・競合・version判断を各consumerへ複製しない。
maintenance-plugin-context自身は同じ内部処理へ入り、再帰呼出ししない。
think-throughの毎turn適用と、通常の返信・内部指示fileの読直しは、新規起動として定期取得する理由にしない。
元作業がまだ未確定なら、その担当が確定してから取得し、別作業の指示を推測適用しない。

進行中の更新は管理担当が対象consumerへ返す。通知されていない編集の即時発見や、未更新の旧版skillによる自動取得は保証しない。
steeringおよび単独の作業ownerは既存の作業完了を記録した時に管理担当へ通知し、終了処理を接続する。skillの一呼出し終了を元作業の完了にしない。


#### 検討記録（論点51・イテレーション0）

安定factと暫定指示の依頼・返却を分け、詳細処理は同じmanager内の指示fileへ置く。fact不要時の空instanceと各consumerへの競合判定の散逸を防ぐ。
同一作業再開、別作業、指示なし、取得失敗、版更新、矛盾、取下げ、作業完了、部分・全代替を照合した。取得不能を指示なしにせず、明示置換以外の矛盾をAIの優先順位で解消しない。

## 論点52: skill-update-reviewの内部構成・結果形式と呼出しを具体化する

**ステータス:** 反映済み

**親論点:** 論点1

**種別:** TBDヒアリング

### イテレーション0（論点52）: 既決方針内の具体化をAIが担当する

#### 変更内容0（論点52）

**判断根拠:** 明示委任

直前の「具体化はAIが担当し、変更と理由は個別に記録・報告する」進め方への利用者のokを根拠とする。
委任は既決方針の具体化に限る。以下をdesignの該当部分へ反映し、その後の実装の基準とする。新たな採否や架空の利用者feedbackは作らない。

##### 新skillの構成と各fileの役割

`plugins/tumeda-dev/skills/skill-update-review/` を次の構成とする。

```text
skill-update-review/
├── SKILL.md
├── collect-review-material.md
├── assess-structure.md
├── templates/review-result.md
└── agents/openai.yaml
```

SKILL.mdは入力・対象更新の判定、設計時か編集後か、同じ担当の続行・再reviewへのrouting、返却先の確認を持つ。
collect-review-material.mdは `## 入力と比較元を揃える`、`## 実物と必要依存を読む`、`## 確認範囲と内容を識別する` を持つ。
assess-structure.mdは `## 全体の責務と進行を照合する`、`## 変更caseで構造を評価する`、`## 前の指摘と全体を再判定する`、`## 結果を返す` を持つ。
前者は材料の充足と読取集合、後者は構造判定と指摘の接続を担当する。SKILL.mdへ同じ詳細規則を複製しない。

templateには必要時だけの不合格詳細・未確認・将来候補・前回指摘対応の部品と記入例を置く。
openai.yamlはskill名とdescriptionに整合するUI情報を持ち、callerからの明示適用と単独の明示reviewを案内する。
既存のskills/README.mdに入口を加える。汎用skill-creatorのfileは変更しない。

##### 既決基準をどう判定へ落とすか

| 実物に見える構造 | 今回の扱い |
| --- | --- |
| 長いが一つの目的・変更理由で完結 | 長さだけでは不合格にしない |
| 固有の判断・状態・完了・独立改訂・検証を持つ内部工程 | 同じskill内の実行指示へ分ける。現在は混線していなくても必要 |
| 同一規則が独立した複数正本で手管理 | 同期が要る具体caseを示して不合格。正本集約でも解消できる |
| 分割で必須読取・状態・停止・再開・返却が消える | 不合格。fileを分けただけでは合格にしない |
| 将来の再利用予測だけによる別skill化 | 根拠にしない。現在の単独利用・他caller要求なら検討できる |
| 共有先だけの独立問題で対象に無影響 | 所在と根拠・無影響の理由を返すが、それだけで対象完了を止めない |

例としてdeployの独立した復旧工程が固有状態と再開条件を持てば、同じskillの内部fileへ分ける。
別の帳票skillでCSVとPDFが値の切替にすぎず、同じ判断・状態・完了で動くなら、その違いだけで分割しない。
同じ定義を一度だけ持ち、説明や使用例から参照しているものを二重正本とは数えない。
机上caseは何を変えるとどこへ不要に波及するかまで示し、過去の障害を創作しない。

##### 結果と内容照合の例

返却は自然なMarkdownを許容し、固定JSON・専用報告file・global IDは必須にしない。
必須情報は対象・段階・読んだ実物と範囲・比較元、判定と根拠、返却先である。
必要資料が欠けた判定と、実際に分かった不合格は併記する。

以下は架空例であり、実在の判定や実際のhashではない。

```markdown
## 対象と確認材料

対象: deploy/SKILL.md、編集後の更新。
取得元: 編集中のrepository。更新前比較元: 保存済みの編集前版。
読取: SKILL.mdと内部の復旧指示全文。共有の配布定義は使用節と共通条件。
内容識別: 対象fileごとのSHA-256と解決先を記録する。

## 判定

不合格。通常処理と復旧処理が同じ配布record項目を別々の正本で持つ。
項目追加に両箇所の同期が必要である。
解消条件: 単一の定義を両処理が参照し、復旧時の状態と返却が保持される。
方向: 定義を集約する。復旧工程の独立性は別途、状態・完了条件から評価する。

## 未確認

外部commandの失敗時の戻り値を読めなかった。復旧の停止・再開の整合は未判定。
この不足と既知問題の両方が解消するまで合格にはしない。

## 返却先

編集担当へ戻す。担当が既存の実装reviewへ結果と根拠を保存し、保存先を返す。
```

実物ではpathと比較元の所在、読取節、実際に読んだbytesのSHA-256を記し、例の説明文で代用しない。
設計資料と同じfileへ追記する結果は、評価部分の出典・当時内容を辿れる根拠と評価部分のhashを分けて残す。
新しいhash専用scriptやsnapshot fileを毎回要求しない。
返却前と結果利用時に対象集合と必要依存を再照合し、古い合格の扱いは既決の版照合に従う。

##### 呼出しの順序と完了条件

task-designは汎用skillの構造案が揃った時、構造案採用前にskill-update-reviewを明示適用する。
合格後も利用者合意は別に必要であり、不合格は根拠を設計へ戻し、材料不足は先に補う。
task-designが自分で編集する経路はskill-creatorを使う編集後、完了宣言前に編集後reviewを通す。
plan経路ではtasklist-design.mdとtemplates/tasklist.mdに同じ確認をtaskとして組み込み、tasklist-executorが実装後・DoD判定前に明示適用する。
既存のdocument-review、機能検証、独立した動作検証、ユーザー確認とcheckboxのownerは保つ。
steeringは新たな設計reviewを重ねず、既存resultの検証へ戻る。

単独で呼ばれた場合は目的・段階・対象・作業場所を確認し、同じ結果を返す。
適切な既存保存先がなければ同じ作業内のreview記録を使うが、実行結果からuser合意や編集権限を作らない。
plugin経路を使わず外部のskill-creatorだけを直接実行した変更を、自動検出・強制reviewする機構は作らない。

実装後は全対象の二層migration ledgerとwhite-box照合、未確認・不合格・再review・表記修正除外・共有先問題・版差のscenario、document-reviewと既存plugin validatorを通す。
構造reviewの合格だけで実行能力や配布全体の完成を宣言しない。


#### 検討記録（論点52・イテレーション0）

資料の充足・読取集合と構造判定は、判断と完了条件が異なる内部処理なので分ける。呼ぶのは設計・編集ownerとし、steeringの重複設計や外部creatorの改造を加えない。
一責務、独立工程、二重定義、失われる読取条件、将来再利用、共有先問題、未読source、版差で具体化した。構造・文書・機能・安全の検証を保ち、例のhashや判定を実績にしない。
