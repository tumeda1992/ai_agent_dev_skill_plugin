# skill構造review

[全体設計へ戻る](../design.md)

skill-update-reviewは、汎用skillが進化できる構造かを判定し、根拠と問題を設計・編集担当へ返す。
編集はskill-creatorが担う。構造の合格と、利用者の合意・機能・安全・動作検証の合格は区別する。

## いつ使い、誰へ返すか

汎用skillの新規作成と、起動条件・指示・入出力・役割分担・参照や読取条件・scriptの動作を変える更新が対象。
差分と参照先から意味・構造不変と示せる誤字・書式修正だけは除外する。
file種類・行数・「軽微」という呼び名で除外せず、不明な変更や実行内容が変わる変更は対象とする。
明示的に頼まれたreviewと既知の不合格への対応、既存の検証・合意条件は省略しない。

| 段階・経路 | 呼出しと後続 |
| --- | --- |
| 設計時 | task-designが構造案採用前に明示適用。不合格は設計へ、材料不足は追加確認へ戻す |
| task-design内で編集 | skill-creatorによる編集後、完了宣言前に明示適用 |
| tasklist経由で編集 | planへ確認taskを組み込み、tasklist-executorが実装後・DoD判定前に明示適用 |
| 単独review | 目的・段階・対象・元作業を確認し、指定された担当へ同じ形式で返す |

設計時の合格を編集後へ流用せず、設計時に実行指示やscript全文の先行完成を求めない。
steeringに重複する設計reviewは加えず、既存resultの検証へ戻す。
pluginを経由しない外部skill-creatorの直接実行を自動検出・強制reviewする仕組みは作らない。

設計・編集した同じagentが明示適用してよい。
作成時の思い込みを持ち越す弱点はあるが、別agentへの引き渡しを毎回の必須条件にはしない。
明示された独立review、skill-creatorが別途求める独立した動作検証、checkboxの既存担当は維持する。

## 材料を揃えて読む

呼出し側は次を既存contextから揃える。専用依頼fileや利用者の手動記入、固定構文は必須にしない。

- 対象skillの入口path、新規・更新と設計時・編集後の区別
- 目的・変更内容・保持する要件と、その根拠
- 確認材料の所在、更新前の比較材料、再reviewなら先行指摘と対応
- 元作業の場所と、結果を返す担当

設計時は全体の分担・読取条件・判断・状態・結果の受渡しを持つ構造案を使い、新設の予定入口も認める。
既存更新では現行一式も読み、編集後は実物一式・構造案・実在する更新前後の比較材料を使う。比較元はcommitに限定しない。
読んで埋まる不足は自ら確認し、対象不明・必読資料の取得不能・要件不足は影響と共に返す。
要件を創作せず、別作業を探索しない。読取許可を任意の実行・生成・編集許可へ広げない。

| 対象 | 読む範囲 |
| --- | --- |
| 対象skillのSKILL.md・補助指示 | 全体。未変更処理も含む |
| そのskillが役割と改訂を管理する専用script・内部module | 実際のsource全文。所在・拡張子で除外しない |
| 共有指示・共有module | 目次・利用規則、利用部分、共通定義・条件・例外、必要な参照と前提 |
| 呼ぶだけの別skill | SKILL.md全文と受渡しの参照。条件・入力・判断・状態・完了・失敗・中断・返却・再開を呼出し側と照合 |
| 外部command・library | 利用する入出力・失敗・副作用などの条件と必要な根拠 |

共有先の独立性が不明、全文読取の明示がある、内部実装が構造判定に必要という場合は読取を広げる。
別skillの入口と契約で確認できない場合は必要な内部指示まで辿る。
内部処理を直接使う場合も、飛ばす入口の判断・状態・前提を確認する。

対象skill自身と今回更新する呼出先は全体を確認する。
一方、呼ぶだけの別skillや全依存先の独立reviewを自動連鎖させない。
既存の必読条件は維持し、要約・前段結果・test成功で実物の読取を代替しない。
実際の取得元・解決先と読んだfile・範囲を結果へ残す。

## 構造を判定する

対象skill全体について、指示とコードの分担、入出力、判断・状態、停止・再開・返却、
同じ規則の正本、独立した改訂理由と検証のまとまりを確認する。
今回編集しない内部処理に既存の不合格があっても、通常完了までに解消する。
整理が元の合意を越えるなら設計へ戻し、必要な合意が得られなければ未完として止める。

| 構造 | 判定の基準 |
| --- | --- |
| 長いが一つの目的と変更理由で完結する | 長さだけでは分割を要求しない |
| 固有の判断・状態・完了条件、独立した改訂理由と検証を持つ工程 | 同じskill内の実行指示fileへ分ける。混線の実績がなくても、一fileへ抱え込む構成は不合格 |
| 同じ規則を別々の正本として手管理する | 変更時に同期が要る具体caseを示して不合格。単一正本への集約でも解消できる |
| 分割で必須読取・状態・停止・再開・返却が消える | 不合格。file分割そのものを合格条件にはしない |
| 別skillへ独立させる | 現在の単独利用・他callerの具体要求が必要。将来予測だけでは独立させない |

親skill内だけで使う処理は、必要なら内部指示へ切り出す。
現在の外部利用要求が生じた時は、実装済みcallerや実績を待たず別skill化を検討できる。
内部指示には読む条件・所有する判断と状態・親への返却を明示し、分割後の全体flowと能力を保持する。

根拠は実際の改訂・実行・review記録に加え、現物に即した変更の机上検討でもよい。
何を変え、どこへ不要な連動修正・重複同期が生じるかまで示す。
新skillでも評価できるが、過去の障害は創作せず、反証があれば再判定する。
要約・使用例や単一正本からの生成、要求上必要な波及を重複不良と取り違えない。
全不合格を分割命令へ変換せず、機能・安全・既存要件の不備は対応する既存gateでも扱う。

### 別の具体例へ当てる

deployの復旧工程に固有の状態・再開条件・完了があれば、同じskill内の内部fileへ分ける。
帳票skillのCSVとPDFが同じ判断・状態・完了の値の切替にすぎなければ、その違いでは分けない。
同じ配布record項目を通常処理と復旧処理が別々に手管理し、項目追加で両方の同期が要るなら二重正本の不合格である。
一度だけ定義して双方から参照する場合は、その共有自体を不良にしない。

### 共有先に見つかった問題

利用処理・共通定義などを通じて対象skillへ影響する問題は必須対応にする。
共有先の別用途だけの独立問題で無影響と確認できたものは、所在・根拠・無影響の理由を返すが、それだけでは今回の完了を止めない。
影響が不明なら必要確認へ戻り、確認不能なら未確認と影響を返す。推定で範囲外へ除外しない。
対象skill自身の未変更処理と、依頼された共有文書の更新範囲をこの除外へ含めない。
範囲外の現在の問題を将来候補へ薄めず、対象skillの合格を共有先全体の合格へ拡張しない。
後続は元のworkflowへ返し、別作業・外部連絡・無断編集を始めない。

## 結果と、保存する担当

返却は自然なMarkdownを使え、固定JSON・global ID・専用報告fileは必須にしない。
対象、確認段階、実際の読取材料と範囲、更新前の比較元、判定と根拠、返却先を毎回示す。

| 判定 | 条件 |
| --- | --- |
| 不合格 | 具体的な構造上の問題がある |
| 材料不足 | 不合格の根拠はないが、必要な範囲を確認できていない |
| 合格 | 必要な範囲を確認し、不合格がない |

不合格と未確認が併存すれば両方を示し、既知の問題を直しただけで合格にしない。
各不合格には問題箇所・根拠・解消条件・整理の方向と、保持すべき境界・状態・受渡しを示す。
実装可能な完成構成の作成は設計へ返し、reviewが毎回完成案まで作ることは要求しない。
未確認には不足材料・理由・判定への影響・再開に必要なものを示す。
将来の改善候補は現時点で非必須と明示し、材料不足の言い換えにしない。

再reviewでは先行指摘の所在・対応・解消または未解消を対応付け、撤回にも理由を残す。
旧指摘だけへ確認を狭めず、現物全体を再判定する。該当しない空見出しは作らない。

結果は呼出し側が権限を持つ既存の設計議論・taskの検証記録・実装reviewへ保存し、保存先と対象箇所を返す。
適切な保存先がない単独利用なら同じ作業内へ記録を用意する。
既存のwriterを維持し、chatだけの結果や架空のfeedback、同じ根拠の正本の複製は作らない。

### 結果の記入例

架空例であり、実際の判定やhashではない。

```markdown
## 対象と確認材料

対象: deploy/SKILL.md、編集後の更新。
取得元: 編集中repository。比較元: 保存済みの編集前版。
読取: SKILL.mdと復旧指示の全文。共有定義は利用部分と共通条件。
内容識別: 対象fileごとの実解決先とSHA-256。

## 判定

不合格。通常処理と復旧処理が同じ配布record項目を別の正本で持つ。
項目追加に二箇所の同期が必要である。
解消条件: 単一の定義を参照し、復旧時の状態と返却を保持する。
整理の方向: 定義を集約する。復旧工程の独立性は状態と完了条件から別に評価する。

## 未確認

外部commandの失敗時の戻り値を確認できず、復旧の停止・再開は未判定。
既知問題と不足の両方が解消するまで合格にはしない。

## 返却先

編集担当が既存の実装reviewへ保存し、保存先を返す。
```

実物には実際のpath・比較元の所在・読取範囲と、読んだbytesのhashを記す。
例の説明文で内容識別を代用しない。

## 確認した内容の版と照合する

結果には実際の取得元・入口・解決先・確認段階・読取集合と範囲、必要依存・資料の内容識別根拠を残す。
可変なローカル指示file・sourceは内容hashで識別し、skill名・version・commitだけで未commitの実物の一致を認定しない。
要件・構造案・先行指摘は評価部分と当時の内容を辿れる根拠を持ち、評価対象と結果追記を分けて自己参照のhash不一致を避ける。

返却前と、呼出し側が次工程・作業再開に結果を使う時に照合する。
以前のfileのhashだけでなく、追加・削除、必要な参照・解決先・前提の変化を確認する。
review中に変化した材料を混ぜたまま現行版の合格にしない。

| 確認後の変化 | 結果の扱い |
| --- | --- |
| 意味・構造不変と示せる表記修正 | 変化と無影響の根拠を残して維持できる |
| 共有文書の未使用の独立節だけ | 利用部分・共通定義・適用規則への無影響を示して維持できる |
| 構造や必要な前提が変化 | 対象skill全体と必要な依存を再review |
| 影響不明、必要資料が不足 | 追加確認へ戻し、不足と影響・既知問題を併記。旧合格で通さない |

以前の判定は履歴として残し、維持・再reviewの根拠を後続へ結ぶ。
たとえば復旧指示が未commitで変わった時、versionが同じでも状態や返却が変われば全体を再reviewする。
hashは読了・合格・機能検証・実在する更新前比較材料の代替ではない。
必要な比較元を読めなければ資料不足とする。

既存履歴・保存済み版を使え、毎回の専用snapshot・全資料複製・hash専用scriptを要求しない。
各返信での監視、全repositoryの追跡、排他lock、将来の配布・導入・実行内容の一致は保証しない。
構造合格だけで動作・安全・作業完了を認定しない。

## 実装するfileと接続

`plugins/tumeda-dev/skills/skill-update-review/` を新設する。

| file | 担当と見出し |
| --- | --- |
| SKILL.md | 対象更新の判定、入力、段階、同一担当の続行・再review、返却先へのrouting |
| collect-review-material.md | 入力と比較元を揃える / 実物と必要依存を読む / 確認範囲と内容を識別する |
| assess-structure.md | 全体の責務と進行を照合する / 変更caseで構造を評価する / 前の指摘と全体を再判定する / 結果を返す |
| templates/review-result.md | 不合格・未確認・将来候補・前回指摘対応の必要な部品と記入例 |
| agents/openai.yaml | 名称・descriptionに整合するUI情報。callerからの明示適用と単独の明示reviewを案内 |

材料の充足・読取集合と構造判定は判断と完了条件が異なるため内部指示を分け、詳細規則をSKILL.mdへ複写しない。
既存skills/README.mdへ入口を追加する。外部のskill-creatorは変更しない。

task-design/SKILL.mdへ設計時と内部編集後の呼出しを接続する。
task-design/tasklist-design.mdとtask-design/templates/tasklist.mdへ確認taskを組み込み、tasklist-executor/SKILL.mdへ実装後・DoD判定前の明示起動を接続する。
document-review、機能・安全の検証、独立した動作検証、利用者確認は保持する。
