# 情報構造化の標準

大きなナレッジ（あるドメインの仕様・知識のかたまり）を、**正しいだけでなく、初見の人でも理解しやすい**形に構造化するための標準。この README だけで考え方を掴めるように書く。

`documentation_standards/` は「ドキュメンテーションの標準」の傘であり、このファイルはその中の **情報構造化** を扱う。文体・レビュー手順など他の標準は別に定める。

（この標準を実際のナレッジに**適用する手順**は、これを読み込む skill が担う。ここでは「どういう形が良いか（型と理由）」だけを述べる。）

---

## 1. なぜこの標準があるか

情報が 1 万個あるとき、100 だけ知りたい人が 1 万個すべてを読まないと目的に辿り着けない——これは「書いてある内容は正しいが、理解しにくい」状態。

この標準のゴールは、**正しさの上に「理解しやすさ」を積む**こと。読み手が **必要な分だけを、必要な深さで読める** ように情報を構造化する。「間違っていないドキュメント群を作る」ことがゴールではない。間違っていないのは前提で、その上で理解が容易であることを目指す。構造の判断はすべて「読み手が早く正しく理解できるか」に向ける。

## 2. 全体像 — ドメインを 1 つの「仕様」として組む

ナレッジは **ドメイン**（`orders`・`inventory` のような業務のまとまり）ごとに置く。そして、ドメインのディレクトリの中に `spec/`（仕様置き場）をわざわざ作らない。**ドメインのディレクトリそのものが仕様として機能する**ように中身を並べる。読む人にとっては「このドメインのことは、このディレクトリを開けばいい」という一箇所になる。

ドメインの中身は、役割の違う 3 種類でできている。

- **overview** — ドメイン全体を、少数の概念で、平易に説明する入口。
- **ナレッジモジュール** — overview が持ち出した概念のうち、深いものを深掘りする場所。
- **cases** — 「起こりうること」を漏れなく並べ、網羅を保証する索引。

overview とモジュールで「仕様の中身」ができ、cases が「その全体を漏れなく押さえたか」を保証する。以降でそれぞれを説明する。

そして、ドメイン直下に **README** を置き、全体の索引にする——役割・読む順の目安・**ナレッジモジュール一覧**（各概念モジュールが何を扱い・なぜ要るか）・直下のファイル/ディレクトリ。README は初見の入口であり、**構造を提案・合意する単位**でもある: overview は骨子概念しか導線しないので、直下の索引まで見て初めて、概念モジュールでない要素（テーブル・値辞書・testing 等）も含めた全体が見える。雛形は [`README.template.md`](./README.template.md)。

## 3. overview — 概念で全体を掴ませる入口

overview は、そのドメインを初めて見る人が **これだけ読めば全体像を掴める** ことを目標に書く、ドメインの入口。ドメインの中身 3 種のうち「腹落ちの入口」を担う（合格ラインは「最低限説明した」でなく「**初見が腹落ちする**」こと——詳細をモジュールに譲っても、その人の目的には overview だけで足りる状態にする）。

**overview の役割・貫く思想（what を書く／腹落ちのゴールから構成する）とそのアンチパターン・満たすための構造とテクニックは、[writing_overview.md](./writing_overview.md) にまとめてある。** overview を書く・レビューするときはそこに従う。

## 4. ナレッジモジュール — 概念ごとの深掘り

overview が名指した概念が、モジュールの候補になる。

- ただし、**深さのある概念だけ**をディレクトリ（モジュール）として実体化する。深さのない概念は overview の中の一節で足りる。「概念だから」という理由で薄いディレクトリを乱立させない。
- したがって **モジュールの一覧は overview から導かれる**。先に overview を書けば、どのモジュールが要るかが見えてくる。**逆に、overview を書き終える前にモジュールのディレクトリ構成を決めてはいけない**。plan 段階でモジュール構成が先に在るのは順序が逆で、たいてい他ドメインのガワの流用になる（§9）。
- モジュールの中身は、そのナレッジの**性質に合わせて個別に設計する**。全モジュールに同じ雛形を機械的に貼らない。あるものは「版 × 実装 × 判断」、あるものは「状態の遷移」、あるものは「API 単位」と、切り方は変わってよい。
- **overview から各モジュールへの導線（地図）を張る。** 概略で足りる読者は overview だけで済むが、深く知りたくなった読者は overview を起点に各概念の詳細（モジュール）へ出ていく。だから各概念の詳細をどこに譲るかを示す導線は必須——無いと overview とモジュールが連関なく散逸する。導線の張り方（役割でなく構造テクニックである点・乱発しない・置き場）は [writing_overview.md](./writing_overview.md) の「地図」節。

## 5. cases — 網羅の索引

overview とモジュールで中身は説明できるが、「起こりうることを漏れなく押さえたか」は別に保証が要る。それを担うのが cases。

- cases は「起こりうる状況（パターン）」を漏れなく並べたもの。**これさえ網羅すれば全ユースケースを網羅した**、と言える単位にする。
- overview と並ぶ存在だが、**薄く書くのは論外**。すべてを網羅する、いちばん厚い存在になりうる。仕様が固まって初めて網羅を確定できるので、**最後に書く**。
- 各状況では「何が起きるか」と、そのケースを理解するのに必要な情報を書く。**深い詳細（仕組み・データ・式）はモジュールに譲る**（指し示すだけで再説明しない）。ただし譲るのは深い詳細だけで、ケース自体を理解するのに要る情報は cases に書く。
- 目安として、**overview と cases だけを読めば、モジュールを開かなくてもドメインの全体像が掴める**状態にする。

内部構造は、いきなり個々のケースを並べない:

1. まず **概念図（幹）** を置く。
2. そこから **どの軸で枝分かれするか** を示す。
3. その先に **個々のケース（葉）** を置く。

こうすると、読み手は最初の図と分岐で骨子を掴み、個々のケースはその枝の先の穴埋めとして読める。葉の書き方は**先にテンプレートを宣言する**（例:「各ケースは〈影響・状態・見え方〉の観点で書く」）。本文はその穴埋めになり、抜け漏れも見つけやすくなる。

この**入口（幹＋分岐の地図）は cases 自身の overview** にあたる。初見がそれだけを見て、個々のケースを読まずに骨子（何がどの軸で枝分かれするか）を掴める状態か——**入口を書いた時点で一度、全部書き上がった時点でもう一度レビューする**（overview と同じく、単独で概略が掴めることを確かめる）。

**cases に書くのは「具体的な状況」であって、抽象的な軸ではない。** 「状態遷移・掛け算・横断不変条件」は、**どんな種類のケースを取りこぼしていないかを確かめる不可視のチェック**であって、ファイル名や見出しにする構造ラベルではない。**軸をそのまま構造にすると、たとえば「掛け算」を「相手の状態」のような抽象に畳んでしまい、具体的な掛け算ケースを丸ごと落とす**（実際に起きた失敗）。

種類ごとに、**具体で・内容名のファイル**に書く:

- **状態遷移のケース** — トリガーで状態がどう動くか。cases の幹（概念図 → 分岐 → 葉）はこれ。**1 本の読める樹形**にまとめる。
- **具体的な掛け算のケース** — ある軸（例: 注文 × 配送ステータス〈未出荷 → 出荷済 → 配達済〉）と掛け合わせた**実際のケース群**。抽象軸として樹形に畳まず、内容のある独立ファイル（例: `shipping_status_cases.md`）に**具体値で**書く。数が少なくても「毎回その場で考えると漏れる」ので固定して残す。
- **横断不変条件** — どのケースでも壊れてはいけない整合性（認可・冪等・合算など）。「何が起きるか」でなく「何が壊れてはいけないか」なので、内容名の独立ファイル（例: `data_integrity.md`）にする。

**ファイル名は中身で付ける**（`transitions.md`・`掛け算.md` のような軸名にしない）。エッセンスは「**最初を読めば骨子・枝が自明・各ケースは掛け合わせのセル（横展開結果）**」——これが生きているかを常に確かめる。

**cases は常にディレクトリ（`cases/`）で切る。** 1 ファイルで足りる規模でも、複雑化したときに素直に割れる力学を働かせるため、最初からディレクトリにしておく。

## 6. 配置 — 何に一番強く結びつくかで決まる

どのナレッジをどこに置くかは、そのナレッジが **何に最も強く結びついているか** で決める。

- ドメイン全体に効く骨格（overview / cases / 概念モジュール）→ **ドメイン直下**。
- 特定の概念にべったり結びつくもの → **その概念モジュールの中**。近くに置くこと自体が「密結合」を表す。
- 仕様ではない補助的なナレッジ → **2 種を分ける**。**(a) そのドメインの内容に関する補助**（テスト・seed 等）→ ドメイン直下に置き、中は関心ごとに階層を組む（**対等でないものを同じ階層に並べない**。例: e2e はテストの一種なので `testing/e2e`）。**(b) docs 群の書き方・移植運用のメタ資料**（執筆原則・import プロンプト等）→ 原則ドメインに置かず docs 標準側に集約する（そのドメイン固有の運用だけを最小限隔離してよい）。
- 役目を終えたナレッジ → 捨てずに、**それが元々居た場所**に `histories` として残す。`archive` でなく `histories` にするのは、有効だった期間があるナレッジを当時の文脈ごと残すため（単なる没メモ置き場ではない）。ただし「あり得たが頓挫した構想」も将来また浮上しうるので、残す価値がある。

**ドメイン固有のテーブルは、1 テーブル 1 ファイルの `*.model.md` を必ず作る**（各カラムを「何を表し・どの仕様で使うか」で説明する。物理名＋型の羅列や、README の役割表・関連図だけで済ませない——それだとテーブルの中身が落ちて致命的）。**全カラムを残す**こと（仕様に絡まない列は「共通列」等とまとめてよいが、存在ごと消さない・型や制約は残す）。カラムの**一次ソースは実スキーマ（`db/schema.rb` 等）**——散文資料には全カラムが載らないので、散文だけで書き起こさず実スキーマを開いて取る（散文にある列だけ書くと静かに間引かれる）。「重要な列だけ抜粋」は情報量削減にあたり不可（`*.model.md` は「羅列するな＝各行に意味を付す」と「情報量を削るな＝全カラム残す」を両立させる）。**書式は既存の [`table_description.template.md`](../../doc_templates/table_description.template.md) に従う**（独自の書式を発明しない）。

### `*.model.md` の置き場所 — 「テーブル」で寄せ集めず、結びつきで決める

置き場所は、そのテーブルが**何に一番強く結びつくか**（絡み合いの強さ）で決める。**原則は「テーブルという種類でひとつの箱に寄せ集めない」**——概念モジュールに紐付くものは、そのモジュールの中へ。上から順に検討する:

- **特定の概念モジュールにべったり結びつく → そのモジュールの中に置く**（第一に検討）。近くに置くこと自体が密結合を表す。
  - 一般例: EC ドメインで「返品」モジュールがあり、返品明細テーブルが返品でしか使われないなら、`returns/return_line.model.md` としてモジュール内へ。
- **どのモジュールにも一意に属さない中核・単純なテーブル → ドメイン直下にそのまま置く**。複数モジュールが参照する芯のエンティティで、構造自体は素直なもの。
  - 一般例: 「注文本体」`order.model.md` を EC ドメイン直下に（注文・出荷・返品など複数モジュールが参照する中核）。
- **どのモジュールにも一意に属さず、かつ複数テーブルが絡み合って初めて理解できる → 泣く泣く専用ディレクトリ（`data_models/` 等）を組む**（最後の手段）。これは「テーブルをとりあえず一箇所に集めたい」という書き手の欲（種類での寄せ集め）と紙一重。**各テーブルが本当に単一モジュールに帰属できないこと・関連図を見ないと個々が読めないことを確かめてから**にする。安易に選ぶと、上 2 つで概念モジュールへ配れるテーブルまで巻き込んで空の寄せ集め箱になる。
  - 一般例: 顧客の残高が「台帳・明細・相殺結果・イベント」の数テーブルで初めて意味をなし、どの業務モジュールにも一意に属さないとき。

**コード値の辞書は、テーブル定義とは別のナレッジ。** 区分コード・enum・外部連携の種別値などは「値 → 意味」の対応が正本で、処理の説明に溶かさず独立させる（例: `value_descriptions/`）。テーブル定義（何を持つか）と値辞書（値が何を意味するか）は別物。

### 時間軸の 3 状態で置き場所を分ける

ナレッジは時間軸で 3 つに分かれ、それぞれ置き場所が違う。

- **現行**（仕様本体）— overview / モジュール / cases。
- **過去**（役目を終えた）— それが居た階層に `histories` として、**当時の文脈（記入者・日付・原記録の体裁）ごと保全**する。ただし**現行の本文には固有名（記入者名等）を持ち込まない**（決定の結果だけ残す）。**過去版と現行版で同じパラメータの値が違うとき（例: 旧 返品期限 10 日 → 現行 30 日）、現行本文には最新版の値だけを書き、旧値は `histories` に隔離する**（両者を現行本文に混在させない。方針書＝過去 と 現行実装＝現在 を同格の正本として混ぜると、旧値が現行に流れ込む）。
- **未確定**（これからどうなるか）— 独立ファイル（`open_questions` 等）に隔離**しない**。**該当する現行トピックにインラインで `⚠️ 未確定:` として置く**。読者はその仕様を読む文脈で未確定を知るべきで、独立させると現行と乖離して腐る。一覧性は grep で担保する。

（`histories`＝過去・`⚠️ 未確定`＝未来。役割が近いので、過去か未確定かで置き場所を明確に分ける。）

### 同じ状況を複数の関心から書くときは「状況 ID」で貫く

同じ状況を、複数のモジュールが別々の関心から書くことがある（例: あるケースについて「ケース索引」「データがどう変わるか」「判定根拠」）。このとき**状況に安定した ID を振り、各モジュールは同 ID で対応づける**（例: 状態遷移表の `V3`・cases の `V3`・判定ロジックの該当パターンが同じ `V3`）。散文の相互リンクより、ID で貫く方が読者は対応箇所を即座に辿れる。ID の採番の正本は cases が持つ。

特に、**同じ状況の「業務から見た結果」（cases）と「その裏でデータがどう書き換わるか」（`data_models` 側）を、同一 ID で二層に分ける**と両面から引ける。データ書き換えが複雑なら、cases（業務結果）とは別に `data_models` に「状況 ID 対応のデータ遷移」を独立させる。

**ただし cases が正本を持つのは、ドメイン内部で採番した状況 ID に限る。** 外部ツール・外部工程が持つ ID 体系（テスト生成区分など）は、その工程のモジュール（`testing` 等）側に置き、cases とは**対照表**で結ぶ。cases 本体に外部都合の ID を混ぜない（cases が外部工程の都合を知りすぎると層が逆流する）。

## 7. 読者 — 書く側が深さを測る「物差し」

誰に向けて、どの深さで書くか。それを測る物差しが「読者」で、職種でなく **関与の仕方** で捉える。読者の定義——関与の仕方による段階（概観読者／ライト利用読者／ヘビー利用読者／改修読者／設計読者）・重ね着・露出しないルール——は標準 [`core_readers.md`](../core_readers.md) にまとめてある。本標準はそれを前提に、扱う成果物を「**どの読者が単独で読めれば成立か**」で設計する:

- **overview** は、**概観読者** が単独で腹落ちできる水準（§3）。
- **cases** は、**ヘビー利用読者** が「これで全ユースケースを押さえた」と網羅を判断できる水準（§5）。
- **モジュール** は、**改修読者** が現行を追って変更できる水準（§4）。判断の経緯・棄却案は現行本文に混ぜず histories に置き、**設計読者** がそこを辿る（§6）。

読者像は書く側の道具であって、読者に見せない（本文・見出し・ディレクトリ名に読者名や定義を出さない。見せるのは README の「読む順の目安」程度の導線だけ）。詳細は [`core_readers.md`](../core_readers.md) §3。

## 8. 書き方の作法

構造が正しくても、書き方で理解しやすさは大きく変わる。

- **散文・箇条書き・表・図の使い分け（記法）は別標準 [`expression_notation.md`](../expression_notation.md) に従う。** とくに「新概念を列挙で並べない」「悪い箇条書きを出さない」はそこで点検する。
- **説明の順序は、網羅の対称でなく理解の流れに従える。** 例: 注文の確定を説明した次は、理解が自然に進む出荷（次の段階）へ行く。「確定があるから取消も」と注文の取消を対称で先に出すのは、理解優先でなく説明（網羅）優先で、読み手の腹落ちを止める。
- **章の頭に「地図」を置く。** その章がどう枝分かれするかを最初に示してから詳細に入る。全体のトップに詳細を盛りすぎない——上が重く階層のない構造は「網羅している風で機能しない」。**概略 → 章の概略 → 詳細** と、深さを段階的に配る。
- **見出しは、読み手が場面を掴める分かりやすさで付ける。** 書き手都合の内部符号・冗長な接頭辞を避ける。情報差の小さい見出しは統合する。
- **結論を先に置く。** 式・収束・不変条件のように「答え」があるものは、導出より先に答えを打つ（例: 冒頭「合計は常に X に収束する」→ 後段で段階的に証明）。
- **処理フロー（探索順・呼び出し順）は仕様語に還元して本文に書く。** 例:「注文番号の一致を第一に、次に顧客 ID・日付・金額で推定」。メソッド呼び出し順そのもの・SQL・クラス名・ファイルパス・バッチ名は本文に置かず、各モジュール末尾の「実装の入口」にまとめて隔離する。判断基準は「その順序が**仕様**（変わりにくい業務判断）か**実装都合**（変わりうる）か」。
- **データのカラムは物理名＋型の羅列でなく「何を表し、どの仕様で使われるか」で書く。** DDL 転記は実装ベタ書きと同じく腐る。
- **情報量は削らない。** 構造化とは、整形・順序変更・階層化であって、情報を減らすことではない。

## 9. やりがちな失敗

構造を作るとき・見直すときに、自分に問う。

- **既存の構造・ファイル名から発想する。** 「再構成」なのに、書き手都合の既存の箱を名前だけ変えて温存していないか。情報の洗い出しと読者の必要から組み直す。
- **他ドメインのディレクトリ構成（ガワ）を、中身の必要性を確かめず複製する（過学習）。** 参考ドメインに `app_view/` `prompts/` があったからと同じ箱を置いていないか。毎回あるとは限らない箱を、自分のドメインに実在を確かめず機械的に真似ない。構成は**そのドメインの overview から導く**もので、他ドメインの模写ではない。
- **手順（どこに何を足すか）から入る。** 何を作るか（情報の全体像と読者の必要）を先に決める。
- **全モジュールに同じ雛形を機械的に貼る。** 中身を見て考えていない証拠。
- **モジュール内を「概念 / 条件 / 手順」「定義 / フロー」のような情報の種類で切る。** これは書き手都合の切り方。読者は「どの業務状態か」「どの API か」「どのライフステージか」で引く。切る軸は情報の種類でなく**読者が引く単位**にする。
- **フラットに並べる／意味のない中間ディレクトリで階層に見せる。** 深さは中身の性質から作る。
- **書き手の内部符号（読者ラベル等）をファイル名・本文に出す。** 読み手に辞書引きを強いる。
- **仕様でなく実装（メソッド名・SQL・行番号・クラス名・ファイルパス・バッチ名）を書き込む。** ナレッジが管理すべきは「変わりにくい仕様」。実装は変わるたびに直す羽目になる。実装は正しさの裏取りに使い、成果物には仕様の言葉で残す（→ §8 の「実装の入口」に隔離）。
- **冪等性・認可などの横断不変条件を cases に持たせ忘れる。** 状態遷移の樹形に埋もれて落ちやすい。独立章として確保する。
- **overview で新用語を用語集として並べる。** 概念の腹落ちにならない（列挙の失敗と同根）。
- **cases の分岐を思いつきで作る。** 概念図から導いた枝でないと、網羅している確信が持てない。
- **合意した構造を、その基準そのもので自己検証しない。** 「要素が揃った」を「良い構造になった」と取り違える。提示前に「最初を読んで骨子が掴めるか」を自分で読み返す。
- **元資料を読み切らずに「あるはずのもの」を落とす。** 見出しだけでなく本文まで読み、別ソースがあれば突き合わせる。

## 10. 命名方針

- ファイル名・ディレクトリ名は英語。日本語のファイル名は使わない。
- 表記（`snake_case` など）は、**そのドキュメントが属するツリーの既存の慣習に合わせる**。「どれが絶対に正しい」ではなく、周囲を調べて従うのが方法論。外れ値があれば正規化する。
- 命名は工程の最後に確定してよいが、後回し＝手抜きではない。名前は構造の本質。
