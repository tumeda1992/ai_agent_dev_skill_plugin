# 命名の基本

名前を付ける対象が何であっても成立する原則。対象種別に固有の規則は同階層の各fileが持つ（[README.md](./README.md)）。

## 初見でも自明にわかる名前にする

その名前が生まれた経緯・議論を知らない初見の人が、**名前だけ見て中身を正しく受け取れる**こと。参加者だけに通じる略語・対比・内部符号は避ける。

- ✗ `spec_over_implementation` — 何の spec か、なぜ implementation との対比なのか、議論を知らないと読めない
- ○ `business_specification` — 「ビジネス仕様の標準」だと初見で受け取れる
- ✗ 章や節へ `S1`〜`S9` のような連番 ID を振り、本文の相互参照をその ID で行う — ID が中身を示さないため ID→意味の変換表を常に要求し、章の追加・統合・分割で番号が壊れる
- ○ 参照先自体が内容を示す名前を持ち、その名前で参照する

この原則を満たしているかは、名前を見た初見の人が何を想像するかを書き出して実態と照合することで検算できる。手順は [reverse_translation.md](./reverse_translation.md) が持つ。

## 手続き的な how でなく、宣言的な what / why を表す

「どう実現するか（手順）」でなく「何であるか・何のためか」で名付ける。手順は変わるが、what / why は変わりにくい。

- ✗ `recalculate_and_save_balance` — やり方の羅列
- ○ `settle` — 何をするか（結果・意図）

### 何をもって宣言的とするか

宣言的であることは、ジョブを **「input に処理を与えて out が出る（out な状態になる）」** と抽象化した上で、**どれを名指すか** で決まる。

out は二つに分かれる。

- **output**: そのジョブが生み出す成果物
- **outcome**: そのジョブを経た状態変化。なぜその output を返すのか、それによって何を得るのか、どういうゴールに至るのか、何が変わるのか、何が分かるのか

優先順位は次である。

1. **outcome** を名指す
2. outcome だけでは存在理由を説明できないとき、**output** を名指す
3. それでも差別化できず、差別化要素が input にあるなら **input** を入れる
4. 差別化要素が処理のストラテジーなら、**処理** を抽象化して入れる

判断の問い: **「手段が変わっても名前が変わらないか」**

手続き的な命名を禁止する規則ではない。同列に並ぶ要素を差別化するために処理を名前へ表す場合がある。優先順位 3 と 4 は、outcome と output だけでは区別がつかないときに降りる先である。

### 具体例: 単体のジョブ

ユーザーの退会処理を考える。input は退会前の会員、処理はセッションの破棄・個人データの削除・確認メールの送信、output は退会レコード、outcome は退会した状態になることである。

- ✗ `destroy_session_and_delete_data_and_send_mail` — 処理の羅列
- ✗ `create_withdrawal_record` — output を名指している。退会レコードを作ることが目的ではない
- ○ `withdraw` — outcome を名指している

物理削除から論理削除へ変えても、メール送信をやめても `withdraw` は変わらない。`create_withdrawal_record` は、レコードを作らず状態フラグだけ更新する実装へ変えると合わなくなる。

冒頭の `settle` / `recalculate_and_save_balance` も同じ構造である。前者は outcome（決済が済んだ状態）、後者は処理の羅列を名指している。

### 具体例: 判断の場が同列に並ぶとき

新規事業を検討する文書を四つに分ける場合を考える。それぞれが判断を下す場所である。

| output を名指す | outcome を名指す |
| --- | --- |
| `market.md` | `is-there-a-market.md` |
| `product.md` | `what-do-we-build.md` |
| `finance.md` | `does-it-pay-off.md` |
| `team.md` | `who-builds-it.md` |

左は「市場について何か書いてある」ことは伝わるが、市場調査の結果を置く場所なのか、市場があるかを判定する場所なのかが読み手に分からない。名詞が並ぶだけで、そのファイルが何をする存在なのかが読めない。

### output で名付けて成立する場合

output を名指すと必ず落ちるわけではない。次のいずれかに当たるなら output でよい。

- 成果物を置くだけの場所であり、判断を下す場所ではない
- 既に確立した名前がある。`Context` / `Decision` / `Consequences`（アーキテクチャ決定記録）のように、読み手がその分野で共有している

差が出るのは、**判断を下す場所であり、かつ既存の確立した名前がない**場合である。この条件を確認せずに outcome へ書き換えると、既に成立している名前まで変えることになる。

### 優先順位を降りる前に確認する

outcome で名付けられないと判断する前に、その判断が特定の語形の制約によるものでないかを確認する。

- `decided-items`（過去分詞）は決定済みのものだけが入るように読める
- `decisions`（名詞）なら、決まりかけのものも含められる

過去分詞や進行形という語形の制約を、outcome 全体の制約と取り違えない。名詞で表せば状態を問わず含められることが多い。

## 中身が大まかにわかる具体性を備える

名前から内容が大づかみできること。汎用化・意味抜きをしすぎて「**間違ってはいないが、何も意味していない**汎用的な名前」になる失敗を避ける。

- ✗ `data` / `manager` / `info` / `util` — 何でも入る＝何も言っていない
- ○ 実態を名指す具体語にする

## 修飾の向きで指すものが変わる

同じ 2 語でも「A の B」と「B の A」は別物である。修飾の向きが変われば、名前が指す対象が変わる。

- 判断の問い: **「その名前が指すのは、出来事（行為）か、状態を持つ物か」**
- 出来事 → 行為を表す名詞形にする
- 物 → 状態を形容詞で修飾した形にする

- ✗ `retry_notification`（通知のリトライ＝出来事）を、リトライ済みの通知を指す名前として使う
- ○ 出来事なら `retry_notification`、物なら `retried_notification`

MUST: 形容詞を単独で名詞の位置に置かない（`retried` だけでは何が retried なのか示せない）。形容詞形を採るときは修飾先の名詞を伴わせる。

## 表現が同じでも、名前空間が違えば別の意味を持つ

同じ表現が既に別の場所で使われていても、それだけを理由に候補から外さない。

- 判断の問い: **「その2つは、同じ読み手が同じ場面で出会うか」**
- 出会う → 同じ名前空間にある。次の問いへ進む
- 出会わない → 名前空間が違う。表現が同じでも共存してよい

出会う場合に問うべきは「被っているか」ではなく **「意味が同じか」** である。

- 意味が違う → 別の名前にする
- 意味が同じ → **その語こそが正しい名前である。** 避けて別の語を作らない

避けて別の語を作ると、読み手は確立した語との差を探すことになる。差がないのに別名を与えると、差があるという誤った示唆を与える。

- ○ 「直前の変更を取り消す操作」に `undo` を使う。編集操作の名前空間で確立しており、実態が一致する
- ✗ 同じ操作に `revert_change` や `rollback_edit` を与える。読み手は `undo` との差を探す
- ✗ 映画やゲームの `pre-production`（本制作前に企画・試作を固める段階）を、ソフトウェアの制作段階へ使う。構造は似ているが、読み手にとって `production` は本番環境を指すため意味が一致しない

やってしまいがちな失敗: 既存用語と被った時点で候補から外す。意味の一致を確認しないため、その分野の確立した概念と実態が同じ場合でも、わざわざ別の語を作ることになる。

名前空間はディレクトリやmoduleの境界だけで決まらない。読み手と場面で決まる。同じfile内でも扱う対象が違えば別の名前空間になり得る。逆に別fileでも、同じ読み手が同じ判断のために両方を読むなら同じ名前空間である。境界で定義すると、境界をまたぐ参照がある場合に判定を誤る。

- ✗ 語の出現箇所をgrepで数え、ヒットしたことだけを理由に候補から外す
- ○ その2つが同じ読み手に同じ場面で出会うかを問い、出会わないなら共存させる

やってしまいがちな失敗: 出現数の多い一般語（`state`、`owner`、`context`等）を、他所で使われているという理由だけで使用不能にする。これらは文脈ごとに違う意味で使われており、それで機能している。正しい判断のための問い: 「その2つは、同じ読み手が同じ場面で出会うか」。

## 名前を単独で評価しない

名前は、それが属する名前空間の中で読まれる。単独で評価すると、置かれた場所での読まれ方を見落とす。

評価するときは次の形で読む。

- 親がある場合は `親/自分` の形で読み、意味が通るかを確認する
- 同列に並ぶ要素を列挙し、抽象度と表記が揃うかを確認する
- レシーバーがある場合は `レシーバー.メソッド名` の形で読む（[method.md](./method.md)）

単独で評価すると次が起きる。

- 親が既に語っていることを子で繰り返し、冗長になる
- 同列の要素と抽象度がずれ、どちらが上位でどちらが下位かが読めなくなる
- 単独では通る名前が、親と並べると意味が重複または矛盾する

具体例。`documentation_standards/business_specification.md` は、単独では「ビジネス仕様」としか読めないが、親と並べれば「ビジネス仕様のドキュメンテーション標準」と読める。

対比として `utils/helpers.md` は、単独評価では「helpers は汎用的すぎる」までしか気づけない。親と並べて初めて「この階層全体が何も言っていない」ことが見える。

判断の問い: **「この名前を、置かれた場所の形で読んだか。単独で読んで判定していないか」**

この原則を対象種別ごとに具体化したものが [file.md](./file.md) の「同階層の存在と足並みを揃える」「直上ディレクトリのコンテキストを継承する」と、[method.md](./method.md) の「`レシーバー.メソッド名` で意味が通る名前にする」である。

## 命名後、名前と実態の対応をレビューする

付けた名前と実態の対応を上の観点で見直し、外していたら**改名して再レビュー**する。命名は工程の最後でも本質として詰める（軽視して流さない）。

レビューの書き方（記述形式、評価水準の合わせ方、レビュー結果の扱い）は [review.md](./review.md) が持つ。
