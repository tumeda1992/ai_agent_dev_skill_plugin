# 次に何を試すか

命名で行き詰まったとき、または名前をより良くしたいときに引く索引と手段。

**これらは毎回通す手順ではない。** 使わずに良い名前ができるなら、それでよい。引くかどうかは、得られるものと手間のトレードオフで決める。命名の機会は多く、すべての場面で全部を通すことはできない。

## 実態を一文で説明する

名前が決まらないとき、命名を離れて実態を一文で説明する。

「これは何か」「これは何をするか」を、名前を考えずに書く。

書けないなら、実態が固まっていない。名前ではなく実態を先に決める。名前が決まらない原因が実態の未確定にあるとき、候補をいくら出しても薄いままになる。

書けたら、その一文から名前を導く。導き方は [core.md](./core.md) の「何をもって宣言的とするか」が持つ。一文の中から、そのジョブを経た状態変化（outcome）にあたる部分を探す。

具体例。「このクラスは、入力を検証してから正規化し、永続化する」と書けたなら、outcome は「入力が検証済みかつ正規化された状態で保存されていること」である。ここから名前を導く。一文が書けていないうちは、outcome がどこにあるかも分からない。

やってしまいがちな失敗: 実態を言語化しないまま候補を出し続ける。候補が薄い原因を語彙不足だと考え、類語をさらに探す。原因は語彙ではなく、何を名付けようとしているかが未確定であることにある。

判断の問い: **「実態を一文で言えるか。言えないまま候補を出していないか」**

## 役割の言語化が中身を覆っているか確認する

候補が特定の側面へ偏るとき、役割の言語化を疑う。

役割を一文で言語化し、それが対象の中身をすべて覆っているかを確認する。覆っていない部分に対応する候補は出ない。

具体例。あるクラスが検証・変換・保存の三つを行うとき、役割を「データを保存する」と言語化すると、候補が `DataSaver` / `RecordWriter` / `PersistenceHandler` のように保存系へ偏る。検証と変換が名前から落ちる。

やってしまいがちな失敗: 候補を個別にレビューして偏りに気づこうとする。役割の言語化を間違えると、そこから演繹した候補がすべて同じ方向へ偏るため、相対比較では気づけない。全候補が同じ欠落を持っていると、比較では差が出ない。

判断の問い: **「この役割の言語化は、対象の中身をすべて覆っているか」**

## 予約語との衝突を解く

予約語と重なったとき、案ごと落とさない。順に試す。

1. **意味が一致するか確認する。** 一致するならその語を使う（[core.md](./core.md) の「表現が同じでも、名前空間が違えば別の意味を持つ」）
2. **重なった部分だけを一般語へ置き換える。** 構造が良いなら、衝突している一語だけを差し替える
3. **品詞を変える。** 置き換え先の一般語が見つからないとき、品詞を変えると予約語性が消えることがある

具体例。`planning` はスクラムの Sprint Planning と衝突するが、`plan`（名詞）にすると活動名ではなく成果物を指すため衝突が薄れる。`build` は CI/CD と衝突するが、`ready-to-make` のように句の中で動詞として置くと、ビルド処理ではなく「作る」と読まれる。

やってしまいがちな失敗: 予約語を検出した時点で案ごと落とす。構造が良く、一語だけが衝突しているだけの案を取りこぼす。

判断の問い: **「この案が落ちる理由は、構造にあるか。それとも一語だけか」**

## 語数を上げる

短い案がどれも伝わらないとき、語数の制約を外す。

1. まず 1〜4 語で試す
2. 通らなければ、長すぎてもよいので意味が完全に通る版を書く
3. そこから部分ごとに意訳して削り、各段階で[逆翻訳](./reverse_translation.md)を当てる
4. 削ると意味が落ちる箇所で止める

削れない部分が、その名前に必要な要素である。

やってしまいがちな失敗: 語数を 2〜3 語に制約したまま案を出し続ける。制約は自分で課したものであり、対象から要請されたものではない。新しい概念には既存の短い語がないため、短くしようとすると必ず意味が落ちる（[review.md](./review.md) の「評価基準を到達可能な水準へ合わせる」）。

手間が大きいのは、長い版を書いてから一段ずつ削り、各段階で逆翻訳を当てるためである。短い名前で足りる場面では引かない。
