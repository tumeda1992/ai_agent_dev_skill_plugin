# 検証の記録

## 主張と確かめ方

claim、合格条件、方法、対象範囲を実施前に保存する。期待どおり動いた例だけで広いclaimを支えないよう、境界と反例を含める。
実行、机上照合、目視、文字列検査を区別し、何を観測できる方法かを明記する。

## 期待と実際の結果

対象ごとに期待と実測を対応付ける。成功・失敗・未実施・取得不能を区別し、出力の存在だけを挙動の正しさにしない。
結果後、支持できる結論と限界を冒頭へ加え、方法と証拠へ降りて読める形にする。

## 反例・未検証範囲から結論の射程を定める

反例があればclaimか案を修正し、次の検証を定める。限定された成功を全能力保存へ拡張しない。
次actionや最終案への影響を残す。validatorが通ることと、理由・順序・失敗時挙動を保持したことは別に扱う。

## 検証の記入形と例

開始形：

```markdown
##### 検証: 再送が初回の宛先を維持するか

###### claim・合格条件・方法

初回送信後に宛先設定を変えて再送し、配送adapterへ渡る宛先が初回snapshotと一致するかをテスト環境で確認する。新規送信は変更後の宛先になることも対照にする。
```

結果後の例：

```markdown
**通常再送では初回宛先が保たれ、新規送信は現在値になった。** 手動の宛先override経路は未検証であり、すべての再送経路へ一般化しない。

###### 期待と実測

通常再送二件と新規送信一件でadapter入力を照合し、期待に一致した。配送サービス側の実配達はこの検証に含めていない。

###### 未検証と次の確認

override経路が同じcontractを持つかは別途確認する。今回の案が保証する範囲は通常再送に限定する。
```
