# ケース網羅の標準

`documentation_standards/` の傘の下の 1 トピック。あるドメインで「起こりうる状況（ケース）」を **漏れなく** 挙げ、しかも **漏れていないと読み手が確かめられる** 形で書くための標準。ケースをどこに置くか・どうファイル分割するかは [`information_structuring`](../information_structuring/README.md) が、記法は [`expression_notation.md`](../expression_notation.md) が扱う。ここは **中身の作り方** を扱う。記入例は [`example_cases/`](./example_cases/overview.md)、空の雛形は [`cases.template.md`](./cases.template.md)。

cases が満たすべきは 2 つ:

1. **どの状況も漏れなく拾っている。**
2. **漏れていないと読み手が確かめられる。** 「全部書きました」という書き手の主張ではなく、読み手が骨格を見て埋まり具合を自分で検査できる。

作り方は 2 つの塊に分かれる:

- **洗い出し** — 状況の全量を軸で張り、網羅を崩して確かめる方法とアンチパターン → [`enumeration.md`](./enumeration.md)
- **表現** — 網羅を確かめられる形で見せ、個々のケース（葉）を書く → [`presentation.md`](./presentation.md)

そのうえで、状況の網羅とは別軸で**データ整合性の不変条件**を押さえる（下記）。

## データ整合性の不変条件（認可・冪等性・独立性）

状況の列挙（どのマス・どの遷移が起きるか）とは別に、**どのケースを通っても壊れてはいけないデータの整合性** がある。「何が起きるか」でなく「**結果のデータが正しいか**」。状態遷移には乗らないので、独立して書き出す（例: `data_integrity.md`）。ドメインを問わず効くのは主に 3 つ:

- **認可（スコープ）** — 他人のデータが見えない・触れない（IDOR を防ぐ）。DB 上は全員のデータが同じ表に並ぶので、本人での絞り込みが常に効く。
- **冪等性** — 同じ操作・イベントが再送・重複・リトライで複数回来ても、二重に計上・適用しない。
- **複数データの独立性** — 同じ人が複数のデータ（旅程・利用など）を持っても、対象だけが処理され他に及ばず、合計が正しく分離・集計される。

各々〈不変条件・なぜ重要・どこで点検〉で書き、動作確認で検証する。**利用者への金額が正しいか等のビジネス上の正しさは、これとは別**——各ケースの期待状態が個別に担う。ここはデータ・システム側の整合性に絞る。状況の網羅とは別に、これも押さえて初めて cases は完成する。

## つまり

網羅と「網羅していると伝わること」は、別々の作業ではない。**変化の軸で分解し、その分解（掛け合わせのマス）を見える形で示す**——この一手で両方が同時に達成される。書き手は思いつきでなく系統的にマスを埋め、読み手は同じ骨格を見て埋まり具合を確かめる。
