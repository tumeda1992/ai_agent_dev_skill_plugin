# overview の書き方

`information_structuring` の傘の下の 1 トピック。ドメイン直下に置く `overview.md` が**何のためにあり、どう書けばその役割を果たすか**を扱う。構造化の全体像（overview・モジュール・cases の 3 種をどう組むか）は [README](./README.md) が、記法は [expression_notation](../expression_notation.md) が扱う。

**overview を書くときの狙いと、レビューするときの物差しは同じ 1 つ**（下の役割・思想）。書く側とレビュー側で別の基準を持たない。

## overview の役割 — 腹落ちの入口と、深掘りへの地図

overview の役割は 2 つ（主は腹落ち、あわせて地図）:

- **腹落ちの入口**（主）: 初めて見る人がこれだけ読めば全体像を掴める。欠ければ「読んでも何も分からない**単なる目次**」に堕ちる。
- **地図**: ドメイン知識全体の入口として、概略で足りる読者はここで済み、深く知りたくなった読者はここを起点に各概念の詳細（モジュール）へ出ていく。無いと overview とモジュールが連関なく散逸する。

その上で:

- **読者**: 概観読者。プログラミングにもそのドメインにも詳しくなく、腰を据えて精読せず 1〜5 分で「要は何の仕組みか」だけを掴みたい初見（人物像は [core_readers](../core_readers.md)）。書くときもレビューするときも、まずこの人になりきる。
- **合格ライン**: 「最低限説明した」ではなく「初見が腹落ちする」こと。詳細はモジュールに譲ってよいが、**概略だけ書いて詳細を読まないと分からないのは失敗**——その人の目的には overview だけで足りる状態にする。読んだ人がその後を自分で再現・判断できるまで書き、腹落ちのために概念どうしの繋がりや順序を尽くす（1 つの見方でまとまれば腹落ちしやすいが、それは手段の一つにすぎず必須ではない）。

## 貫く思想（ここが核）

役割を満たすには、まず思想を外さないこと。下の 2 つが核で、これを外すと、見せ方をどれだけ工夫しても腹落ちしない。

### 思想 1: what を書く

初見が掴みたいのは「要は何をする仕組みか（**what**）」であって、「どう実装・表現しているか（**how**）」ではない。overview に載る各文が what を語っているかを、書きながら・レビューしながら問う。

崩れ方は **how 基準の説明に流れる**こと。たとえば「注文の状態は単一のステータス列でなく、複数の独立した軸の組合せで持つ」——設計の見どころに見えるが、これは状態を**どう保持するか（how）**の話だ。初見が知りたいのは「注文は**どんな**状態を経るか（what）」であって、how の難しさを overview で説明しても腹落ちには一切効かない（そういう詳細は改修読者向けのモジュールへ譲る）。

### 思想 2: 腹落ちのゴールから構成を決める

「初見がこれを読んで何を掴めれば腹落ちか」を先に据え、その達成に要るものだけを・要る順で並べる。構成は**腹落ちのゴールから**導くのであって、手元の資料の並びから導くのではない。

崩れ方は **説明都合・資料転用の構成になる**こと。たとえば元にした調査資料に「ハブ」「テーブル一覧」の章があったからと、overview にも同名の節を作ってしまう——それは資料の都合であって、腹落ちのゴールから導いた構成ではない。「情報として重要」「元資料にあった」で節を作らない。

そして、概念が増えても**ドメイン自体を分割する方向に逃げない**。自身の配下をうまく分割し（各概念をモジュールや入れ子の overview へ押し下げ）、overview 自身は全体を掴ませる役に徹する。

## 役割を満たすテクニック（手段）

役割（腹落ちの入口・地図）を、思想を外さずに実現する書き方。地図を機能させる導線と、腹落ちの見せ方からなる。

### 地図を機能させる — 導線の置き方

地図の役割（深掘りへの入口）を働かせる書き方。各概念の詳細をどこに譲るかを示す導線を置く——ただし**理解に侵食させない**。禁止するのは乱発（`→ ○○の深掘り` を本文の至る所に撒く・「詳細は譲る」を連呼する、で理解の流れが分断され導線が主役になること）。置き場は**末尾に集約**（「もっと知りたいとき」の一覧など）でも、**各トピックの節末に一言**でもよい。

### 見せ方のテクニック

各項は軽いので箇条書きで（狙い ／ 崩れ方）:

- **冒頭に 3 行程度の要旨（結論先行）** ／ 崩れ方: 要旨がなく、最後まで読まないと要点が掴めない
- **少数概念で、他を開かず腹落ちするまで説明**（両手で数えられるくらいになりがち。ただしこれは経験則で、「少なくないと誤り」ではない——豊穣な情報を持つドメインはざらにある。薄い言及で終わらせず、一つずつ説明する）／ 崩れ方: 像を結ばない・どこが幹か分からない・用語を並べただけ
- **知らない概念は使う前に接地**（身近な言葉や具体で先に導入）／ 崩れ方: 未定義語のまま説明が進む
- **絵になる構造は図で**（流れ・分岐・状態遷移。散文の壁にしない。[expression_notation](../expression_notation.md)）／ 崩れ方: 構造が段落に埋もれる・逆に箇条書きで済むものを図にして重い
- **読む順が理解の積み上がりに沿う**（前を読めば次が分かる）／ 崩れ方: 網羅の都合で並ぶ
- **大きければ `overview/` ディレクトリに**。概念自体が複雑なら、その概念のモジュールの中にさらに overview を置いて入れ子にしてもよい
