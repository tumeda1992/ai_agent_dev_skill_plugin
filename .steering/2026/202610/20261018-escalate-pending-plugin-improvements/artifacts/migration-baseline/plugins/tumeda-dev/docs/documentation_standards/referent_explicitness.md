# 指示対象の明示

`documentation_standards/` の傘の下の 1 トピック。**文中の語が指す実体を、読み手がその文だけから復元できるか**を扱う。

## 一般則（許可から始める）

指示対象が読み手にとって自明なら、指示語を使ってよい。同じ理由で、主語や目的語を省略してよい。自明でないなら、語を実体へ置き換えるか、実体を併記して埋める。

指示語はこそあど言葉に限らない。抽象名や system 内部語も、実体と結ばれていなければ暗黙の指示語として働く。書き手は指示対象の実体を知っているため、省略しても自分では読める。読み手は実体を知らないため復元できない。この非対称が、「内容は難しくないのに読めない」文章を生む。

## 埋めるべき三条件

次のいずれかに当たる指示対象は、実体を埋める。

1. **document の外にある** — 参照先が同じ document に無く、読み手が別 file を探さないと分からない。
2. **離れている** — 参照先が同じ document 内にあっても、当該文から離れており、前後だけでは分からない。
3. **複数候補に読める** — 参照先が一つに定まらず、どの実体を指すかで意味が変わる。

## 判定の問い

**この語が指すものを、この document しか読んでいない人が言えるか。**

言えるなら自明であり、そのまま使ってよい。言えないなら、上記三条件のどれに当たるかを特定し、実体を埋める。

## 指示語の範囲

- **こそあど言葉**（これ・それ・この・その 等）
- **抽象名**（「契約」「条件」「対応」等、それ自体では何を指すか定まらない語）
- **system 内部語**（「repository context」「返却」等、system 固有の意味を持つがどの実体かは別途定まる語）
- **主語省略**（動詞の主語・目的語が文中に無い）

こそあど言葉以外は一見具体語に見えるため気づきにくい。「repository context」も「返却」も、文としては完成しているように読めるが、どの file のどの記載を指すかは別途定まっており、その結びつけが文中に無いと指示語と同じ機能を持つ。

## 型ごとの、だめな例と直した形

### 型1: 動詞の主語と目的語が無い

- だめな例: 「repository context の返却を条件にして成果物を生成・省略する契約は、`maintenance-plugin-context` の返却形式で条件を書く」
  - なぜ切り離すと意味が取れないか: 「書く」の主語（誰が書くのか）と目的語（何の file へ書くのか）が無い。この文だけを読んだ人は、書く行為が誰の作業なのかを言えない。
- 直した形: 「`task-design` は、`.agents/skills/tumeda-dev-plugin-context.md` に local Git 運用条件の記載があるかどうかで、commit section を生成するか省略するかを判定する。記載が無ければ利用者へ確認する」

### 型2: system 内部語を実体と結ばずに使う

- だめな例: `plugins/tumeda-dev/skills/task-design/tasklist-design.md:122` の「local Git運用条件がrepository contextから返された場合」
  - なぜ切り離すと意味が取れないか: 「repository context」がどの file を指すか、「返された」が何と比較して真になるかがこの文に無い。読み手は「返された」を「context 全体が存在すること」と読むこともできれば、「該当項目が明示されていること」と読むこともでき、どちらかに定まらない。
- 直した形: 「`.agents/skills/tumeda-dev-plugin-context.md` に local Git 運用条件の記載がある場合」

### 型3: 指示語の根拠が離れている

- だめな例: 「3箇所とも今は『返ってきた場合だけ生成する』としか書いてない」
  - なぜ切り離すと意味が取れないか: 「3箇所」がどの3箇所かの列挙が、この文の近くに無い。読み手はこの文だけを読んで、対象が `tasklist-design.md` の2箇所と `runtime-execution-contracts.md` の1箇所であることを言えない。
- 直した形: 「`tasklist-design.md:122`（commit section の生成条件）、同 `:123`（push・PR section の生成条件）、`runtime-execution-contracts.md` の `Repository context` 節。この3箇所は、どれも条件があるときの動作しか書いておらず、条件を満たさないときの動作を書いていない」

## 検知手段

**その文を前後から取り出して読む。** 取り出した文だけで指示対象を言えるかを確認する。言えなければ、埋めるべき三条件のどれかに当たっている。

この検知手段は、document 全文の自己完結までは求めない。同じ段落内・直前直後で実体が明示されていれば十分であり、「document を最初から読み返さないと分からない」ことを禁止条件にはしない。

## 該当しない例

- `content_density.md` の「読者が下駄を履いた状態」: 抽象的な比喩だが、同じ document 内でこの語の直後に「3つが同時に立っている状態」として定義が続く。指示対象が document 内で自明であり、埋める対象ではない。
- `naming/core.md` の `spec_over_implementation`: 読みにくい識別子だが、これは命名標準が扱う「名前の付け方」の問題であり、指示語や省略の問題ではない。この標準の対象は文中の指示対象であり、識別子そのものの命名品質は `naming/core.md` の管轄である。

この標準は、すべての抽象語・比喩・省略を禁じるものではない。指示対象が自明な場合は許可されており、上記二つはその許可の範囲に収まる例である。
