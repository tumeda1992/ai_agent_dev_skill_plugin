# ビジネス仕様を書く

docs には **ビジネス仕様** ——「実装が変わっても変わらない、業務としてのふるまい・規則」—— を書く。この標準は「何を・どの粒度で書くか」を定める。

`documentation_standards/` の中で、この標準は **記載レベル**（どの抽象度で書くか）を扱う。情報の並べ方（構造化）や文体は、それぞれ別の標準に委ねる。

---

## 1. なぜ — 仕様は残り、実装は変わる

同じ業務ルールでも、それを実現するコードは何度も書き換わる。メソッド名・クラス構成・SQL・処理順は実装の都合で変わるが、「業務として何が起きるか」は簡単には変わらない。

docs が実装の写しになっていると、実装を変えるたびに docs も直す羽目になり、やがて追随されず腐る。**ビジネス仕様の粒度で書けば、実装変更に巻き込まれない**。「腐らない」はこの粒度で書いたことの帰結であって、目的ではない。目的は「業務としてのふるまいを、読み手が正しく掴めること」。

判断の中心にある問い: **「この記述は、実装が変わっても変わらないか？」**
- 変わらない → ビジネス仕様。本文に書く。
- 実装を変えたら変わる → 実装都合。本文から外し、必要なら §3「実装の入口」へ。

---

## 2. 何を書くか — ビジネス仕様の粒度

### 2.1 処理は「実装の語彙」でなく「仕様の語彙」で書く

メソッド名・行番号・SQL・クラス名・ファイルパス・バッチ名を本文に書かない。処理フロー（探索順・呼び出し順・分岐）は、**業務判断の言葉に還元**して書く。

- ✗ 実装ベタ: 「`Order#current_shipment_status` が `shipments` を `id desc` で引き、`status == 'delivered'` のとき `DELIVERED` を返す」
- ○ 仕様: 「注文の配送状態は、最新の配送記録の結果で決まる。配達済なら『配達済』、輸送中なら『輸送中』、配送失敗なら『失敗』、未出荷なら『未出荷』」

- ✗ 実装ベタ: 「`MatchingService#match` が `where(order_no:)` を先に呼び、空なら `where(customer_id:, date:, amount:)` で再検索」
- ○ 仕様: 「配送実績と注文の突き合わせは、注文番号の一致を第一に、一致しなければ顧客 ID・日付・金額で推定して突き合わせる」

判断: その順序・分岐が **業務判断**（変わりにくい）か、**実装都合**（変わりうる）か。業務判断なら仕様語で本文に、実装都合なら本文に書かない。

### 2.2 データは「意味と用途」で書く（物理名＋型の羅列にしない）

カラムを DDL のように転記しても、それが業務上何を表すかは伝わらず、しかもスキーマ変更で腐る。**「何を表し、どの業務仕様で使われるか」**を書く。

- ✗ 転記: 「`customers.status` : integer, NOT NULL, default 0」
- ○ 仕様: 「顧客ステータスは顧客のライフステージ（仮登録／本登録／休眠／退会）を表し、出荷の可否や配送方法の分岐に使われる」

### 2.3 コード値は値辞書として独立させる

区分コード・enum・外部連携の種別値などは、「値 → 意味」の対応が正本になる。処理の説明の中に「`status == 1` のとき」と溶かし込まず、**値辞書として独立**させる（処理側からは意味の名前で参照する）。

- ○ 値辞書: 「顧客ステータス区分 — `0`=仮登録 / `1`=本登録 / `2`=休眠 / `3`=退会」
- ○ 参照側: 「本登録のときのみ出荷対象になる」（`status == 1` とは書かない）

テーブル定義（何を持つか）と値辞書（値が何を意味するか）は別のナレッジ。混ぜない。

### 2.4 観測・スナップショットを仕様として残さない

いま観測できた値・件数・日付・"currently"・メトリクス・ログ出力は、時間が経てば嘘になる。仕様は「**こうでなければならない**」を書く。「**いまこうなっている**」は書かない。

- ✗ 観測: 「現在アクティブ顧客は約 123 万名」「2026 年時点ではリトライは 3 回」
- ○ 仕様: 「送信に失敗した通知は再送する（回数は運用パラメータ）」

どうしても現状に触れる必要があるときは、観測としてでなく「制約」「規則」に抽象化できないかを先に問い、できなければ書かない。

## 3. 実装の裏取りと「実装の入口」

実装を読むことは、仕様の正しさを裏取りするために必要。ただし裏取りの過程（メソッド名・`file:line`・SQL）は **成果物の本文に混ぜない**。

根拠を残す価値がある場合（調査中・レビュー用など）は、本文と分けて各トピック末尾の **「実装の入口」** に隔離する。本文は仕様語のまま保ち、そこを辿れば実装に降りられる、という構造にする。

## 4. 提示前のセルフチェック

1 つでも該当したら本文を直す。

- [ ] メソッド名・行番号・SQL・クラス名・ファイルパス・バッチ名が本文に漏れていないか
- [ ] 処理フロー・探索順を、業務判断の言葉に還元したか（実装都合の順序を仕様のように書いていないか）
- [ ] データを「意味と用途」で書いたか（物理名＋型の羅列になっていないか）
- [ ] コード値を値辞書として独立させたか（処理説明に生の値を埋めていないか）
- [ ] 観測・スナップショット（現在値・件数・日付・メトリクス）を仕様として残していないか
- [ ] すべての本文について「実装が変わっても変わらないか？」を問うたか
