# 既存 doc を直すときの記述方針

`documentation_standards/` の傘の下の 1 トピック。**すでにある doc を直すとき**に固有の失敗を扱う。

隣接トピックの担当:

- 図・表・箇条書き・散文の選び分け → [`expression_notation.md`](./expression_notation.md)
- 何をどこに置くか（構造・配置）→ [`information_structuring/README.md`](./information_structuring/README.md)
- 誰にどの深さで書くか（読者段階）→ [`core_readers.md`](./core_readers.md)

新規に書くときの失敗（薄い・散らかる）と、直すときの失敗は形が違う。
**直すときは、書き手が「指摘を受けた状態」で書く**ので、指摘した人を second reader に置いてしまう。
その人に向けた文が本文に残ると、初見の読者には意味の無い記述になる。

## 議論の経緯や指摘への反論を本文に持ち込まない

原則: **本文は、その doc しか読んでいない初見の読者だけに向ける。**
議論セッションのやりとり・レビューでの指摘・前の版の誤りは、読者が持っていない前提なので、本文から見えてはいけない。

### なぜ起きるか

指摘を受けて直すとき、書き手の頭には「前はこう書いていた」「こう指摘された」が乗っている。
この状態で書くと、文が自然と**指摘への回答**の形になる。書き手にはまっとうな文に見える。
一方の読者は前の版も指摘も知らないので、**存在しない主張への反論**を読まされることになる。

しかも修正は**量を増やす方向に働く**。指摘された箇所ほど「今度は誤解されないように」と厚くなるので、
doc の中で**いちばん重要でない箇所がいちばん厚い**という逆転が起きる。

### 実際に落ちた現物

「引当済み在庫」ドメインで、3 つの形が同時に出た。

#### 形 1: 存在しない主張への反論

倉庫別の残在庫だけ古い方式を使っている理由を、指摘を受けて書き直したとき。

> 倉庫別の残在庫だけ随時更新方式なのは、**移し忘れではなく**意図して引当側に合わせている。

「移し忘れ」と思っていたのは、前の版でそう書いた書き手だけである。
読者は移し忘れを疑っていないので、否定された瞬間に「誰がそう言ったのか」を探すことになる。
反論の枠を外すと、事実だけが残る。

> 倉庫別の残在庫だけ随時更新方式を使うのは、**表示を引当の判定と一致させるため**。

#### 形 2: 修正の正しさを補強する肥大

同じ箇所は、直す前は 1 行だった。

> 倉庫別の残在庫だけ随時更新方式から借りているのは、都度集計方式に倉庫別の集計が無いため。

理由が誤りだと指摘されて書き直した結果、**15 行**になった。増えた分の内訳は 3 つで、
理由を 2 つに割ってそれぞれ 3 行で力説した部分、すぐ下の節と内容が重複する結論、
そして「では全体の残在庫はなぜ移せたのか」という**書き手の推論 3 行**である。

最後のものが最も悪い。**確認が取れていない理由を、修正の補強のために書いた**からで、
次にこの doc を読む人はそれを確定した仕様として引く。最終的に 4 行に戻した。

#### 形 3: 同じ弁解の増殖

「2 つの方式の差は意図したものではない」と指摘されたあと、同じ趣旨を 5 ファイルに撒いた。

> 対象の定義が随時更新方式と違うのではなく、いま追いつけていない
> 狙って外しているわけではない
> 目録を狭めているのではなく、追いつけていない状態
> 対象の定義が方式ごとに違うのではなく、追いつけていない
> ズレは移行の途中だから残っているだけで、狙った差ではない

1 つずつは間違っていない。だが読者は**同じ弁解を 5 回読む**ことになる。
しかも書き手は「指摘された点を全ファイルで直した」と満足できるので、この増殖は自覚しにくい。
1 箇所（overview）に集約し、残りは肯定形の事実に書き換えた。

### 戻した基準

**否定形は、読者が自分で抱く誤解にだけ当てる。** 書き手の前の版やレビューでの指摘には当てない。
判定は 1 つ、**その否定を、doc しか読んでいない人が自分で思いつくか**。

- 当てる —— 「2 つの方式は違う数字を出そうとしているのではない」。
  方式名が 2 つ並べば、初見は自然に「別物を数えているのか」と思う。先回りする価値がある。
- 当てない —— 「移し忘れではなく」。誰も移し忘れだとは思っていない。

**判定するのは記述の由来ではなく、読者への効き。**
指摘をきっかけに書いた文でも、読者の理解に効くなら残る —— `⚠️ 未確定` の注記や、
比較表を「設計として狙った差」と誤読させないためのキャプションはこれにあたる。
逆に、指摘が無ければ絶対に書かなかった補強・弁解・推論は落とす。

### 守る点

- **修正で増えた分は、増えた理由を疑う。** 指摘された箇所ほど厚くなるのが自然な力学なので、
  厚みが読者の必要から来ているのか、指摘への応答から来ているのかを分ける。
- **確認が取れていない理由を、修正の補強に使わない。** 推論を仕様として置くと、次の読者が事実として引く。
- **同じ趣旨の否定が 2 ファイル以上に現れたら過剰補正。** 1 箇所に集約し、残りは肯定形の事実にする。
- **表記だけを直して済ませない。** 「のではなく」を消しても、指摘に応えるために積んだ段落が残っていれば同じこと。

### 検知

単体で読み返しても気づけない（書き手には自然な文に見える）ので、**差分を見るのが要**。

- **`git diff` で、その修正が何行増やしたかを見る。**
  1 行の記述が 10 行になっていたら、増えた分の大半は読者向けでなく指摘向けである可能性が高い。
- **増えた文それぞれに「読者が自分で抱く疑問に答えているか、指摘に答えているか」を問う。** 後者なら落とす。
- **否定形を検索する**（「のではなく」「わけではない」「ではない」）。
  否定している主張を読者が自分で抱くかどうかで、残すか消すかを決める。
- **同じ趣旨の文が複数ファイルに無いかを検索する。** あれば 1 箇所へ集約する。
