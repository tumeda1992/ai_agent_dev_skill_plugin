# 退避エンティティ

あるデータを作り、元データを削除する事象を**データ退避**と呼ぶ。作られる側が退避エンティティである。history、archive、状態遷移による別テーブルへの移動がこれに当たる。

ライフサイクルを問わない判断は [core.md](./core.md) が持つ。この file は退避という状況を前提にしないと成立しない判断だけを扱う。

## `core.md` と既定が逆転する

| | 既定 | 判断の問い |
| --- | --- | --- |
| 通常のエンティティ（[core.md](./core.md)） | 持たない（opt-in） | このエンティティはこのフィールドなしで完結した意味を持つか。Yes なら追加しない |
| 退避エンティティ | **持つ（opt-out）** | この項目を引き継がないと決めた理由を書けるか。書けないなら引き継ぐ |

MUST: 退避エンティティを設計するとき、`core.md` のフィールド追加基準を適用しない。この file の既定が優先する。

### なぜ逆転するか

回復可能性が非対称であるため。

- 通常のエンティティで足さなかった項目は「まだ無い」だけであり、必要になれば後から足せる
- 退避エンティティで引き継がなかった項目は、元データの削除とともに**失われる**。後から足しても、過去に退避した分は戻らない

## 全項目を列挙して分類する

MUST: 元データの全項目を一度列挙し、引き継ぐ／落とすを分類する。未分類の欠落を失敗とする。落とすものには理由を残す。

これは [`common_standard/function_migration_policy.md`](../../common_standard/function_migration_policy.md) が移行時に全rangeを登録し未分類の削除を失敗とするのと同じ構造である。データ退避も、元データが持っていたものを取りこぼさずに新しい形へ移す作業だからである。

## やってしまいがちな失敗

### 退避先を「その操作に必要最低限のデータ」で設計する

→ 操作の観点では不要に見えても、元データの持ち主にとって意味のある項目が落ちる。**操作の必要性は、元データの持ち主が何を保存したかを決める根拠にならない。**

→ 正しい問い: 「この項目を引き継がない理由を、いま書けるか」

### 項目が落ちることに気づき、UIへ「〇〇は失われます」と警告を出して済ませる

→ **警告は喪失を正当化しない。** 警告が要ると感じた時点が、既定（保存）へ戻す合図である。ユーザーに告知しても、失われて困る事実は変わらない。

→ 正しい問い: 「なぜ警告が要ると感じたのか。それは喪失が許容できないと自分でも思っているからではないか」
