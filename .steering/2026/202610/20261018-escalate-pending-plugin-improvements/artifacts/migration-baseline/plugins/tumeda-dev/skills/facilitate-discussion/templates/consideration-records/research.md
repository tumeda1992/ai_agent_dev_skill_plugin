# 調査の記録

## 調べる問いと探索範囲

「何を知ればどの判断が進むか」を先に定める。対象fileを読むこと自体を問いにしない。問い・探索範囲・source・方法・必要な証拠を実施前に保存する。
sourceの所在を示し、検索だけなら検索語・対象範囲・除外範囲、実体を読んだなら対象箇所を残す。読むfile一枚ごとの日誌ではなく、同じ問いへのfindingをテーマ別にまとめる。

## テーマ別finding

### 見つかった事実

問いに関係する事実と根拠を結び、引用や観測と自分の解釈を区別する。見つけた項目を列挙して終わらず、何の条件を満たしたか、何はまだ分からないかを示す。
問いが粗いと肯定的findingも空虚になる。「機能があるか」だけでなく、必要な入口・適用範囲・境界まで問う。

### 範囲内で見つからなかったこと

不在の主張には探索範囲と方法を付ける。文字列不一致は同じ能力の不在を証明しない。別名・間接参照等が残るなら限界として示す。
何が見つからなかったかと、代わりに何が見つかったかを併記し、否定的結果によって候補を除外できるのか、調査方法を変える必要があるのかを示す。

### 取得できなかった・まだ調べていないこと

権限不足、接続失敗、未読はnegative findingではない。失敗した対象・方法・理由と、未確認のまま残る問いを残す。「不存在」へ言い換えない。

## 言える範囲と、調査を終える根拠

事実からの解釈、残る不足、次actionと案への影響を記す。終了は回数でなく、判断に必要な証拠が得られたか、取得可能範囲を尽くして外部条件へ返す必要があるかで判断する。
別の問いへ移る前に結果を保存する。関連が薄いsourceを無制限に増やさず、必要判断との接続が失われたら問いを見直す。

## 調査の記入形と例

開始時には次の入力だけを保存する。結果欄を先に埋めない。

```markdown
##### 調査: 再送時にも通知先の変更が反映されるか

###### 問い・探索範囲・方法

通知設定を再送時に読むか、初回値を保持するかで、設定変更後の扱いが変わる。送信入口、再送worker、保存schemaを読み、再送payloadと宛先解決の関係を追う。
```

結果後の例。ここでいうsource名は例示である。

```markdown
###### 再送payloadで保持されるもの

workerは通知IDだけを受け取り、そのIDから送信記録を読む。初回の宛先snapshotはschemaに存在する。これは「設定を必ず読み直す」根拠にはならない。

###### 今回の範囲で確認できなかったもの

worker本体と直接calleeには設定の再取得がない。一方、配送adapter内部は取得失敗で未読であり、最終宛先が常にsnapshotに固定されるとはまだ言えない。

###### 解釈・残る不足・次action

worker単体では初回宛先を使うが、最終配送先の変更余地はadapterに残る。次はadapterの読取を再試行し、取得不能ならその範囲を外部条件として返す。現時点で「再送は新設定を反映する」という案は採れない。
```

positive／negative／取得不能の三見出しを毎回固定する必要はない。存在した種類をテーマに合う見出しで示す。
