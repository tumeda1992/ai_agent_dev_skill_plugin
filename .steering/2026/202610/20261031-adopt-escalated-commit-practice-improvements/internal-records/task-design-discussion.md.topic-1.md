# 内部検討記録: 論点1 — 提案1（commit の境界を決める段階で plan-commits の基準を当てる導線）を取り込む理由

**discussion:** [task-design-discussion.md](../task-design-discussion.md)

**論点:** 論点1

## 開始context

利用先 repository から引き渡された提案1 は、「task-design が design の段階で commit の境界を決める時に、plan-commits の判断基準を当てる導線を足す」である。提案の根拠は提案者（assistant）が書いたもので、利用者と合意していない。
この論点では、design.md の TL;DR に書く取り込む理由（WHY）を決める。理由が変わると、導線を置く場所と書く内容が変わる。

範囲外: 導線を置く file と書く文（次の論点）、提案2。

<a id="iteration-0"></a>

## イテレーション0: 取り込む理由

<a id="iteration-0-record-1"></a>

### 調査: commit の境界を決める段階と、plan-commits の適用条件

#### 入力

- 問い: plugin の中で、commit の境界を決めるのはどの段階か。そこから plan-commits の基準へ辿れるか。plan-commits はその段階で使えるか。
- 方法: 2026-10-31 に、plugin 8.2.0（`c1122f5`）の `plugins/`、`docs/`、`scripts/verification/` を `plan-commits`、`意味単位`、`revert`、`commit` で検索し、該当箇所と plan-commits の `SKILL.md` を読んだ。

#### 結果

- `plan-commits` を参照しているのは `skills/README.md` の skill 一覧だけ。task-design、`tasklist-design.md`、tasklist-executor、steering は参照していない。
- 境界を決める段階は二つある。
    - tasklist の段階: `tasklist-design.md` が commit section を「phase単位かつ意味単位で分け」と定め、`templates/tasklist.md` は「同一phase内でも意味的に異なる変更を分割する（例: DB migration、domain model、GraphQL、frontendは別commit）」と書く。何を比べて分けるかは書いていない。
    - design の段階: 要件に revert の単位がある時など、境界が設計判断になる。`task-design/SKILL.md` と templates には、その節も手順も無い。利用先の作業では design.md に独自の「変更の単位と順序」節を作った。
- plan-commits の適用条件: 「依頼されたrepositoryと比較元にある実差分から」計画し、「Git情報を読まず、designやtasklistの見出しだけから計画を作らない」と定める。design の段階には実差分が無いため、skill をそのまま起動する形にはならない。使えるのは判断基準（意味で分ける、取り消した時に消したい効果と残したい効果を比べる、編集の手間や本数で境界を変えない）である。

#### 限界

- 他の利用先 repository で同じ取り違えが起きたかは分からない。根拠は利用先の一件である。

<a id="iteration-0-record-2"></a>

### 判断: 取り込む理由をどう書くか

推奨: 「境界を決める段階で何を比べるかの基準が手元に無く、必要条件や手間を境界の基準と取り違える。plan-commits の基準へ辿れるようにして取り違えを減らす」を理由にする。決め手は、利用者の問い「コミット計画のスキル考えても同じ結論に至る？」が、その場で基準へ辿る導線として働き、結論を変えたこと。

#### 判断対象・必須条件・根拠

- 判断対象: design.md の TL;DR に書く、提案1 を取り込む理由。
- 必須条件:
    - 起きた事象と、導線で防げる範囲を一致させる。導線で当てはめの誤りそのものは保証できない。
    - 導線の置き場所と中身（次の論点）を先取りしない。
- 根拠: [record-1](#iteration-0-record-1)、利用先での経緯（提案の具体例）、利用者の保留指示「1:b」（「c) skill は直さない」を選ばなかった）。

#### 案の評価

- 基準へ辿れないことを理由にする（推奨）
    - 利用先では、問い一つで基準へ辿り着いた後、四つの commit へ分け直せた。基準の不在ではなく、辿る道の不在が効いていた。
    - 主な原因は当てはめの誤りであり、導線は補助にとどまることを理由の中で明示する。過大な期待（導線を足せば境界の誤りが無くなる）を持たせないため。
- 「意味単位」の定義を plugin に書くことを理由にする
    - plan-commits が既に基準を持つ。定義を別の場所へ書くと二重の正本になる。
- 取り込まない（理由を立てない）
    - 利用者は保留の時点で「skill は直さない」を選ばなかった。利用先の一件で、問いが結論を変えたことが確かめられている。

#### 判断結果が規定するもの

- design.md の TL;DR と、提案1 に関する要件の書き方。
- 次の論点で、導線の置き場所を「境界を決める段階」から選ぶこと。

<a id="iteration-0-record-3"></a>

### 診断: 不要な問いを出した理由

#### 入力

- 期待との差: 利用者は提案0 に「そりゃOKだけど、なんでこんなことが聞かれてるかわからない」と答えた（2026-10-31）。問いが不要だったと受け取れる。
- 確認元: 利用先の作業の記録（保留メモの「保留の指示」、実装後の振り返りの論点1）、task-design の 3-1。

#### 結果

- 提案1 の理由は、利用先の作業で assistant が「原因と再発防止の候補」を示したうえで「a) 今すぐ plugin へ引き渡す b) 保留して元作業の後で引き渡す c) skill は直さない」と問い、利用者が「1:b」と答えて合意されていた。
- 提案2 も同じで、利用先の実装後の振り返りの論点1 で、assistant が「local の commit は push の前なら直せるため、利用者の確認で守りたいもの（確かめていない変更を公開しないこと）は push の前の確認で守れる」を推奨の理由として示し、利用者が「1:b」と答えた。
- task-design 3-1 は「上位について相手の言葉を引用できないなら TBD」とする。引用できる言葉（「1:b」と、その問いに添えた理由）はあった。assistant は「理由の文を書いたのが assistant である」ことを、未合意の印と取り違えた。

#### 原因の所在

当てはめの誤りであり、skill の不足ではない。3-1 の二段の判定を当てていれば、引用できる合意があることに気付けた。引渡しの記録（保留メモ）にも、問いと利用者の答えが残っていた。

#### 次への影響

提案2 の理由も同じく合意済みであり、問いにせず、既決事項からの導出として design.md へ書く。
