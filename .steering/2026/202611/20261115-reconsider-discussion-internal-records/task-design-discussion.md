# 議論記録

## 論点1: discussionの検討記録が、それ単体で満たす条件

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0（論点1）: 回をまたいだ検討の変遷を、検討記録にどこまで書くか

#### 提案0（論点1）

利用者がissue #10に書いた方向を、そのまま提案とする。

> CodexとClaudeで共通するのはちゃんとした検討記録を書いてもらうこと。それはサマリじゃなくて、ちゃんと検討を重ねた記録がdiscussionに載り、その果てに今の提案に活きていることが残せること。
>
> だから、今みたいな検討記録にinternalなログのリンクだけ載せるのではなく、
> internalな記録ログはgit管理対象外にして、Codex特有の副産物のように扱って、検討記録は検討記録単体でイテレーション間の時系列をちゃんとサマリすぎないで残す扱いにすればいいかなって思った

#### 検討記録（論点1・イテレーション0）

assistantが細部を調べて独自の提案本文を作ろうとした回は、応答が安全判定で止まり、保存できなかった。
そのため、この回の提案はissueの原文だけとし、assistantの独自の案は含めない。

#### 提案0へのフィードバック（論点1）

**結果:** 利用者が決定として確定

> ディティール探ってもらって、ディティールに沿った提案してもらおうと思ったけど、やることは決まってんだから、そのやり方で議論しろっつってんの

### 決定（論点1）

issue #10の方向で進める。discussionの検討記録は、それ単体で回をまたいだ検討の時系列を、要約しすぎずに残す。内部記録へのlinkだけで済ませない。内部記録はgit管理の対象外とし、Codexで出る副産物として扱う。

## 論点2: issue #10の「自動ok」が指す仕組み

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0（論点2）: 「自動ok」がどの仕組みを指すかを確かめる

#### 認識合わせ0（論点2）

`facilitate-discussion`の中で、利用者の明示の合意を待たずに先へ進む仕組みは、`derived-change.md`だけと読んでいる。
既に決まったことからassistantが一つに導ける変更は、変更内容を報告し、次の利用者の応答を受けてから反映する。合意の確認は取らない。

「自動ok」はこの仕組みを指しているか。

- a) 指している
- b) 別の仕組みを指している（どれかを教えてほしい）

#### 検討記録（論点2・イテレーション0）

`derived-change.md`は`.steering/2026/202610/20261018-escalate-pending-plugin-improvements/`で、利用者への質問を減らすために導入された。
issueの文面だけでは、この仕組みを指すのか別の仕組みを指すのかを確定できない。

#### 認識合わせ0への回答（論点2）

**結果:** おおむね一致。今回の作業の対象から外す指示を受けた

> 多分そう

続けて、利用者から次の指示を受けた。

> あと、自動適用については今回ついで程度だから、内部記録の方を中心にやりたいの。自動適用はエラーばっか出るなら無視でいい

この論点を扱おうとした応答が、安全判定で止まった。利用者の指示の条件に当たるため、今回は扱わない。

### 決定（論点2）

「自動ok」は`derived-change.md`の仕組みを指すものとして扱う（利用者の回答は「多分そう」）。
今回の作業では扱わず、内部記録の見直しを中心に進める。issue #10で付随的な扱いだったためである。
利用者が自動適用の見直しを改めて依頼した時に、別の作業として扱う。

## 論点3: 内部記録を前提にしている手順を、discussionだけで回る形へどう畳むか

**ステータス:** 応答待ち

**種別:** TBDヒアリング

### イテレーション0（論点3）: 内部記録を正本から外した後の手順の形

#### 提案0（論点3）

論点1で、内部記録はgit管理の対象外の副産物になった。そこで、内部記録を読む・書く・照合する手順を全てやめ、discussionの検討記録だけで回る形にする。

| 今の手順 | 変えた後 |
| --- | --- |
| 調べる前に、問いと方法を内部記録へ保存してから調べる（`iteration.md`「内部検討を記録する」） | やめる。調べた結果・分かったこと・採らなかったことは、作成中の回の検討記録へ書く |
| 回を作る時に、内部記録の骨子も用意する（`iteration.md`「二層の骨子を順に保存する」） | discussionの骨子だけを保存する |
| 中断からの復帰を、内部記録の保存状態で判定する（`iteration.md`「保存境界から中断処理へ戻る」） | discussionの保存状態、tool結果、chatだけで判定する |
| 記録漏れの回復で、内部記録とdiscussionへ書き分ける（`record-recovery.md`） | discussionだけへ再構成する |
| 読取helperの起点照合で、内部記録も`--log`で照合する（`read-discussion.md`、`scripts/inspect-discussion.mjs`） | 手順から外し、scriptの`--log`引数とそのtestも消す |
| task-designのhandoffで、内部記録を読み、digestの対象にする（`task-design-work-handoff-contracts.md`、`task-design/SKILL.md`） | 内部記録を読む契約を外す |
| 内部記録の保存形（`templates/internal_record.md`）と、discussionから内部記録へのlink（`SKILL.md`「二層の保存先と読取範囲を解決する」、template の link行） | 保存形のfileを消し、linkの規則とlink行を外す |

作業用のメモを残すこと自体は禁じない。残す場合は、discussion directoryの`internal-records/`へ置き、git管理の対象にせず、discussionからlinkせず、検討記録の代わりにしない。skillはメモを作ることを求めない。

この提案に含めないもの:

- commit済みの内部記録122 fileを残すか消すか。手順の形とは独立に決められるため、次の論点で扱う。
- 目的別の記入形（TBD4）、利用先repositoryでの担保（TBD5）、肥大化を防ぐ書き方（TBD6）。

#### 検討記録（論点3・イテレーション0）

内部記録は、論点1で「git管理の対象外、Codexで出る副産物」になった。
副産物を正本として読む・照合する手順が残ると、gitに無いfileを前提に復帰や照合をすることになり、別のsessionやmachineでは成り立たない。
そのため、正本として扱う手順は一部だけ残すのではなく、全てやめる形を推す。

`--log`を手順から外すだけでscriptに残す案もある。使われない引数とtestが残ると、後から読む人がまだ使う機能だと誤解するため、消す方を推す。
