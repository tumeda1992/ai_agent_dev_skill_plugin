# discussionへ検討経緯を残し、狭い再承認の用途をβで支える

## 元の依頼内容

steeringスキルで [https://github.com/tumeda1992/ai_agent_dev_skill_plugin/issues/10](https://github.com/tumeda1992/ai_agent_dev_skill_plugin/issues/10) を対応したい

## TL;DR

提案に至る比較・訂正が内部logへ分散すると、discussionを読んでも何が次案を変えたかを追えなくなる。
discussionを検討経緯・提案・応答・決定の正本とし、内部logはGit管理外の任意の作業控えにする。
本文、template、読取・再開・回復、consumer、ignore、validatorを合わせて変更し、内部logがない環境でも同じdiscussionから議論を続けられる。

既合意の内容への再承認が重なる稀な用途は、通常は読まない同skill内のβ補助へ分ける。
assistantが今回任せる範囲を具体化し、既存の明示委託へつなぐ。独立した導出の常設経路は外す。

## 完成後の姿

### skillの役割と方針

#### facilitate-discussion

明示された議論について、検討を積み重ねた経緯と、提示した案・利用者の応答・現在の決定をdiscussionへ残す。
前の応答から何を確認・比較し、どの見方を訂正して今回の提案へ至ったかを、本文だけで理解し判断できる状態を作る。

##### 提案の理由と、その理由へ至った経緯を残す

最終案に都合のよい背景だけへ整理せず、成立しなかった案とその理由、次の確認・提案を変えた事実と訂正を、起きた順序と理由が分かる本文にする。
確認事実、そこからの判断、未確認の範囲を区別し、実施していない検討や合意を補わない。
過去の提案と応答はその場所に保ち、今回増えた検討と変化を記録する。

例えば再送先の議論では、単に最新設定へ変更すると書くだけでなく、初回の送信内容との対応を調べ、何を固定し何を更新するかを分けた経緯を残す。
表記訂正なら、その箇所と意味が変わらない根拠で足りる。架空の比較を増やして同じ分量へ揃えない。
長い比較には見出しや表を使い、短い訂正は一段落で示せる。固定の欄や文字数を埋めることを完成条件にしない。
長い検討記録では、先頭に今回の案を採る直近の理由を短く置き、その後に見出し付きの時系列で比較・訂正の詳細を残す。
先頭と後半を全文二重化せず、受容された具体性と、次の回へ必要な未確定・未検証の情報を保つ。

##### 内部logを作ること自体を工程にしない

内部logは、長い調査の作業控え等が必要な場合だけ作るローカルの記録であり、Git管理対象や必須成果物にしない。
ClaudeとCodexへ別々の必須手順を作らず、共通してdiscussionの本文が完成することを要求する。
内部logが存在すること、読めること、linkがあることを、discussionの完成や再開の条件にしない。

作業控えだけへ経緯を残すと、別環境にはその説明が届かない。
そのため、提案や決定の理解に必要な証拠・比較結果・訂正は、提示前にdiscussionへ反映する。
新しいdiscussionにGit管理外logへの必須linkを置かず、linkで本文の説明を代替しない。

### 作業の流れと担当

担当とsingle writerは従来どおり同じdiscussion担当である。
consumerは議論の目的・制約と適用先を持ち、facilitate-discussionは採番、親子関係、提示、応答、決定と経緯の保存を持つ。

1. discussionの入口・現在状態・対象範囲を解決し、本文の版を固定して読む。
2. 同じ回の検討記録へ必要な入力を残し、確認・比較・検証と結果・訂正を積み重ねる。
3. 内部logは必要な場合だけ作る。使った場合も、提示と引継ぎに必要な説明をdiscussionへ反映する。
4. 提案または認識合わせ、経緯を説明する検討記録、対応する応答欄を本文へ保存して提示する。
5. 実際の応答を対応する提示へ保存し、具体案への明示合意があれば現在の決定を確定する。
6. 同じdiscussionから再開し、内部logを利用しない場合も現在の案と検討経緯を読める。

#### 必要な証拠の不足と、任意の控えの不存在を分ける

内部logは、存在して実際の根拠として使う場合だけ、その全文と必要な後続訂正を読む。
この場合は既存のsnapshotへ対象を含め、原文の版を照合する。
旧discussionにlogへのlinkがあっても、本文に説明が揃い、logを根拠として使わないなら、その不存在だけでは停止しない。

一方、既に比較根拠へ選んだlogの取得失敗、必要な証拠の不足、discussion自体の取得失敗は確認済みにしない。
何が不足し、その不足が判断へどう影響するかを明示する。
分割・回復でも原文snapshot、候補実体、tool結果と必要な控えから実施済み境界を確認し、原文の版や候補を特定できない状態で盲目的に再実行しない。

### 文書以外に作るfileの中身

配置・役割は維持し、既存の各担当箇所の内容を整合させる。新しいskill、wrapper、別の状態管理fileは作らない。

表のpathは`plugins/tumeda-dev/skills/`配下である。
skill本体、内部指示、templateはいずれもMarkdownで、各fileが従来持つ役割・見出しと対応関係を維持する。

#### Git管理と配布version

`.steering/.gitignore`と`plugins/tumeda-dev/skills/steering/.gitignore.sample`へ`**/internal-records/`を加える。
steering以外の利用先では、そのdiscussion directoryの内部logを利用先のignoreで管理外にする。
既存のtrackedな内部logや過去のdiscussionは一括削除しない。
既存記録で必要な説明が控えだけに見つかった場合は、その時点で確認した内容を本文へ追記し、昔から本文にあった形へ書き換えない。

配布versionは`9.0.1`である。
既存skill指示の修正であり、新しい呼出し方やparameterを増やさないためPATCHとする。
両plugin manifest、marketplaceの二つのversion宣言、validatorの`expectedRelease`を揃える。
旧成果物の見出し・採番・labelは引き続き読めるため、旧成果物を読めなくする名称変更はない。

### 自動okの狭い用途をβとして残す

利用者が示した用途は、長大な仕組みの設計で、既に合意して自明な内容の再承認を避けることである。
実需要は利用者が報告した一案件であり、比較元の通常の自己reviewは利用実績へ含めない。

#### 通常の本体とβ補助

通常の権限分類を、利用者の未決事項、明示委託、意味を変えない機械適用の三経路へ揃える。
AIが合意から一意に導出したと判断したことだけで進める独立経路は外す。
明示委託でも個別の再承認を省け、根拠・変更前後・報告・訂正を残せるため、稀な用途に独立経路を常設する利益は小さい。

`facilitate-discussion/SKILL.md`の「変更の権限から経路を選ぶ」と「共通本体へ接続する」に、既合意の再承認が重なって利用者が困っている時だけ読む短い入口を置く。
通常の提示準備ではβ本文を読まない。苛立ち一般を承認や委託に替えない。

新規の`facilitate-discussion/agreement-based-delegation-beta.md`は、次の内容を持つ。

- 読む場面と、通常の未決判断との違い。
- 合意の原文・出典、具体化する対象と固定条件を対応させ、任せる範囲を組み立てる方法。
- 同じ範囲の既存委託を取り直さず、残る利用者判断を分ける方法。
- 具体化した範囲を既存の明示委託へ戻す方法。
- 合意済みの複数skillの役割・入出力から未作成の指示文へ具体化する例と、新しい契約を通常の判断へ戻す境界例。
- 次の実例から同じ補助指示を育てる担当と経路。

役割・入出力・境界が合意済みでも、各SKILL.mdの説明構成、入力確認・受渡しの指示文、条件を示す例をまだ作っていない時は、その具体化に選択が残る。
assistantが範囲の具体案を示し、任された後は同じ範囲の具体化ごとの採否を取り直さない。
既に同じ範囲を任されていれば、その委託の出典を確認して変更報告へ進む。
新しいskillや必須入力、利用者が判断する場所の変更は、合意済みの説明へ混ぜず通常の提案へ戻す。
具体的な文章と掲載先まで承認済みのlink追記等は、既存の機械適用で足りる。

#### 共用の記録・報告・反映

`derived-change.md`から独立した導出の分類と根拠を外し、明示委託と機械適用の既存条件を残す。
委託原文と範囲、候補比較、個別の変更内容・現在の変更、session報告、次の実応答と反映・訂正の対応は共用処理として維持する。
報告に別okを要求せず、統合確認用の論点・fileを作らない。
βへ共用処理の状態・完了条件を複写せず、具体化した範囲を既存の委託処理へ渡す。

`templates/discussion_entry.md`の変更例は、合意からの導出を根拠にする例から、実際の委託と範囲を根拠とする例へ揃える。
過去の導出記録は引き続き読めるまま保持し、readerの実装や旧形式は変えない。
`scripts/verification/validate-plugin.mjs`の該当検査を、通常の三経路、β入口、明示委託と機械適用の保持へ合わせる。

#### 次の実例から同じfileへ還元する

実際に使ったdiscussion担当が、適用根拠、組み立てた範囲、実応答、有効・過剰・不足だった点を同じ論点へ残す。
再利用できる改善が見つかった時は、既存の`escalate-plugin-skill-fix`から保守担当へ具体例と修正候補を渡す。
利用先固有情報、明示保留、既存の転送先は同skillの規則で扱う。
保守担当は、既存の`skill-creator`と`skill-update-review`で同じβfileの発見条件・範囲の作り方・境界例へ還元する。
新しいmode・独立skill・専用台帳・毎回の更新義務や承認儀式、利用先cacheの自動書換えは加えない。

実需要が一案件のためβとして置き、次の実例で入口の広さ・不足・既存委託で十分な範囲が分かった時に修正・昇格・撤去を見直す。
βの位置付けはfile名と冒頭に示し、配布versionは既存の`MAJOR.MINOR.PATCH`規約に従う。

#### β本文の実物と配置

[設計用draft](drafts/agreement-based-delegation-beta.md)は、完成後のβ本文を示す。
最終配置は`plugins/tumeda-dev/skills/facilitate-discussion/agreement-based-delegation-beta.md`とし、適用時は冒頭の設計用注記を除く。
通常は本文を読まない補助指示であり、単独skillや新しいmodeとして公開しない。
現在は設計用draftに留め、最終skill pathへは未適用である。

### 検討記録の具体性と、両側で確認した範囲

具体例では、今回案を変えた比較、成立しなかった前提、訂正、未確定・未検証を本文へ残す。
例えば、原因を掘るだけでは目標の範囲が選べなかった比較や、痛みのない要望を扱えない反例を、何を変えた理由かとつなげて示す。
細かな固有情報、読取commandの順序、同じ旧案や応答の全文は、その理由に使わない部分を繰り返さない。
先頭の直近理由は現在の判断を短く渡し、後の見出し付き時系列はその判断の根拠となった具体的な経緯を渡す。
実応答を受けた次の回では、何が受け入れられ、何が未確定かを引き継ぐ。

指定PRの同じ固定版で、Claude側の切替前の論点41・0→1回はdiscussion本文、Codex側の切替後の同6→7回は本文と対応内部fileを照合した。
前応答、比較・訂正、次案への影響、限界、次の回へ渡る状態を、見出し付き両例へ残せることを机上で確認した。
対応内部fileはCodexへの切替後から始まるため、Claude側の経緯はdiscussion本文を根拠にする。別の内部fileがあったとは補わない。
この区分は元Issueの担当区分と内部fileの開始記載に基づくものであり、今回のmodel実行traceで独立に判定したものではない。

両modelへこの指示を実行させる新しい検証は行っていない。
原資料の照合と書き直し案の机上確認を、両modelの継続的な動作や性能の保証へ広げない。

## 要件（Requirements）

### MUST（必達）

- 指定された実記録の比較から、本文へ検討の積み重ねを残す共通の要求を判断する。
- 内部logをGit管理外の任意の控えにし、その有無だけで提示・読取・再開・回復を止めない。
- 取得不能な必要証拠と、任意のlogがないだけの場合を区別する。
- 既存のtrackedな内部log、過去の提案・応答、採番・親子関係・single writerと、本文の版照合を維持する。
- 新しい必須linkを外し、関連するconsumerと検証を同じ変更で整合させる。
- 常設の独立導出を外し、通常は本文を読まない同skill内のβ補助から、assistantが範囲を具体化して既存の明示委託へつなぐ。
- 既存委託の取り直し、苛立ちによる承認、報告への追加okを作らず、機械適用と未決の利用者判断を区別する。

### 非目標

- 利用先の過去記録そのものの一括改変。このpluginの以後の記録と読取を変更し、既存の履歴は保持する。
- 通常の自己点検工程の要否、モデル別能力、無軌道な作業の防止策、全般的な権限分類や導出変更の反映時点の一括変更。今回の自動okの必要性判断へ広げない。
- 記録の分量やツール別の能力を、全model・全作業に対して保証すること。

### 受け入れ基準

- 内部logなしのfixtureで、本文・現在の問い・snapshotを取得し、compareがexit 0になる。
- 根拠として既存logを使う場合は版照合でき、そのlogが消失した場合はexit 1として取得不能を成功扱いしない。
- 任意のlogを使わない場合はdiscussionだけで読取が成立する。
- plugin validator、既存の引継ぎ検証、読取helperの自己testが成功する。
- 新しい内部logがignoreされ、既存のtrackedな内部logの削除を含まない。
- 通常の三経路とβの狭い入口が対応し、合意済みの具体化、既委託、未決判断、機械適用、苛立ちだけの場合を区別できる。
- β本文に共用の反映状態を複写せず、既存の委託・機械適用と過去の導出記録の読取を維持する。
- source適用後に文書review、編集後の切り出しreview、該当validatorと関連する検証を終え、未適用・未検証を残したままphase完了にしない。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| ignoreだけを追加し、本文へ経緯が届かない | 正本と記録先、必須link、読取・再開を合わせて変更する |
| logが任意であることを、証拠の取得失敗を無視する意味に取る | 明示根拠logの消失を失敗にするcaseを検証する |
| 本文の記録を増やすため架空の比較や冗長な全文反復を作る | 短い訂正の境界例と、過去の回を保持した増分記録を指示する |
| 記録の変更へ未合意の権限変更を混ぜる | 記録変更は既存権限を維持する。β変更は合意した独立導出の削除だけへ限定し、明示委託・機械適用・報告後の実応答と訂正を保持する |
| βで苛立ちを承認に替える、または既存委託を問い直す | 合意と委託の原文・範囲を対応させ、未決判断と機械適用を境界caseで照合する |

## テスト方針

Node標準testでlogなし・既存log・根拠logの消失を検証し、既存のreader・handoffの検証を合わせて通す。
新しいmodelによる記録の生成確認はfixtureへの限定したsmokeとし、model一般の性能や全経路の保証には広げない。
検査の実測結果、文書review、切り出しreview、意味保存の照合は[検証記録](validation.md)に残す。
βの設計用draftは文書・構造reviewと境界caseの机上照合を終えた。sourceの反映とその後の検証は未実施であり、過去の検証実績へ含めない。

## （付録）前提とする既存仕様

- `facilitate-discussion/SKILL.md`は、議論の保存とdecision単位の引渡しを担当する。
- 読取helperの`--log`はもともと任意であり、helperの実装codeは今回変更しない。
- 既存のreaderはcanonical h2とlegacy h3、単一・分割形式、現在の決定と未完の回を読める。
- 旧成果物の名称変更を伴わず、既存の読取形式を維持する。
