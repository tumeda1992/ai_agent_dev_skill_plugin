# 議論記録

## 論点1: 範囲との照合の規範を、どこに、どの適用範囲で書くか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0（論点1）: 規範の置き場所・適用範囲・文言

#### 提案0（論点1）

規範を命名の標準 `plugins/tumeda-dev/docs/development_standards/naming/core.md` に置き、名前の付いたもの全般（file、directory、module、class、method、文書の見出し）へ当てる。naming の群の範囲を「名前を付ける場面」から「名前の付いたものへ中身を足す場面」まで広げるため、群の入口の説明二つも改める。三つの file の変更は、範囲を広げる一つの判断から出るため、まとめて採否を決める。

##### `naming/core.md` に section を足す

末尾の「命名後、名前と実態の対応をレビューする」の後に、新しい h2 を足す。既存の section は変えない。

```diff
 ## 命名後、名前と実態の対応をレビューする
 
 付けた名前と実態の対応を上の観点で見直し、外していたら**改名して再レビュー**する。命名は工程の最後でも本質として詰める（軽視して流さない）。
 
 レビューの書き方（記述形式、評価水準の合わせ方、レビュー結果の扱い）は [review.md](./review.md) が持つ。
+
+## 中身を足す前に、名前が約束する範囲に入るかを確かめる
+
+名前と実態の対応は、名前の付いたもの（file、directory、module、class、method、文書の見出し）へ後から中身を足した時にも崩れる。名前は変わらず実態だけが広がるため、命名後のレビューの場面が来ない。
+
+足す前に、そのものの範囲を確かめ、足す中身と照合する。範囲は次の三つが約束している。
+
+- 名前。置かれた場所の形で読む（[名前を単独で評価しない](#名前を単独で評価しない)）
+- 入口の説明。上位の索引の一行、file や class の冒頭の説明
+- 既に入っている中身。既存の見出し、method、処理
+
+入らないなら、次のどれかを選ぶ。
+
+- 範囲に入る別の既存のものへ足す
+- 範囲を広げると決め、名前と入口の説明を改める。広げた名前が[中身が大まかにわかる具体性](#中身が大まかにわかる具体性を備える)を保てる時に限る。どちらの中身にも正確には当たらない上位語にしかならないなら、広げない

+
+判断の問い: **「足そうとしている中身は、この名前・入口の説明・既に入っている中身が約束する範囲に入るか」**
+
+やってしまいがちな失敗: 読まれる頻度や呼ばれる頻度で、足す先を選ぶ。
+
+- 例えば、基盤の役割分担の原則を、最も読まれるという理由で、application の層の構造を扱う文書へ足そうとした。その文書の名前・入口の説明・見出しはどれも application の code の構造を指しており、基盤の役割分担は入らなかった。
+- 足していれば、文書の名前が中身を表さなくなる。基盤の原則を探す人も、その名前からは辿り着けない。
+- 届けたい人に届くかは、足す先の選び方ではなく、入口からの導線で補う。
+
+この照合が働かないのは、`utils` のように何でも入る名前の入れ物である。原因は名前の具体性の不足であり、[中身が大まかにわかる具体性を備える](#中身が大まかにわかる具体性を備える)で直す。
```

- skill（doc-enricher、task-design、steering）からこの section を引く入口。別の論点で決める。
- `naming/README.md` の「各fileの守備範囲」の表。`core.md` の行（名前を付ける対象が何であっても成立する原則）は、足した後も正しい。

#### 検討記録（論点1・イテレーション0）

**規範は file に限らず成り立つ。** 起点の失敗（読まれる頻度で、範囲の外の文書へ足そうとした）を、性質の違う case に当てた。

- class: 注文の永続化の class へ、いつも import されるという理由で email の送信を足す。範囲の外であり、失敗の形が同じ。
- directory: 外部 service への接続の directory へ、日付の整形の helper を足す。範囲の外。
- 標準の file: ログの保存期間の標準へ出力形式の規則を足す。範囲の外。名前を「ログ」全般へ広げると具体性が落ちるため、広げずに新しい file にする。
- 上位の索引への一行の追加: 索引の範囲に入り、規範は過剰に発火しない。

照合が働かないのは、`utils` のような何でも入る名前だけだった。これは名前の具体性の不足であり、`core.md` の既存の section が扱う。

**置き場所は `naming/core.md` を推す。** 名前と実態の対応を見直す既存の section（「命名後、名前と実態の対応をレビューする」）は、名前を付けた時だけを trigger にしている。この規範は、同じ対応を「中身を足す時」に見直すものである。対象を問わない原則を置く `core.md` に置けば、file 以外の case も落とさず、正本も一つに保てる。この規範を `core.md` 自身に当てると、名前（命名の基本）と既存の見出し（名前と実態の対応）の範囲には入る。ただし群の入口の説明は「名前を付けるあらゆる場面」で、中身を足す場面を含んでいなかった。そこで、規範の三つ目の選択（範囲を広げ、入口の説明を改める）を自分自身に当て、入口の説明二つを改める。

採らない置き場所:

- 文書の標準（`documentation_standards/`）に新しい標準を置く: 範囲が文書の file に狭まり、class・directory の case を落とす。名前と実態の対応を二箇所で持つことになる。
- 情報構造化の標準の「6. 配置」を広げる: domain の知識の構造化に限った基準であり、広げるとその標準の範囲を越える。この規範を自分自身に当てると通らない。
- docs に置かず、skill の手順に問いだけを書く: skill は手順と ownership、docs は種別横断の規範という境界から外れ、同じ問いを複数の skill へ写すことになる。

引き渡しの時の根拠（文書の標準に近い規則が無い）は、調べた範囲が狭かった。命名の標準に、trigger だけが違う近い規則があった。

引き受ける代償: doc-enricher は `development_standards/` を全て読む契約を持たないため、skill からの入口を別の論点で用意する必要がある。
