# 議論記録

## 論点1: 6「確認の途中で確認の対象を変えたら、最初からやり直す」を取り込むか、どこに置くか

**ステータス:** 反映済み

**種別:** TBDヒアリング

### イテレーション0（論点1）: 取り込むかと置き場を、既存の規則と照らして決める

#### 提案0（論点1）

取り込む。置き場は `plugins/tumeda-dev/skills/tasklist-executor/SKILL.md` の「最重要原則」にある「**DoD の各条件は「試みた」ではなく「実際に通過した」ことを確認してから `[x]` にする**」の下へ、既存の三つ（テスト、visual-inspector、同一性の照合）と並ぶ sub-bullet として一つ足す。

足す規則の中身は次の二つ。文面は次の論点で決める。

- 確認の途中で、確認の対象（code、依存の宣言、設定）を変えたら、その確認を最初の手順からやり直す。確認を通すために直した場合も同じである。変更が確認の対象に載ってから（起動・build・deploy をし直してから）やり直し、変える前に通った手順の結果を、変えた後の対象の結果として使わない。
- 確認の手順の一部を他の担当に委ねている時は、変えたことと、最初からやり直すことをその担当へ伝える。

あわせて `scripts/verification/validate-plugin.mjs` に、足した文の `requireText` を足す。新しい docs の標準 file は作らない。

#### 検討記録（論点1・イテレーション0）

##### 起点の失敗で、何が欠けていたか

元の依頼内容の 6 の具体例では、tasklist の各段に共通の確認（1 起動 → 2 応答 → 3〜6 共用の DB へ書き込む確認 → 7 全 test）があった。executor が手順 1 の後に依存の宣言を変え（手順 7 の test を通すため）、server を起動し直さないまま手順 3〜6 が流れた。手順 3〜6 は、段の最後の状態ではなく、変える前の状態に対して流れたことになる。手順 7 は別の process で流れたため通り、誰も気づかなかった。

欠けていたのは「確認の結果は、確認した時点の対象についてだけ言える」という前提である。変えた後の対象について通ったと言うには、変えた後の対象で確認し直すしかない。

##### 既存の規則に同じ問いがあるか

plugin の skill・docs を「やり直」「再実行」「確かめ直」等で探した。

- `tasklist-executor/SKILL.md` は、DoD を「試みた」ではなく「実際に通過した」ことを確かめてから `[x]` にすると定め、テスト、visual-inspector、同一性の照合の三つについて「通過した」の意味を具体化している。visual-inspector で異常が出た時は「修正して再確認する」とあるが、直した後に確認のどこからやり直すかは定めていない。
- `task-design/templates/tasklist.md` と `tasklist-design.md` の品質 check は「errorがあれば修正して再実行する」。直した後に、それより前に通った check もやり直すかは定めていない。
- `docs/development_standards/infrastructure/change_verification.md` は、基盤を変えた後に影響下の動きをすべて実物で確かめると定める。失敗事例に「role を付けた後、apply は成功し画面も開いたが、role を付ける前に build された deploy が動いていたため、deploy し直すまでログが出なかった」がある。変更が実行中のものへ載っていなかった、という起点と同じ形だが、規則としては「変えた後に確認をやり直す」を持たない。

どこにも、確認の途中で対象を変えた時の扱いは無かった。

##### 一般則として成り立つか（起点以外の case）

起点以外の case に当て、意図した結果になるかを確かめた。

| case | 規則を当てた結果 |
| --- | --- |
| 品質 check で lint が通り、test が落ちたので code を直した | lint から通し直す。直した code は lint を通っていない |
| 基盤の確認の途中で、ログを書く role を足した（`change_verification.md` の失敗事例） | deploy し直してから、影響下の動きを最初から確かめ直す。事例で起きた見落としを防ぐ |
| visual-inspector で異常が出て、表示の code を直した | 直した code を載せてから、その確認の項目を最初から撮り直す。既存の「修正して再確認する」と同じ向きで、どこからやり直すかが決まる |

どれも、変える前に通った結果を変えた後の結果として使わない、という一つの軸で答えが出る。「最初の手順から」とするのは、どの手順が変更の影響を受けるかを確認の途中で見積もると、その見積もり自体が誤る余地があるためである。起点の失敗も、手順 7 だけをやり直せば足りると見たことから起きた。

## 論点3: 7「確認のために作ったデータは、確認が途中で落ちた時も確認の中で消す」を取り込むか、どこに置くか

**ステータス:** 反映済み

**種別:** TBDヒアリング

### イテレーション0（論点3）: 取り込むかと置き場を、6 の置き場と既存の規則に照らして決める

#### 提案0（論点3）

取り込む。置き場は 6 と同じ `plugins/tumeda-dev/skills/tasklist-executor/SKILL.md` の「最重要原則」の DoD の節で、6 の項目の次に sub-bullet を一つ足す。あわせて、同じ file の「スクリーンショット確認」にある「まずテストデータを自分で作成して確認する（フォームから入力・DB に直接挿入など）」に、作ったデータの後始末はこの DoD の項目に従うことを一言添える。

足す規則の中身は次のとおり。文面は次の論点で決める。

- 確認のために、作業を破棄しても残る場所（本番の環境、他の人や他の app と共用の DB 等）へデータを作ったら、確認の中で消し、消えたことを確かめてから `[x]` にする。
- 確認が途中で落ちた時も同じである。落ちた時点で、作ったデータが残っていないかを確かめ、残っていれば消してから報告する。
- app の操作で消せない時は、消し方を利用者へ示して確認を取り、消すまで次へ進まない。
- 自分だけが使い、作業と一緒に捨てる環境（その作業の中だけで使う test 用の DB 等）に作ったデータは対象にしない。

`scripts/verification/validate-plugin.mjs` に足した文の `requireText` を足す。

#### 検討記録（論点3・イテレーション0）

##### 起点の失敗で、何が欠けていたか

元の依頼内容の 7 の具体例では、6 と同じ件で、確認の登録が途中で落ち、人物の保存と計算結果の保存が別々の transaction だったため、人物だけが本番と共用の DB に残った。一覧の画面は計算結果の無い人物で落ちるようになり、本番の app も同じ DB を見ているため影響を受けた。app の削除は計算結果があることを前提にしており、そのままでは消せなかった。

確認の手順には、通った時の削除（手順 6）はあったが、落ちた時の後始末は無かった。後始末は利用者に問う形で行われ、利用者は「動確用の確認用データを残して当然で掃除しないって思想だったらいただけない」と、確認用のデータを掃除しない前提を否定した。

欠けていたのは「確認のために作ったデータを消すまでが確認であり、落ちた時もそれは変わらない」という前提である。

##### 既存の規則に同じ問いがあるか

- `tasklist-executor/SKILL.md` の「スクリーンショット確認」は、確認対象のデータが無い時に「まずテストデータを自分で作成して確認する（フォームから入力・DB に直接挿入など）」と定める。作ったデータを消すかは定めていない。
- `task-design/SKILL.md` の Step 4「作業の外へ残る変化の引き継ぎ」と `tasklist-design.md` の「作業の外へ残るactionを含むphaseの原則」は、作業を破棄しても残る変化（本番データの移行・削除等）を、後から確認・復旧できるようにし、単独の phase と利用者の確認で扱う。これは残すと決めた変化の扱いであり、残さないつもりで作る確認用のデータは対象にしていない。
- `docs/development_standards/infrastructure/change_verification.md` は、確かめる動きの列挙を定め、確認のために作ったものの後始末は扱っていない。

どこにも、確認用のデータの後始末と、落ちた時の扱いは無かった。

##### 対象の範囲を「作業を破棄しても残る場所」にした理由

すべての確認用のデータを消す規則にすると、作業の中だけで使い、作業と一緒に捨てる test 用の DB まで後始末の対象になり、意味の無い手順が増える。残して困るのは、作業の外の人や app が同じデータを見る場所である。task-design の Step 4 が持つ問い「この作業で起きる変化は、この作業を破棄しても残るか」を、そのまま範囲の判定に使える。開発の DB が開発者ごとに分かれているかは利用先で違うため、判定の答えは利用先の状況で決まる。

### 決定（論点5）

4 を取り込む。`plugins/tumeda-dev/skills/task-design/SKILL.md` の「Step 4. design合意判定」の確認の並びで、「**作業の外へ残る変化の引き継ぎ**」の次に、同じ形（太字の見出し語、本文、判定の問い・やってしまいがちな失敗・判断基準の sub-bullet）の項目を一つ足す。中身は、design が定める確認（各段の確認、受け入れ基準、テスト方針の項目）のそれぞれについて、誰が（assistant か利用者か）、どの手段で確かめるか、その手段が今の環境で使えるかを design の合意の前に決めて `design.md` の「テスト方針」に書き、書けていなければ合意へ進まないこと、手段が使えない時は整える作業を範囲に入れるか担当・手段を変えるかを design で決めること、利用者が確かめる項目に入れてよいものの判定は `tasklist-design.md` の「実装後feedbackと公開action」を参照すること。あわせて `templates/design.md` の「テスト方針」の記入例を、誰がどの手段で確かめるかも書く形に変える。`scripts/verification/validate-plugin.mjs` に足した文の `requireText` を足す。文面は別の論点で決める。

選択理由: 起点の失敗は、確認の項目を何を見るかだけで合意し、誰が何で見るかを tasklist の段で初めて問うたことから起きた。Step 4 は合意の前に確かめることを並べる場所で、同じ形の失敗を持つ「作業の外へ残る変化の引き継ぎ」が既にあるため範囲に入る。tasklist-design は気づいた時点そのもので手戻りを防げず、template の記入例だけでは合意の前の関門にならない。Step 4 の項目と記入例は、同じ判断の関門と書く場所である。代償として、Step 4 の確認の並びが一項目長くなる。
