## 論点13: 2「version の上げ方全般」を取り込むか、どこに置くか

**ステータス:** 反映済み

**種別:** TBDヒアリング

### イテレーション0（論点13）: 取り込むかと置き場を、development_standards の群の範囲と照らして決める

#### 提案0（論点13）

取り込む。`plugins/tumeda-dev/docs/development_standards/development_flow/` に新しい標準 `version_upgrade.md`（runtime・framework・library の version の上げ方）を作る。同じ群の `README.md` の「development_flow/」へ新しい file の一行を足し、「維持規律」の file 数と分量を直す。

新しい標準に書く中身は次のとおり。文面は次の論点で決める。

- 当てはめる範囲: runtime・framework・library の version を、複数の版をまたいで上げる時。
- 上げる前に、今の版のまま起動と test を通して基準を作る。理由: 上げた後に動かないものを、version に起因すると切り分けるため。
- 最初から細かく刻まない。大きく上げ、動かない時だけ細かく刻む。
  - 上げる対象が一つ: 大きく上げる → 動かなければ細かく刻む、の二段階。
  - 上げる対象が二つの組み合わせ（例: 言語の runtime と framework）: どちらも上げる → 一方だけを最大まで上げ、他方をそれに合わせる → それでもエラーなら細かく刻む、の三段階。
  - 理由: 最初から細かく刻むと、動く場合にも全段の確認を通す手間がかかる。大きく上げて動けば一段で済み、動かない時だけ刻めば、切り分けの手間を必要な時に限れる。
- 最終の版の手前の版を経由し、手前の版で動く状態を確かめてから最終の版へ上げる。最終の版へ上げる時に変えるものが多すぎれば、手前の版で止める。

### イテレーション1（論点13）: 細かく刻む時の刻み方を、SemVer の入れ子と、詰まりを解消した後の戻り方で定める

#### 提案1（論点13）

提案0 のうち「最初から細かく刻まない」の中身を次のとおり変える。置き場、README と `validate-plugin.mjs` の変更、当てはめる範囲、基準、手前の版の経由、やってしまいがちな失敗、含めないものは提案0 のままとする。

- 最初から細かく刻まない。大きく上げ、動かない時だけ細かく刻む。
  - 上げる対象が一つ: 大きく上げる → 動かなければ細かく刻む、の二段階。
  - 上げる対象が二つの組み合わせ（例: 言語の runtime と framework）: どちらも上げる → 一方だけを最大まで上げ、他方をそれに合わせる → それでもエラーなら細かく刻む、の三段階。
  - 理由: 最初から細かく刻むと、動く場合にも全段の確認を通す手間がかかる。大きく上げて動けば一段で済み、動かない時だけ刻めば、切り分けの手間を必要な時に限れる。
- 細かく刻む時の刻み方（対象の数によらず同じ）:
  - SemVer の上の桁から入れ子で刻む。まず major で刻み（例: 6.0.0 から 8.3.5 へ一度に上がらなければ、6.0.0 → 7.0.0）、その段で詰まったら、その段を minor で刻み、それでも詰まったら patch で刻む。最初から下の桁（6.0.1 から一つずつ）で刻まない。
  - 詰まった版（例: 7.2.1）の問題を解消したら、そこから刻み続けず、最初の段階へ戻り、最終の版（例: 8.3.5）を狙う。
  - ただし、解消した後に次に詰まる版が見えていれば、そこまで minor や patch で刻むか、詰まりそうな版まで一度に上げてもよい。
  - 二つの組み合わせでは、第2段階で最大まで上げた側の版を刻み、他方はそれに合わせる。
  - 理由: 詰まりを解消した後も刻み続けると、残りが一度に上がる場合にも、全段の確認を通す手間がかかる。

#### 検討記録（論点13・イテレーション1）

##### 利用者の入力から一意に決まるもの

- 刻む単位: SemVer の上の桁から入れ子にする。major → minor → patch。
- 当てはまる範囲: 対象が一つの二段階と、二つの組み合わせの三段階の、どちらの「細かく刻む」にも当てはまる。そのため、二段階・三段階の各項目へ書き分けず、刻み方を一つの項目にまとめた。
- 詰まりを解消した後: 刻み続けず、最初の段階へ戻って最終の版を狙う。「最初」は、対象が一つなら大きく上げる段、二つの組み合わせなら「どちらも上げる」段である。どちらも最終の版を一度に狙う段であり、「最初の段階へ戻る」と書けば両方に当たる。
- 例外: 次に詰まる版が見えていれば、そこまで minor・patch で刻むか、詰まりそうな版まで一度に上げてよい。

##### assistant が補ったもの

- 二つの組み合わせで、どちらの版を刻むか: 利用者の入力には無い。第2段階で最大まで上げた側を刻み、他方はそれに合わせる、とした。第3段階は第2段階でも動かなかった時に入るため、第2段階の形（一方を最大、他方を合わせる）を保って刻むと、第2段階からの差分が刻み方だけになる。元の作業の design の第3段階も、framework の版を刻み、runtime をそれに合わせて上げる順だった。
- 詰まりを解消した後に戻る理由: 利用者の入力には無い。大きく上げる理由（動けば一段で済む）と同じ考えを、詰まりを解消した後へ当てた。

##### 確かめた case

| --- | --- |
| 6.0.0 から 8.3.5 へ一度に上がらない | 6.0.0 → 7.0.0 を試す。通れば 7.0.0 → 8.0.0 を試す。7.0.0 → 8.0.0 で詰まれば minor で刻み、7.2 系で詰まれば patch で刻み、7.2.1 で詰まりを見つける。解消したら 7.2.1 から 8.3.5 を一度に狙う |
| 7.2.1 の詰まりを解消した時に、8.1 系で使っている機能が消えると release note で分かっている | 次に詰まる版が見えているため、8.1 の手前まで一度に上げるか、そこまで minor で刻み、8.1 の詰まりを単独で扱ってよい |
| framework と runtime の組み合わせで、第2段階（framework だけを最大）でも動かない | framework の版を major から刻み、runtime は各段の framework が要する版に合わせる。詰まりを解消したら「どちらも上げる」段へ戻る |

##### 食い違いに気づいた経緯

2 の文面を書く途中で、決定（論点13）の二つの項目を並べると食い違うことに気づいた。

- 「最終の版の手前の版を経由し、手前の版で動く状態を確かめてから最終の版へ上げる」は、条件を持たない。読者はいつも手前の版を経由する。

いつも手前の版を経由するなら、最初の段階が狙うのは手前の版になり、利用者の例と合わない。

##### 元の作業で手前の版を経由した理由

元の作業の記録（引き渡しの元の議論）を確かめた。

- 手前の版を経由したのは、言語の runtime（最新の major の 4.0）だけだった。4.0 は出て間もなく、source から build する DB の driver の最新版が 4.0 より前の release で、build できるかを確かめていなかった。3 系の最後の版（3.4）は release から約 2 年経ち、library の対応が確かだった。

### 決定（論点13）

新しい標準の中身:

- 当てはめる範囲: runtime・framework・library の version を、複数の版をまたいで上げる時。
- 上げる前に、今の版のまま起動と test を通して基準を作る。上げた後に動かないものを、version に起因すると切り分けるためである。

## 論点14: 2 の標準に、一つの段へ入れる変更の決まり（段の分け方）を含めるか

````markdown
# version の上げ方

開発の進め方のうち、runtime・framework・library の version を、複数の版をまたいで上げる作業の進め方を扱う。複数の版をまたがない更新（例: patch の版を一つ上げる）には当てはめない。

**前提: 動かなくなった時に、原因を一つの変更へ帰せる形で上げる。** 上げる前に基準を作り、一つの段には一種類の変更だけを入れるのは、このためである。**一方、最初から細かく刻まない。** 大きく上げて動けば一段で済み、刻むのは動かない時だけでよい。

この前提が共有されていないと、二つの方向に崩れる。一つは、framework の upgrade guide が推奨する刻みをそのまま進め方にし、一度に上げても動く場合にも全段の確認を通す方向である。もう一つは、version の更新と他の変更を一つの段に混ぜ、動かなくなった時に原因を絞れなくなる方向である。

## 上げる前に基準を作る

上げる前に、今の版のまま起動と test を通す。上げた後に動かないものを、version に起因すると切り分けるためである。今の版で既に動かないものがあると、上げた後の失敗と区別できない。

## 一つの段には一種類の変更だけを入れる

各段の終わりに、基準と同じ確認を通す。

version を上げる段に入れてよいのは、上げるために要る変更（上げた版で使えなくなる library の置き換え等）だけである。次の変更は別の段にする。

- 今の版のままでも行える変更（例: JavaScript の bundler の置き換え）
- 挙動を変える既定値の切り替え（例: framework の設定の既定値を新しい版のものへ移す）

version の更新と他の変更を一つの段に混ぜると、その段の失敗を version と他の変更のどちらにも帰せない。別にした変更を上げる前の段に置くか後の段に置くかは、変更ごとに作業の design で決める。

判断の問いは **「この段が動かなかった時に、原因をこの段の一つの変更へ帰せるか」** である。

## 大きく上げ、動かない時だけ刻む

上げる対象の数で、試す段階を変える。

- 上げる対象が一つ: 大きく上げる → 動かなければ細かく刻む、の二段階。
- 上げる対象が二つの組み合わせ（例: 言語の runtime と framework）: どちらも上げる → 一方だけを最大まで上げ、他方をそれに合わせる → それでもエラーなら細かく刻む、の三段階。

最初から細かく刻むと、動く場合にも全段の確認を通す手間がかかる。大きく上げて動けば一段で済み、動かない時だけ刻めば、切り分けの手間を必要な時に限れる。

- やってしまいがちな行動: framework の upgrade guide が推奨する刻み（minor を一つずつ上げ、各段で test を通す）に従い、最初から細かく分ける
- それをやると何が起きるか: 一度に上げても動く場合にも、全段で同じ確認を通すことになる。例えば、framework と言語の runtime をそれぞれ複数の major 上げる作業を、最初から 9 段に分ける案を出した。利用者はこれを採らず、大きく上げると指定した。実際には、基準を作った後、どちらも上げた段で起動とすべての test が通り、刻む段は要らなかった
- 正しい判断のための問い: 「最初に一度に上げてみたか。刻むのは、動かなかった時か」

## 細かく刻む時は、SemVer の上の桁から入れ子で刻む

対象の数によらず、細かく刻む時は次のとおり刻む。

- まず major で刻む。例えば 6.0.0 から 8.3.5 へ一度に上がらなければ、6.0.0 → 7.0.0 を試す。その段で詰まったら、その段を minor で刻み、それでも詰まったら patch で刻む。最初から下の桁（6.0.1 から一つずつ）で刻まない。
- 詰まった版（例: 7.2.1）の問題を解消したら、そこから刻み続けず、最初の段階（大きく上げる段、または、どちらも上げる段）へ戻り、その段階が狙う版（例: 8.3.5）を一度に狙う。詰まりを解消した後も刻み続けると、残りが一度に上がる場合にも、全段の確認を通す手間がかかる。
- ただし、解消した後に次に詰まる版が見えていれば、そこまで minor や patch で刻むか、詰まりそうな版まで一度に上げてもよい。
- 二つの組み合わせでは、第2段階で最大まで上げた側の版を刻み、他方はそれに合わせる。

## 最終の版で動くかが不確かな時は、手前の版を経由する

最終の版で動くかが不確かな時（例: 最終の版が出て間もない major で、使っている library が対応しているかを確かめていない）は、最終の版の手前の版（例: 一つ前の major の最後の版）を経由する。手前の版で動く状態を確かめてから、最終の版へ上げる。最終の版へ上げる時に変えるものが多すぎれば、手前の版で止める。

手前の版で動く状態を確かめておけば、最終の版で動かないものを、最終の版に起因すると切り分けられる。止める先も残る。

最終の版で動くと見込める時は、手前の版を経由せず、最終の版を狙う。
````
