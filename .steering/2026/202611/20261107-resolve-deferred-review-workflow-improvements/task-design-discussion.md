# レビュー境界・モデル分担・自走skillの設計議論

三件の再開指示と詳細合意を区別する。[受領記録](escalation-receipt.md)が原文の受領・再開の出典を持つ。現在はレビュー境界を先に提示し、独立に調べられるmodel現物調査を並行した。model分担と新skillの具体案は、この論点への応答を他の詳細合意へ読み替えず、別のdecisionとして扱う。

## 論点1: 挙動維持が保護する対象を正常操作と業務仕様に定める

**ステータス:** 反映待ち

**種別:** レビュー指摘

### イテレーション0（論点1）: 内部の欠陥修正と業務変更の境界

#### 提案0（論点1）

`exhaustive-review`における「挙動維持」は、正常な認可ユーザーの既存操作、業務上の入出力・制約、正常時に観測する結果を維持する意味にする。関数内部の戻り値・例外・拒否条件・transaction境界は、その維持を実現するために変更できる。

不正な他者データへのアクセス拒否、例外時の部分更新防止、業務仕様に反する競合状態の修正は、正常操作・業務仕様を保つ修正として扱う。内部の変更だから無条件に許容するのではなく、期待される認可や整合性の根拠を示す。

| case | 判定 |
| --- | --- |
| 自分の資源を操作する既存手順を維持し、他者の識別子による更新だけ拒否する | 挙動維持の適用範囲で修正可能 |
| 正常成功の結果は同じで、失敗時に途中の保存をrollbackする | 挙動維持の適用範囲で修正可能 |
| 未定義の同時操作について、どちらの業務結果を正とするか決める必要がある | 業務仕様を調べ、決められない部分のみ確認 |
| 以前許されていた正常操作へ新たな前提条件や操作手順を足す | 業務仕様の変更として別判断 |
| 修正に新たな常設serviceや運用負担・費用が必要 | 構成・運用条件として別判断 |

この意味を`exhaustive-review/SKILL.md`の合意と適用へ置き、`templates/finding.md`の「振る舞いへの影響」を、維持する正常操作・業務仕様、修正する不正操作・異常系、内部変更、根拠の順に整理する。関数の戻り値等は影響を説明する材料として残し、全量不変の条件へしない。

レビューだけでは修正しない契約、合意済み範囲のみ適用する契約、既存許可を再確認しない契約、1指摘1コミット、誤指摘撤回、証拠の記録は維持する。`function_migration_policy.md`の全量維持はpluginの機能移行の規範なので変更しない。applicationレビューの正常操作維持と混同しない。

この境界を採用するかが今回の問い。model役割や新skillの名前・構造への合意は含まない。

#### 検討記録（論点1・イテレーション0）

利用者は「IDOR対応とかは関数の挙動を変えているだけでユーザの挙動も変わらず内部だけの話だから問題ないし」（原文の該当部分抜粋）と指摘した。正常操作の維持を全関数の結果固定と読んだ失敗が背景にある。

現物のfinding templateは「維持する戻り値・例外・順序・副作用・公開API」を求め、利用者の操作と内部実装を区別していない。一方で本体は認可と異常系の欠陥抽出を明示しており、内部修正を一律除外すると目的と競合する。正常操作・業務仕様を基準にすると、指摘された修正を許容しつつ、新たな業務制約を内部修正に混ぜることも防げる。

すべての内部変更を許す案は、実装の見え方で業務判断まで決められてしまうため採らない。全関数の返値・例外を固定する案は、今回の失敗を再現するため採らない。既存業務仕様が不明なcaseは内部だけでは断定できないという限界が残る。

[内部検討記録: 論点1・イテレーション0](review-boundary-consideration.md#iteration-0)

#### 提案0へのフィードバック（論点1）

**結果:** 追加の採否確認を要求せず、既指示の具体化として扱う。

引継ぎownerは、元の利用者指示と「マージした。じゃあescalate片付けようか」が三件を片付ける行動依頼であり、設計上の具体化を追加確認で止めないと判断した。利用者が提案0の詳細文を直接発言・承認したという記録ではない。上位の実行方針に従い、正常操作・業務仕様の維持と内部欠陥修正の許容を設計へ反映する。

### 現在の変更（論点1）

提案0の対象はreview本文とfinding template。引継ぎownerは利用者へ境界を変更報告したと通知し、設計担当へ反映を指示した。designは更新済み。sourceにはTerraによる途中差分があり、結果監督と検証は未完了。実装担当の利用上限による停止後、設計文書を共有するためsourceを固定した。追加の利用者発言を捏造せず、元の指示による実行許可と区別する。共有後に同じ作業treeで検証へ戻る。

## 論点2: モデル分担を既存の役割とprofileへ対応させる

**ステータス:** 反映待ち

**種別:** レビュー指摘

### イテレーション0（論点2）: 既存profileを正本にして委譲する

#### 変更内容0（論点2）

利用者原文「solじゃないといけないのは方針検討とハンドリングとエージェントがやってることの結果監督で、あとはterraに投げていいよ。これもescalate案件」に従い、runtime-model-profiles.mdへSolの方針・ハンドリング・結果監督とTerraへ委譲できる実装・読取・テストを対応させる。既存のselectorを各skillへ散在させず、adapterの選択可能時はTerra、不可時は継承して制約を報告する。

高推論reviewのAstra指定をTerraへ一律置換する変更は含めない。「委譲していい」という許可から既存の高推論review契約の廃止を導けないためである。logical ownerとphysical launcherも維持する。実物調査で見つかったCodex節のmodel指示不足は、profileへの参照で補う。Claude Codeの既存adapterは保持する。

#### 検討記録（論点2・イテレーション0）

Terraによるread-only調査では、mainはhost default、Codexの実作業は「標準coding model」と曖昧で、適用skillが三件に限定されていた。profileが要求するCodex節のmodel指示も現物にはなかった。一方high-reasoning-reviewはAstraを要求する独立契約だった。役割の正本をprofileに集約すると曖昧さを解消でき、既存review品質を落とさない。引継ぎownerはこの区別を利用者へ報告済みとして、具体化の反映を指示した。[内部検討記録](model-and-autonomy-consideration.md#topic-2-iteration-0)へ経緯と限界を保存する。

### 現在の変更（論点2）

変更報告済みというowner通知を受領、design反映済み。sourceのprofile・関連adapterにはTerraによる途中差分があり、結果監督と検証は未完了。設計文書共有までsourceを固定し、共有後に同じ作業treeで検証へ戻る。モデルの役割は変更するが、既存ownerの書込み権限・停止・再開は移動しない。

## 論点3: 不在中の承認不要作業を単独skillにする

**ステータス:** 反映待ち

**種別:** レビュー指摘

### イテレーション0（論点3）: unattended-executionを追加する

#### 変更内容0（論点3）

利用者の二つの原文は[受領記録](escalation-receipt.md#応答できない間の自走)を参照。名前はunattended-executionとし、承認が必要な操作の保留と、独立した承認不要作業の継続を一つのloopとして実装する。元workflowがtask・checkbox・完了を所有する。不在skillを追加のtasklist ownerにしない。

SKILL.mdの見出しは「役割と適用条件」「操作前の承認判定」「保留して独立作業を進める」「権限境界を維持する」「記録と再開」「返却と終了」。新たな人向けpromptを起こして許可可否を探らず、既存prefixで自動許可されることが確認済みの正規操作は進める。require_escalated flagだけで人の承認必須と分類しない。広いprefixや別toolを同等の拒否操作の迂回へ使わない。

保留は元workflowの既存記録、なければ指定済みworkdirのapproval-deferrals.mdへ保存する。未実行か結果不明か、必要許可、依存、再開条件を残す。独立作業が尽きたら未完了を返し、復帰後に実承認と最新状態を確認する。runtime-execution-contractsは入口参照と元owner維持だけを持ち、policyを複製しない。versionは新skill追加のMINOR 8.3.0に揃える。

#### 検討記録（論点3・イテレーション0）

利用者には単独skillの具体要求があり、別callerの将来予測だけによる分割ではない。既存runtime-execution-contractsには実行環境gateで止められたら停止する契約がある。新skillは拒否操作の停止を維持しながら独立作業を選び、権限不足を消したことにしない。

既存executorへ不在modeを埋め込む案では、task-designや任意command実行から単独で使えず、明示要求に届かない。別skillは入口と元ownerを分離できる。新たな全体状態fileを設ける案は既存checkboxと二重正本になるため採らない。判断に必要な境界caseをdesignへ保存し、引継ぎownerは名前と具体方針の変更報告後、反映を指示した。[内部検討記録](model-and-autonomy-consideration.md#topic-3-iteration-0)へcaseと構造reviewを保存する。

### 現在の変更（論点3）

変更報告済みというowner通知を受領、design反映済み。新skillと参照・validator・versionにはTerraによる途中差分があり、対応assertionの完成・編集後review・全体検証・結果監督は未完了。設計文書共有までsourceを固定し、共有後に同じ作業treeで再開する。main取り込み・正式reloadは元のescalate ownerが行い、設計担当は代行しない。利用者が追加依頼した作業途中のcommit・push・PRによる共有も、元のownerがshare-work-in-progressで行う。

## 設計文書の共有依頼

利用者原文:

> design.mdが出来上がったら見たいから $tumeda-dev:share-work-in-progress もして

引継ぎownerからこの追加依頼を受領した。設計本文は完成しており、実装完了やplanless_completeを共有条件にしない。設計文書と実装途中状態を同期して共有する。実装の検証成功を主張せず、共有後に三件の完遂へ戻る。
