## 論点1: 利用者の確認の task に、何を入れるか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0（論点1）: 利用者の確認の task の中身の境界

#### 提案0（論点1）

tasklist の利用者の確認の task に入れるのは、次のどちらかに当たる確認だけにする。

- **利用者が触って確かめるもの**: 画面を操作した時の感触、利用者の端末での表示。今の規則のとおり、自動 test と screenshot はこれを代替しない。
- **利用者のところにだけ届くもの**: 利用者の受信箱に届く email、利用者の端末への通知、利用者の account でしか見えない結果。

それ以外の確認は、assistant が実行・照合できる確認として、その phase の DoD と品質 check の task に入れ、executor が自分で行う。例えば command の exit code やログ、test、API の response、差分が design のとおりかの照合である。

判断の問い: **「この確認の合否を、assistant が command の出力・file・撮影した画面から判定できるか。できないのは、利用者の手と目、または利用者のところにだけ届くものが要るからか」**

差分が design のとおりかの照合は、利用者の確認の task に入れない。assistant が照合する。利用者が差分を見るのは review と merge の場面である。

この論点で決めないもの:

- 利用者の確認の task をいつ置くか。phase ごとか一度か、commit の前に利用者が触れるものが無い時どうするか、前回の決定（commit・push・PR の前に利用者の確認）との関係。次の論点で決める。
- 変える file と文。

#### 検討記録（論点1・イテレーション0）

**起点の三つの確認は、どれも利用者の確認ではなかった。**

- 入口が理由を出して非 0 で終わること、image の中で同じ command が非 0 で終わり version のログが出ることは、command の出力で判定できる。
- 基盤の定義の差分が design のとおりかは、差分と design の照合で判定できる。
- 三つとも、利用者の手と目も、利用者のところにだけ届くものも要らない。実際に executor が三つを確かめて先へ進んだ。

**今の規則は、利用者の確認の task に何を入れるかを決めていない。**

- `tasklist-design.md` は「自動testとscreenshotは機械的確認であり、ユーザーが実際に触る動作確認を代替しない」と書く。機械的な確認で利用者の確認を置き換えることを禁じている。
- 逆向き、つまり機械的な確認を利用者の確認の task に入れることは禁じていない。
- template の「動作確認」の task は「ユーザーに動作確認を依頼する（{どの操作をしてもらい、何を観測できれば満たすか}）」で、中身の制約が無い。起点では、ここに機械的な確認が入った。

**他の場面への当てはめ:**

| 場面 | 確認 | 入る先 |
| --- | --- | --- |
| 画面の操作を変える | 利用者が操作して、感触と表示を見る | 利用者の確認 |
| 通知の email の文面を変える | 利用者の受信箱に届いた email を読む | 利用者の確認 |
| 画面の無い API を変える | request を送り、response を見る | assistant の確認 |
| 文書だけを変える | 差分が design のとおりか照合する | assistant の確認 |
| 画面の撮影（visual-inspector） | 撮影した画面を見る | assistant の確認。利用者が触る確認は別に要る |

最後の行は、今の規則（screenshot は利用者の確認を代替しない）と同じ結論になる。この境界は今の規則を緩めず、逆向きの抜けを埋める。

**採らない境界:**

- assistant が確かめられる確認も、念のため利用者の確認の task に入れてよいとする: 起点の待ちがそのまま残る。利用者が確かめる必要の無い確認で、executor が止まる。
- 利用者の確認の task から、差分の review を外さず残す: 動作確認と review は場面が違う。review は PR と merge の場面で入る。

## 論点2: commit の前に利用者が触れるものが無い作業で、利用者の確認をどこに置くか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0（論点2）: 置く場所と、前回の決定との関係

#### 提案0（論点2）

利用者の確認の task は、利用者が触って確かめるもの・利用者のところにだけ届くもの（論点1）が初めて現れる phase に置く。

- **commit の前に、利用者が触れるものがある作業**: 今の契約のまま。利用者の確認の後に commit・push・PR をする。確認環境へ載せるための commit・push は、確認の前に行ってよい（前回の決定。変えない）。
- **commit の前に、利用者が触れるものが無い作業**: commit・push の前に利用者の確認の task を置かない。commit・push は、機械的な確認（test・lint・型検査、assistant が行う照合）の後に進む。利用者の確認は、利用者が触れるものが初めて現れる phase（本番へ入れた後に届く email を見る phase など）に置く。
- **最後まで利用者が触れるものが無い作業**（文書だけの変更など）: 利用者の確認の task を置かない。利用者の目は、review と merge の場面で入る。

「commit・push・PR より前にユーザー動作確認を必須にする」は、「commit・push・PR より前に、利用者が触れるものがあれば、その確認を必須にする」と読める形に改める。文は次の論点（変える file と文）で決める。

この論点で決めないもの: 利用者が触れるものが複数の phase に現れる時に、phase ごとに置くか、まとめて一度に置くか（別の論点にする）。

#### 検討記録（論点2・イテレーション0）

**前回の決定と食い違わないか。** 前回の取り込みは、今の契約を変えず、確認環境のための commit・push の例外だけを足した。利用者は、phase ごとに確認の前に commit する形を「review環境で確認するとか必然性があるコミットを許可してるだけなのに」と退けた。退けたのは、確かめるものがあるのに確認の前に commit する形である。この案は、確かめるものがある作業では順序を変えない。確かめるものが無い作業でだけ、確認の task を commit の前に置かない。

**起点の作業への当てはめ:** 本番の基盤を作る作業では、commit の前に利用者が触れるものが無かった。この案なら、品質 check の後に、executor が三つの確認を自分で行って commit・push へ進む。利用者の確認は、本番へ入れた後の、成功の email と失敗の通知が届く phase に置かれる。実際の作業もこの順で進み、利用者は email を受信箱で確かめた。

**他の場面:**

| 場面 | 利用者が触れるもの | 利用者の確認の位置 |
| --- | --- | --- |
| 画面の操作を変える | commit の前（手元か確認環境） | commit の前（今と同じ） |
| 画面から部品を消す | commit の前（確認環境） | commit の前（今と同じ） |
| 本番で動く job と通知を作る | 本番へ入れた後に届く email | 本番へ入れた後の phase |
| 文書だけを変える | 無い | 置かない（review と merge で見る） |

**採らない置き方:**

- commit の前に利用者が触れるものが無くても、何かしら利用者の確認を置く: 起点の待ちが残る。
- 利用者の確認を常に作業の最後に一つだけ置く: 画面を変える作業で、確認の後に commit する今の順序（前回の決定）を崩す。

## 論点3: 利用者が触れるものが複数の phase に現れる時に、確認を phase ごとに置くか、まとめて一度に置くか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0（論点3）: 確認の回数

#### 提案0（論点3）

利用者の確認は、まとめて一度、利用者が触れるものがすべて揃った phase の後に置く。

- 例外: 後の phase の作業が、その確認の結果に依存する時（確認で方向が変わると、後の phase を作り直すことになる時）は、その phase の後にも確認を置く。tasklist にはその依存を理由として書く。
- 論点2 の順序は変えない。commit の前に利用者が触れるものがある作業では、まとめた確認の後に commit・push・PR をする。

#### 検討記録（論点3・イテレーション0）

**起点:** 一つ前の作業で、tasklist が phase ごとに利用者の確認を置き、利用者が「つど確認必要？最後まで終わってでいいんじゃない？」と問うた。各 phase の画面の変更は、後の phase の作業に依存されていなかった。

**例外を置く理由:** 画面の構成を大きく変える最初の phase の結果を見て、利用者が方向を変えることがある。その時に後の phase まで作り終えていると、作り直しになる。作り直しの範囲が大きい時だけ、途中で確かめる。

**他の場面:**

| 場面 | 利用者の確認 |
| --- | --- |
| 画面を複数の phase で少しずつ変え、後の phase が前の phase の見え方に依存しない | 最後に一度 |
| 最初の phase で画面の構成を新しく作り、後の phase がその構成の上に部品を足す | 最初の phase の後と、最後 |
| 本番へ入れた後に、成功の email と失敗の通知の両方を確かめる | 両方が届く phase の後に一度 |

**論点2 との関係:** まとめて一度にすると、commit の前に利用者が触れるものがある作業では、全 phase の commit がその確認の後になる。前回の取り込みの決定（確認環境のための commit・push を除き、確認の後に commit する）とも、論点2 とも食い違わない。

**採らない置き方:**

- phase ごとに置く: 起点の問いのとおり、利用者が確かめる必要の無い待ちが phase の数だけ増える。
- 例外を置かず、常に最後に一度: 後の phase が依存する時に、作り直しの範囲が大きくなる。
