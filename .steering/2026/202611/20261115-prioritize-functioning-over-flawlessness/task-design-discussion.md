# 議論記録

## 論点1: 到達点の原則を思考標準のどこに置くか

**ステータス:** 反映済み

**種別:** TBDヒアリング

### イテレーション0（論点1）: 置き場の候補を比べる

#### 提案0（論点1）

原則を、`plugins/tumeda-dev/docs/think_standards/starting_to_think.md`（場面「考え始めるとき」）の補助節として置く。

- 位置: file の末尾。既存の「正しい判断のための問い」の後に、`## 補助: …` を一つ足す。見出しと本文の文面は次の論点で決める。
- 主軸「事象から原因へ降り、提案を検証まで通す」と、`think_standards/README.md` の一行は変えない。
- `scripts/verification/validate-plugin.mjs` に、足した見出しの `requireText` を足す。

#### 検討記録（論点1・イテレーション0）

置き場を選ぶ基準は四つある。

- 失敗が起きる時点で、読み手がその場面を引くこと（`evolution_policy.md`「場面から引けることを保つ」）。
- 場面の主軸を一つに保つこと。
- コアへは、場面を問わず例外なく常時適用するものだけを置くこと。
- 足す中身が、置き先の名前・入口の説明・既存の中身が約束する範囲に入ること（`naming/core.md`）。

起点の三つの失敗は、どれも自分が到達点を決めていると気づかないまま、提案を作る途中で起きた。
そのため「到達点を決めるとき」という新しい場面を作っても、気づいていない時には引かれない。
`core.md` は常に読まれるが、問いへの回答や review のように到達点を決めない場面もあり、例外なく適用するものではない。重要だという理由で加えることは、`evolution_policy.md` が禁じている。

残る候補は、提案を作るたびに通る二つの場面である。

| 候補 | 範囲に入るか | 評価 |
| --- | --- | --- |
| `starting_to_think.md` の補助 | 検証の段が「弱点の有無を形式として求めない」「課題に対して解決が図れそうかで測る」と既に定めている。到達点を「機能すること」に置く原則は、その延長として到達点の高さを定める | 推す |
| `making_and_choosing_options.md` の補助 | 主軸は「判断材料が枯れているか」で、到達点の高さは材料の話ではない。範囲の外の判断を問いにいった失敗は、案を作る場面でもなかった | 成立はするが、範囲の合致が弱い |

代償として、案を作る場面（`making_and_choosing_options.md`）からは直接引けない。提案を作る時は考え始める場面も通るので、到達できると判断した。

関係する既存の記述との分担:

- `questioning_existing.md`: 三つの失敗のうち一つ（誤りを含む文書を退避しようとした）にだけ当たる。分類に「直す」が無いことは、design の TBD 2 として別の論点で扱う。
- `development_standards/development_flow/work_scope.md`: 一段目（目的の外の判断は論点にしない）が、範囲の外の判断を問いにいった失敗に当たる。補助の本文からはその所在を示す。どう示すかは文面の論点で決める。
- `development_standards/naming/review.md`「評価基準を到達可能な水準へ合わせる」: 命名のレビューに限った同じ向きの判断。思考標準の原則はそれを場面を問わず一般化したものになる。

### 決定（論点1）

原則を `plugins/tumeda-dev/docs/think_standards/starting_to_think.md`（場面「考え始めるとき」）の補助節として、file の末尾（既存の「正しい判断のための問い」の後）に一つ足す。主軸と `think_standards/README.md` の一行は変えない。`scripts/verification/validate-plugin.mjs` に足した見出しの `requireText` を足す。

選択理由: 起点の失敗は、到達点を決めていると気づかないまま提案を作る途中で起きたため、新しい場面からは引かれない。考え始める場面は提案を作るたびに通り、検証の段が既に「課題が解けそうか」で測ると定めているので、到達点の高さはその延長として範囲に入る。`core.md` は例外なく常時適用するものではないため置かない。代償として、案を作る場面（`making_and_choosing_options.md`）からは直接引けない。

## 論点2: 「考え始めるとき」に足す補助節の文面

**ステータス:** 反映済み

**種別:** TBDヒアリング

### イテレーション0（論点2）: 下書きを、置き場と既存の文体に合わせて仕上げる

#### 提案0（論点2）

`plugins/tumeda-dev/docs/think_standards/starting_to_think.md` の末尾に、次を足す（既存の行は変えない）。

````diff
 正しい判断のための問い:
 - 「この原因は、解消すれば再発が止まるか？事象の言い換えになっていないか？」
 - 「この提案に合意したら、何がどう変わるか読み取れるか？」
 - 「この提案で、目下の課題は解けそうか？」
 - 「深堀りした結果は、深堀り前より良くなったか？」
+
+## 補助: 到達点は「間違いが無いこと」ではなく「機能すること」に置き、今の視座で届く限界を目指す
+
+直す・作るときの到達点を「間違いが無いこと」に置くと、間違いを含むものを消す・書かない方へ倒れる。
+消せば間違いは無くなるが、その場所は空になり、使えるものは増えない。
+到達点は、それが今より機能すること（読み手が使える、動く、判断の拠り所になる）に置く。
+検証の段で、弱点の有無ではなく課題が解けそうかを見るのと同じ向きである。
+
+到達点の高さは、理想の 100 点から逆算しない。
+100 点を描き、そこから見た欠けを数えると、二つの方向へ倒れる。
+一つは、欠けの多さに対して最低限の形で止める方向。
+もう一つは、今の作業では決められない範囲まで詰めにいく方向である。
+今 20 点なら、まず 30 点にする。
+ただし、少し頑張れば 80 点に届くのに 30 点で止めるのも違う。
+今いる視座の中で、現実的に届く限界を目指す。
+
+実際に落ちた形を書く。同じ作業の中で、三つの向きに続けて倒れた。
+
+> AI で開発する環境を整える作業で、上位の設計に並んだ設定 file を置くだけで終え、それらが置き換える指針の仕組みを作らなかった。最低限で止まった。
+> 続けて、一部が code と食い違う既存の概念説明の文書を、置くべき場所にあるのに「間違っているから」と退避しようとした。間違いを無くすことだけを見ていた。
+> さらに、参考の文書の節を埋めるため、その作業では決められない product の判断（何ができれば及第点か）を問いにいった。100 点を描いて範囲の外まで詰めにいった。
+
+文脈を離れた例で確かめる。一部が古くなった API の README があるとする。
+古い記述があるからと消せば、間違いは無くなるが、利用者は endpoint を探せなくなる。
+一か所だけ直して、同じ作業で見えている隣の古い節を残せば、30 点で止まる。
+逆に、この機会に全 endpoint の仕様を書き揃えようとすると、今の作業で確かめられない仕様まで推測で書くことになる。
+見えている古い記述を直し、確かめられない仕様は書かなければ、README は今日から使える。
+
+この補助は、消すことを禁じるものではない。
+必然性の無いものや、誤った案内しかしない記述は、消した方が機能する。
+基準は間違いの有無ではなく、機能するかである。
+また、届く限界は今の作業の範囲の中で測る。
+どこまでが今の作業の範囲かは、作業の目的が決める（[`work_scope.md`](../development_standards/development_flow/work_scope.md)）。
+「少し頑張れば届く」を、目的の外へ広げる根拠にしない。
+
+- やってしまいがちな行動: 是正を「間違いを無くすこと」と捉え、間違いを含むものを消す・書かない方へ倒す
+- やってしまいがちな行動: 理想の完成形を描き、そこからの欠けを今の作業で全部埋めにいく。または欠けの多さに怯んで最低限で止める
+- それをやると何が起きるか: 前者は、間違いが減る代わりに使えるものも減り、空いた場所は誰かが埋めるまで機能しない。後者は、範囲外の判断を推測で固定するか、少し頑張れば届いた水準を取り逃す
+- 正しい判断のための問い: 「これをやった後、今より機能するか。今の視座で、現実的にどこまで届くか。そこまで行ったか」
````

`validate-plugin.mjs` には、この見出しの `requireText` を足す。

#### 検討記録（論点2・イテレーション0）

出発点は、利用先で保留した時に保存した下書きである（見出し、原則、三つの実例、文脈外の例、やってしまいがちな行動、問い）。利用先の固有名は含まない。下書きの原則・実例・問いは保ち、三点を足した。

- 検証の段とのつながり（第一段落の最後の一文）: 論点1 で、到達点の高さを検証の段の延長として置いた。読み手が主軸と補助の関係を読めるようにする。
- 文脈外の例の、最低限で止める向き（「一か所だけ直して…30 点で止まる」）: 下書きの例は「消す」と「全部書き揃える」の二つの向きしか無く、起点の三つ目の向きが例で確かめられなかった。
- 境界と所在（「この補助は、消すことを禁じるものではない」の段落）: 基準は「機能するか」なので、必然性の無いものを消すことは妨げない。ここが無いと「消すな」と読まれる。また「少し頑張れば届く」を目的の外へ広げる根拠にする誤適用を、`work_scope.md` への所在で防ぐ。

利用者の原文の要素（間違いをしないより機能することを優先する、100 点を夢想して欠けを数えない、まず 30 点、少し頑張れば 80 点なら 30 点に甘んじない、今の視座で届く限界）は、第一・第二段落と問いに残している。

起点以外の case として、本文の API の README と、本文に載せない一部が落ちる test 群に当てた。どちらも三つの向き（消す、最低限で止める、範囲の外まで詰める）と原則での判断が具体的に書けた。消してよい境界は、もう存在しない機能の test を消す case で成り立つ。

## 論点3: 「既存のものを消す・残す」の分類に「直す」を足すか

**ステータス:** 反映済み

**種別:** TBDヒアリング

### イテレーション0（論点3）: 拾うかの判定と文面

#### 提案0（論点3）

この作業で拾い、`plugins/tumeda-dev/docs/think_standards/questioning_existing.md` の分類を三つから四つにする。

```diff
 - 正しい判断のための問い: **「これが今そこにあるのは、そう置くほかなかったからか、たまたまそこへ置かれたからか」**
-- 分離した結果は三つに分かれる。必然性があり配置も正しい（残す）、必然性はあるが配置が誤っている（移す）、必然性がない（消す）。二択で考えると「移す」が見えなくなる
+- 分離した結果は四つに分かれる。必然性があり配置も中身も正しい（残す）、必然性があり配置も正しいが中身の一部が誤っている（直す）、必然性はあるが配置が誤っている（移す）、必然性がない（消す）。二択で考えると「移す」と「直す」が見えなくなる
+- 中身の一部が誤っていることは、消す理由ではなく直す理由である。誤りを無くすことを目的に消すと、必然性のある場所が空になる（[考え始めるとき](./starting_to_think.md)の補助「到達点は「間違いが無いこと」ではなく「機能すること」に置き、今の視座で届く限界を目指す」）
```

`validate-plugin.mjs` に、「（直す）」を含む分類の文の `requireText` を足す。主軸と `think_standards/README.md` の一行は変えない。

#### 検討記録（論点3・イテレーション0）

引き渡しに添えられた気づき（利用者は未判断）である。起点の失敗の一つ（一部が code と食い違う概念説明の文書を、置くべき場所にあるのに退避しようとした）は、この「既存のものを消す・残すを判断するとき」の場面で起きた。今の分類では、必然性があり置き場も正しいが中身の一部が誤っているものの行き先が無い。

作業の範囲は `work_scope.md` の二段で判定した。

- 一段目: この作業の目的は到達点の原則を足すこと。「直す」を足しても足さなくても補助節は成り立つので、目的の外の不備にあたる。
- 二段目: 一行の変更と検査一つで、同じ思考標準・同じ版上げに収まる。今の作業の review・revert・本番適用の単位を崩さないので、既定どおり拾う。

「残す」に中身の修正を含めて読むこともできる。ただ、起点の失敗はその読みが働かず、誤りを含むものを消す方へ倒れた。明示しないと届かないので、分類として分ける。原則の本体は補助節が持つので、ここには一文と所在だけを置く。三分類を書いている箇所は、この一行だけだった（`.steering/` を除く git grep）。

起点以外の case に当てると、四分類でどれも一つの行き先に落ちた。古くなった値が一つある設定 file は直す、もう呼ばれない機能の README は消す。正本と成果物に同じ規則がある既存の失敗例は、従来どおり移す（成果物には所在の指示を残す）で、判断は変わらない。
