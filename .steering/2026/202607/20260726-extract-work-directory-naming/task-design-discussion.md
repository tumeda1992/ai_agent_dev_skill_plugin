# Task Design Discussion

## 論点1: 新 skill の責務を何に基づいて抽象化するか

**ステータス:** 決定

**種別:** 認識齟齬、レビュー指摘

**提起の背景:** steering に埋め込まれていた命名規則を切り出す際、切り出し元、文字列の生成手順、利用目的のどれを新 skill の責務として扱うべきかが揃っていなかった。

### 議論の変遷

#### 事象の記述

- 最初の提案では、既存の消費側を起点に `name-steering` という名前を選んだ。
- ユーザーから「切り出し元である steering が、なぜ新しい責務に関係するのか」と指摘された。
- 切り出し元への依存を除いた次の提案では、形式変換を起点に `generate-dated-slug` とした。
- ユーザーから、形式変換だけでは手続き的であり、ディレクトリ名に使う目的を含めるべきだと指摘された。

#### 原因の追跡

- なぜ: 既存記述の所在を、そのまま新しい概念の所属先として扱った。
- なぜ: 切り出し後も残る安定した責務ではなく、変更前のコード構造を抽象化の起点にした。
- なぜ: 切り出し元への結合を除くことに集中した後も、出力形式という手段から目的へ抽象化を戻さなかった。

#### 根本原因₀ + 提案₀

- **根本原因₀**: 新 skill の責務を「誰が使っていたか」で定義し、「何のための名前か」で定義していなかった。
- **提案₀**:
  - 総論: steering 用の命名 skill として切り出す。
  - 各論:
    - ルール: steering directory の名前を決める skill を `name-steering` とする。
    - 適用例: steering が作業開始時に `name-steering` を呼ぶ。

#### イテレーション1

##### 検証

- **観点**: ユーザーが、切り出し元は新 skill の本質ではないと指摘した。
- **弱点**: `name-steering` では他 workflow が同じ命名規則を再利用できず、責務が消費側へ逆向きに結合する。

##### 修正先の判断

- **診断レベルへの遡及**: skill の所属ではなく、入力と出力の変換を責務として再定義する。

##### 根本原因1 + 提案1

- **根本原因1**: 変更前の配置を概念境界として扱っていた。
- **変更点**: steering への参照を新 skill の名前と責務から除いた。
- **提案1（現時点）**:
  - 総論: 日付と作業内容から dated slug を生成する。
  - 各論:
    - ルール: 新 skill を `generate-dated-slug` とし、`YYYYMMDD-slug` を返す。
    - 適用例: 任意の workflow が同じ文字列形式を必要とするときに呼ぶ。

#### イテレーション2

##### 検証

- **観点**: ユーザーが、形式変換の手続きだけでなくディレクトリ命名という目的を含めるべきだと指摘した。
- **弱点**: `generate-dated-slug` は文字列生成一般に見え、出力をどの判断基準で評価するかが名前から分からない。

##### 修正先の判断

- **診断レベルへの遡及**: 入出力形式ではなく、生成物が果たす利用目的を責務の中心に置く。

##### 根本原因2 + 提案2

- **根本原因2**: 手段から切り出し元を除いた後も、「何のためにその手段を使うか」まで抽象化できていなかった。
- **変更点**: dated slug の生成ではなく、作業ディレクトリの命名を主語にした。
- **提案2（現時点）**:
  - 総論: 作業成果物を格納するディレクトリの basename を命名する。
  - 各論:
    - ルール: 新 skill を `name-work-directory` とし、`YYYYMMDD-slug` 形式の basename を返す。親パスと作成は消費側に残す。
    - 適用例: steering は basename を受け取り、`.steering/YYYY/YYYYMM/` 配下へディレクトリを作る。

**決定:** `name-work-directory` を採用する。責務は作業ディレクトリの basename の命名であり、steering は消費側の一つとしてのみ依存する。

**ネクストアクション:** `design.md` の D1〜D5 に、skill 名、命名規則、責務境界、steering 連携、既存成果物を改名しない方針を記録する。

## 論点2: 切り出す責務の抽象化軸を再利用可能な思考原則として残すか

**ステータス:** 決定

**種別:** レビュー指摘

**提起の背景:** 今回の認識修正は `name-work-directory` 固有の命名調整ではなく、再利用可能な概念を切り出すあらゆる場面で再発しうる。次回も切り出し元や実装手段から責務を命名すると、同じ軌道修正が必要になる。

### 議論の変遷

#### 事象の記述

- 新 skill を最初は切り出し元に基づく `name-steering`、次は生成手順に基づく `generate-dated-slug` と捉えた。
- ユーザーの指摘を二度受けて、切り出し後も残る利用目的に基づく `name-work-directory` へ到達した。
- 既存の `information_structuring.md` には「既存の構造・ファイル名から発想しない」という上位原則があるが、skill 切り出し時の思考手順としては常時適用されない。

#### 原因の追跡

- なぜ: 抽象化するときに、変更前から見えている名詞と処理をそのまま候補にした。
- なぜ: 「切り出し後に複数の消費側が使っても変わらない目的は何か」を先に問わなかった。
- なぜ: skill・template 修正時の思考手順に、切り出しの抽象化軸を検査する規則がなかった。

#### 根本原因₀ + 提案₀

- **根本原因₀**: 再利用可能な責務を切り出す際、切り出し元・実装手段・利用目的を区別して評価する思考手順が共有されていなかった。
- **提案₀**:
  - 総論: `think-through` の S5 に、切り出し後も安定する利用目的から責務と名前を決める原則を追加する。
  - 各論:
    - ルール: skill・module・template から責務を切り出すときは、切り出し元や生成手順を名前の主語にせず、「何のための責務か」を先に定義する。
    - 適用例: `name-steering`（切り出し元）や `generate-dated-slug`（手順）ではなく、`name-work-directory`（利用目的）とする。
    - 文脈外の適用例: CSV import から日時解釈を切り出す場合、`csv-helper`（切り出し元）や `split-and-parse`（手順）ではなく、`parse-local-datetime`（責務の目的）とする。

#### イテレーション1

##### 検証

- **観点**: 別文脈から移植された `development_standards/naming.md` に、「初見でも自明」「手続き的な how でなく宣言的な what / why」「名前と実態の対応をレビューする」という一般原則が既に定義された。
- **弱点**: `think-through` に同じ命名判断を追加すると、命名標準との重複正本になる。

##### 修正先の判断

- **提案レベル**: 原則の内容は維持し、反映先だけを `think-through` から専用の命名標準へ変更する。

##### 根本原因1 + 提案1

- **根本原因1**: 命名原則が不足していたのではなく、専用標準が存在しない前提で反映先を選んでいた。
- **変更点**: `think-through` への追加を取り下げ、`development_standards/naming.md` を正本として利用する。
- **提案1（現時点）**:
  - 総論: 命名判断は専用の命名標準へ集約する。
  - 各論:
    - ルール: `name-work-directory` の命名は、命名標準の what / why、具体性、名前と実態の一致で検証する。
    - 適用例: `generate-dated-slug` は how に寄るため退け、`name-work-directory` を採用する。

**決定:** `development_standards/naming.md` で今回の原則は充足する。`think-through` への重複追加は行わない。

**ネクストアクション:** `name-work-directory` の作成時に命名標準を判断根拠として使い、`think-through` は変更しない。
