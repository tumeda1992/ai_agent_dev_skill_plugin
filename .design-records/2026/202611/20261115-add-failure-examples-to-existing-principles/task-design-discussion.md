**ステータス:** 反映済み

**種別:** TBDヒアリング

### イテレーション0（論点1）: 位置と文面

#### 提案0（論点1）

`plugins/tumeda-dev/skills/task-design/SKILL.md` Step 5 の「file数、調査量、discussion回数…を掲載理由にしない」の段落の直後に、次の三行を足す。

```diff
 file数、調査量、discussion回数、実行可能な言語で書かれていることだけを掲載理由にしない。（…この段落は変えない…）補助tool自体が今回利用者へ届ける本番productなら、名前やpathでは除外せず第一条件へ戻す。
 
+- やってしまいがちな行動: 利用者に確かめる点があることを、条件2の中間checkpointと読み替える。例: domainのmoduleごとに資料とcodeから案を作り、利用者に確かめてからREADMEを書く作業を、moduleごとのtaskに分けてtasklistへ載せた
+- それをやると何が起きるか: task-design内の議論と適用で済む文書の作業に、tasklistの合意と実行のgateが重なる。案への確認は合意すればその場で書けるため、tasklistに載せても確認の回数は減らず、往復だけが増える
+- 正しい判断のための問い: 「この中間の確認は、実行して初めて得られる状態を見るものか。それとも案への合意を取るものか」。後者はtask-designのdiscussionで扱う
+
 test codeは単独の自動掲載条件ではなく、（…以降は変えない…）
```

`validate-plugin.mjs` に、問いの文の `requireText` を足す。

#### 検討記録（論点1・イテレーション0）

execution plan 対象の基準を持つのは、`SKILL.md` Step 5 だけだった（`tasklist-design.md`・`roadmap-design.md`・templates を grep。`templates/design.md` には表の `掲載理由` 列があるだけ）。そのため例は Step 5 に置く。NG 集 G の項目は Step 5 を指しているので変えない。

形は、`SKILL.md` の「commitの境界が設計判断になる時」と同じ三行（やってしまいがちな行動 / それをやると何が起きるか / 正しい判断のための問い）にした。新しい条件は足さず、条件 2 の「中間checkpoint」の読み方を、問いで分けて示す。

問いは、起点以外の case で意図どおりに分けた。

| case | 中間の確認の中身 | 判定 |
| --- | --- | --- |
| 本番データを batch に分けて埋め直し、各 batch の後に件数を確かめてから次へ進む | 実行して初めて得られる状態 | 条件 2。tasklist に載せる |
| feature flag を一部の利用者にだけ有効にし、指標を見てから広げる | 実行して初めて得られる状態 | 条件 2。tasklist に載せる |
| 複数の文書を書き直し、文書ごとに文言を利用者に確かめる | 案への合意 | task-design の discussion で扱う |

設計時の `skill-update-review` の結果: この変更に関わる切り出し候補は無い。直すのは Step 5 の一段落の後だけで、他の工程を直す必要は出なかった。ただし読んだ範囲は、`SKILL.md` の全文と、内部指示（`tasklist-design.md`、`roadmap-design.md`）の見出しと grep までで、templates と内部指示の全文は読んでいない。skill 全体の切り出し候補の探索は、`SKILL.md` の範囲に限られる。

### 決定（論点1）

task-design `SKILL.md` Step 5 の「file数、調査量、discussion回数…を掲載理由にしない」の段落の直後に、提案0 の三行（やってしまいがちな行動 / それをやると何が起きるか / 正しい判断のための問い）を足す。新しい条件は足さず、条件 2 の中間checkpointと、案への合意を取る確認を、問いで分けて示す。`validate-plugin.mjs` に問いの文の `requireText` を足す。

## 論点2: 「提案を出す前に確かめる」に足す具体例の位置と文面

**ステータス:** 反映済み

**種別:** TBDヒアリング

### イテレーション0（論点2）: 位置と文面

#### 提案0（論点2）

`plugins/tumeda-dev/docs/think_standards/making_and_choosing_options.md`「提案を出す前に確かめる」の、既存の二つの箇条にそれぞれ一行足す。三つの確認は変えない。

```diff
 やってしまいがちな行動:
 - why が決まっているため上位は埋まっていると判断し、what と how の設計を飛ばして how の選択肢を並べる
 - 案が否定されるたびに別の how を出し、否定の理由から共通の基準を取り出さない
 - 事実を一つ見つけた時点で三案へ畳み、その三案が依拠する前提を疑わない
 - 調査対象を最初に思いついた範囲へ絞り、「前例が無い」と結論を出す
 - 規定力の大きい判断を先に扱うところまでは正しく進み、扱うことと決めることを区別せずに確定させにいく
+- directory の一覧のような既存の構造から作業対象を列挙し、各対象に中身があるかを確かめずに含める。例えば module の directory ごとに説明文書を書く計画を立て、将来のために置かれただけの空の directory まで対象にした
 
 それをやると何が起きるか:
 - 前提が誤っていた場合、三案とも同時に無効になる。案ごとの比較検討は残らない
 - 不確実性が大きい判断ほど下位への制約が大きいため、誤った確定の影響が広く波及する
+- 列挙した一覧を前提に合意（受け入れ条件、作業の順序）が積み上がり、中身の無い対象に入って初めて気づいた時に、それらを直し直すことになる
```

`validate-plugin.mjs` に、足した「やってしまいがちな行動」の文の `requireText` を足す。

#### 検討記録（論点2・イテレーション0）

この形は、節の確認のうち一つ目（調べれば分かることを調べずに前提に置いていないか）と三つ目（既存成果物からの演繹だけになっていないか）の両方に当たる。確認は既にあるので、節が「三つは実際に起きた失敗の形であり、網羅のために足したものではない」と限っている確認の数は変えない。既存の「やってしまいがちな行動」と同じ粒度で、一つの失敗の形を一行で足す。

「それをやると何が起きるか」の既存の二行は、前提が誤ると三案が同時に無効になること、誤った確定が下位へ波及することを書いている。今回の帰結は、列挙した一覧の上に合意が積み上がり、後から直し直すことになる形で、既存の二つとは別なので一行足す。

起点以外の case でも同じ形になる。API の route 定義から文書化する endpoint の一覧を作ると、無効にした route まで含めうる。DB の table 一覧から移行する table を決めると、使われなくなった空の table まで含めうる。どちらも、列挙の元は候補を示すだけで、中身があるかまでは示さない。

### 決定（論点2）

`making_and_choosing_options.md`「提案を出す前に確かめる」の「やってしまいがちな行動」に、既存の構造から作業対象を列挙して中身を確かめずに含める形を一行、「それをやると何が起きるか」に、一覧の上に積み上がった合意を直し直すことになる帰結を一行足す。三つの確認は変えない。`validate-plugin.mjs` に、足した「やってしまいがちな行動」の文の `requireText` を足す。

適用: `making_and_choosing_options.md` に二行を足し、`validate-plugin.mjs` に `requireText` を足した。配布 version を `8.3.5` へ上げた（宣言値 4 か所と `expectedRelease`）。`validate-plugin.mjs`、`test-task-design-handoff.mjs` が通り、`inspect-discussion.test.mjs` は 24 pass・0 fail・1 skip。足した文を一時的に変えると検査が落ちることを確かめた。この decision について `doc-enricher` の提案 review を行い、候補は無かった。
