# 内部検討記録: 論点2 — 「提案を出す前に確かめる」に足す具体例の位置と文面

**discussion:** [task-design-discussion.md](../task-design-discussion.md)

**論点:** 論点2

## 開始context

- 問題: 利用先の作業で、directory の一覧から作業対象（README を置く module）を列挙し、中身があるかを確かめずに含めた。空の directory まで説明文書を書く対象にし、その module の論点で初めて気づいた。`making_and_choosing_options.md`「提案を出す前に確かめる」の確認（前提は確定しているか、どこから導いたか）は既にあるが、この形の具体例が無い。
- 決める範囲: 具体例を置く位置と文面。
- 開始時の既決条件: 新しい確認を足さない（design の MUST）。節は「三つは実際に起きた失敗の形であり、網羅のために足したものではない」と確認の数を限っている。
- 残る不足: 位置と文面。

## イテレーション0: 位置と文面

<a id="iteration-0-record-1"></a>

### 判断: 具体例をどこに、どう足すか

推奨は、節の既存の「やってしまいがちな行動」と「それをやると何が起きるか」の箇条に、それぞれ一行ずつ足す案。三つの確認は変えない。

- 必須条件: 三つの確認の数を変えない。既存の箇条と同じ粒度（一つの失敗の形を一行で）にする。利用先固有の情報を含めない。
- 根拠: 既存の「やってしまいがちな行動」は五つで、どれも確認を飛ばした具体的な形（例:「調査対象を最初に思いついた範囲へ絞り、「前例が無い」と結論を出す」）。今回の形は、確認の一つ目（調べれば分かることを調べずに前提に置く）と三つ目（既存成果物からの演繹だけ）の両方に当たる。
- 「それをやると何が起きるか」の既存の箇条は、前提が誤ると三案が同時に無効になること、誤った確定が下位へ波及すること。今回は、列挙した一覧の上に合意が積み上がり、後から直し直すことになる形で、既存の二つとは別の帰結なので一行足す。

#### 起点以外の case での確認

| case | 列挙の元 | 確かめずに含めると |
| --- | --- | --- |
| API の route 定義から、文書化する endpoint の一覧を作る | route 定義 | 無効にした route や、もう呼ばれない endpoint まで文書化する計画になる |
| DB の table 一覧から、移行する table を決める | schema | 使われなくなった空の table まで移行の対象にする |

どちらも、列挙の元（既存の構造）は対象の候補を示すだけで、中身があるかまでは示さない。今回の具体例の形がそのまま当てはまる。
