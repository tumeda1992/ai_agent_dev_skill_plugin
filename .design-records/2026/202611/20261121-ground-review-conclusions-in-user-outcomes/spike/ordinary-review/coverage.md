## 契約と実測の突き合わせ

会場の担当者は、返された1社に必要品をまとめて注文できる必要がある。公開担当者は、来場者自身が各社を組み合わせられる案内を用意する。下の3ケースではすべて確認済みで、ID、価格（Z が10、A が20）、入力順、全社を合わせた必要品の充足を固定した。必要品は机と照明。

| Z の品目 | A の品目 | 選定の期待 → 実際 | 公開の期待 → 実際 |
| --- | --- | --- | --- |
| 机 | 照明 | `None` → Z | [Z, A] → [Z, A] |
| 机 | 机・照明 | A → Z | [Z, A] → [Z, A] |
| 机・照明 | 照明 | Z → Z | [Z, A] → [Z, A] |

未確認社だけが不足品を扱うケースでは両方とも `None`。未確認社が最安の完備社でも、確認済み2社で全品を扱えるケースでは、選定が確認済み適格社の最安を、公開が確認済み全社を入力順に返した。空入力では両方とも `None`。公開ではさらに、机と照明の両方を扱う2社に続いて幕だけを扱う確認済みの会社が載る例を確認した。公開関数には価格フィールドを渡していない。[具体例と結果](evidence/results.txt)

Python 3.12.14 で、各入力列0〜3社、品目は机・照明の4部分集合、確認フラグ2通り、価格0または1、必要品は非空の3部分集合を列挙した。選定の期待値は価格順に並べた後で各社を個別に判定して求めた。公開の期待値は、確認済み各社の扱う品目を残りの必要品から取り除いて求めた。各入口13,107件のうち、選定は適格社なしで296件、適格社ありで1,652件の不一致。公開の不一致は0件。これは有限の照合であり、一般の場合の判断は下の契約とコードの対応に基づく。再実行はこのレビューのディレクトリで `python3 -B evidence/replay.py`。終了コード0は比較を最後まで実行したことを表し、契約との差は出力に表示される。[スクリプト](evidence/replay.py)・[記録](evidence/results.txt)

## 調達先選定の再検討

1. 既出の修正を現物で確認した。2行目の確認済みリストだけが後続へ渡る。それでも、どの会社にも一括注文できない分散ケースで ID が返ったため、会社ごとの適格性を調べる責務を特定した。
2. 適格な会社が存在するときの比較を調べ直した。存在判定だけを会社単位にする仮定では、2行目の全社から最安を返す箇所が残り、表の2行目を解消できない。候補を作ってその同じ候補から返すところまで CR-001 を広げた。両症状の修正責務はひとつ。
3. この改善を適用したと仮定し、返り値から逆に追った。候補が空なら担当者が選べる会社はなく、`None` が契約に一致する。候補があれば、全候補が単独で全品を扱い、適格な確認済み会社は全て比較に参加する。そこで価格最小の ID を取れば、安い部分対応社・安い未確認社に負けず、複数の完備社がある場合も最低提示額を返せる。同額なら入力順を保持できる。この2分岐が有効入力と出力を覆うため、確認範囲では [CR-001](findings/CR-001-eligible-supplier.md) で重要な不足を解消できると判断した。修正後の実測は行っていない。

## 公開処理の再検討

1. [publication.py](../publication/publication.py) の2行目で確認済みだけを抽出して入力順を保持する。3行目は「各必要品に、それを扱う確認済みの会社が少なくとも一つある」を判定する。これは来場者が会社を組み合わせたときに全品が揃う条件と一致する。足りない品が一つでもあれば5行目の `None` に進み、担当者は案内を補える。必要品が非空なので、確認済み0社でもこの分岐に入る。
2. 全品が揃う場合に公開される顔ぶれを再点検した。4行目は2行目のリスト全体を同じ順で ID に変換する。全品を扱う会社の有無、各社で扱う品目数、価格は一覧の選抜に使われない。分散、部分対応、必要品を扱わない確認済み社の同席、未確認社の混在、辞書順と異なる入力順を現行入口で確認した。ここに一括受注の制限を加えると、表の1行目で来場者が実際に組み合わせて利用できる2社の案内を失う。
3. 追加指摘0件のまま、担当者が案内を補う場合と公開できる場合に漏れがないかを照合した。前者は不足品の存在、後者は全品の登場と確認済み全 ID の順序で決まり、コードがそのままこの条件を判定し出力している。これが公開側で既出の修正だけで足りると判断した根拠である。

## 範囲と限界

対象は受付による検証後の関数入力から ID・一覧・`None` の返却まで。空の必要品、重複 ID、不正な入力形式、価格の不正は README の前提外。発注・保存・案内の配信サービスは両入口に呼出しがなく、外部での履行は確認対象に含まれない。対象ディレクトリの既存テストはなく、再現は現行関数を直接呼び出した。レビュー記録の作成後、対象一覧、全4ファイルの SHA-256 と HEAD を開始時の値と照合した。
