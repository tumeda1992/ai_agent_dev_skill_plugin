# 議論記録

## 論点1: 消した後に何を確かめるかを、新しい標準で扱うか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0（論点1）: 新しい標準と `change_verification.md` の境目を決める

#### 提案0（論点1）

新しい標準は「何を消し、何を残すかの一覧」を受け持つ。一覧を作るところから、消した後に一覧と実物を突き合わせるところまでを書く。消したことで影響を受ける動きの確かめは `change_verification.md` に任せ、新しい標準からは参照だけを置く。

新しい標準に足すもの:

- 四つ目の原則: 消した後、一覧と実物を突き合わせる。消すとした全件が無く、残すとした全件が残っていることを確かめる。
- `change_verification.md` への参照の一文: 消すことも基盤の変更である。消したことで影響を受ける動きの確かめは `change_verification.md` に従う。例えば、残したものを使う別の仕組みが動くこと、消した仕組みを起動していた経路が何も起こさないことである。

`change_verification.md` は変えない。

境目の軸は次のとおり。

| 受け持つもの | 置き場 |
| --- | --- |
| 何を消し、何を残すかの一覧（作る、消す前に確かめる、消した後に実物と突き合わせる） | 新しい標準 |
| 変えたことで影響を受ける動きの確かめ（消すことも含む） | `change_verification.md` |

#### 検討記録（論点1・イテレーション0）

##### 起点

元の依頼の具体例では、消した後に「消したものが無く、残すものが残る」ことを確かめ、誤って消したものが無いことを確認した。合意済みの三原則（作ったもの・付けたものまで辿って一覧にする、共有されているものは残す、消す前に他から使われていないことを確かめる）は、どれも消す前の話であり、消した後に何を確かめるかは決まっていない。

##### `change_verification.md` の範囲を確かめた

- 冒頭の説明は「基盤（cloud の resource とその構成）を作る・変えた後に、何を確かめれば完了とするかの判断基準」である。
- MUST は「変えた component の影響を受ける動きを列挙し、それぞれが意図どおりに動いていることを実物で確かめる」である。
- 列挙の観点は六つで、どれも「動き」である。
  - 利用者の操作
  - 利用者の操作を伴わない処理
  - 出力
  - 権限
  - 同じ component を共有する別の環境
  - 作る・更新する経路

消すことは基盤の変更に当たるため、消したことで影響を受ける動きは、この標準の範囲に入る。一方、「一覧の全件が消え、残すものが残っている」という状態の突き合わせは、どの観点にも当たらない。

##### 三つの案を比べた

- 消した後の確かめを、すべて `change_verification.md` に任せる案:
  - 一覧と実物の突き合わせを持つところが、どこにも無くなる。
  - 突き合わせを `change_verification.md` に足すと、新しい標準が作る一覧を前提にした項目が `change_verification.md` に入る。一覧を定めるところと使うところが、二つの file に分かれる。
- 新しい標準が、消した後の確かめをすべて持つ案:
  - 影響を受ける動きの確かめ（共有する別の仕組みが動くか等）を新しい標準に書き直すことになり、`change_verification.md` と重なる。
- 一覧に関わることは新しい標準、動きは `change_verification.md` に分ける案（提案0）:
  - 一つの軸（一覧か、動きか）で分かれる。
  - 重なりも、持ち主のいない確かめも生まれない。

##### 具体例に当てはめた

元の依頼の具体例で、消した後に行った確認を、提案0 の境目に当てはめた。

| 確認 | 受け持つ標準 |
| --- | --- |
| 消すとした webhook、pipeline、role、policy、object、application、repository が無い | 新しい標準（一覧との突き合わせ） |
| 共有の artifact の bucket と CodeDeploy の service role が残っている | 新しい標準（一覧との突き合わせ） |
| 共有の bucket を使う別の app の pipeline が動く | `change_verification.md`（共有する別の仕組みの動き） |
| 以後の push で旧 pipeline が起動しない | `change_verification.md`（消した仕組みを起動していた経路の動き） |

具体例の作業で実際に行ったのは上の二行である。下の二行は、この境目に従えば `change_verification.md` が確かめを求める動きである。

##### 合意済みの範囲への影響

利用者が受諾した中身は三つの原則である。提案0 は四つ目の原則を足すため、合意済みの範囲を広げる。今回の問いはこの追加の採否を含む。

#### 提案0へのフィードバック（論点1）

**結果:** 合意

> ok

### 決定（論点1）

新しい標準は「何を消し、何を残すかの一覧」を受け持つ。一覧を作る、消す前に確かめる、消した後に実物と突き合わせる、までを書く。

- 合意済みの三原則に、四つ目の原則を足す: 消した後、一覧と実物を突き合わせる。消すとした全件が無く、残すとした全件が残っていることを確かめる。
- 消したことで影響を受ける動きの確かめは `change_verification.md` に任せる。新しい標準には、消すことも基盤の変更であり、その確かめは `change_verification.md` に従うという参照の一文だけを置く。`change_verification.md` は変えない。

境目の軸は「一覧か、動きか」である。一覧に関わることは新しい標準、動きは `change_verification.md` が持つ。これで、重なりも、持ち主のいない確かめも生まれない。

## 論点2: 新しい標準の見出しの構成と、各見出しが扱う内容

**ステータス:** 応答待ち

**種別:** TBDヒアリング

### イテレーション0（論点2）: 四つの原則を見出しに割り当て、他の標準との境目を置く

#### 提案0（論点2）

新しい標準を、使わなくなった基盤の仕組みを消す時に何を消し何を残すかの判断基準として、次の見出しで作る。file 名は論点3 で決める。

```text
# 基盤の仕組みを消す時の範囲
├── （冒頭の一文）
│   └── 扱う判断: 使わなくなった基盤の仕組み（別の仕組みへ置き換えて旧を消す時を含む）を消す時に、何を消し、何を残すか
├── ## 作ったもの・付けたものまで辿って、消す一覧を作る
│   └── MUST。辿る先の三種類（相手側の登録、それだけに付いた権限、書き出した成果物）と、種類ごとの例。
│       理由（直接は見えないため漏れる。漏れたものは権限や費用として効き続ける）。
│       例外: application のログは消さない（`log_retention.md` に従う）。判断の問い
├── ## 共有されているものは残す
│   └── MUST。共有しているものは一覧から外し、その中のこの仕組みの分（共有の bucket のうち、この仕組みの prefix の下等）だけを消す。
│       理由（一覧に入れると、別の仕組みを壊す）。判断の問い
├── ## 消す前に、他から使われていないことを確かめる
│   └── MUST。読み取りで確かめる観点（付き先の一覧、参照元、prefix が他と前方一致しないこと）。
│       確かめた結果が一覧と違えば消さず、一覧を直して合意し直す。判断の問い
├── ## 消した後、一覧と実物を突き合わせる
│   └── MUST（消すとした全件が無く、残すとした全件が残る）。
│       消したことで影響を受ける動きの確かめは `change_verification.md` に従う、という参照の一文
└── ## やってしまいがちな失敗
    └── 起点の具体例を利用先固有の情報を除いて一件。
        最初の調査で見えた resource だけで一覧を作り、相手側の webhook、role だけに付いた policy、prefix の下の object が漏れた。
        消す前の読み取りで、漏れと、共有していて残すべきもの（deploy の service role、artifact の bucket）が分かった
```

見出しの順は、作業の順（一覧を作る → 残すものを外す → 消す前に確かめる → 消した後に突き合わせる）に合わせる。

#### 検討記録（論点2・イテレーション0）

##### 同じ directory の標準の形に揃えた

同じ directory の標準（`log_retention.md`、`change_verification.md`、`database_separation.md`、`reference_implementation.md`、`review_environment.md`、`cost_judgment.md`）は、次の形で揃っている。

- 冒頭の一文で、扱う判断を示す。
- 原則ごとに見出しを立て、MUST、理由、判断の問いを持つ。
- 最後に「やってしまいがちな失敗」または「失敗事例」を置く。

新しい標準もこの形にする。四つの原則を、それぞれ一つの見出しにする。

##### 既存の標準と食い違わないかを確かめた

`log_retention.md` は、application のログを「それを出す resource を消しても残す」を MUST にしている。一つ目の原則の「書き出した成果物」には、ログも含まれ得る。例外を書かないと、二つの標準が食い違う。そのため、一つ目の見出しに例外として書き、`log_retention.md` を参照する。これは新しい判断ではなく、既存の MUST に揃えるものである。

`review_environment.md` は、review 環境を止める・起動する扱いを持つ。これは仕組みを使わなくなって消す話ではないため、新しい標準の範囲に入らない（下の当てはめを参照）。

##### 起点以外の具体例に当てはめた

| 具体例 | 当てはめた結果 |
| --- | --- |
| 使わなくなった定期実行の function（schedule で起動する function）を消す | 当てはまる。相手側の登録は schedule の rule と target。それだけに付いた権限は、function の実行 role とその policy。書き出した成果物は、function の image や package。function が出す log の保管先は、`log_retention.md` に従い残す。共有している network（VPC、subnet、security group）は残す |
| Terraform で管理していた仕組みを、定義から外して消す | 当てはまる。state にある resource は apply で消える。一方、state に無いもの（function が自分で作った log の保管先、bucket に書き出した object、外部の service へ手で登録したもの）は、辿らないと残る。infrastructure as code で管理していても、一つ目の原則が要る |
| review 環境を止める | 当てはまらない。仕組みを使わなくなったのではなく、次に使う時に起動する。止める・起動する扱いは `review_environment.md` が持つ |

当てはまらない例で、新しい標準が働かないことを確かめた。冒頭の一文の「使わなくなった」が、その境目になる。

#### 提案0へのフィードバック（論点2）

**結果:** 合意。同じ応答で、file 名（論点3）の決定と、design 全体の受諾も述べられた

> ok。ファイル名もtbdであげてる名前でいいよ。それで出来上がったdesign.mdを受諾

### 決定（論点2）

新しい標準は、冒頭の一文、四つの原則の見出し（作業の順）、「やってしまいがちな失敗」から成る。

- 冒頭の一文: 使わなくなった基盤の仕組み（別の仕組みへ置き換えて旧を消す時を含む）を消す時に、何を消し、何を残すかの判断基準であることを示す。
- 「作ったもの・付けたものまで辿って、消す一覧を作る」: MUST、辿る先の三種類（相手側の登録、それだけに付いた権限、書き出した成果物）と例、理由、判断の問い。application のログは消さない例外を、`log_retention.md` への参照と一緒に書く。
- 「共有されているものは残す」: MUST、共有しているものの中のこの仕組みの分だけを消すこと、理由、判断の問い。
- 「消す前に、他から使われていないことを確かめる」: MUST、読み取りで確かめる観点（付き先、参照元、prefix の前方一致）、一覧と違えば消さずに一覧を直して合意し直すこと、判断の問い。
- 「消した後、一覧と実物を突き合わせる」: MUST と、影響を受ける動きの確かめは `change_verification.md` に従うという参照の一文。
- 「やってしまいがちな失敗」: 起点の具体例を、利用先固有の情報を除いて一件。
