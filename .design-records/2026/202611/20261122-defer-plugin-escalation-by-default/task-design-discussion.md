## 論点1: 既定で保留した提案を、元の作業のどの時点で引き渡すか

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0（論点1）: 「作業の後」を元の作業の完了判定へ対応させる

#### 提案0（論点1）

既定の保留の再開条件を「元の作業の完了」にする。

- 元の作業は、提案が生じた時に進めていた作業である。
  - steering の中で生じたら、その steering。
  - roadmap の子 steering の中で生じたら、roadmap 全体ではなく、その子 steering。
- 完了は、その作業の既存の完了判定で決める。新しい判定は作らない。steering なら次の時である。
  - planless の完了を報告した時（Step 5-1）。
  - tasklist-executor の完了を照合した時（Step 6-1）。
- 保留メモの再開条件には「既定（即時の指示なし）: 元の作業の完了」と書く。
- 利用者が別の時点を指示した時（「設計が終わったら渡して」等）は、その指示を再開条件にする。今の `pending-escalations.md` の扱いと同じである。

この再開条件は、今の `pending-escalations.md` の「条件が『作業完了』なら元作業の既存完了判定が対応する」と同じ対応である。元の担当（steering、task-design、tasklist-executor）が状態の遷移で再確認を依頼する仕組みも、そのまま使える。

#### 検討記録（論点1・イテレーション0）

##### 起点

利用者の原文は「デフォルトを作業後にして」である。「作業」がどの単位を指し、「後」がどの時点かは書かれていない。同じ応答の直前の保留指示は「今回のエスカレ適用はは実装後に保留する」だった。その作業では、tasklist の実行が終わり、steering が executor の完了を照合した時を再開条件にした。再開した後、利用者が PR を merge する前に、保留した提案を一件ずつ引き渡している。

##### 今の仕組みで使える対応を確かめた

`pending-escalations.md` の「元担当の状態遷移から再確認する」には、次の対応がある。

- 条件が「設計完了」なら、同じ作業の design phase の完了が対応する。
- 条件が「作業完了」なら、元作業の既存完了判定が対応する。

元の担当が再確認を依頼する時点は、次のとおりである。

- steering: Step 3（ready result の照合の後）、6-1（executor の完了の照合の後）、6-2（roadmap の phase の完了の後）、元作業全体の完了時。
- task-design: 再開時と、design phase の完了時。
- tasklist-executor: 再開時と、task・phase の完了時。

「元の作業の完了」を既定にすれば、新しい監視の仕組みは要らない。

##### 時点の候補を比べた

| 候補 | 採らない・採る理由 |
| --- | --- |
| design の完了 | 採らない。design から実装へ移る時に中断が起きる。提案は実装の途中でも生じる。起点の作業でも、利用者は実装の後を選んだ |
| 元の作業（leaf の steering）の完了 | 採る。利用者が一つのまとまりとして進める単位であり、その間は中断しない。既存の完了判定と再確認の仕組みがそのまま使える |
| roadmap 全体の完了 | 採らない。子 steering が複数ある roadmap では、引渡しが何日も先になる。その間に同じ不備が他の子 steering でも効き続ける |
| PR の merge | 採らない。merge は利用者の操作であり、元の担当が状態の遷移として記録しない。起点の作業でも、merge の前に引き渡した |

### 決定（論点1）

既定の保留の再開条件は「元の作業の完了」とする。

- 元の作業は、提案が生じた時に進めていた作業である。steering の中で生じたらその steering、roadmap の子 steering の中で生じたらその子 steering（roadmap 全体ではない）。

`pending-escalations.md` の「条件が『作業完了』なら元作業の既存完了判定が対応する」と同じ対応であり、元の担当が状態の遷移で再確認を依頼する今の仕組みをそのまま使う。

## 論点3: 即時の指示が効く範囲

**ステータス:** 決定

**種別:** TBDヒアリング

### イテレーション0（論点3）: 今の明示保留の範囲の扱いと揃える

#### 提案0（論点3）

即時の指示を、今の明示保留と同じ二つの範囲で扱う。

- 個別: 「この改善はすぐ渡して」。その提案だけを即時にする。
- 同じ作業の中の全部: 「この作業中の改善は全部すぐ渡して」。指示の後、同じ元の作業の中で生じる提案を即時にする。

指示はその対象・元の作業だけに効き、別の作業へ広げない。範囲（個別か、作業の中の全部か）や期間が分からない時は、その不足だけを利用者へ確かめる。慣習や過去の指示から即時を補わない。

#### 検討記録（論点3・イテレーション0）

##### 今の明示保留の扱いを確かめた

`pending-escalations.md` の「保留を保存する」は、次の二つを扱う。

- 「この改善は後で」という個別保留。
- 「この作業中の改善は全部後で」のような、対象・期間付きの指示。

範囲・期間が不明なら不足だけを確認し、慣習、agent の方針文書、既存メモの存在から保留を補完しない。保留指示はその対象・元作業だけに効き、別作業の保留や権限へ広げない。

| 今の明示保留と同じ二つの範囲で扱う（提案0） | 採る。保留と即時の指示の扱いが対称になり、読み手が二つの規則を覚え分けずに済む |
