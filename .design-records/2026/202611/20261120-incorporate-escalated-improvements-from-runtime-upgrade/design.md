# Design: 利用先の作業から引き渡された 7 件の改善提案を取り込む

## 元の依頼内容

利用先 repository の一つの作業（既存の web application の実行環境を更新し、開発機のローカルで動かす作業。上位の roadmap の一 phase として子の steering で行った）の中で生じた、plugin の skill・docs への改善提案である。`escalate-plugin-skill-fix` で引き渡す。1〜5 は利用者の指示で保留し、元の作業の完了時に利用者へ確かめて引き渡す。6・7 は元の作業の終わりに新しく出たものである。利用先固有の情報（repository 名、path、commit、issue・PR の番号、固有の model 名）は除いた。

### 合意の範囲（全件に共通）

- 引き渡すことへの合意: 元の作業の完了時に、assistant が「001〜005 と新しい 2 件を、今 plugin repository へ渡すか。推奨は全部まとめて今渡す」と問い、利用者は「ok」と答えた。
- 提案の中身への合意: 各件に書く。利用者の原文で確かめられない中身（置き場、文面、assistant が書いた規則文）は未合意であり、この repository の設計で改めて合意を取る。

### 1. 個人用の service では、本番と開発で DB を共用してよい

- 提案: 開発の環境を本番から分けるか（特に DB を分けるか）を設計する時の判断基準を足す。
  - 個人用の service は、本番と開発で DB を共用してよい。特に、利用者が本当に自分しかいないものはそうする。
  - 今は自分だけが使っていても、他の人が使うことになるもの、または長く運用して data が溜まり、それを毀損しない形にしたいものは、他の人が使う system と同じく、分離を検討する。
- 具体例:
  - 上位の作業で、全体構成（各 component をどこで動かし、何で繋ぐか）を決める論点の提案の中に、assistant が「ローカルでは DB の container を compose に持つ」を一行として含めた。依頼文の「ローカルでも E2E が動く形は担保したい」から、開発用の DB を本番から分けると推論したものである。独立した論点として問わず、component の配置の合意と一緒に design と roadmap へ入った。
  - 後の子の作業で、そのローカルの DB に入れる data を問うた時に、利用者が合意したつもりは無いと訂正した。親の design・roadmap と、子の三つの論点の決定を直すことになった。
  - 同じ利用者の別の repository（今は一人で使うが、他の人が使う可能性がある service）は、開発用の compose を分けつつ、DB は本番と共有している。
- 根拠: 判断基準が無いと、assistant は「本番と開発は分けるもの」という一般の system の前提で、個人用の service にも DB の分離を持ち込む。分離すると、開発のたびに schema と data を用意する作業が増え、利用者が望まない構成が design に入る。
- 利用者の原文（別の repository の名前だけを伏せた）:

  > 開発環境のローカル用のMysqlを使うなんて議論一回も合意したつもりは無いんだけど。これエスカレ対象として後で適用して欲しいんだけど、個人用サービスは本番と開発用DBを共用することは厭わない。特に利用者がマジで自分しかいないもの。[別の repository]みたいに、今は自分しか使ってないけど、他の人が使うってなったり、運用期間が長くてデータが溜まってるから、それを毀損しない形にするものは、他の人が使うシステムのように分離することも検討するんだけども。

- 中身の合意: 判断基準の中身は利用者の原文による。置き場と文面は未合意。

### 2. version の上げ方全般

- 提案: runtime・framework・library の version を上げる進め方を足す。元の作業で合意・指定された進め方は次のとおり。
  - 上げる前に、今の版のまま起動と test を通して基準を作る。動かなくなった時に、version に起因すると切り分けるためである。
  - 最終の版の手前の版を経由し、手前の版で動く状態を確かめてから最終の版へ上げる。最終の版へ上げる時に変えるものが多すぎれば、手前の版で止める。
  - 上げる対象が一つなら「大きく上げる → 動かなければ細かく刻む」の二段階。二つの組み合わせ（例: 言語の runtime と framework）なら「どちらも上げる → 一方だけを最大まで上げて他方を合わせる → それでもエラーなら細かく刻む」の三段階。
- 具体例:
  - framework を複数の major version、言語の runtime を複数の major version 上げる作業を設計した。assistant は framework の upgrade guide が推奨する刻み（minor を一つずつ上げ、各段で test を通す）に従い、最初から 9 段に分ける案を出した。利用者はこれを採らず、大きく上げる方向を指定した。
  - 実際の作業では、基準を作った後、「どちらも上げる」段で起動と全 test が通り、細かく刻む段は要らなかった。
- 根拠（assistant の読み。利用者の原文には無い）: 最初から細かく刻むと、動く場合にも全段の確認を通す手間がかかる。大きく上げて動けば一段で済み、動かない時だけ刻めば、切り分けの手間を必要な時に限れる。
- 利用者の原文:

  > 7は、大きく上げて動かなかったら細かくあげる方向で。これ他でも使う進め方かもだからエスカレで文書に残しておいて

  > 今回のエスカレは、今回のバージョンアップの仕方全般だからね。最初に大きくあげることだけじゃない。大きくあげるのと、細かくあげるの2段階じゃない方がいいな。というのもあげる対象が1つならそれでいいけど2つで組み合わせだから、3段階あるかな。1どっちも上げる、2どっちかだけマックスまで上げて、片方はそれに合わせる3それでもエラーなら細かくあげる

- 中身の合意: 三段階の進め方と、対象が上げ方全般であることは利用者の原文による。基準を作ること・手前の版を経由することは、元の作業の議論で利用者が指定・合意したもの（原文は利用先の記録にある）。置き場と文面は未合意。

### 3. 提案の図や表の一行に、別の判断が入っていないかを確かめる

- 提案: `facilitate-discussion` の「decision の境界を判定する」へ、次の問いを足す。
  - 提案の図・表・構成の一覧の一行が、それ自体で別の判断（採否を独立に決められるもの）になっていないか。なっていれば、別の論点として問う。
- 具体例: 1 の具体例と同じ件。「各 component をどこで動かし、何で繋ぐか」の論点の提案に、構成の図の一行として「ローカルでは DB の container を compose に持つ」を含めた。開発の DB を本番と分けるかという独立した判断だったが、論点として問わず、component の配置の合意と一緒に入った。`facilitate-discussion` には「一つの leaf 論点を一つの decision に限定する」規則があるが、図や表の中の一行に別の判断が入っている形を見分ける問いが無かった。
- 根拠: 図や表は全体像を示すために多くの要素を一度に載せるため、その中の一行が独立した判断であることに、書き手も読み手も気づきにくい。
- 中身の合意: 提案の文は assistant が書いた。利用者は保留に「ok」と答えただけで、中身は未合意。

### 4. design の確認の項目ごとに、誰がどの手段で確かめるかを design の合意前に決める

- 提案: `task-design` の design 合意判定（Step 4）へ、次の確認を足す。
  - design が定める確認の項目（各段の確認、受け入れ基準の確認）ごとに、誰が（AI か利用者か）、どの手段で確かめるか、その手段が今の環境で使えるか（例: visual-inspector の検査環境が repository の context に記述されているか）を、design の合意の前に決めている。
- 具体例: design で、各段の確認に「人物を登録する form で、かなが自動で入る」を入れ、利用者の合意を得た。tasklist を作る段で、これを AI が各段で何で確かめるかが決まっていないと分かった。かなの自動入力は browser で JavaScript を動かさないと確かめられず、visual-inspector は検査環境が repository の context に無いため使えなかった。design へ戻って、確かめ方（各段は HTTP、画面の動きは利用者が最後に一度、検査環境はこの作業で整える）を論点として決め直した。
- 根拠: 確認の項目は「何を見るか」だけを書くと合意でき、「誰が何で見るか」は tasklist を作る時まで問われない。tasklist の規則（止まる task の制限、visual-inspector の要件）と突き合わせて初めて、確認が実行できないと分かる。
- 中身の合意: 提案の文は assistant が書いた。中身は未合意。

### 5. 議論の途中で前提が変わったら、同じ前提を書いている文書を repository 全体で探す

- 提案: `task-design`（または `facilitate-discussion` の決定の反映）へ、次の手順を足す。
  - 議論の途中で、design の前提（構成、原則、環境）が変わる決定をした時は、その前提を書いている文書を repository 全体で探し、直す対象に加える。上位の design・roadmap を直しただけで終えない。
- 具体例: 子の作業の議論で「開発でも本番の DB を共用する（ローカルの DB の container を持たない）」と決めた。親の design と roadmap は直した。repository の上位のアーキテクチャ文書（「原則を変える時は、この文書を直してから design へ進む」と定める文書）も「ローカルは DB の container」と書いていたが、見落とした。steering の終了前の doc-enricher の review で初めて見つかった。`task-design` の設計前調査には「変更対象 file を説明している既存 docs を探す」があるが、議論の途中で前提が変わった場合の探し直しは定めていない。
- 根拠: 前提を変える決定は、その決定の論点の外の文書にも効く。論点の中で扱う design・roadmap だけを直すと、古い前提を書いた文書が残り、次の作業がそれを正として読む。
- 中身の合意: 提案の文は assistant が書いた。中身は未合意。

### 6. 確認の途中で確認の対象を変えたら、確認を最初の手順からやり直す

- 提案: tasklist の確認（各段の共通の確認等）の途中で、確認の対象（code、依存の宣言、設定）を変えたら、確認を最初の手順（起動）からやり直す。後の手順は、段の最後の状態で起動した server に対して流す。置き場の候補は `task-design/tasklist-design.md` の確認の task の作り方、または `tasklist-executor`。
- 具体例: tasklist の各段に共通の確認（1 compose で起動 → 2 画面の応答 → 3〜6 本番と共用の DB へ確認用の人物を登録し、詳細・JavaScript の配信・削除を確かめる → 7 全 test）を置いた。ある段で、executor が手順 1 の後に、言語の runtime の更新で標準から外れた library を依存の宣言へ足した（手順 7 の test を通すため）。server を起動し直さないまま、手順 3〜6 を流した。動いている server はその library を読み込んでおらず、登録の途中で落ちた。手順 7 の test は別の process で流したため通り、気づけなかった。
- 根拠: 手順 1 の後の変更が動いている server に載っていないと、手順 3〜6 は段の最後の状態を確かめていない。共有の環境へ書き込む確認では、不完全な data を残す（7 の具体例）。
- 中身の合意: 提案の文は assistant が書いた。利用先の tasklist には同じ規則を足し、利用者はその報告に ok と答えた。plugin へ足す中身は未合意。

### 7. 確認のために作ったデータは、確認が途中で落ちた時も確認の中で消す

- 提案: 確認のために共有・本番の環境へ作ったデータ（確認用の人物等）は、確認が途中で落ちた時も、確認の中で消す。落ちた時点で残っていないかを確かめ、残っていれば消してから報告する。app の操作で消せない時は、消し方を利用者へ示して確認を取り、消すまで先へ進まない。置き場の候補は 6 と同じ。
- 具体例: 6 の件で、登録は人物の保存と計算結果の保存が別々の transaction になっており、人物だけが本番と共用の DB に残った。一覧の画面は計算結果の無い人物で落ちるようになり、本番の app も同じ DB を見ているため影響を受けた。app の削除は計算結果があることを前提にしており、そのままでは消せなかった。assistant は片付け方（server を起動し直し、同じ値で更新して計算結果を作ってから、app の削除で消す）を利用者へ問い、利用者は片付け方には同意しつつ、下の原文で、確認用のデータを掃除しない前提を否定した。
- 根拠: 確認用のデータは確認のために作るものであり、確認が落ちた時に残すと、共有の環境（特に本番と共用の DB）を壊したままにする。確認が通った時だけ消す手順では、落ちた時の後始末が誰の仕事でもなくなる。
- 利用者の原文:

  > 2でも削除でもいいんだけど、
  > 動確用の確認用データを残して当然で掃除しないって思想だったらいただけない

  （「2」は、assistant が示した片付けの手順の 2 番目（同じ値で更新して計算結果を作る）を指す。）
- 中身の合意: 確認用のデータを掃除しない前提を否定したことは利用者の原文による。提案の規則文と置き場は assistant が書いたもので、未合意。

## TL;DR

利用先 repository の一つの作業で、plugin の skill・docs に判断の基準や問いが無いために起きた失敗と、利用者が示した進め方が 7 件あった。この作業で、7 件それぞれについて plugin へ取り込むかを決め、取り込むものを、次に同じ場面に来た読者が引ける場所（docs の標準、または該当する skill の手順）へ書く。終了時には、取り込んだ件の判断の基準・問いが plugin にあり、検証 script の assertion がそれを守っている。

7 件すべてを取り込んだ。6・7 は `tasklist-executor` の DoD の節、4 は `task-design` の Step 4 と design の template、5 は `task-design` の Step 3、3 は `facilitate-discussion` の「decisionの境界を判定する」、1 と 2 は `docs/development_standards/` の新しい標準（`infrastructure/database_separation.md`、`development_flow/version_upgrade.md`）へ書いた。配布 version は 9.0.1 から 9.0.2（PATCH）へ上げた。

## 完成後の姿

### 文書にまとめる知識と、その保ち方

**文書にする知識:**

- 暗黙知・散らばった知識・困りごと（元の依頼内容の 7 件。各件の具体例が、何が無くてどんな誤った判断をしたかを示す）
  1. 個人用の service で、開発の DB を本番から分けるかの判断基準が無く、一般の system の前提（分ける）を持ち込んだ。
  2. version を上げる進め方の標準が無く、framework の upgrade guide の刻みに従って最初から細かく分けた。
  3. 提案の図・表の一行に独立した判断が入っている形を見分ける問いが無く、問わずに合意へ入った。
  4. design の確認の項目について、誰がどの手段で確かめるかを design の合意前に決める問いが無く、tasklist を作る段で実行できないと分かった。
  5. 議論の途中で前提が変わった時に、同じ前提を書いた文書を探し直す手順が無く、上位の文書を見落とした。
  6. 確認の途中で確認の対象を変えた時に、確認を最初からやり直す決まりが無く、段の最後の状態を確かめないまま共有の環境へ書き込んだ。
  7. 確認のために作ったデータを、確認が落ちた時にも確認の中で消す決まりが無く、本番と共用の DB に不完全なデータが残った。
- 再び使える原則へ引き上げるもの:
  1. 個人用の service は、本番と開発で DB を共用してよい。他の人が使うことになる、または溜まったデータを守りたい service は、分けるかを利用者と検討する。
  2. version は、基準を作ってから大きく上げ、動かない時だけ SemVer の上の桁から刻む。一つの段には一種類の変更だけを入れる。
  3. 提案の図・表・一覧の一行ずつに、消すか別の値にしても論点の問いへの答えが成り立つかを問い、成り立つ行は別の論点にする。
  4. design の確認ごとに、誰が、どの手段で、今の環境で確かめられるかを、design の合意の前に決める。
  5. 作業の外でも読まれる前提を変える decision では、変わる前の前提を書いた文書を repository 全体から探す。
  6. 確認の途中で確認の対象を変えたら、変更を対象へ載せてから、確認を最初の手順からやり直す。
  7. 作業を破棄しても残る場所に確認のために作ったデータは、確認が落ちた時も確認の中で消す。

**読者と、読んでできるようになる判断:**

- 1・2: `task-design` を進める assistant。設計前調査で `development_standards/` の配下をすべて読むため、全体構成や作業の段を設計する前に、開発の DB を分けるか、version を上げる段をどう分けるかを判断できる。
- 3: `facilitate-discussion` で提案を作る assistant。提案を保存する前に、図・表の一行に入った独立した判断を見つけ、別の論点として問える。
- 4・5: `task-design` を進める assistant。design の合意の前に確認の担当と手段を決められ、前提を変える decision の後に古い前提を書いた文書を見つけられる。
- 6・7: `tasklist-executor` を進める assistant。確認の途中で対象を変えた時と、確認が落ちた時に、`[x]` にしてよいかと後始末を判断できる。

**決まりの理由と、当てはめる範囲:**

件ごとに、下の「完成後の文書の構成」の中身・範囲に入る理由・届かない範囲・文の組み立ての理由に書いた。

**内容を最新に保つ方法:**

正とする記述は、件ごとの置き場（skill の `SKILL.md`、design の template、`development_standards/` の標準と README）の文である。`scripts/verification/validate-plugin.mjs` が、規則の本体の文と、新しい標準への README からの link を `requireText` で検査する。理由・例・失敗の形は、書き換えても規則の意味が変わらないため検査しない。

**完成後の文書の構成:**

件ごとの置き場と、足す規則の中身。

- 6（確認の途中で確認の対象を変えたら、最初からやり直す）: 取り込む。
  - 置き場: `plugins/tumeda-dev/skills/tasklist-executor/SKILL.md` の「最重要原則」にある「DoD の各条件は「試みた」ではなく「実際に通過した」ことを確認してから `[x]` にする」の下。既存の三つ（テスト、visual-inspector、同一性の照合）と並ぶ sub-bullet を一つ足す。新しい docs の標準 file は作らない。
  - 中身: 確認の途中で確認の対象（code、依存の宣言、設定）を変えたら、変更を対象へ載せてから（起動・build・deploy をし直してから）確認を最初の手順からやり直し、変える前に通った手順の結果を使わない。確認を通すために直した場合も同じ。手順の一部を他の担当へ委ねている時は、変えたことと最初からやり直すことをその担当へ伝える。

    - 上げる前に、今の版のまま起動と test を通して基準を作る。上げた後に動かないものを、version に起因すると切り分けるためである。
    - 最初から細かく刻まない。大きく上げ、動かない時だけ細かく刻む。上げる対象が一つなら二段階（大きく上げる → 動かなければ細かく刻む）、二つの組み合わせなら三段階（どちらも上げる → 一方だけを最大まで上げ、他方を合わせる → それでもエラーなら細かく刻む）。最初から細かく刻むと、動く場合にも全段の確認を通す手間がかかるためである。
    - 細かく刻む時は、対象の数によらず、SemVer の上の桁から入れ子で刻む（major → minor → patch）。詰まった版の問題を解消したら、刻み続けず最初の段階へ戻って最終の版を狙う。次に詰まる版が見えていれば、そこまで minor・patch で刻むか、詰まりそうな版まで一度に上げてよい。二つの組み合わせでは、第2段階で最大まで上げた側の版を刻み、他方を合わせる。
    - 最終の版で動くかが不確かな時（例: 出て間もない major で、使っている library の対応を確かめていない）は、手前の版（例: 一つ前の major の最後の版）を経由し、手前の版で動く状態を確かめてから最終の版へ上げる。最終の版へ上げる時に変えるものが多すぎれば、手前の版で止める。最終の版で動くと見込める時は、経由せず最終の版を狙う。
    - 段の分け方: 一つの段には一種類の変更だけを入れ、各段の終わりに基準と同じ確認を通す。version を上げる段に入れてよいのは上げるために要る変更（上げた版で使えなくなる library の置き換え等）だけで、今の版のままでも行える変更（例: JavaScript の bundler の置き換え）と挙動を変える既定値の切り替えは別の段にする。動かなくなった時に、原因をその段の変更に帰せるようにするためである。段の順は作業ごとの design で決め、標準に書かない。
    - やってしまいがちな失敗: framework の upgrade guide が推奨する刻みに従い、最初から細かく分ける。
  - 範囲に入る理由: `development_flow`（開発の流れ）という名前、README の「開発の進め方の判断基準」、既にある二つの file の「開発の進め方のうち、…を扱う」のどれにも入る。
  - 読まれる場面: `task-design` は設計前調査で `development_standards/` の配下をすべて読むため、段の分け方を設計する時点で読まれる。
  - 手前の版を経由する条件の理由: 元の作業で手前の版を経由したのは、出て間もない major の言語の runtime だけで、framework は最新の版へ直接上げた。経由は、最終の版で動くかが不確かな時に、最終の版で動かないものを最終の版に起因すると切り分けるための決まりである。
  - 段の分け方を含める理由: 基準を作ることと同じく、動かないものの原因を切り分けるための決まりであり、version を上げる段に別の変更を混ぜれば基準の切り分けが成り立たない。
  - 文面: `version_upgrade.md` は次の内容にする。

    ````markdown
    # version の上げ方

    開発の進め方のうち、runtime・framework・library の version を、複数の版をまたいで上げる作業の進め方を扱う。複数の版をまたがない更新（例: patch の版を一つ上げる）には当てはめない。

    **前提: 動かなくなった時に、原因を一つの変更へ帰せる形で上げる。** 上げる前に基準を作り、一つの段には一種類の変更だけを入れるのは、このためである。**一方、最初から細かく刻まない。** 大きく上げて動けば一段で済み、刻むのは動かない時だけでよい。

    この前提が共有されていないと、二つの方向に崩れる。一つは、framework の upgrade guide が推奨する刻みをそのまま進め方にし、一度に上げても動く場合にも全段の確認を通す方向である。もう一つは、version の更新と他の変更を一つの段に混ぜ、動かなくなった時に原因を絞れなくなる方向である。

    ## 上げる前に基準を作る

    上げる前に、今の版のまま起動と test を通す。上げた後に動かないものを、version に起因すると切り分けるためである。今の版で既に動かないものがあると、上げた後の失敗と区別できない。

    ## 一つの段には一種類の変更だけを入れる

    各段の終わりに、基準と同じ確認を通す。

    version を上げる段に入れてよいのは、上げるために要る変更（上げた版で使えなくなる library の置き換え等）だけである。次の変更は別の段にする。

    - 今の版のままでも行える変更（例: JavaScript の bundler の置き換え）
    - 挙動を変える既定値の切り替え（例: framework の設定の既定値を新しい版のものへ移す）

    version の更新と他の変更を一つの段に混ぜると、その段の失敗を version と他の変更のどちらにも帰せない。別にした変更を上げる前の段に置くか後の段に置くかは、変更ごとに作業の design で決める。

    判断の問いは **「この段が動かなかった時に、原因をこの段の一つの変更へ帰せるか」** である。

    ## 大きく上げ、動かない時だけ刻む

    上げる対象の数で、試す段階を変える。

    - 上げる対象が一つ: 大きく上げる → 動かなければ細かく刻む、の二段階。
    - 上げる対象が二つの組み合わせ（例: 言語の runtime と framework）: どちらも上げる → 一方だけを最大まで上げ、他方をそれに合わせる → それでもエラーなら細かく刻む、の三段階。

    最初から細かく刻むと、動く場合にも全段の確認を通す手間がかかる。大きく上げて動けば一段で済み、動かない時だけ刻めば、切り分けの手間を必要な時に限れる。

    - やってしまいがちな行動: framework の upgrade guide が推奨する刻み（minor を一つずつ上げ、各段で test を通す）に従い、最初から細かく分ける
    - それをやると何が起きるか: 一度に上げても動く場合にも、全段で同じ確認を通すことになる。例えば、framework と言語の runtime をそれぞれ複数の major 上げる作業を、最初から 9 段に分ける案を出した。利用者はこれを採らず、大きく上げると指定した。実際には、基準を作った後、どちらも上げた段で起動とすべての test が通り、刻む段は要らなかった
    - 正しい判断のための問い: 「最初に一度に上げてみたか。刻むのは、動かなかった時か」

    ## 細かく刻む時は、SemVer の上の桁から入れ子で刻む

    対象の数によらず、細かく刻む時は次のとおり刻む。

    - まず major で刻む。例えば 6.0.0 から 8.3.5 へ一度に上がらなければ、6.0.0 → 7.0.0 を試す。その段で詰まったら、その段を minor で刻み、それでも詰まったら patch で刻む。最初から下の桁（6.0.1 から一つずつ）で刻まない。
    - 詰まった版（例: 7.2.1）の問題を解消したら、そこから刻み続けず、最初の段階（大きく上げる段、または、どちらも上げる段）へ戻り、その段階が狙う版（例: 8.3.5）を一度に狙う。詰まりを解消した後も刻み続けると、残りが一度に上がる場合にも、全段の確認を通す手間がかかる。
    - ただし、解消した後に次に詰まる版が見えていれば、そこまで minor や patch で刻むか、詰まりそうな版まで一度に上げてもよい。
    - 二つの組み合わせでは、第2段階で最大まで上げた側の版を刻み、他方はそれに合わせる。

    ## 最終の版で動くかが不確かな時は、手前の版を経由する

    最終の版で動くかが不確かな時（例: 最終の版が出て間もない major で、使っている library が対応しているかを確かめていない）は、最終の版の手前の版（例: 一つ前の major の最後の版）を経由する。手前の版で動く状態を確かめてから、最終の版へ上げる。最終の版へ上げる時に変えるものが多すぎれば、手前の版で止める。

    手前の版で動く状態を確かめておけば、最終の版で動かないものを、最終の版に起因すると切り分けられる。止める先も残る。

    最終の版で動くと見込める時は、手前の版を経由せず、最終の版を狙う。
    ````

    `README.md` は、「development_flow/」の `work_scope.md` の行の次へ「[version_upgrade.md](./development_flow/version_upgrade.md) — runtime・framework・library の version を、複数の版をまたいで上げる進め方。上げる前に基準を作り、一つの段には一種類の変更だけを入れ、大きく上げて動かない時だけ SemVer の上の桁から刻む。」を足し、「維持規律」を 17 file・約 75KB と、`development_flow/` の一覧に version_upgrade を足した形に直す。

  - 文の組み立ての理由: 同じ群の `work_scope.md`・`branch_pr_issue.md` と同じ形（冒頭の「開発の進め方のうち、…を扱う」、太字の前提と崩れる方向、失敗の三行）にする。見出しは作業で出会う順にする。手前の版を経由する時は最初の段階が狙うのが手前の版になるため、刻む節は「その段階が狙う版」と書く。
  - 保ち方: `validate-plugin.mjs` が、決まりの本体の七つの文と README からの link を `requireText` で検査する。

## 要件（Requirements）

### MUST（必達）

- 7 件それぞれについて、plugin へ取り込むか（取り込む／取り込まない）を利用者と決め、取り込まない件は理由を残す。
- 取り込む件は、利用者が合意した置き場と文面で plugin の skill・docs へ書く。利用者の原文で確かめられない中身（置き場、文面、assistant が書いた規則文）は、この design の議論で合意してから書く。
- 書いた件ごとに、`scripts/verification/validate-plugin.mjs` へ契約の文が残っていることを検査する assertion を足す。
- 利用先 repository 固有の情報（repository 名、path、commit、issue・PR の番号、固有の model 名）を、skill・docs・この steering の成果物に書かない（`maintenance_policies/migration.md`）。
- 一つでも取り込んだら、配布 version を一度だけ上げる。上げる区分は `maintenance-plugin-context` の規約で決める。

### SHOULD（できれば）

- なし

### MAY（あれば嬉しい）

- なし

### 非目標

- 利用先 repository の成果物（その repository の tasklist・context の instance 等）を直すこと。利用先で必要な分は、利用先の作業で既に直している。
- 利用先 repository への plugin の update と、利用先の進行中の作業への反映。`escalate-plugin-skill-fix` の「取り込みと反映」が扱う。

### 受け入れ基準

- `node scripts/verification/validate-plugin.mjs` が `plugin validation passed` を出す。
- 取り込んだ件ごとに、合意した置き場に合意した文面があり、対応する assertion がある。
- 変更した範囲を `grep` で調べ、利用先 repository 固有の情報が無い。
- この作業を破棄しても残る変化は、`main` への取り込みと配布 version の 9.0.2 である。`escalate-plugin-skill-fix` の「取り込みと反映」に従って取り込み、plugin を update した後、install された plugin の commit が `main` の先端と一致し、version が 9.0.2 であることで確かめる。戻す時は `main` で取り込みを revert し、配布する変更として version を上げる。

## （付録）前提とする既存仕様

- `docs/development_standards/README.md`: 開発の成果物と手順についての判断基準を置く群。`task-design` は設計前にこの群の配下をすべて読む。file を増やす時は、増やした後も読み切れるかを確かめる（維持規律）。現在の群は `naming/`、`entity_modeling/`、`development_flow/`（`branch_pr_issue.md`、`work_scope.md`）、`infrastructure/`（`log_retention.md`、`change_verification.md`。cloud の resource の作り方）。開発環境と本番の分け方、version の上げ方を扱う標準は無い。
- `docs/development_standards/infrastructure/change_verification.md`: 基盤を作る・変えた後に、変えた component の影響下にある動きをすべて実物で確かめる。「同じ component を共有する別の環境」も観点に含む。確認のために作ったデータの後始末と、確認の途中の変更は扱っていない。
- `skills/facilitate-discussion/SKILL.md` の「decisionの境界を判定する」: 各部分が別の問いへの答えで、一方を確定しても他方について別に決める結論が残るなら分ける。file 数・hunk 数・箇所数で数えない。図・表の一行に別の判断が入っている形を見分ける問いは無い。
- `skills/task-design/SKILL.md` の PrepareStep 3: 設計前調査で、変更対象 file を説明している既存 docs を探し、変更後に不正確になる記述を変更対象へ含める。議論の途中で前提が変わった時の探し直しは定めていない。
- `skills/task-design/SKILL.md` の Step 4（design合意判定）: 「確認範囲が主張範囲を覆っているか」「作業の外へ残る変化の引き継ぎ」等の確認を持つ。design が定める確認の項目について、誰がどの手段で確かめるかの確認は無い。
- `skills/task-design/tasklist-design.md` の「実装後feedbackと公開action」: 利用者の確認の task に入れるのは、利用者にしか確かめられないもの（触って確かめるもの、利用者のところにだけ届くもの）だけで、それ以外は tasklist-executor が自分で行う。確認の途中の変更と、確認用のデータの後始末は扱っていない。
- `skills/runtime-execution-contracts.md` の「状態の正本とsingle writer」: tasklist を更新できるのは tasklist-executor だけである。
- `skills/maintenance-plugin-context/maintenance_policies/migration.md`: 利用先 repository から得た内容を取り込む時は、その repository 固有の情報を抜き、汎用知識だけを書く。
